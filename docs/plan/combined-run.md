## How a slice session reads this plan

1. Read this file in full: the rules below, the Order, and the slice's section here.
2. Read the source plan in full, then the slice's text there. The source plan's line numbers
   were checked at the commit its own `Status:` line names and may be stale; re-verify every
   cited identifier before editing.
3. The slice's files are the union of what the source slice names and what the section below
   lists. Stay inside them. The section's Files line is the orchestrator's scheduling input,
   so a slice that must edit a file not listed in either place stops and reports BLOCKED with
   the file, instead of editing it.
4. The source plan's Decisions apply with their defaults; the orchestrator takes each default
   unless the user overrides it before the run.
5. Do not edit this file, the source plan, or `docs/plan/README.md`. The orchestrator records
   landings here and leaves the source plans' `Status:` lines as they are until retirement.

## Run rules (for the orchestrator)

- `Status:` above is the record: `<id> (<hash>)` per landed slice, ids as below. The
  `docs/plan/README.md` entry for this plan carries the landed count; the entries of the
  source plans stay as they are.
- Wave membership: two slices run in one wave only when their Files lines (and the files their
  source slices name) are disjoint. Test files count as files. A shared owning guide is not a
  constraint across plans: two slices of different plans may edit `self-host-server.md` in one
  wave, and the second to land takes a docs-only conflict, which the orchestrator resolves at
  cherry-pick as plan-runner step 6 allows. Within one plan, the source plan's "same guide"
  dependencies stand.
- Walk order: the Priority list under Order is the order the orchestrator walks when filling a
  wave. A slice section's position in this file does not matter.
- Decision points that stop a chain, not the run:
  - DA0 reports pass/fail per probe (a)–(e) in its final report. The orchestrator writes the
    result into `Status:` here (for example `DA0 (<hash>) probe a–e pass`). If (a), (b), or
    (c) fails, DA3–DA7 and ST0–ST5 are `blocked` until the user re-plans Direct Asset URLs
    under its D1 (b); every other slice goes on.
  - ST0 rewrites Server Thumbnails slices 1–2 (docs only). After it lands, the orchestrator
    re-reads those two slices, updates the Files lines of ST1 and ST2 here in the same plan
    commit, and re-confirms the schedule with the user as plan-runner step 7 requires for a
    changed schedule.
- Chat Checkpoints' `heap-memory-reduction` dependency is gone: that branch merged on
  2026-10-20 (`b122ae132`, archived), so CC6 depends only on CC5, and the "take the heap
  dependency" clause in CC5 no longer applies. CC1–CC5 still do not edit `src/ts/storage/`.
- Final checks (plan-runner step 8), once: `pnpm check`, `pnpm format:check`,
  `pnpm --silent test:agent`, then `pnpm --silent test:agent --e2e`, plus the production-server
  checks TK4 and ST1 name (`pnpm build`, `docker build`, one request each in the container).
- Retirement: when every slice has landed, the eight source plans and this index are archived
  together, one archive row per source plan with its slices' hashes copied from `Status:`
  here, and the manual follow-ups the slice sessions reported. A source plan whose remaining
  slices are all `blocked` stays active with a note, and this index is archived without it.
- Run length: in worktree mode the base branch is fast-forwarded only at the end. With 77
  slices and three sessions at once, the run spans days; prefer main-checkout mode, or
  `--base` onto a long-lived integration branch, so the user can stop after any wave with
  everything landed so far on a branch.

## Decisions

- D1. One index over the source plans rather than one merged file. Options: (a) this index,
  with the slice text left in the source plans; (b) one file holding every slice's text.
  Default (a): a slice session reads this file and one source plan (under 1,000 lines),
  instead of the 3,600 lines of all eight; and the source plans keep their Problem, Approach,
  and Decisions where the archive expects them.
- D2. Guide overlap across plans is not a wave constraint. Options: (a) as the Run rules say;
  (b) serialize every pair that edits the same guide, as the source plans do within
  themselves. Default (a): `self-host-server.md` alone owns 18 slices and is edited by more, and (b) would
  make most of the run sequential; a docs-only conflict is resolved by the orchestrator at
  cherry-pick.
- D3. ST0 is a slice, not an orchestrator step. Options: (a) a docs-only slice on Opus under
  `opus-lite`; (b) the orchestrator stops and the user re-plans by hand. Default (a): the
  rewrite follows a decision the owner already took, and (b) idles the run until the user is
  free. The orchestrator still re-confirms the changed schedule afterwards.
- D4. Priority order. Options: (a) the list under Order; (b) plan by plan, in the order of
  `docs/plan/README.md`. Default (a): the critical path and the data-loss fixes get slots
  first, and the small independent slices fill the rest.

## Not In This Plan

- Any design change to a source plan. A slice that finds its source text wrong reports
  BLOCKED; the fix is a source plan edit by the user or the orchestrator, then a new dispatch.
- `--max-parallel` above 3 (plan-runner's ceiling) and the Codex weekly quota: the run takes
  as many waves as it takes.
- Upstream Integration's Not In This Plan items and the deferred Inventory rows.

## Open Questions

- Should the run start in main-checkout mode on `metatron`, or in a worktree with `--base
metatron` and a single fast-forward at the end? The Run rules recommend main mode for a run
  this long; the user decides at plan-runner step 2.
