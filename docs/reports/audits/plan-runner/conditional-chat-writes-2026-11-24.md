## P1 findings

**CW-01 · P1 · Web Crypto alone excludes supported tabs.** D1 says, “The digest is SHA-256 over the canonical JSON serialization in `shared/` (one function used by the tab and the server; the tab computes it with Web Crypto).” The application supports plain-HTTP LAN origins, and its translation hash explicitly documents that those origins have no `crypto.subtle`. The tab already computes SHA-256 in pure JavaScript for Structured Memory. **Correction:** share the canonical string or bytes, specify UTF-8 and the wire encoding, and use the existing SHA-256 implementation in the tab, either always or as a fallback. Include a parity case with `crypto.subtle` unavailable. [HTTP support](../../../../shared/ids.ts:7) · [Web Crypto restriction](../../../../shared/translation/hash.ts:4) · [existing tab SHA-256](../../../../src/ts/process/structuredMemory.svelte.ts:2056)

**CW-02 · P1 · Filing a draft is too late to capture its original value.** D7 says, “A new chat draft stores, per op, the digest of the field value the tab held when the draft was written; Apply sends it as the condition.” By filing time the mirror can already contain the _result_ of the edit. Pending ops can carry an original `before`, but resend and refused layers contain plain `ChatOp[]`. `draftChat` also strips the pending envelope. A new draft made from an old in-flight group can therefore lack a before-value even after the feature ships. Hashing the mirror at Apply would authorize overwriting the very edit being protected. **Correction:** capture the before-value at the original mutation, before modifying the mirror. Carry it through pending, dispatch, resend, quarantine, draft conversion, narrowed retry and skipped-content filing. Represent _unknown_ separately from _known absent_. Gate confirmation on the evidence for the actual operations, rather than the draft’s creation date. [journal layer contracts](../../../../src/ts/storage/draftJournal.ts:112) · [pending versus resend capture](../../../../src/ts/storage/chatStore.svelte.ts:817) · [refused layer capture](../../../../src/ts/storage/chatStore.svelte.ts:869) · [kf-data draft flattening](/home/codex/worktrees/kf-data/src/ts/storage/journalRecovery.ts:767) · [remainder filing](/home/codex/worktrees/kf-data/src/ts/storage/journalRecovery.ts:1397)

**CW-03 · P1 · A `data` digest cannot protect every field recovery writes.** D2 says, “`setText`, `setMessage`, `patchMessage` (when it sets `data`), and `remove` may carry `ifData: <digest>`.” The Goal promises, “A recovery draft applied again after a newer edit does not set the edited fields back.” A stale `setMessage` can replace `name`, `saying`, or other fields while `data` still matches. A multi-field patch can do the same, and a patch exclusively to `disabled` carries no condition under D2. Recovery also reissues `setTranslation`. A newer hand-edited translation of the same source text passes the source-hash check, and a clear has no source-hash check. The server already implements `expectTranslation` for its detached translator, but the tab recovery writer does not send it. **Correction:** guard all fields a recovered operation can overwrite, or narrow the operation and retain confirmation or copy-only recovery for the rest. Use the existing translation expectation for translation edits and clears. Keep D6’s deliberately narrower text-only deletion contract explicit. **CW-04 · P1 · The client queue can erase a condition before it reaches the server.** D7 says, “Apply sends it as the condition.” Consecutive text, row, patch, and metadata writes can fold into the earlier op. The metadata fold excludes `ifOocUnanswered` but knows nothing about `ifFields`. `kf-data` separates an Apply from surrounding edits, but still permits folding _within_ that Apply. There is a second route around a guard: an edit releasing a loaded quarantine can be absorbed into a whole-chat `replace`, returning before the guarded op or its recovery receipt is registered. **Correction:** establish a queue boundary for guarded writes unless the fold is proved equivalent for both success and refusal. Preserve the first before-value per field and its receipt identity. Prevent quarantine release or snapshot collection from turning a guarded edit into an unconditional replacement. Exercise the actual dispatched and journaled groups. **CW-05 · P1 · Running the memory rule first can admit a value under a mode that was refused.** D3 says, “The existing `ifOocUnanswered` and memory-field rules are unchanged and run first.” The HypaV3 guard computes `modeAfter` from the _requested_ `memoryMode`. Suppose the stored mode selects Structured Memory, a guarded change away from it fails its digest, and the same op supplies unsealed HypaV3 summaries. Checking memory first can admit the summaries based on the requested mode, then leave Structured Memory selected when the mode change is refused. The opposite ordering of values can discard a valid write. The V2/Supa path also records job-write stamps before the field write. **Correction:** determine which mode change will actually apply before evaluating ownership against the effective mode. Stamp only admitted job fields. Preserve the stored-before ownership and checkpoint-restore exceptions. Test both directions with a refused mode and a sibling summary. **CW-06 · P1 · Extending the receipt alone can still retire refused work.** D5 says, “`refusedMeta` gains the refused keys of a meta op and a `data` refusal of a message op, with the reason `changed`.” On `kf-data`, the reader maps one detail per op index. It narrows only `memoryFields` in `set`/`unset`; an unfamiliar detail otherwise retains the whole op. More importantly, `ackChatWork` marks the flush discarded only for the old memory/OOC aggregate flags. A `changed`-only receipt can settle as success, and the success path removes the source even if a remainder was calculated. An optimistic removal has already hidden the row, and a fresh-revision refusal need not otherwise trigger a reread. **Correction:** define one lossless result per sent index, including multiple reasons and all four metadata forms. Use it for exact remainder, caller outcome, mirror refresh and retirement on both fresh and replayed receipts. Keep `targets`, checkpoints, translations and legacy aggregates meaningful. Test an all-refused group at the current revision, a mixed-reason op, and an unrelated caller sharing the group. **CW-08 · P1 · A hello checked at the user action does not protect a queued or rebooted write.** D5 says, “An older server ignores the unknown keys”; Q2 proposes “a capability flag in the server’s hello.” The first statement is correct for the proposed keys.
