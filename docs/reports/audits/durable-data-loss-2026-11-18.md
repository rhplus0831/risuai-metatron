# Durable database loss audit, 2026-11-18

At commit `1513f9288`, a plugin returning an old database snapshot could erase messages, whole chats, and newly created characters that had already been saved. Two ordinary UI actions also removed saved history in a real browser: dismissing the message-removal dialog with Escape, and closing a tab during a group reroll. In each case the missing rows were absent from SQLite.

**For a reported 1–3 day rollback**, the age of a plugin's saved copy can explain that boundary across several chats. Deleting the suffix of one chat can produce the same boundary there. **For a whole database that suddenly looks old or empty**, check which save directory or volume the server opened and whether a restore occurred. This audit found no automatic selection of a days-old snapshot during normal startup. No affected user's database, logs, or deployment were available to attribute a particular incident.

## Findings

### 1. A plugin can write a stale view back over several characters

A plugin with database read and write access reads the characters, holds the result while the user continues chatting, and later returns it through `setDatabaseLite` or `setDatabase`. Even if the plugin meant to change only a setting, supplying `characters` makes the host reconcile the whole list. Three losses were reproduced using synthetic data, the real client save adapter, and a SQLite-backed store. Each check verified the data existed on the server before calling the setter.

| Saved after the plugin's read          | What the later save did                                                                                                                                                                                                      |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A message appended to an existing chat | Both database setters deleted the message. The setter used the current transcript as the baseline and interpreted the older copy's missing message as a removal.                                                             |
| A new character with a chat            | Both database setters permanently removed the character and its chat. The missing character ID was treated as a deletion from the current inventory.                                                                         |
| A new chat on an existing character    | Even the narrower `getCharacter` / `setCharacter` round trip, tested through its `getChar` / `setChar` aliases, deleted the new chat. Per-chat read baselines do not record which chats existed when the character was read. |

The setters use the tab's current revisions for the resulting writes, so the database can accept a stale plugin decision as a fresh deletion. The membership loop covers every absent character. A copy taken before a large import can therefore remove the entire newly imported group of characters once they are idle. The fixture exercised one such character. Two controls that omitted the `characters` key preserved the newly saved data. Omitting only a character's `chats` field preserves that character's transcripts but still leaves the outer character list subject to reconciliation. The tests granted the plugin permissions and mocked the sandbox transport. [Database getter and setters](../../../src/ts/plugins/apiV3/v3.svelte.ts#L2840), [character list reconciliation](../../../src/ts/plugins/apiV3/v3.svelte.ts#L2149), [chat reconciliation](../../../src/ts/storage/chatStore.svelte.ts#L4861), [message removal calculation](../../../src/ts/storage/chatStore.svelte.ts#L4689), [server character cascade](../../../server/src/data/chatStore.ts#L3279).

**Fix first.** Track the membership and revisions observed by the getter. Apply only changes relative to that read. When the baseline is unavailable or a destructive change overlaps a later write, require a fresh read or an explicit deletion by ID. A settings-only plugin can avoid this path today by passing only the setting it changed.

### 2. Escape at the second removal prompt deletes the rest of a chat

With “Remove subsequent when message remove” enabled, click Remove on an old message, confirm “Remove this message?”, then press Escape at “Do you want to remove just one message?” The hotkey dismisses the dialog with an empty answer. The boolean confirmation helper maps that to false, and the caller interprets false as a request to remove the selected message **and every later message**. A comment's removal button and a long press also reach this second question. The English prompt describes only “the message after it.” [Removal handler](../../../src/lib/ChatScreens/Chat.svelte#L702), [comment button](../../../src/lib/ChatScreens/Chat.svelte#L1550), [long press](../../../src/lib/ChatScreens/Chat.svelte#L1900), [Escape handling](../../../src/ts/hotkey.ts#L77), [confirmation result](../../../src/ts/alert.ts#L400), [prompt text](../../../src/lang/en.ts#L1205).

**Browser verification.** A four-message chat had one message dated on each of four consecutive days. Dismissing the second prompt on message two and flushing left only message one in SQLite. No other tab, plugin, or storage failure was involved. Locked messages can block the removal, and Structured Memory can ask another question when events cite the rows. Give the dialog distinct **Cancel**, **Delete one**, and **Delete this and all later messages** outcomes, with the affected count. Escape should cancel. [Queued removal](../../../src/ts/storage/chatStore.svelte.ts#L4064), [SQLite deletion](../../../server/src/data/chatStore.ts#L2664).

### 3. Two clients can each delete the other's intended last surviving chat

A character has chats A and B. One client deletes A expecting to keep B. A second deletes B expecting to keep A before either sees the other's change. Each client enforces the last-chat rule against its own two-item list. Each normal save sends a deletion with the target chat's revision and no chat-order precondition. Removing A leaves B's revision valid. The server accepts both writes. On the next boot, a character with no chats gets an empty “Chat 1,” which can make the loss look like a reset. [Client last-chat check](../../../src/ts/storage/chatStore.svelte.ts#L3570), [save groups and orders](../../../src/ts/storage/chatStore.svelte.ts#L5903), [server deletion](../../../server/src/data/chatStore.ts#L2342), [server order checks](../../../server/src/data/chatStore.ts#L3363), [boot repair](../../../src/ts/storage/chatStore.svelte.ts#L5082).

**Store verification.** Two independent client store instances saw the same two chats. Their normal save batches contained one deletion each and zero order changes. After both committed, the database had zero chats for that character and its order was empty. Enforce the last-chat rule inside the server transaction for a surviving character, evaluating its final membership so intentional replacements can still succeed.

### 4. A fast client clock can permanently purge a recently trashed character

Moving a character to Trash records the deleting browser's clock. Every boot compares that timestamp with the opening browser's clock and schedules a permanent character deletion after three days. The server checks the character revision and generation lock, then cascades to its chats. It never checks whether three days have elapsed. A freshly trashed character can therefore disappear as soon as a device with a sufficiently fast clock opens the app. Several trashed characters can be affected in one boot. [Trash timestamp](../../../src/ts/characters.ts#L940), [expiry rule](../../../shared/characters.ts#L11), [boot sweep](../../../src/ts/bootstrap.ts#L484), [server admission and cascade](../../../server/src/data/resourceStore.ts#L1907).

**Boot verification.** Starting with a fresh browser cache and a saved character, chat and message, advancing the fixture clock by four days and running boot and flush removed the character and chat from the server. The in-process fixture shared a fake clock. Source inspection establishes that the browser alone makes the age decision. Use server time for both the trash timestamp and the purge condition, and recheck that the record is still trashed in the deletion transaction.

### 5. An old Lua transcript can overwrite messages appended while a script waits

A card button reads its full chat, waits for user input, edits a message in its saved copy, then calls `setFullChat`. In a real server/worker test, another client appended a message during the wait, received HTTP 200, and read it back. When the button finished, the stored chat contained only the original two rows with the requested edit. The independently saved third row had disappeared. The setter preserves metadata on matched messages, but constructs the entire replacement list from the script's copy. It refreshes the revision immediately before writing. [Lua bindings](../../../server/src/lua/bindings.ts#L1553), [message matching](../../../server/src/lua/bindings.ts#L733), [revision used for the write](../../../server/src/lua/bindings.ts#L488).

The loss can span all messages added since that read in the affected chat. Compare against the revision at read time, or apply a change set against that baseline that preserves independent appends. An existing chat checkpoint can help if it includes those messages.

### 6. Closing a tab during a group reroll can discard the previous replies

When a turn has multiple replies and cannot reroll one message in place, the client keeps the old reply bundle in memory, removes it from the chat, then flushes before requesting a replacement generation. The tab owns the fallback that puts the replies back after a refusal or failure. [Reroll selection](../../../src/lib/ChatScreens/DefaultChatScreen.svelte#L938), [removal and restoration](../../../src/lib/ChatScreens/DefaultChatScreen.svelte#L1033), [in-memory history](../../../src/ts/process/rerollHistory.ts#L41), [preflight flush](../../../src/ts/process/serverCommands.ts#L1183).

**Browser verification.** In a bound group chat containing a question and two members' replies, the test held the generation request before it reached the server. Both replies were already absent from SQLite. Closing the page left only the question, even though the server had never admitted a replacement job. Keep the original rows until the server can commit the replacement, or retain a durable copy with the pending reroll that survives a client exit. The exposed history is the removed reply bundle. [Turn boundary](../../../shared/rerollCandidates.ts#L317), [job creation after preparation](../../../src/ts/process/serverCommands.ts#L1283).

### 7. Externally restored or cloned databases can reuse a cached revision for different data

This requires two copies of the **same** database, divergent writes, a matching revision for the affected record, and a browser returning to the same origin with an eligible cache entry for the same app and cache format. A revision contains the database epoch, row sequence, and revision counter. Two copies can advance the same character once in different ways and produce identical tokens. The boot route then tells the browser to reuse its cached body. The application's own restore assigns a new epoch. [Token construction](../../../server/src/data/resourceStore.ts#L1118), [boot cache decision](../../../server/src/routes/resourceBoot.ts#L184), [client installation](../../../src/ts/storage/bootCache.ts#L372), [restore epoch](../../../server/src/data/resourceStore.ts#L3223).

**Store verification.** Two temporary SQLite copies produced identical tokens for different character data. Boot omitted the server's character body and a write based on the other copy's token overwrote the stored description. In a second fixture, a deletion with that token removed an active character and its chat. An automatic route to that deletion follows from finding 4: one copy marks the character as trashed, the other edits it while keeping it active, and the cached trash timestamp has expired by the next boot with no generation lock blocking deletion. The cache match and deletion were exercised directly. The combined divergent-copy and browser-expiration sequence was traced in source. [Whole-record save choice](../../../src/ts/storage/resourceSync.svelte.ts#L2666), [character deletion from the tab](../../../src/ts/storage/resourceSync.svelte.ts#L2866), [boot maintenance](../../../src/ts/bootstrap.ts#L484).

Provide a supported way to give an externally restored copy a fresh epoch before serving it. Validating cached bytes can fix the boot read, but already-open clients also need their old write tokens invalidated.

## Recovery and whole-database symptoms

- **If all data looks old or empty after a deployment**, first identify the actual database. The default path is `save/data/resources.sqlite` under the server's working directory. `RISU_SAVE_DIR` can override it, and the documented container command mounts a named volume at `/app/save`. A different mount, working directory, or save directory can expose an empty or older database while the intended copy still exists. Versions 1 and 2 of the resource database cause startup to stop. Preserve those files for recovery. [Startup root](../../../server/src/main.ts#L25), [path selection](../../../server/src/listenConfig.ts#L38), [database open](../../../server/src/app.ts#L359), [legacy version check](../../../server/src/data/resourceStore.ts#L3878), [Docker run command](../../../README.md#L110).
- **If a chat still exists**, an earlier chat checkpoint can restore its transcript. Automatic checkpoints require a per-chat policy and eligible completed generations. **If the chat or character was deleted**, SQLite also deletes its checkpoint records. Look for a pre-deletion server snapshot or independent backup. In Settings → Storage → Snapshots, pin a candidate before it rotates. The Restore action replaces the entire resource database. For a single missing chat, keep an untouched copy, open a working copy on an isolated server with a fresh browser profile, and use chat JSON export/import to recover the transcript selectively. If the character was in Trash, inspect its timestamp offline first. When it has expired, set the isolated browser's clock within the original three-day window before opening the working copy, then restore the character from Trash. Otherwise the recovery session can immediately purge it again. [Checkpoint policy and cascade](../../../server/src/data/checkpointStore.ts#L47), [automatic capture](../../../server/src/data/checkpointService.ts#L108), [snapshot UI](../../../src/lib/Setting/Pages/Storage/StorageSnapshots.svelte#L39), [JSON export](../../../src/ts/characters.ts#L346), [chat import](../../../src/ts/characters.ts#L538).
- **Snapshot coverage can have a multi-day gap.** The default timer checks every ten minutes and keeps the newest 20 unpinned snapshots, with up to 20 more pinned. Rotation counts snapshots, so with continuous writes the unpinned history can turn over in roughly 3 hours 20 minutes. Startup initializes the scheduler's baseline to the current process write count. A shutdown before the next tick forgets that work for scheduling purposes. An isolated restart test retained the saved value in the live DB and produced zero snapshots over six following timer intervals with no new writes. Disk-space failures can also skip ticks. A later loss of the live DB would leave a recovery point only as recent as the last successful copy. The default snapshot directory, `save/backups/`, shares the live database's storage volume. Losing that volume takes both copies unless one was backed up elsewhere. Persist the last snapshotted generation or compare against the last snapshot at startup. The timer itself never restores a database. [Defaults](../../../server/src/data/snapshots.ts#L10), [startup baseline](../../../server/src/data/snapshots.ts#L156), [rotation and disk checks](../../../server/src/data/snapshots.ts#L313), [shutdown](../../../server/src/data/snapshots.ts#L535).
- **A full restore can explain a database-wide rollback.** The native restore validates a staged copy, rechecks the epoch under maintenance, takes a safety snapshot of the live data, and installs the replacement in one transaction. A failed install rolls back. Writes that committed while the source was being validated can therefore be present in the pre-restore safety snapshot and absent from the selected older copy. Preserve both before choosing a recovery point. The member lists and messages of an upstream import also depend on the source archive. For example, the import review reports a missing cold-storage payload before installing a chat with no messages. [Restore admission](../../../server/src/routes/backups.ts#L246), [safety snapshot](../../../server/src/routes/backups.ts#L627), [atomic install](../../../server/src/data/resourceStore.ts#L3234), [cold chat import](../../../server/src/data/upstream/importCharacters.ts#L553).
- **A saved local backup omits model credentials in `llmSecrets`.** The native file exporter deliberately scrubs this record. The local-backup dialog can report success without mentioning it, and loading the file replaces the live record along with the rest of the database. Internal server snapshots retain the record. Disclose the omission at export and restore so someone relying on the file alone can arrange independent credential recovery. [Archive scrub](../../../server/src/routes/backups.ts#L340), [local backup result](../../../src/ts/drive/backuplocal.ts#L284), [backup dialogs](../../../src/lib/Setting/Pages/UserSettings.svelte#L19).
- **Power-loss durability depends on configuration.** The resource DB uses SQLite WAL with `synchronous=FULL` by default. The opt-in `RISU_SQLITE_SYNCHRONOUS=normal` can lose recent acknowledged commits after an OS crash or power loss. The code establishes no fixed 1–3 day loss interval. Server snapshots are self-contained database copies. A copy of only the main file of a running WAL database can omit committed pages still in its WAL. [Configuration](../../../server/src/app.ts#L1389), [SQLite initialization](../../../server/src/data/resourceStore.ts#L3856), [snapshot copy](../../../server/src/data/resourceStore.ts#L3178).

## Verification scope

The browser checks used fresh temporary save directories and read-only SQL to verify saved rows. The plugin, Lua, two-client deletion, clock, snapshot scheduler, and divergent-database checks used synthetic fixtures. Their frequency in deployed instances is unknown. A narrower risk remains for competing edits to one existing message. The editor warns once it observes a remote change, but the server accepts a stale by-ID text write if the other edit has yet to reach the tab. An asynchronous trigger can likewise write a changed field or remove a baseline message using the refreshed revision after another writer edits the same row. These two cases were traced in source. [Editor warning](../../../src/lib/ChatScreens/Chat.svelte#L294), [text save](../../../src/lib/ChatScreens/Chat.svelte#L739), [server revision rule](../../../server/src/data/chatStore.ts#L2237), [stored text update](../../../server/src/data/chatStore.ts#L2623), [trigger working copy](../../../server/src/jobs/runSetup.ts#L395), [trigger reconciliation](../../../server/src/jobs/chatResult.ts#L109).

The audit covered normal boot and resource saves, the plugin and Lua write paths above, character trash, chat deletion and reroll, checkpoint and snapshot restore, and native and upstream backups. It did not simulate a failing disk or OS power cut or inspect any production data. A separate HTML chat export/import issue found during the audit is recorded in [the backlog](../../backlog/found-issues.md#html-chat-exports-can-fail-to-import-or-change-the-original-message-text).
