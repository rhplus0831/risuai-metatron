# Backups, Realm Hub

## Scope

- Owns:
  - local `.bin` backup export and import (full and partial) and the server snapshot restore button, as client UI over the server backup routes,
  - Realm hub browse and download (upload, report, and remove were removed),
  - the settings report export.
- Paths:
  - `src/ts/drive/backuplocal.ts` (the folder name is historical; Google Drive sync, Risu Account sync, and Kei auto-backup were removed)
  - `src/lib/UI/Realm/*`
  - `src/lib/Setting/Pages/Advanced/SettingsExportButtons.svelte`
- Not here:
  - The save adapter and resources → `persistence.md`.
  - The archive format, snapshots, and the backup routes → `self-host-server.md`.
  - Hub URL and card codecs → `characters-modules.md` (`characterCards.ts`).
  - Node `/hub-proxy` → `self-host-server.md`.
  - `localNetwork.ts` → `global-api.md`.

## Files

- `drive/backuplocal.ts` (the server builds and reads the archive; see `self-host-server.md`):
  - `SaveLocalBackup`: `flushResources`, then `POST /api/backups/export` (every asset on the server, inlays included, plus a snapshot of the resources), streamed to a file through `LocalWriter.write`. The manifest (first record) is read from the stream head; assets the database references but the archive lacks are reported. When the pre-backup flush replaced a local change (`flushResources`' `discarded` is non-empty: another writer's version is what the archive holds), the success alert or the missing-asset report says so (`backupDiscardedChanges`); the reload notice, in its own store, also stays above the progress alerts.
  - `SavePartialLocalBackup`: the same with `{ partial: true }`; the server selects character/group profile images, persona icons (including the selected user icon), background, folder images, and preset images from the resource snapshot it archives (no inlays, emotion images, additional assets, VITS, or CC assets). `shared/backups.ts` `selectPartialBackupAssets` defines these categories for both sides; the client's `partialAssets` uses it only to label the manifest's `missing` entries. A key absent from the client's inventory is reported as "Unknown Asset".
  - `SaveUpstreamLocalBackup` ("RisuAI-compatible backup", `docs/plan/upstream-bin-compat.md` S7): a `.bin` upstream RisuAI's "Load Backup" restores. See Flows. It shares `streamToFile` (the `LocalWriter` loop with the size wait text, cancel and abort on failure) with `downloadArchive`, and names the file `upstreamBackupFileName()` (`RisuAI-backup-YYYY-MM-DD.bin`, local date).
  - `LoadLocalBackup`: reads the chosen file's first record name (`readFirstRecordName`, from `file.slice(0, 4 + 4096)`). `manifest.json` (a version-2 archive): posts the `File` to `POST /api/backups/import` and reloads. Anything else goes to the upstream import (`upstreamBackupClient.ts`, loaded on demand): upstream RisuAI backups and metatron's own from before Phase 1 (`database.risudat`), which the compatibility rule (`persistence.md` Invariants) owes a one-way migration.
- `drive/upstreamBackupClient.ts` (`docs/plan/upstream-bin-compat.md` S5; routes in `self-host-server.md`): `prepareUpstreamImport(file, onProgress)` (the file as the body with the tab's epoch, through `serverImportClient.ts` `importOverServer`; its `readResult` reads each `{ phase, done, total }` line's phase), `commitUpstreamImport(token, acceptWrites?)` (`{ committed }`, or `{ changedWrites }` for the server's `409 changedSinceReview`; a 412 goes through `epochMismatch`), `cancelUpstreamImport(token)` (best effort), and `restoreUpstreamBackup(file)`, the flow below. The export side (S7, `server/src/routes/backupsUpstreamExport.ts`): `tabExportRequest(includeSecrets)`, `prepareUpstreamExport(request)` (`{ token, report }`), `downloadUpstreamExport(token)` (the response, the token used up), `cancelUpstreamExport(token)` (best effort); a refusal is `UpstreamExportRequestError` (status and the server's text).
- `lib/Setting/Pages/UpstreamImportReport.svelte`: the report dialog (`alert.ts` `alertUpstreamImportReport(report, { changedWrites? })`, alert type `upstreamImportReport`, rendered by `AlertComp` like the request logs popup): the counts, the converted and left-out lists (each code one `language.upstreamImport` line with its count and example names), the missing assets by owner and role (the first 50; non-`.png` ones marked as never backed up by RisuAI), the full-replace warning, Cancel and Restore.
- `globalApi.svelte.ts` `loadInternalBackup` ("Load Internal Backup" in `UserSettings.svelte`): lists the server snapshots (taken every 10 minutes while data changes, 20 kept), restores the chosen one, reloads.
- `UI/Realm/RealmMain.svelte`: browse via `characterCards.ts:getRisuHub`.
- `RealmPopUp.svelte`: detail, copy link, and `downloadRisuHub`.
- `RealmHubIcon.svelte`, `RealmLicense.svelte` (`CCLicenseData`).
- `SettingsExportButtons.svelte`: a redacted settings report (strips characters, keys, `irisDialogue`, `googleSearchCredentials`, and `pluginCustomStorage`), the request logs popup (`alertRequestLogs`, `global-api.md`), and statistics.

## Flows

- Entry points:
  - `UserSettings.svelte`: local backup buttons (full, partial, RisuAI-compatible), internal backup restore, dataset export.
- RisuAI-compatible backup (`SaveUpstreamLocalBackup`): after the button's backup confirmation, "Include API keys?" (`alertConfirm`; No is the recommended answer, and the text says it covers every key: without it the auxiliary service keys, the characters' TTS keys, and the MCP OAuth secrets are blank too, unlike the version-2 archive, which keeps those). Then `flushResources` (a failure stops here), and the prepare with `tabExportRequest`: this tab's selection (`settingsViews.svelte.ts` `tabSelectionIds`, ignoring the open chat's binding), its open chat (`chatStore.svelte.ts` `currentChatRef`, as `selectedChat`), and the keys answer. The report (`shared/upstreamExportReport.ts`: counts, the converted and left-out lists with examples, the first 20 missing assets by owner and role, the flush's discarded-change note) is a confirmation ending in "Download it now?". No cancels the prepared export; yes downloads it (the token is used up) and streams it through `LocalWriter` to `RisuAI-backup-<date>.bin`. Nothing is read from the stream (the file has no manifest). A refusal (409 too many waiting, 413 too large, 404 expired) shows the server's text.
- Upstream RisuAI backup restore (`restoreUpstreamBackup`): the upload and the server's conversion show as a wait alert with the phase and its counts. A refusal (a Risu Account backup's U4 message, a damaged file, a backup too large or over the worker's memory limit, another import waiting) is an `alertError` and nothing changes; a 412 reloads. Then the report dialog: Cancel cancels the prepared import. Restore commits with a wait alert; a `409 changedSinceReview` asks again in the same report dialog with the count of changes saved since the preview (on this or another device; the safety snapshot keeps them), and Restore resends with `acceptWrites` set to that count (asked again if more arrived), Cancel cancels. Only the report dialog’s own Restore button authorizes a commit. The selection (D4: the upstream-selected prompt preset, model preset, and persona) is known from the prepare's answer. Before each commit, `resourceSync.svelte.ts` `beforeRestoreReload` registers a synchronous hook that writes it with `selection.svelte.ts` `persistSelection` (storage only, not applied) when a restore is detected, before the terminal notice. The notice never waits for the commit's answer; a successful answer writes its own selection and reloads. A changed-since-review answer or definite refusal unregisters the hook (before epoch handling for a 412); a lost connection keeps it registered and reports that the restore may have happened. A prepared import not committed (cancelled, refused, or failed) is cancelled on the server. Other tabs see the maintenance 503 retries, then the new epoch, and reload.
- PeerJS multiuser chat (rooms, peer sync, and the `peerjs` dependency) was removed.
- Realm: `MainMenu` (the Explore card) → `RealmMain` → `getRisuHub(search, page, nsfw, sort)` → `RealmPopUp` → `downloadRisuHub`. There is no upload path.
- Realm download: `downloadRisuHub(id)` asks the server to download and stage the card (`prepareRealmImport`, `POST /api/import/realm`, `storage/realmImportClient.ts`, `self-host-server.md`); the tab never fetches realm.risuai.net or holds the file. The server validates a CharX or PNG card, writes nothing, and answers its card text (a CharX file's embedded `module.risum` too) and a token. The tab then reads the card and asks its questions (`commitRealmCard` in `characterCards.ts`): an `rcc` card's password (decrypted in the tab, `readPngCard`) and the `lowLevelAccess` confirmation (`confirmCardLowLevelAccess`). A card that is declined, has a wrong password, or fails to read is cancelled (`cancelRealmImport`, `POST /api/import/realm/cancel`), so nothing is stored; otherwise the tab commits (`commitRealmImport`, `POST /api/import/realm/commit`), the server stores the assets and the image and answers their keys, and the tab builds the character (`importCharxCard`/`importPngCharacter`, the question not asked again). A commit that fails is cancelled too (404 `Import expired` after 10 minutes is `realmImportExpired`; a prepare refused while 4 imports wait is `realmImportTooManyWaiting`). A legacy JSON answer is passed through and imported in hub mode as before (its portrait and hub-mode assets fetched through `/hub-proxy`).

## Invariants

- The archive format (version 2, `manifest.json` first) is defined by the server; the client only streams it and reads the manifest. An archive or snapshot whose resource database has another schema version than the server's (3 since Phase 3) is refused with a message. Those versions are formats of metatron's implementation phases, so no migration is owed. Archives in the upstream format (upstream RisuAI and metatron before Phase 1) are restored through the upstream import under the compatibility rule (`persistence.md` Invariants): a one-way, full-replace migration with a report before anything is replaced; the version-2 import route still refuses them with a message naming the upstream import. A Risu Account backup (`encryption.risudat`) is refused with a message (U4).
- Export, change, and restore are covered end to end on a version-3 store (Phase 4 closeout): an archive import undoes changes made after the export (a plugin `setCharacter`, an MCP tool), and restoring the safety snapshot the import took brings them back.
- A backup restore replaces every resource and only adds assets that do not exist yet; the app reloads afterwards because every revision the tab held is void (new epoch).
- Private backups carry everything, including `googleSearchCredentials`, the Iris dialogue, plugin storage, and the plugin permission grants.
- `getLocalNetworkRequestOptions` must stay paired with `isLocalNetworkUrl`. Browsers reject the local route.
