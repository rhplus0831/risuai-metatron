# Persistence: Database, Server Resources, Save Adapter

## Scope

- Owns:
  - the persisted DB model and its migrations,
  - how the in-memory `Database` maps onto the server resources (load, the save adapter, conflicts),
  - the chat mutation module (every chat write, server job locks and the streaming state, per-tab chat selection),
  - the browser-local data import and the list of stores that stay browser-local,
  - chat paging defaults.
- Paths: `src/ts/storage/*`, `src/ts/chatLoadPages.ts`, `shared/` (the persisted shapes; the meaning of a shape stays with the guide that owns its original module, e.g. `shared/triggers.ts` → `scripts-triggers.md`, `shared/llm.ts` → `llm-requests.md`), plus their tests.
- Not here:
  - The server side of the resources (store, routes, snapshots, archives) → `self-host-server.md`.
  - Backup and export UI → `backup-sync-hub.md`.
  - `saveDb` is exported from `src/ts/globalApi.svelte.ts` (see `global-api.md`); it only starts the adapter described here.

## Flows

Resources (server kinds; `shared/resources.ts`):

- Singletons, id `main`: `presets` (`botPresets`), `modules`, `plugins`, `pluginStorage` (`pluginCustomStorage`), `pluginPermissions` (not in `Database`).
- Phase 3 singletons, id `main`, created by the server when missing and normalized there (`server/src/data/normalize/`): the sections `providers`, `secrets`, `llmSecrets`, `ui`, `memoryTranslateMedia` (each holds its `SECTION_FIELDS` under their `Database` names; `llmSecrets` also holds `presets`, the `proxyKey` of each preset by id, and `customModels`, the `key` of each custom model by id; it is write-only and read masked, `self-host-server.md`) and the collections of `COLLECTION_FIELDS` (the field's value; `translatorPresets` and `hypaV3Presets` hold `{ items, selectedId }`). The client mirrors them into `DBState.db` under the same flat field names; `translatorPresetId` and `hypaV3PresetId` are the ids of the selected entries.
- Per record: `characters` (id = `chaId`, the character without `chats`, `chatPage`, and `reloadKeys`), `inlays` (id = inlay id; see `chat-pipeline.md`).
- Chats (their own tables, not a kind; see `self-host-server.md`): one chat per (`chaId`, chat id) with its metadata, its messages as rows keyed by message id, one revision per chat, and one chat order per character. They travel in the batch as `chats` groups of ops and `chatOrders`, and are read with `?chats=1` or `refs`/`chats`/`chatCollections`.

Load (`bootstrap.ts:loadData`):

1. `readKinds` for every kind and every chat in one request (one committed state plus the epoch).
2. `seedResources` records each record's revision and JSON text before anything changes the data; `seedChats` records each chat's and chat order's revision; `seedInlays` fills the inlay cache.
3. The `Database` is assembled (`assembleDatabase`): every field of each section, each collection (`{ items, selectedId }` unpacked into its two fields; `llmSecrets` as `mirrorFields` of its masked record, which `setMaskedSecrets` adopts), the Phase 1 collections, and the characters in store order (creation order). A missing section, collection, or `presets` record is an error: the server creates them. `assembleChats` puts each character's chats in its chat order (a chat missing from the order is appended, an order entry without a chat is skipped, both logged).
4. `loadSelection` reads this tab's selection first; `setDatabase` (the preset and persona backstops; `setDatabaseLite` moves the record fields into the records, giving characters without a valid or unique `chaId` a new one before any wrapper exists, installs the forwarding accessors, and resolves the selection), and `checkNewFormat` (the trash pruning through `removeCharacters`) run; the characters arrive normalized by the server and get no client default at boot. `initializeChats` selects each character's remembered chat (`localStorage` preference) and gives a character without chats a new one.
5. `saveDb()` starts the adapter, which marks every collection and character once so the normalization is saved (unchanged records compare equal and are not sent).
6. `importBrowserLocalData`, `loadPluginPermissions`, then `loadPlugins`, then the UI flags.

Save (the adapter, `resourceSync.svelte.ts`):

1. The settings records (`records.svelte.ts`: the sections, the settings collections, `presets`, `modules`, `plugins`, `pluginStorage`) mark themselves: every local write of one, through `DBState.db`'s accessors or a wrapper, marks its record at once (Phase 6 slice 4; their watchers are gone). For `llmSecrets` the record's text is its readable siblings; the credentials are queued, below. The characters are write-through records too (Phase 6 slice 5): a write of a character's own fields at any depth, selected or not, through `DBState.db.characters` or the character module, marks that character (`setCharacterWriteListener`); its `chats`, `chatPage`, and `reloadKeys` are outside the record (raw, the chat module's). A membership change (only through `characterStore`) wakes the loop. Chat writes reach the loop through the chat module's work listener. There is no character watcher and no mark helper.
2. After a 500 ms debounce one cycle runs (never two at once). Each dirty record is serialized (a settings record from its live record with `JSON.stringify`, a section's fields in `SECTION_FIELDS` order, so an own `__proto__` key of a user-keyed map survives and the text equals the server's normalized text; a character with `$state.snapshot` per field, without `chats`, `chatPage`, and `reloadKeys`) and skipped when the text equals what the server holds. The `chaId` list is diffed against the saved characters: new ids are created, vanished ids deleted (the ids are unique by construction).
3. Everything goes in one `POST /api/resources/batch` with the chat module's unsent work (`takeChatWork`: per chat one group of ops on the chat revision it was based on, plus reorders; one transaction on the server; split above 5,000 operations or the 100 MiB body limit measured in UTF-8 bytes, or to isolate an unindexed permanent refusal; a chat's group never split inside a request; a chat with more than 5,000 unsent ops sends them over several cycles; a single record over the limit is quarantined by its content with a 413 reason before taking dependent chat work). A chat created with its character travels with the character when the batch fits, or after its character when split. On success the sent text becomes the saved text and `ackChatWork` records the chat revisions; a key marked again during the request stays dirty. A `stale: true` chat result keeps its old base and marks it for an idle re-base: the cycle reads it back without overlapping a batch and checks again after the read that no work, lock, deferral, or quarantine intervened. An idle chat accepts the server copy and revision without a discard or reload notice; a busy chat keeps the mark for a later cycle.
4. A network error, 5xx, or 429 retries with backoff (up to 30 s); a chat create whose answer was lost is resent and recognized when the server already holds it. A 400 that names one chat group (`chats[i]...`) quarantines that chat (one alert; its later edits are not sent) and resends the rest (a chat group over the body limit is quarantined client-side before any request); a 400 naming `ops[i]` quarantines that resource key (`kind` + NUL + `id`) at its refused projection text and alerts once per key per session. The client-side 413 pre-check does the same. Unchanged refused content is skipped; editing that record releases it for another attempt. Other records and chats continue saving. An unindexed 400/413 isolates the next cycle into separate requests for each resource, chat group, and reorder, preserving character-before-chat ordering. An isolated refused resource waits for a content change and alerts once per change; a refused chat is quarantined, and a refused order waits for its ordered ids to change. Quarantined character creates stay out of `creating`, so their chats wait and membership is not acknowledged early. Quarantine does not keep an idle save cycle scheduled, and `flushResources` rejects immediately with a quarantined record's refusal reason.
5. A 409 reads the conflicting records back (`readRefs`) and writes them into the mirror in place (a section's fields replaced in place, a collection replaced, a character replaced, inserted, or removed; the selected character removed → home screen). The local edits of those records are discarded and `resourceReloaded` is shown once per episode. When the server already holds exactly what was sent (a retry after a lost response), nothing is reloaded. A character or the `statics` record is merged instead (`mergeConcurrentChange`, Phase 5 Stop D fixes) when every top-level field the server changed against the saved base is one this client can take without losing anything (`benignChanges`): a field the server holds as this client does, a field neither the base nor this client has (another tab filled it in, such as a default its character screen binds; the server's value is taken), a character's `lastInteraction` (the later of two finite stamps), or a `statics` count (`imports`, `messages`, best effort: the server's count plus this client's increments since the base; two tabs raising a count to the same value, or a count a lost answer already holds, can be off by those increments). The changes go into the mirror, the base moves to the server's revision, and the key stays dirty, so the next cycle writes the merged record with no discard and no reload notice; a field taken from the server other than the stamp is announced to `onRemoteRecordApplied` listeners. Any other remote change, even of a field this client did not touch, conflicts as above, so a group's parallel member arrays are never combined from two sources. So another tab opening a character or counting a send no longer discards this tab's edit. Not for a create, a delete, or a taken field the mirror object only inherits (`toString`, `constructor`, ...: `assignsInherited` in `shared/mutationValidation.ts`; a Svelte proxy would not store it, so the record conflicts as above). A chat conflict (`recoverChatConflicts`) reads the chat back: non-conflicting groups are requeued, recognized create/delete replays are settled, and other conflicting chats discard their queued edits with the notice. A refused create (including a resend) whose read-back is null is quarantined with an alert and retained in the mirror, including through a deferred reload and subsequent collection refresh; if its character is gone, character recovery handles that deletion. A chat a server job streams into defers its reload until the job's locks are released (`isChatDeferred`); the reload then discards its queued edits, as any conflict does. A stale acknowledgement uses the quiet idle re-base in step 3 instead of a conflict reload. A character a server generation runs on is reloaded at once like any other (Phase 6 slice 5 removed the tab-side deferral): the job reads its own configuration and refreshes character records from the server at its barriers, and the server's message locks still refuse what touches the generating message. A server copy goes into the character records raw (`applyRawCharacter`, `patchRawCharacter` for a merge), marking nothing. Every reloaded record is announced to `onRemoteRecordApplied` listeners (boot registers the inlay cache invalidation).
6. A 409 entry with `reason: "generating"` (a server generation job owns a message the change touches; also a refused character delete) is not a reload: the chat's work is requeued and blocked for `JOB_RETRY_MS` (5 s), a refused character delete stays an unsaved membership change for the same time, one cycle is scheduled at the retry time, and `chatGenerating` is shown once per refusal episode. Blocked work counts as unsaved (unload warning, flush obligations) but not as runnable; `flushResources` rejects at once with the generation error while it is blocked.
7. `applyHydration({ kind, id, characterId?, revision, data })` applies a record a server job sent without any outgoing write: no discard, no `discardSequence` bump, no settled key, no notice. It applies only a token of the loaded epoch newer by `(seq, revision)` (`compareRevision`) than the held one, and only when the client has no local change of that record (not in the batch in flight, its projection equal to the saved text, not blocked); a dirty mark alone, with the projection unchanged, is no change. A record refused for a local change keeps its newest event, checked again after the next save cycle. A record the client does not hold, a deletion, `llmSecrets`, and `authRefreshes` are not hydrated; `chats` goes to `hydrateChat`.
8. Credential writes (Phase 5 slice 7b): after the cycle's batch, the `llmSecrets` ops queued when the cycle collected its work (a later one waits for the next cycle, after its resource) are sent one at a time through `/api/llm-secrets/*` (`resourceClient.ts` `sendSecretRequest`) on the record's held revision. A cleanup is sent only once its owner is gone from the mirror and from the saved copy; it is dropped while the mirror holds the owner (a conflict restored it) and waits, without keeping the loop scheduled, while only the saved copy does. A reply's revision and masked record are adopted, and its siblings judged by text against the saved text: mirror siblings equal to it take the server's; a local edit over unchanged server siblings is kept and written on that revision; a local edit where the server's siblings changed too is the normal conflict (the server's copy wins, the discard is recorded, the reload notice shown). A 409 rereads the record and retries, at most twice per op per cycle; a 400 or 404 drops the op, reports it as a discard (`llmSecrets/<path>`), and alerts; any other failure keeps the queue for the next cycle with the save backoff (a 412 halts as below). The queue counts as pending and unsaved work, and `flushResources` waits for the ops queued at its call. `awaitSecretWrites()` waits for the ops queued now and throws when one was refused, when only cleanups behind an unsaved deletion are left, or when saving is halted (also with an empty queue; `assertSaveAdmission`); `auxFetch` calls it first. A page unload does not send queued credential ops (the unload warning shows them as unsaved).
9. Live updates (Phase 6, `noteRemoteChanges` from `eventFeed.ts`): another writer's committed refs. Each resource ref is compared with the held revision on arrival and dropped unless newer (this client's own save, or a job event that applied it first); `inlays` and `pluginPermissions` go to their owners; a newer record of a mirrored kind (a section, a collection including `authRefreshes` and `pluginStorage`, `presets`, `modules`, `plugins`, a character, including one this client does not hold) waits in a set, with the newest revision announced. A chat ref goes to `noteRemoteChat` (the idle refresh of step 3, so a chat with local work, a generation, a deferral, a quarantine, or a retry block is read later); a chat-order ref newer than the held one, or a new chat, queues the character's chat list. The cycle (50 ms later) reads them in one `readRefs`, before its batch, never alongside one: a waiting entry at or below the held revision is dropped without a read; one whose record has a local change (in the batch in flight, its projection different from the saved text, quarantined, blocked, a character deferred or generating) is not read and waits (its save lands, making the update older, or conflicts through step 5). After the read it checks again (after `tick()`), then applies through `applyToMirror` with the saved text set to the mirror's projection: no discard, no `discardSequence` bump, no settled key, no notice; `reconcileSelection()` after a collection or `presets` replacement; a new character inserted with its chat list (`applyRemoteCollection`; a chat or order ref that arrives for it before its insertion reads its list again afterwards); a deleted character removed (the selected one → home) only when the held revision is unchanged since the read was issued, else read again. A read settles only the notice it was issued for, or a later one its answer covers (a record's entry by identity, a chat list by its notice sequence); a deletion notice for a character this client never inserted drops its entry, and a read finding it gone settles the create notice. A chat an idle read finds gone is removed only when its held revision is unchanged since the read was issued, never by creating a replacement chat (the character's only chat stays until the writer's new chat arrives); a chat list removes an idle local chat only under the same fence, keeps a chat this client deleted but has not saved out, and drops a chat's notice only when the adopted copy covers it. `llmSecrets` is adopted as in step 8 with every credential path invalidated, but where a local sibling edit meets a changed server sibling nothing is applied and the entry waits for the local text to change (the save's 409 decides). At most 1,000 records and 1,000 chat lists (new characters' first) per cycle, and 1,000 chats per idle refresh read; the rest wait. A mutation also checks right before it goes out, after authentication and signing (`setMutationAdmission`), that saving has not halted. A cycle stops after each awaited stage and before each batch once saving halted for a restore (captured chat work is requeued). `reconcileRemote(listing)` runs after every `hello`: every listed record, chat, and order goes through the same comparison, every held record or chat the server no longer lists is a deletion, and each owner outside the mirror reconciles its own kind (`reconcileInlays` drops cached metadata older than listed or no longer listed). The translator and HypaV3 `selectedId` values are shared records, so choosing one in a tab switches it in the others (the preset and persona selections stay per tab).
10. A 412 (the server was restored) stops saving, shows `resourceRestored` as the terminal notice (`alertTerminal`, `global-api.md`: no other alert can replace it), and reloads the page once the user acknowledges it. A transform request the restore refused shows no failure toast (`transformClient.ts`). The transport runs the same halt for a 412 on any other resource request (inlays, permissions, a backup import) and for a read after boot that answers with another epoch. A server job that a restore or import ended (`maintenance`) makes its tab watch for the replacement (`watchForRestore`, below in Known Hazards), so a send's owner is told without another action; the job's error shows only when nothing was replaced.

`flushResources()` saves everything changed before the call (including queued chat work), and resolves when it is on the server, with the keys a conflict discarded (`chats/<chaId>/<chatId>` for chats); backup export and the browser-local import call it.

Chats (`chatStore.svelte.ts`):

- Every chat write goes through the module: it updates the mirror, bumps the chat's local version, and queues an op; ops of one chat coalesce (text writes, meta patches, end appends) until the save loop takes them. `character.chats` and `chatPage` are typed read-only (`DeepReadonly`), so a direct assignment, `push`, or `splice` fails `pnpm check`; `bind:` on a chat field does not, so components bind through getter/setter pairs or a synced editing copy (HypaV3 modal, local lore draft).
- A `meta` op's `merge` adds entries to a chat field that is a map (`CHAT_META_MERGE_KEYS`: `toolCalls`) on the server's stored value, so two writers adding different entries keep each other's (`mergeChatMeta`). `chat.toolCalls` entries are validated wherever a chat is written (`{ call: { id, name, arg }, response }` under their own id, each response piece a tool content the request adapters read, at most 1 MiB each); the map has no eviction, and every merge normalizes and stores the whole map again.
- Ops address messages by `Message.chatId`, never by index. By-id ops (`append`, `setMessage`, `setText`, single `remove`, `meta`) apply to a stale chat revision while their message exists; `replace`, `delete`, bulk `remove`, reorders, and a `begin` of an unknown generation need the current revision. A result applied on an older revision says `stale: true`; `ackChatWork` and `settleUnloadWork` keep the older base and request an idle re-base. The save cycle reads the chat and rechecks eligibility after the await: no pending entry, in-flight group (including an unload request), server job lock, deferral, or quarantine. Only then does it apply the server copy and revision, bumping the mirror version without discarding work or showing a reload notice. Otherwise the refresh mark stays for a later cycle. A send still building its prompt without a lock can be refreshed; its baseline still protects changes made meanwhile.
- Selection is per tab: the module keeps the selected chat id per character, derives `chatPage` from it after every create, delete, reorder, and reload, and remembers the last selection in `localStorage` as a preference for the next boot (not synchronized live between tabs).
- Whole-chat writers (triggers, Lua `setFullChat`, plugin setters, `editChat`) capture a baseline and call `applyChatResult`: the changed copy is diffed three ways against the baseline and the chat as it is now, and applied as by-id ops, with `replaceChat` only when a diff cannot express it. Changes made meanwhile by others are kept.
- A never-sent chat's create group is the current mirror payload alone (the mirror already holds every queued change).
- Deferral: a conflict on a chat a server job streams into (`isChatGenerating`) is deferred: the chat is excluded from batches and reloaded (`deferredReloads`, `finishDeferredReload`) once the job's locks are released, since replacing it earlier would drop the streamed text. The deferred chat's local work is discarded by that reload, as for any conflict.
- Server generation jobs: a job's reply is locked by `applyServerGeneration`, or already by the job's chat hydration that lists it as `streaming` before the job's `accepted` arrives (the reply appended with `begin`: the lock starts with no stream update received, its sequence below every protocol sequence and its buffer the mirror's text, so the first `accepted`/`chunk` records the raw text whatever its claim; Phase 5 cutover) (no client generation id passes; edit, delete, and regenerate are off) until its chat's hydration no longer lists it as `streaming` or the job's terminal event (`endServerJob`, which marks a chat still holding streamed text for an idle refresh). `hydrateChat` replaces the mirror's chat with the server's when its revision is at least the held one and the chat has no pending, in-flight, deferred, quarantined, or blocked work (otherwise the chat is marked for an idle refresh); only that whole-chat write moves the chat's revision. It writes the mirror directly: no `ensureChat`, no discard, no settle, no queued op. The event's `streaming` entries give each still-generating message's generation and the newest chunk `seq` the copy holds (a watermark): streamed text above it is put back, text at or below it is older than the copy (a processed checkpoint stays). Every other lock of that job in the chat is released (the reply is final in the copy), as is another owner of a listed message; another job's locks stay. A copy older than the held revision, or job metadata older than the newest taken for the chat (even from a copy that could not be applied), changes nothing; a copy that could not be applied releases locks but sets no watermark. A replaced or ended generation is retired: its late chunks are dropped. The streaming state follows the lock: a generation's first `accepted`/`chunk` (not the placeholder lock of a chat event) sets `streamingState` to its message with `DBState.db.streamingDisplayOptimizationMode ?? "off"`, and every release of that generation's lock (`endServerJob`, a hydration that no longer lists it, another owner of the message) clears it; a later generation takes it over. A message-id adoption renames it. A chat the mirror lacks, or one this client has not seen on the server, is not hydrated. An idle refresh whose read is older than the held revision is not applied.
- Unload: while any unsaved work exists, the save loop prepares and refreshes a signed unload token. `visibilitychange` to hidden immediately runs a normal save cycle, bypassing debounce/backoff with no keepalive size cap; if a cycle is already running, it finishes before a follow-up saves pending work. `beforeunload` requests the browser warning (never once saving halted for a restore or an import: nothing more can be saved, and the notice's reload must go through) for dirty records, a cycle in flight, or unsaved chat work (including unload requests); unchanged quarantined records/chats/orders and chats waiting on a quarantined character create are excluded. On `pagehide`, pending by-id ops (`append`, `setText`, `setMessage`, single `remove`, `meta`) for already-created chats go out within a shared 60 KiB budget, one request per chat; earlier unsafe operations are never skipped. Every outstanding keepalive body, including from an earlier `pagehide`, counts against the same budget. Chats with a request in flight are skipped. Only a sent group leaves its ordinary queue, counts as in flight, and settles through `settleUnloadWork` as an ordinary acknowledgement; a failed group is requeued ahead of newer edits. Resource records, chat creates, deletes, replacements, and reorders use normal cycles only. Keepalive is best effort.

Browser-local import (`importBrowserLocalData`, every boot, before plugins load):

- LocalForage `inlay` (inlays, incl. old data-URI values), `plugin` (`safe_plugin_*` → `pluginCustomStorage._safeLocalPluginStorage`), `plugin_permissions` (→ the `pluginPermissions` record), `iris_dialogues`/`current_dialogue` (→ `irisDialogue`, in the `ui` record), and `google-search-credentials`/`credentials`/`google-search-creds` (→ `googleSearchCredentials`, in the `secrets` record).
- Per entry: when the server already holds it, the server copy wins; otherwise it is written, read back from the server, and only then deleted locally. A local entry is deleted only while it still holds the value that was imported (`sameLocalValue`; another tab may have changed it). An inlay whose server metadata exists without its media file (a partially restored archive) is repaired from the local bytes when they are the file the metadata names, and kept in the browser otherwise. A value that is not plain JSON (plugin storage) stays in the browser. A failed step leaves its entries for the next boot. The `risuSaveCache` database and the `risuauth` `localStorage` key are removed.

The block save format (`risuSave.ts`, `database/database.bin`, `dbbackup-*.bin`, remote `remotes/*` payloads, the `risuSaveCache`) and remote saving were removed in Phase 1 without a migration; the `save/database` and `save/remotes` folders of older versions are left on disk and no longer read.

## Invariants

- Every loaded or imported DB passes through `setDatabase`. It also deletes the legacy Risu Account `account` token, the legacy `coldstorage` and `enableRemoteSaving` flags, and `pluginCustomStorage._coldplugin`. Initialize nested parents before assigning children (`??=`).
- Every `Database` field belongs to exactly one resource (`shared/sections.ts`: a section, a collection, or a Phase 1 collection), is forwarded (`FORWARDED_ROOT_KEYS`: served from the selected preset or persona, or from this client's selection), or is dropped (`DROPPED_FIELDS`). The assembly, the records (`takeRecordFields`, the accessors), the projections, and `applyToMirror` iterate those lists, so a new field needs only its place in `shared/sections.ts` (and its `SectionSpec` entry on the server). A new Phase 1-style collection also needs a server kind (`server/src/data/kinds.ts`) and the branches in `bootstrap.ts` and `resourceSync.svelte.ts`.
- A section or settings collection's projection must equal the server's normalized text for an unchanged record (`normalize(project(assemble(normalized))) === normalized`); otherwise every boot writes it. So the client applies no default to those fields, and boot code must not rewrite them.
- Chats are their own records: two tabs editing different chats, or different messages of one chat, save independently. A chat change never rewrites its character.
- Only `chatStore.svelte.ts` writes `character.chats` and `chatPage` (the module's `writable` view). Code that holds a changed copy of a chat applies it with `applyChatResult` (or `chatEdits.ts`); code that changes a chat field calls `setChatMeta`.
- A message being generated is changed only by its generation. Other writers get an error from the module (`Chat.svelte` disables that message's edit, partial edit, delete, disable, and regenerate controls from `isMessageLocked` and checks every affected id again when the write is made (a delete-from-here that reaches a locked reply alerts), which also covers a finished reply whose final write is not yet acknowledged and a previous group speaker's reply; reroll and chat deletion check `isChatGenerating` and alert `chatGenerating`).
- Character defaults (Phase 6 slice 5b) live in one pure helper, `normalizeCharacter` (`shared/characters.ts`): the server's `characters` normalizer applies it on every write and in its startup pass; the client applies it when a character enters (`prepareNewCharacter`, also the creation steps: `creation_date`, the lorebook conversion, a first chat, each chat's `fmIndex`/`localLore`, the `postHistoryInstructions` transfer, `ttsMode` `"none"`), to a whole replacement (`replaceCharacterFields`), and before a save: a character about to be written whose projection lacks a default gets it raw first (`canonicalCharacterText`, no mark), so the text sent and held is the server's normalized text. No default is applied at boot or on selection, and selecting a character stamps no `lastInteraction` (a send does).
- Every write of a character's own fields is saved, whichever character is selected (the character records, Phase 6 slice 5). The list's membership changes only through `characterStore` (`addCharacter`, `replaceCharacterAt`, `removeCharacter`, `removeCharacters`): a `push`, `splice`, index assignment, or list assignment through `DBState.db.characters` throws, except the no-op self-assignment, and a character's `chaId` never changes.
- Mutation rule per collection (Phase 4, Invariant 2; Phase 6 slice 4): the external contracts write every record through a mutation module. The settings records transport their own writes (`records.svelte.ts`): a write through `DBState.db`'s accessors or a wrapper is saved without any watcher, a bulk writer runs in one `batchRecordWrites` scope, and the core-app writers (the UI, `bind:`) keep writing through the accessors until the reader slices; the settings pages and the registry write through the settings views instead (`settingsViews.svelte.ts`, slice 6: the same records, the same rules). The characters transport their own writes the same way since slice 5. The list Phase 6 inherits is in `docs/plan/phases/phase-4-external-contracts.md`.
- Server data never becomes an outgoing write: the saved text is recorded from the server's own response, and a mirror reload records the text of the hydrated mirror (its own key order), so a root another tab wrote with its keys in another order is not echoed back. A server copy goes into a settings record through `applyRaw`, which marks nothing; after `presets` or `personas` the selection is resolved again.
- Every mutation carries the loaded epoch; after a restore every write is refused until the page reloads. `pluginStorage` is serialized straight from the proxy (not through `$state.snapshot`, which drops an own `__proto__` key) because plugins choose its keys.
- Keep the logical asset key conventions (`assets/<name>`). They are on-disk names.
- A preset field must be added to `botPreset` and `PRESET_DEFAULTS` (`shared/presets.ts`, which `normalizePreset` and the partition in `shared/sections.ts` follow; a field without a default, or with a `null` one, also needs its kind in `kindsWithoutDefault`, or `shared/presets.ts` throws on load). The forwarding layer then serves it as a flat `DBState.db` field, and `activePreset` under its own name; a field whose `null` is a value readers handle also goes in `PRESET_NULLABLE_FIELDS` (`normalizePreset` replaces any other `null` with the default).
- A section field must be added to `SECTION_FIELDS` and to that section's `SectionSpec` in `server/src/data/normalize/` (the type makes a missing entry an error), with its JSON kind and its fresh-boot default. Secret fields must also be scrubbed in `downloadPreset`.
- Every preset, persona, translator preset, and HypaV3 preset carries an `id`, assigned synchronously where the element is created (`normalizePreset`, `newPersonaId`, `createTranslatorPreset`, `createHypaV3Preset`); copies and imports get fresh ids, and the `.risup`, `.risutl`, and HypaV3 JSON exports carry none.
- Preset objects carry no credentials: `openAIKey` is a global `llmSecrets` field and `proxyKey` lives in `llmSecrets.presets` by preset id; `normalizePreset` keeps only `PRESET_FIELDS`, so the server drops both from stored presets. `downloadPreset` still writes them blank (and the other endpoint fields), so readers of the pre-Phase 3 format see the same keys. No credential reaches the tab (Phase 5 slice 7b): the `llmSecrets` reads are masked, its credential fields read `""` in `DBState.db`, and a credential is written only through the secret queue; a key-dependent call goes to the server (`/api/llm/request` or an auxiliary operation of `/proxy2`, `global-api.md` `auxFetch`).
- `exportAsDataset` does no redaction. The settings report in `SettingsExportButtons.svelte` does (it drops every `llmSecrets` field, and also `irisDialogue`, `googleSearchCredentials`, and `pluginCustomStorage`).

## Recipes

- Add a persisted setting:
  1. Add the field to `Database` in `shared/database.ts`.
  2. Give it its place in `shared/sections.ts` (a section's `SECTION_FIELDS`, a collection, or a preset field in `PRESET_DEFAULTS`).
  3. A section field gets its kind and fresh-boot default in that section's `SectionSpec` (`server/src/data/normalize/`), and any migration there; a preset field gets its default in `PRESET_DEFAULTS` (the server `presets` normalizer and the forwarding layer use it).
  4. Verify: a fresh server shows the default, the value survives a reload, and an idle reload writes nothing.
- Add a collection with its own resource: see the field-to-resource invariant above. Verify a save, a reload, a two-tab conflict, and a backup round trip.
- Move more browser-local user data to the server: add a step to `importBrowserLocalData` that writes, reads back, and only then deletes the local entry.
- Change the asset backend: `AutoStorage.Init` and `NodeStorage`. Asset keys are logical, not file paths: the server maps `assets/<name>` to `save/assets/<encoded name>` and accepts no other namespace (see `self-host-server.md`).

## Known Hazards

- A tab learns of a restore or import from the live-update socket's `epoch` frame (or the `hello` of its reconnect, or its next request: 412 or a changed epoch), and halts and reloads (`haltForRestore`). A tab whose server job the maintenance ended (its `maintenance` terminal, which comes before the replacement) also watches for it (`watchForRestore`: one small read a second, each bounded to 5 s, for two minutes), so the owner of a running send is told even when its socket is down.
- A quarantined resource remains only in the local mirror until its projection changes and saves successfully. Other edits do not retry it or acknowledge an unsaved character create. `flushResources` rejects immediately with its refusal reason; closing the tab does not warn solely for quarantined data. Preserve that data by export before reloading if needed.
- A refused create retained locally is quarantined for the session and excluded from collection-removal reconciliation; a server-side deletion of its parent character still follows character recovery.
- An unindexed permanent refusal switches the session to separate resource/chat/order requests; atomicity remains per request, and creating a character precedes creating its chats.
- One chat group larger than the server's 100 MiB body limit cannot be saved (the adapter quarantines the chat and alerts).
- `NodeStorage.removeItem(string[])` hex-encodes each key separately and joins them with `$$`; the server validates every segment before deleting. A filesystem error mid-batch (e.g. a missing file) returns 500 and keeps earlier deletions.
- `getCurrentChat` returns the live read-only mirror chat; take `$state.snapshot` before handing it to code that mutates.
- Folder moves touch the character (`chatFolders`), the chat (`folderId`), and the chat order; a conflict on one of them can leave them inconsistent until a reload.
- A chat quarantined after a 400 stops saving for the rest of the session; `flushResources` then rejects after its retry cycles.
- A server job's message is locked on the server for every client (`reason: "generating"`). (The browser generation path's per-client locks went with it at the cutover.)
- The browser's former LocalForage `mcp-tool-calls` store is no longer read: a remembered tool call lives only in its chat (`chat.toolCalls`), and one remembered before slice 11b or without a chat no longer resolves (alpha, no migration).
- A server job's membership changes (a record or chat created or deleted) are not hydrated on its socket; they reach every tab through the live updates.
- Live updates show another writer's change only when this tab has no unsent change of that record; two tabs editing one record still converge through the 409 path (the later saver's edit is discarded with the notice). An observing tab sees a server job's reply at its 3 s checkpoints (each one a chat read), then the final text. A tab whose socket is disconnected catches up at the reconnect's reconcile.
