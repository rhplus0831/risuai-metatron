# Persistence: Database, Server Resources, Save Adapter

## Scope

- Owns:
  - the persisted DB model and its migrations,
  - how the in-memory `Database` maps onto the server resources (load, the save adapter, conflicts),
  - the chat mutation module (every chat write, server job locks and the streaming state, per-tab chat selection),
  - the browser-local data import and the list of stores that stay browser-local,
  - chat paging defaults.
- Paths: `src/ts/storage/*`, `src/ts/chatLoadPages.ts`, `shared/` (the persisted shapes; the meaning of a shape stays with the guide that owns its original module, e.g. `shared/triggers.ts` → `scripts-triggers.md`, `shared/llm.ts` → `llm-requests.md`), plus their tests.
- Not here:
  - The server side of the resources (store, routes, snapshots, archives) → `self-host-server.md`.
  - Backup and export UI → `backup-sync-hub.md`.
  - The asset reads and writes of `src/ts/globalApi.svelte.ts` (`readImage`, `saveAsset`, `loadAsset`, `getFileSrc`; see `global-api.md`) go through `assetClient.ts` here.

Nothing is wrapped while a record is absent (`hasRecord`).
    - Module readers use two tracked revisions, independent of saving: `moduleMembershipRevision` advances on record/list/element replacement, order changes, and `id`/`namespace`/`mcp` writes; `moduleAssetsRevision` advances on asset writes and replacements. Both use a counter that never resets, and advance under `untrack` at the write, before batched save dispatch. `install` counts a rebuilt module element as membership even when its written field is unrelated; `initializeRecords` goes through `applyRaw`, and `resetRecords` advances both before clearing the metas. Bulk list helpers reach `queueNodeWrite`, which keeps these revision writes untracked too.
    - `moduleFieldPlain(wrapper, field)` resolves the element's `$state` proxy and memoizes a detached plain copy by proxy identity and `moduleItemFieldStamp`, never by id or raw-target identity. Only a cacheable field whose stamp equals the meta lifetime may be read from `proxy[STATE]`: Svelte's raw target is not updated by writes. A raw field that itself holds state falls back to the live proxy, as does a changed field. Uncacheable data is copied untracked on every read (and every wrapper write advances the assets revision, since fields may share state). The raw target is never returned or frozen; callers treat the copies as read-only. Reading a copy never writes record state or creates an absent record.
  - `src/ts/storage/mutationValidation.ts` (the code is `shared/mutationValidation.ts`, re-exported here; the server's RisuAccess host validates with it, and `CHARACTER_FIXED_FIELDS` is the set `updateCharacter` refuses): `isJsonData`/`requireJsonData` (JSON data up to 256 levels, no class instances, cycles, or non-finite numbers), `requireObject`, `requireArray`, `detach`, `detachPatch`, `writeEntries` (an inherited-name key such as `constructor` becomes an own key through a rebuilt object), and the two errors.

Each loaded item is keyed with `globalApi.assetKey` (the key `saveAsset` would give it) and the loaded items are written by `globalApi.saveAssetBatch`, one request at a time, each a batch that fits those caps (a larger single item alone), while the next batch loads; a hash key (no `customId`) already batched in the call is not sent again. Keys resolve in item order; `onProgress` runs per item when its batch is written or fails, or its `load()` throws. After a failed load or batch no further item starts and nothing more is written; the work in flight settles and it rejects with `AssetSaveError` (`failed`: every item of a failed batch, `errors`, `cause`). `savePickedFiles(files, fileName?)` feeds picked `File`s (`selectMultipleFileHandles`) to it, each read when its slot is free. `AssetSaveQueue` (`add`, `whenReady`, `waiting`, `active`) saves one item per `saveAsset` for a producer whose items arrive over time (the in-tab `CharXImporter`). `loadAssetsInBatches(keys, { batchSize = 200, signal })` (slice 3a) is an async generator over `globalApi.loadAssets`, yielding `{ index, key, bytes }` in key order (duplicates kept; `bytes` is `Uint8Array | null`). The prefetched promise's rejection is observed as soon as it starts and surfaced when that promise is next awaited, without an unhandled rejection while the consumer writes. The generator has no retries of its own. Closing the iterator (a consumer `break`/`throw` or `return()`) or aborting through `signal` stops admission, aborts the pending read, and settles it before cleanup returns, swallowing its cleanup rejection.

## Flows

Resources (server kinds; `shared/resources.ts`):

- Singletons, id `main`: `presets` (`botPresets`), `modules`, `plugins`, `pluginStorage` (`pluginCustomStorage`), `pluginPermissions` (not in `Database`).
- Phase 3 singletons, id `main`, created by the server when missing and normalized there (`server/src/data/normalize/`): the sections `providers`, `secrets`, `llmSecrets`, `ui`, `memoryTranslateMedia` (each holds its `SECTION_FIELDS` under their `Database` names; `llmSecrets` also holds the entry map (`SECRET_ENTRY_MAPS`) `credentials`, the `key` of each named API key by id ([credential binding](llm-requests.md); the former `modelPresets` and `customModels` maps are dropped on normalize, [credential binding](llm-requests.md)); it is write-only and read masked, `self-host-server.md`) and the collections of `COLLECTION_FIELDS` (the field's value; `translatorPresets` and `hypaV3Presets` hold `{ items, selectedId }`; `togglePresets` is a plain list, default `[]`, with no selection field). The client holds them in its records and serves them under the same flat field names (`readSettingsRoot`); `translatorPresetId` and `hypaV3PresetId` are the ids of the selected entries. Saved prompt-toggle presets are readable and writable as `settings.togglePresets`, with a per-chat link (`Chat.togglePresetId`).
- Per record: `characters` (id = `chaId`, the character without `chats`, `chatPage`, and `reloadKeys`), `inlays` (id = inlay id; see `chat-pipeline.md`).
- Chats (their own tables, not a kind; see `self-host-server.md`): one chat per (`chaId`, chat id) with its metadata, its messages as rows keyed by message id, one revision per chat, and one chat order per character. They travel in the batch as `chats` groups of ops and `chatOrders`, and are read with `?chats=1` or `refs`/`chats`/`chatCollections`.

Load (`bootstrap.ts:loadData`):

1. `readKinds` for every kind with chat summaries in one request (one committed state plus the epoch).
2. `seedResources` records each record's revision and JSON text before anything changes the data; `seedChats` records each chat's and chat order's revision; `seedInlays` fills the inlay cache.
3. `loadSelection` reads this tab's selection first. The records are installed (`installBootRecords`; there is no whole-database object): every field of each section, each collection (a selectable one as `{ items, selectedId }`; `llmSecrets` as `mirrorFields` of its masked record, which `setMaskedSecrets` adopts), `presets`, `modules` and `plugins` (`[]` when the server has none yet), `pluginStorage` when present, and the characters in store order (creation order), without chats. A missing section, collection, or `presets` record is an error: the server creates them. Nothing is normalized on the client: the server normalizes and materializes every record. `assembleChats` holds each character's chats in the chat module, in its chat order (`orderChats`: a chat missing from the order is appended, an order entry without a chat is skipped, both logged), replacing whatever the module held.
4. `initializeRecords` replaces the record set (characters without a valid or unique `chaId` get a new one before any wrapper exists), then `reconcileSelection()` resolves the selection and `changeLanguage` sets the interface language; `maintainCharacters` (the trash pruning through `removeCharacters`, then `checkCharOrder`) runs; the characters arrive normalized by the server and get no client default at boot. `initializeChats` selects each character's remembered chat (`localStorage` preference) and gives a character without chats a new one.
5. `startResourceSync()` starts the adapter, which marks every collection and character once so the boot's own writes are saved (the `modules`/`plugins` defaults on a fresh server, the maintenance; unchanged records compare equal and are not sent).
6. `importBrowserLocalData`, `loadPluginPermissions`, then `loadPlugins`, then the UI flags.

Save (the adapter, `resourceSync.svelte.ts`):

1. The settings records (`records.svelte.ts`: the sections, the settings collections, `presets`, `modules`, `plugins`, `pluginStorage`) mark themselves: every local write of one, through a view or a wrapper, marks its record at once (their watchers are gone). For `llmSecrets` the record's text is its readable siblings; the credentials are queued, below. The characters are write-through records too: a write of a character's own fields at any depth, selected or not, through the character list's wrappers or the character module, marks that character (`setCharacterWriteListener`); its `chats`, `chatPage`, and `reloadKeys` are outside the record (raw, the chat module's). A membership change (only through `characterStore`) wakes the loop. Chat writes reach the loop through the chat module's work listener. There is no character watcher and no mark helper.
2. After a 500 ms debounce one cycle runs (never two at once). Each dirty record is serialized (a settings record from its live record with `JSON.stringify`, a section's fields in `SECTION_FIELDS` order, so an own `__proto__` key of a user-keyed map survives and the text equals the server's normalized text; a character from an ordinary copy of its own fields, without `chats`, `chatPage`, and `reloadKeys`, each field's value serialized on its own and joined (`characterProjection`), `modules` item field by item field (`moduleProjection`; `itemProjection` also supplies the uncached parts for other dirty id lists and parsed persisted text; other object records use uncached `objectProjection`)) and skipped when the text equals what the server holds. A character field whose value (identity) and stamp (`characterFieldStamp` in `records.svelte.ts`) equal those of that character's last projection reuses its text from it (`characterTexts`, the last 8 characters, at most 64 Mi UTF-16 units), so a save after a small edit serializes only the fields written since: a stamp changes at every write through a wrapper under the field and every raw change of it (`patchRawCharacter`), and all of a character's stamps when its data is fresh (installed, replaced from the server, created). The wrappers copy every plain JSON value written into a character (`adoptCharacterValue`), so neither the caller's object nor another field shares it; a mutator adopts its inserted values once, preserving those exact values only during write-back into that array, and commits any cache taint only after preparation succeeds. Symbol writes use the same adoption rules; a local `reloadKeys` input containing record state at any depth is detached before storage. A character that comes to share its own state between two fields, or to hold data that is not plain JSON (an accessor, a `toJSON` hook, a function, a class instance, a null-prototype object, a cycle), has null stamps and is serialized whole every cycle until its data is fresh again. The raw paths (`initializeRecords`, `applyRawCharacter`, `patchRawCharacter`) take detached JSON data, and no other module writes through `characterData()`. A `toJSON` hook on the character itself or a field value uses whole-record serialization with no cached parts. Modules likewise reuse each element field’s text while its value identity and `moduleItemFieldStamp` match (`moduleTexts`: one last projection text, with field spans in a WeakMap keyed by the element’s `$state` identity, not its potentially repeated id). Every wrapper write under a module field stamps that field; root list moves preserve element identity and its cached fields. Plain JSON written under modules, including whole-list replacements, is copied (`adoptModuleValue`). Own state reused under the same element field, or a whole element moved to another root list slot, stays cacheable; sharing state across element fields or elements, or introducing non-JSON data or symbol keys, makes all module stamps null until `applyRaw` installs fresh detached JSON (also on initialization/reset). Such records serialize whole without caching. Every live module projection uses this cache, including live-update admission, hydration, and quarantine checks; unique ids are required only for item-patch parts, never for caching. In development a cache text that differs from a whole serialization is reported (`console.error`), not repaired. Before a character is sent, `canonicalCharacter` runs `normalizeCharacter` on its field texts (`canonicalShape`: the fields it reads by value, `CHARACTER_SHAPE_FIELDS` in `shared/characters.ts`, parsed; the rest only as present or `null`) rather than a parse of the whole text; without parts it uses the whole parse. The `chaId` list is diffed against the saved characters: new ids are created, vanished ids deleted (the ids are unique by construction). A character removed and added again under the same id before a cycle ran is still a persisted, present record, so it is a field update; its chats are the chat module's reconciliation queued at `installCharacterChats` (above), never a delete-then-create of the record (the server refuses two ops of one id in a batch, and a batch that deletes a character while changing its chats).
3. Everything goes in one `POST /api/resources/batch` with the chat module's unsent work (`takeChatWork`: per chat one group of ops on the chat revision it was based on, plus reorders; one transaction on the server; split above 5,000 operations or the 100 MiB body limit measured in UTF-8 bytes, or to isolate an unindexed permanent refusal; a chat's group never split inside a request; a chat with more than 5,000 unsent ops sends them over several cycles; a single record over the limit is quarantined by its content with a 413 reason before taking dependent chat work). A chat created with its character travels with the character when the batch fits, or after its character when split. A held mirrored record with parts (an update) is sent as a record patch (audit slices A1/3g, `updateOperation`): object records (characters, sections, `pluginStorage`, `statics`, and `{ items, selectedId }` collections) use top-level field parts and `{ set, remove }`; arrays accepted by `itemIds` (plain-object items with unique non-empty string ids, including `modules`, `presets`, `modelPresets`, `modelProfiles`, `personas`, and `credentials`) use `{ items, changes, order? }` (new items whole, changed items as field patches, the id order when it changed). Their parts are diffed by text against the saved text's parts (`baseParts`, parsed once and cached on its entry, or kept from the acknowledged parts). Characters and modules retain their field-text caches; other dirty records compute parts without a cache. `llmSecrets` never gets parts: the server refuses its patch ops, even for readable siblings. A create, a record without parts (including lists without unique ids such as ordinary `plugins`, `loreBook`, and `globalscript`), or a patch no smaller than the whole record in UTF-8 bytes goes whole. A changed top-level `__proto__` sends an object record whole; on an item it sends that item whole. A `toJSON` hook that prevents parts also keeps the whole write. When the texts differ only in key order, no field reading as changed, the local text becomes the saved text at the same revision and nothing is sent. A nested integer key a parse orders differently only makes that field read as changed. On success the sent whole text becomes the saved text (with its parts) and `ackChatWork` records the chat revisions; a key marked again during the request stays dirty. An acknowledged chat order that lists chats this client does not know (another tab created one) keeps the older order revision and puts the character in `listRefresh`: the next cycle's `hydrateCharacters` stage reads its summary list and applies it as a live update (`applyRemoteCollection` with `keepPendingOrder`, data-loss plan slice 4b), during a generation too; a reorder queued meanwhile is held back from the batch until then (`takeChatWork`'s `holdOrders`), keeps this client's order with the new chats after it, and is sent on the new order revision unless a chat this client keeps and holds a revision for is missing from the server's list: then the reorder is discarded with the notice and reported as `chats/<chaId>`. A `stale: true` chat result keeps its old base and marks it for an idle re-base: the cycle reads it back without overlapping a batch and checks again after the read that no work, lock, deferral, or quarantine intervened. An idle chat accepts the server copy and revision without a discard or reload notice; a busy chat keeps the mark for a later cycle.
4. A network error, 5xx, or 429 retries with backoff (up to 30 s); a chat create whose answer was lost is resent and recognized when the server already holds it. A 400 that names one chat group (`chats[i]...`) quarantines that chat (one alert; its later edits are not sent) and resends the rest (a chat group over the body limit is quarantined client-side before any request); a 400 naming `ops[i]` quarantines that resource key (`kind` + NUL + `id`) at its refused projection text and alerts once per key per session. The client-side 413 pre-check does the same. Unchanged refused content is skipped; editing that record releases it for another attempt. Other records and chats continue saving. An unindexed 400/413 isolates the next cycle into separate requests for each resource, chat group, and reorder, preserving character-before-chat ordering. An isolated refused resource waits for a content change and alerts once per change; a refused chat is quarantined, and a refused order waits for its ordered ids to change. Quarantined character creates stay out of `creating`, so their chats wait and membership is not acknowledged early. Quarantine does not keep an idle save cycle scheduled, and `flushResources` rejects immediately with a quarantined record's refusal reason.
5. A 409 first tries `rebuildConflictRecord`: a waiting `remoteRecords` patch whose base exactly equals the held `persisted` revision and whose notice revision equals the conflict revision reconstructs a detached server record from the held text (same epoch/incarnation, exactly one write later); otherwise an exact-revision whole `deferredHydrations` entry supplies it. A malformed or inapplicable patch, a different revision, or a notice that has not arrived yet falls back to `readRefs` as before (feed and HTTP replies use separate connections). Rebuilt and read records share exactly the same retry comparison, merge, `acceptRemote`, and new-character chat hydration below. The recovery writes the server records into the mirror in place (a section's fields replaced in place, a collection replaced, a character replaced, inserted, or removed; the selected character removed → home screen). The local edits of those records are discarded and `resourceReloaded` is shown as the reload notice (`alertReloadNotice`, `global-api.md`: its own store, kept until the user dismisses it, so a discard while it is shown adds nothing and one after the dismissal shows it again; no other alert replaces it). When the server already holds what was sent (a retry after a lost response; compared as JSON values, since a patch's result keeps the server's key order), nothing is reloaded. A character or the `statics` record is merged instead (`mergeConcurrentChange`) when every top-level field the server changed against the saved base is one this client can take without losing anything (`benignChanges`): a field the server holds as this client does, a field neither the base nor this client has (another tab filled it in, such as a default its character screen binds; the server's value is taken), a character's `lastInteraction` (the later of two finite stamps), or a `statics` count (`imports`, `messages`, best effort: the server's count plus this client's increments since the base; two tabs raising a count to the same value, or a count a lost answer already holds, can be off by those increments). The changes go into the mirror, the base moves to the server's revision, and the key stays dirty, so the next cycle writes the merged record with no discard and no reload notice; a field taken from the server other than the stamp is announced to `onRemoteRecordApplied` listeners. Any other remote change, even of a field this client did not touch, conflicts as above, so a group's parallel member arrays are never combined from two sources. So another tab opening a character or counting a send no longer discards this tab's edit. Not for a create, a delete, or a taken field the mirror object only inherits (`toString`, `constructor`, ...: `assignsInherited` in `shared/mutationValidation.ts`; a Svelte proxy would not store it, so the record conflicts as above). The `pluginStorage` record, which every plugin shares, is merged key by key instead (`mergePluginStorage`, data-loss plan slice 5a): a key the server changed against the saved base is taken when this client left it as saved, and kept as this client has it when the server holds the base or this client's value; inside the reserved dictionaries `_pluginStorage` and `_safeLocalPluginStorage` this goes one level down (a saved base that is a list is read as its entries, as the plugin storage module reads it; a list on the server's or this client's side is a value, not a dictionary), while every other top-level key (a `setDatabase` custom key) is compared whole. A key both changed to different values, or a reserved name either side holds as something other than a dictionary, conflicts as above. The merged record is a fresh object of own keys (an inherited name such as `__proto__` stays a key) applied raw, the base moves to the server's revision and the key stays dirty, as above; a record both tabs created (it is created on a plugin's first write) merges against an empty base. When a `pluginStorage` conflict does discard (`acceptRemote`), the `onPluginStorageDiscarded` listeners hear, after the record is settled, the reserved dictionaries' keys whose unsaved value the server copy replaced and whether any other value was replaced too (a custom key, or a reserved name's own shape: created, removed, or replaced; `PluginStorageDiscard`; the v3 `onStorageDiscarded` event, `plugins-mcp.md`). An item list whose items are records of their own, addressed by id (`ITEM_LIST_MERGE_KINDS`: `modules`, `presets`, `personas`, `credentials`, `modelPresets`, `modelProfiles`; not `characterOrder`, `loreBook`, `plugins`, `hotkeys`, or `authRefreshes`, whose items are addressed otherwise), rebases the items this client added (`mergeItemAdds`, data-loss plan slice 5b): the merge is the server's list, its items and order, with every item whose id neither the saved base nor the server's list has appended in this client's order. Every other change of this client must be one the server already holds, or the record conflicts as above: each saved item as saved or as the server has it (a server-only edit or removal is taken; this client's edit, removal, or reorder of a saved item conflicts, even when the server changed only other items), and an item both added under one id equal on both sides. All three lists need unique item ids (`itemIds`). The merge goes into the mirror (`applyToMirror`, which resolves the selections), the base moves to the server's revision and the key stays dirty, so the next cycle sends the added items (an item patch when smaller); a list both tabs created merges against an empty base. So a module imported while another tab renames a different module keeps both changes. A chat conflict (`recoverChatConflicts`) reads the chat back: non-conflicting groups are requeued, recognized create/delete replays are settled, and other conflicting chats discard their queued edits with the notice, a chat gone on the server included (also while its character's list read waits for a generation in a sibling chat). A reorder that conflicted is settled with the notice, without a discard report (its answer may have been lost), and the character's list is read again (`hydrate`); that read (`hydrateCharacters`, through `acceptRemoteCollection`) reports what it discards in turn: a reorder queued since (`chats/<chaId>`) and the work of a chat the list no longer has (`chats/<chaId>/<chatId>`; an idle one is removed without a report). `recoverFromConflict` shows the reload notice once per recovery, after the last read, when anything was discarded; a read that throws after a discard (the conflict read after dropped locked edits, or the `hydrateCharacters` read after `acceptRemote`) still ends in the notice, and the characters left in `hydrate` are read by the next cycle, whose stages show the notice for what they discard (`reloadDeferredChats`, `hydrateCharacters`, `applyRemoteUpdates`). A refused create (including a resend) whose read-back is null is quarantined with an alert and retained in the mirror, including through a deferred reload and subsequent collection refresh; if its character is gone, character recovery handles that deletion. A chat a server job streams into defers its reload until the job's locks are released (`isChatDeferred`); the reload then discards its queued edits, as any conflict does. A stale acknowledgement uses the quiet idle re-base in step 3 instead of a conflict reload. A character a server generation runs on is reloaded at once like any other (there is no tab-side deferral): the job reads its own configuration and refreshes character records from the server at its barriers, and the server's message locks still refuse what touches the generating message. A server copy goes into the character records raw (`applyRawCharacter`, `patchRawCharacter` for a merge), marking nothing. Every reloaded record is announced to `onRemoteRecordApplied` listeners (boot registers the inlay cache invalidation).
6. A 409 entry with `reason: "generating"` (a server generation job owns a message the change touches; also a refused character delete) requeues and blocks the chat's surviving work for `JOB_RETRY_MS` (5 s), a refused character delete stays an unsaved membership change for the same time, one cycle is scheduled at the retry time, and `chatGenerating` is shown once per refusal episode. Blocked work counts as unsaved (unload warning, flush obligations) but not as runnable; `flushResources` rejects at once with the generation error while it is blocked. The chat entry names the locked messages the group's ops target (`messageIds`, absent for a whole-chat `replace`/`delete` refusal that targets none): `recoverChatConflicts` (`dropLockedEdits`) runs before unrelated conflict reads and drops the by-id edits of those messages (`setText`, `setMessage`, `patchMessage`, `setTranslation`, `begin`, a single-id `remove`), in the refused group and in the chat's newer unsent work, since a retry after the job would land over the finished reply. They are discarded (the flush report, the `MutationScope` report, `resourceReloaded`), and the chat is marked stale: it is read whole once its remaining work has landed and this tab's generation locks have released, which puts the server's message back in the mirror (until then the mirror shows the dropped edit). The split itself leaves the held revision unchanged; a later non-stale acknowledgement or whole hydration can advance it before the idle read. Chat-level ops, a multi-id `remove` (it keeps its current-revision requirement and conflicts only if its base is then stale), and ops on other messages stay on the retry-after-job path; the sent group's sequence is settled when none of it is kept, and the chat is blocked only while some of its work remains. The split follows the server's ids, not this tab's locks, so an observer tab and a tab whose follow of its own job ended `lost` (its locks released while the server job continues) are treated alike. Since the change feed carries the locks (step 9), such a tab shows the reply locked once the lock frame arrives; the split is the fallback for an edit sent before that frame, or while a feed lock is released early (below, Known Hazards).
7. `applyHydration({ kind, id, characterId?, revision, data })` applies a record a server job sent without any outgoing write: no discard, no `discardSequence` bump, no settled key, no notice. It applies only a token of the loaded epoch newer by `(seq, revision)` (`compareRevision`) than the held one, and only when the client has no local change of that record (not in the batch in flight, its projection equal to the saved text, not blocked); a dirty mark alone, with the projection unchanged, is no change. A record refused for a local change keeps its newest event, checked again after the next save cycle. A record the client does not hold, a deletion, `llmSecrets`, and `authRefreshes` are not hydrated; `chats` goes to `hydrateChat`.
8. Credential writes: after the cycle's batch, the `llmSecrets` ops queued when the cycle collected its work (a later one waits for the next cycle, after its resource) are sent one at a time through `/api/llm-secrets/*` (`resourceClient.ts` `sendSecretRequest`) on the record's held revision. A cleanup is sent only once its owner is gone from the mirror and from the saved copy; it is dropped while the mirror holds the owner (a conflict restored it) and waits, without keeping the loop scheduled, while only the saved copy does. A reply's revision and masked record are adopted, and its siblings judged by text against the saved text: mirror siblings equal to it take the server's; a local edit over unchanged server siblings is kept and written on that revision; a local edit where the server's siblings changed too is the normal conflict (the server's copy wins, the discard is recorded, the reload notice shown). A 409 rereads the record and retries, at most twice per op per cycle; a 400 or 404 drops the op, reports it as a discard (`llmSecrets/<path>`), and alerts; any other failure keeps the queue for the next cycle with the save backoff (a 412 halts as below). The queue counts as pending and unsaved work, and `flushResources` waits for the ops queued at its call. `awaitSecretWrites()` waits for the ops queued now and throws when one was refused, when only cleanups behind an unsaved deletion are left, or when saving is halted (also with an empty queue; `assertSaveAdmission`); `auxFetch` calls it first. A page unload does not send queued credential ops (the unload warning shows them as unsaved).
9. Live updates (`noteRemoteChanges` from `eventFeed.ts`): another writer's committed refs. Each resource ref is compared with the held revision on arrival and dropped unless newer (this client's own save, or a job event that applied it first); a ref with a record patch (`RecordFieldPatch` for an object record; `RecordItemPatch` for an array with unique item ids, as in step 3) is applied at once without a read when `applyRemotePatch` can (the record held at exactly the patch's base: same epoch and incarnation, one write before; no local change as `canApplyRemote` judges): a character's fields go in raw (`patchRawCharacter`; no fixed, client-only, or inherited field), every other eligible mirrored kind except `llmSecrets` applies its field or item patch to a parse of the held text (`patchedRecord`, `checkFields`/`withFields` or `checkItemPatch`/`applyItemPatch`, `shared/recordPatch.ts`) and the detached result replaces the record through `applyToMirror` → `applySettingsRecord`/`applyRaw` as a read would, including selection reconciliation; the saved text becomes the mirror's projection, the remote-change listeners hear of it unless only a character's `lastInteraction` changed; otherwise the patch waits with its entry and the cycle tries it again before reading, and anything it cannot take is read whole as below (a tab with an unsaved change of the character gets the stamp through its save's 409 and `mergeConcurrentChange`); `inlays` and `pluginPermissions` go to their owners; a newer record of a mirrored kind (a section, a collection including `authRefreshes` and `pluginStorage`, `presets`, `modules`, `plugins`, a character, including one this client does not hold; a mirrored singleton (id `main`) this client has no local record of at all, which is `pluginStorage` absent at boot until a plugin writes it) waits in a set, with the newest revision announced. A singleton this client wrote locally but has not saved is not adopted: the notice waits and its create's 409 decides, as for any concurrent create. A chat ref and its optional by-id patch (`ChatPatchBody`) go to `noteRemoteChat`: `applyRemoteChatPatch` applies it without a read or notice only when the chat is loaded, idle (`canRefreshChat`), not stale, and held at exactly `baseRevision` (chat revisions advance by the applied op count, not necessarily one). It reuses `patchedTail` and `installChatPatch` to apply rows, metadata, and revision, queuing nothing and never calling `settleJobHydration`; a miss does not mark stale and follows the ordinary notice/idle refresh of step 3, so a chat with local work, a generation, a deferral, a quarantine, or a retry block is read later; a chat-order ref newer than the held one, or a new chat, queues the character's chat list. The cycle (50 ms later) reads them in one `readRefs`, before its batch, never alongside one: a waiting entry at or below the held revision is dropped without a read; one whose record has a local change (in the batch in flight, its projection different from the saved text, quarantined, or a character delete the server refused for a generating message and waiting for its retry; a character is not held back because it is generating) is not read and waits (its save lands, making the update older, or conflicts through step 5). After the read it checks again (after `tick()`), then applies through `applyToMirror` with the saved text set to the mirror's projection: no discard, no `discardSequence` bump, no settled key, no notice; `reconcileSelection()` after a collection or `presets` replacement; a new character inserted with its chat list (`applyRemoteCollection`; a chat or order ref that arrives for it before its insertion reads its list again afterwards); a deleted character removed (the selected one → home) only when the held revision is unchanged since the read was issued, else read again; its chats' unsent work (and a queued reorder) is discarded with the reload notice and reported (`forgetCharacter` with `discard`; a queued delete the deletion fulfils is settled, as is all the work for this tab's own deletion). A read settles only the notice it was issued for, or a later one its answer covers (a record's entry by identity, a chat list by its notice sequence); a deletion notice for a character this client never inserted drops its entry, and a read finding it gone settles the create notice. A chat an idle read finds gone is removed only when its held revision is unchanged since the read was issued, never by creating a replacement chat (the character's only chat stays until the writer's new chat arrives); a chat list removes an idle local chat only under the same fence, keeps a chat this client deleted but has not saved out, and drops a chat's notice only when the adopted copy covers it. `llmSecrets` is adopted as in step 8 with every credential path invalidated, but where a local sibling edit meets a changed server sibling nothing is applied and the entry waits for the local text to change (the save's 409 decides). At most 1,000 records and 1,000 chat lists (new characters' first) per cycle, and 1,000 chats per idle refresh read; the rest wait. A mutation also checks right before it goes out, after authentication and signing (`setMutationAdmission`), that saving has not halted. A cycle stops after each awaited stage and before each batch once saving halted for a restore (captured chat work is requeued). A `change` frame's generation locks (`streaming`, `ChatStreaming[]`: per chat, every message a generation job owns, after a job's write or end; slice 2b of `docs/plan/data-loss-concurrency.md`) go from `eventFeed.ts` to `noteRemoteStreaming` after its refs are dispatched, so a fitting `begin` patch puts the row in the mirror before its lock. For a chat the mirror lacks, an unloaded chat, or a patch that does not fit, the lock is installed by id and the row arrives locked with the read. Each listed chat's list replaces its feed locks (`feedLocks`, by message key: the generation and the chat revision of that frame's ref, null without one): a listed message is locked whether or not the mirror holds it yet (a chat or row read later arrives locked), one no longer listed or listed with another generation is released. A feed lock is a lock only: `isMessageLocked`, `assertUnlocked`, `isChatGenerating`, `lockedChatKeys` (and through it the sidebar status and the memory and lore-draft fences), and trimming count it; it holds no stream text, sets no watermark, retires nothing, and never holds the save loop: `canRefreshChat` (feed patches and idle reads), the conflict deferral, `acceptRemoteCollection`'s keep-and-defer and the deferred reloads use `isChatStreamedHere` (this tab's job locks only), so the observer keeps taking checkpoint patches while the reply is locked. It is released by the chat's list without it, by an adopted whole read (`applyRemoteChat`, an unloaded member's `installRead`) at a newer revision than the frame that announced it (or one with none), by the chat found gone (`removeRemoteChat`), by `forgetCharacter`, and by every `hello` (`releaseFeedLocks`: a release may have been sent while disconnected); none of these retires, so the job's next write locks it again while it runs. `reconcileRemote(listing)` runs after every `hello`: every listed record, chat, and order goes through the same comparison, every held record or chat the server no longer lists is a deletion, and each owner outside the mirror reconciles its own kind (`reconcileInlays` drops cached metadata older than listed or no longer listed). The translator and HypaV3 `selectedId` values are shared records, so choosing one in a tab switches it in the others (the preset and persona selections stay per tab).
10. A 412 (the server was restored) stops saving, shows `resourceRestored` as the terminal notice (`alertTerminal`, `global-api.md`: no other alert can replace it), and reloads the page once the user acknowledges it. A transform request the restore refused shows no failure toast (`transformClient.ts`). The transport runs the same halt for a 412 on any other resource request (inlays, permissions, a backup import) and for a read after boot that answers with another epoch. A server job that a restore or import ended (`maintenance`) makes its tab watch for the replacement (`watchForRestore`, below in Known Hazards), so a send's owner is told without another action; the job's error shows only when nothing was replaced.

`flushResources()` saves everything changed before the call (including queued chat work), and resolves when it is on the server, with the keys a conflict discarded (`chats/<chaId>/<chatId>` for chats, `chats/<chaId>` for a reorder); backup export and the browser-local import call it.

Chats (`chatStore.svelte.ts`):

- Every chat write goes through the module: it updates the mirror, bumps the chat's local version, and queues an op; ops of one chat coalesce (text writes, meta patches, end appends) until the save loop takes them. A chat that is not loaded takes only list-field changes (`setChatMeta` of `name`, `folderId`, `bindedPersona`, `promptPresetId`, `modelPresetId`, `bindingReview`, `pinned`, `fmIndex`: its summary changes and the same `meta` op is queued); every other write needs it loaded. The client character types have no `chats` or `chatPage` (the facade's read-only view refuses a write at run time), and the readers' chats are typed read-only (`DeepReadonly`), so a direct assignment, `push`, or `splice` fails `pnpm check`; `bind:` on a chat field does not, so components bind through getter/setter pairs or a synced editing copy (HypaV3 modal, local lore draft).
- A `meta` op's `merge` adds entries to a chat field that is a map (`CHAT_META_MERGE_KEYS`: `toolCalls`, `GLGlobalVariables`, `scriptstate`) on the server's stored value, so two writers adding different entries keep each other's (`mergeChatMeta`); its `mergeUnset` removes entry ids from such a field as stored before the entries are added (removals alone leave a field that is not a map as it is), so one variable can be removed without replacing the map. On the tab `mergeChatMeta(ref, key, entries, removals)` queues it (a removal is sent also when the mirror lacks the entry); the tab's single-variable writers queue one `scriptstate` entry merged this way (`setChatVar`/`setChatVarOf`, so the lore decorators, plugin `runVar` parses and graph memory; `/setvar`, `/addvar`; the DevTool variable editor), and `applyChatResult` merges the entries a hook changed; an explicit whole-field set or unset keeps its replace semantics, and `coalesce` may fold a merge into an earlier set of the field. Entries a write does not name keep another writer's values; a named entry is last writer wins. The client's `coalesce` folds no op carrying `mergeUnset`, nor entries into a field an earlier op sets to a value that is not a map. `chat.toolCalls` entries are validated wherever a chat is written (`{ call: { id, name, arg }, response }` under their own id, each response piece a tool content the request adapters read, at most 1 MiB each); the map has no eviction, and every merge normalizes and stores the whole map again.
- Ops address messages by `Message.chatId`, never by index. By-id ops (`append`, `setMessage`, `patchMessage`, `setText`, `setTranslation`, single `remove`, `meta`) apply to a stale chat revision while their message exists. `setMessage` sends the whole row, so on a stale revision it reverts fields another writer changed meanwhile: it needs the current revision for the fields it does not own (not enforced); `patchMessage` (`set`/`unset` of named fields onto the stored row, never the translation) is the op for a change of some fields (the tab's `patchMessage(ref, id, set, unset)`: the Disable and Disable-above toolbar toggles, the playground role swap, `applyChatResult`; every given field is sent even when the mirror already holds it, the input is checked as the server checks it before anything changes, and nothing is queued when no field is left), and `coalesce` folds it with a later patch or `setText` of the message and into an earlier `setMessage`; `replace`, `delete`, bulk `remove`, reorders, and a `begin` of an unknown generation need the current revision. A result applied on an older revision says `stale: true`; `ackChatWork` and `settleUnloadWork` keep the older base and request an idle re-base. The save cycle reads the chat and rechecks eligibility after the await: no pending entry, in-flight group (including an unload request), server job lock, deferral, or quarantine. Only then does it apply the server copy and revision, bumping the mirror version without discarding work or showing a reload notice. Otherwise the refresh mark stays for a later cycle. A send still building its prompt without a lock can be refreshed; its baseline still protects changes made meanwhile.
- Stored translations ([translation](media-aux.md)): `Message.translation` (`MessageTranslation`, `shared/database.ts`) is shown only while its `sourceHash` equals `translationSourceHash(data)` (`shared/translation/hash.ts`, cyrb53; `storedTranslation` in `shared/translation/messageTranslation.ts`), so an edit makes it stale without clearing it. On an existing message only `setMessageTranslation(ref, id, translation | null)` changes it (op `setTranslation`, never coalesced; the input is checked as its JSON copy, and a translation whose hash does not match the message's current text is not taken and returns false); the tab's callers are the stored-translation edits (`saveStoredTranslationEdit`, `edited: true`, with the source hash captured when the editor opened; `media-aux.md`), while the server runner writes the translations it makes; `createChat`, `appendMessage`, and `replaceChat` take in what their messages carry; `replaceMessage` keeps the held translation, as the server's `setMessage` does. Messages the module takes in (`prepareMessages`: create, append, replace, a hook's result, a character's chats) drop a `translation` that is not a `MessageTranslation`, as the server's `normalizeMessage` does, and `canonicalChat` compares without one.
- Selection is per tab: the module keeps the selected chat id per character (reactive; `selectedChatIndex` is its index in the list), falls back to the first chat only when a membership change removes it (a reorder keeps it; a read never writes it), and remembers the last selection in `localStorage` as a preference for the next boot (not synchronized live between tabs). A selection is immediate, loaded or not: selecting a character or a chat starts the selected chat's load, and the chat screen shows a loading state (with the error and a retry after a failed load) until it is loaded; a load never selects anything.
- Chats that are not loaded refresh from the feed through their character's summary list: `noteRemoteChat` records the notice and answers `"collection"`; the save cycle reads summary lists (`chatSummaryCollections`) for the live collection updates, for characters a recovery inserted or refreshed (`hydrate`: the server's list is taken and what it has no room for discarded with the notice), for characters an acknowledgement showed another writer's chats of (`listRefresh`: applied as a live update that keeps a queued reorder, Save step 3), and for idle stale or noticed unloaded chats (`idleSummaryRefreshes`, then `settleSummaryRefresh`); whole-chat reads are for loaded chats only. A server copy never loads a chat: an unloaded member takes the summary and revision (a job's chat event included), and a loaded chat a summary list shows newer keeps its copy and held revision and is marked stale (read whole in the next cycle).
- Whole-chat writers on the tab (plugin setters, `editChat`/`editChatSync` and the reroll paths; triggers and Lua run on the server) capture a baseline and call `applyChatResult`: the changed copy is diffed three ways against the baseline and the chat as it is now, and applied as by-id ops (a changed message as a `patchMessage` of the fields the hook changed, a map field in `CHAT_META_MERGE_KEYS` entry by entry through `mergeChatMeta`, a map the baseline lacked counting as empty), with `replaceChat` only when a diff cannot express it. The message patches are checked before the mirror changes: an invalid one (an unset `data`, a role that is neither `user` nor `char`) refuses the whole result. Changes made meanwhile by others are kept.
- A never-sent chat's create group is the current mirror payload alone (the mirror already holds every queued change).
- Deferral: a conflict on a chat a server job streams into (`isChatGenerating`) is deferred: the chat is excluded from batches and reloaded (`deferredReloads`, `finishDeferredReload`) once the job's locks are released, since replacing it earlier would drop the streamed text. The deferred chat's local work is discarded by that reload, as for any conflict; `reloadDeferredChats` shows the reload notice only when a chat was replaced or removed (the chat module's discard sequence moved), not when every released chat was skipped. A group the server refuses for a generating message is not deferred: its edits of the locked messages the refusal names are dropped first (Save step 6), and only surviving work is blocked until `JOB_RETRY_MS`; an all-dropped group is not blocked.
- Job chunks (`GenerationChunkEvent`) carry `{ type: "chunk", epoch, messageId, generationId, seq, base, keep, text }`: keep the first `keep` UTF-16 units of the raw stream text at `base` and append `text`. `applyServerGenerationChunk` reconstructs from `serverGenerations`, never the displayed message (which may lag a frame or show a processed checkpoint). A missing message, placeholder, generation, or sequence asks for `{ type: "resyncReply" }` once per follow until an `accepted` arrives or the follow ends; the job answers only its current full-text `accepted` while live with a message id, even during a lock handoff. Retired generations drop silently. This recovery never marks stale or requests the whole chat. The runner still emits cumulative text, and the other-direction provider `ChannelChunk` stays cumulative.
- Callback hydration memory: `jobChannel.ts:rememberHydration(jobId, record)` retains the newest copy per record inside that job's `hydrations` map; `barrier(jobId, event)` retries only those copies after flushing local work. `endJobChannel(jobId)` deletes that job's copies on every terminal or lost follow, after its socket-ordered remembers. The `hydrateAll` barrier still sends whole copies; job patches are not remembered.
- Server generation jobs: a job's reply is locked by `applyServerGeneration`, or already by the job's chat hydration that lists it as `streaming` before the job's `accepted` arrives (the reply appended with `begin`: the lock starts with no stream update received, its sequence below every protocol sequence and its buffer the mirror's text, so the first `accepted` records the raw text whatever its claim; a chunk cannot reconstruct from this placeholder and asks for the reply) (no client generation id passes; edit, delete, and regenerate are off) until its chat's hydration no longer lists it as `streaming` or the job's terminal event (`endServerJob`, which marks a chat still holding streamed text for an idle refresh). `hydrateChat` replaces the mirror's chat with the server's when its revision is at least the held one and the chat has no pending, in-flight, deferred, quarantined, or blocked work (otherwise the chat is marked for an idle refresh); whole-chat hydration, `hydrateChatPatch`, and an eligible feed patch move the chat's revision. `hydrateChatPatch` (a job's `chatPatch`, through `applyPatchHydration`) applies only to a loaded chat that is not marked stale, has none of that work, and holds exactly the patch's `baseRevision` or its `revision` (one epoch and incarnation; a patch is a diff of two stored states, so any other held revision may lack a change it does not carry); the whole result is checked first (`patchedMessages`: unique ids, every `after` present, an existing message already right after its `after`, the final count), it reads only the end of the list, back to the first message the patch touches (`patchedTail`), checks that part first (unique ids, every `after` present, an existing message already right after its `after`, the final count), and writes only the positions that changed; rows are owned copies, every other message keeps its object, and a present `meta` replaces the chat's fields. Otherwise it marks the chat stale and wakes the save loop: `busy` for local work, `mismatch` for the rest. On `mismatch` `applyGenerationEvent` sends the follow's one `resync` (cleared by the job chat's next whole `resource` event); on `busy`, or a whole job chat refused for local work, it waits for `flushResources` and then sends it if the chat is still stale and nothing local would refuse the copy (`chatHydrationHold` is `none`); a failed save or new local work tries again with a growing wait (up to 15 s) for as long as the follow lasts, one recovery per follow, a chat held by work no save settles (deferred, quarantined, job-blocked) asks nothing, and nothing is asked through a follow whose job ended or that closed. After the job, the idle refresh reads a stale chat whole (`endServerJob` wakes the loop even when it released no lock), and `runServerJob` saves and then reads a chat it knows is behind (`refreshStaleChat`, true once `isChatBehind` is false: stale or an unanswered notice) before creating a job, trying save and read once more when a change or notice arrived meanwhile; a chat still behind then goes as it is and the server refuses its old revision. A patch is not remembered for the callback barrier. It writes the mirror directly: no `ensureChat`, no discard, no settle, no queued op. The event's `streaming` entries give each still-generating message's generation and the newest chunk `seq` the copy holds (a watermark): streamed text above it is put back, text at or below it is older than the copy (a processed checkpoint stays). Every other lock of that job in the chat is released (the reply is final in the copy), as is another owner of a listed message; another job's locks stay. A copy older than the held revision, or job metadata older than the newest taken for the chat (even from a copy that could not be applied), changes nothing; a copy that could not be applied releases locks but sets no watermark. A replaced or ended generation is retired: its late chunks are dropped. The streaming state follows the lock: a generation's first `accepted`/`chunk` (not the placeholder lock of a chat event) sets `streamingState` to its message with `settings.ui.streamingDisplayOptimizationMode ?? "off"`, and every release of that generation's lock (`endServerJob`, a hydration that no longer lists it, another owner of the message) clears it; a later generation takes it over. A message-id adoption renames it. A chat the mirror lacks, or one this client has not seen on the server, is not hydrated. An idle refresh whose read is older than the held revision is not applied. The mirror takes at most one stream update per frame (`heldStreamText`): a generation's first update, and one when no frame flush is pending, are written at once; a later one stays in the stream buffer and the frame flush writes the newest (by the same lock, retirement, and watermark rules); `hydrateChat` first flushes the held updates of its chat and `endServerJob` those of its job (others stay held), so the events after them still apply in order. A frame is asked for with a timer beside it, so a hidden tab still shows the text.
- Unload: while any unsaved work exists, the save loop prepares and refreshes a signed unload token. `visibilitychange` to hidden immediately runs a normal save cycle, bypassing debounce/backoff with no keepalive size cap; if a cycle is already running, it finishes before a follow-up saves pending work. `beforeunload` requests the browser warning (never once saving halted for a restore or an import: nothing more can be saved, and the notice's reload must go through) for dirty records, a cycle in flight, or unsaved chat work (including unload requests); unchanged quarantined records/chats/orders and chats waiting on a quarantined character create are excluded. On `pagehide`, pending by-id ops (`append`, `setText`, `setMessage`, `patchMessage`, `setTranslation`, single `remove`, `meta`) for already-created chats go out within a shared 60 KiB budget, one request per chat; earlier unsafe operations are never skipped. Every outstanding keepalive body, including from an earlier `pagehide`, counts against the same budget. Chats with a request in flight are skipped. Only a sent group leaves its ordinary queue, counts as in flight, and settles through `settleUnloadWork` as an ordinary acknowledgement; a failed group is requeued ahead of newer edits. Resource records, chat creates, deletes, replacements, and reorders use normal cycles only. Keepalive is best effort.

Browser-local import (`importBrowserLocalData`, every boot, before plugins load):

- LocalForage `inlay` (inlays, incl. old data-URI values), `plugin` (`safe_plugin_*` → `pluginCustomStorage._safeLocalPluginStorage`), `plugin_permissions` (→ the `pluginPermissions` record), `iris_dialogues`/`current_dialogue` (→ `irisDialogue`, in the `ui` record), and `google-search-credentials`/`credentials`/`google-search-creds` (→ `googleSearchCredentials`, in the `secrets` record).
- Per entry: when the server already holds it, the server copy wins; otherwise it is written, read back from the server, and only then deleted locally. A local entry is deleted only while it still holds the value that was imported (`sameLocalValue`; another tab may have changed it). An inlay whose server metadata exists without its media file (a partially restored archive) is repaired from the local bytes when they are the file the metadata names, and kept in the browser otherwise. A value that is not plain JSON (plugin storage) stays in the browser. A failed step leaves its entries for the next boot. The `risuSaveCache` database and the `risuauth` `localStorage` key are removed, and deleting the IndexedDB `firefox-translations-models` (the models of the removed Bergamot translator) is attempted without waiting (another open tab can block it; a later boot tries again).

Access:

- UI reads and mutates the settings through the record views (`settingsViews.svelte.ts`) and the characters through the character module (`selectedCharacter()`, `characterList()`, the record wrappers they return), reactively, except chats: they are read from the mirror and changed through `chatStore.svelte.ts` (or `chatEdits.ts`).
- Code that serializes, exports, syncs, or hands data to plugins takes a snapshot builder (`snapshots.svelte.ts`), `$state.snapshot`, or `safeStructuredClone`.

Backend:

- Always the self-host server, now only for assets (`assetClient.ts`). The block save format (`risuSave.ts`, `database/database.bin`, `dbbackup-*.bin`, remote `remotes/*` payloads, the `risuSaveCache`) and remote saving were removed in Phase 1 without a migration; the `save/database` and `save/remotes` folders of older versions are left on disk and no longer read.
- Device caches and device state: the browser-local stores that remain. They are rebuildable caches of browser-side features or this device's own state, not user data; nothing cleans them up, and a backup does not carry them.
  - `hypaVector` (LocalForage): embeddings of the browser's `HypaProcesser`, keyed by text and model. Users: the file attachments (`process/files/multisend.ts`), the graph memory (`process/mcp/graphmem.ts`), the embedding playground (`PlaygroundEmbedding.svelte`), and the HypaV3 modal's `HypaProcesserEx` (`process/memory/hypav3.ts`). The server's memory has its own vector store (`save/data/vectors.sqlite`, `self-host-server.md`).
  - `tfCache` (Cache API): Transformers.js model files for the browser-side models: `runTransformers`, `runEmbedding`, `runVITS` (`tts.ts`), and the character editor's ONNX model registration (`CharConfig.svelte`).
  - `LLMTranslateCache` (LocalForage): translated text keyed by `llm:<hash>:<source>`, the hash of the translator pipeline signature, the languages, and the translator note (`media-aux.md`); entries keyed by the bare source (before the pipeline) are no longer read and are not migrated. The translator, the chat's translation, the translation playground, and the language settings' export, import, and clear.
  - `localStorage`: `nightlyWarned` (the nightly-build warning acknowledged), `risu-selection` (this device's last preset, persona, and lorebook page, the start of a new tab; `sessionStorage` holds the tab's own), `risu-selected-chats` (the last selected chat per character), and the plugin `SafeLocalStorage` (`safe_plugin_*`, documented to plugins as device-specific).
  - `sessionStorage`: `risu-generation-client` and `risu-generation-jobs` (this tab's client id and its running server jobs, so a reloaded tab attaches to them again: `resumeSavedGenerations` in `network/generationJobs.ts`).
  - `DPoPDB` (IndexedDB): this browser's non-extractable auth key pair (`serverAuth.ts`).

Cold storage (removed):

- Cold storage was removed without a migration. Data it had offloaded (browser OPFS `coldstorage_<uuid>.json`, Node `coldstorage/<uuid>`) is no longer read, and those files are left on disk.
- Old saves may still hold skeleton characters with a stale `coldstorage` field and chats whose only message is a `COLDSTORAGE<uuid>` pointer. They load as ordinary characters and chats.
- Deleting the selected preset or persona selects the first remaining one; deleting another keeps the selection, and a reorder keeps the selected id (`botpreset.svelte` for both preset kinds, `removeModelPreset`, `PersonaSettings.svelte`). A deletion moves only the tab's selection, never a chat's binding: chats bound to the record show it as deleted and are not sent until another one is picked; the confirmation names how many (`chatsBoundTo`).

## Coupling

- The chain is the records and the chat module → `resourceSync.svelte.ts` → `resourceClient.ts` → `authFetch` (`serverAuth.ts`) → `/api/resources`. Assets go `globalApi` (`readImage`, `saveAsset`, `loadAsset`, `getFileSrc`) or `inlays.ts` → `assetClient.ts` → `/api/read|write`; its batch calls go to `/api/assets/write|read`. Bulk import writes go `saveAssets` (`storage/assetQueue.ts`) → `saveAssetBatch` (`globalApi.svelte.ts`) → `writeAssets` (`assetClient.ts`) → `/api/assets/write`. Card and module export reads go `loadAssetsInBatches` (`storage/assetQueue.ts`) → `loadAssets` (`globalApi.svelte.ts`) → `readAssets` (`assetClient.ts`) → `/api/assets/read`. A `.risum` import goes `importModuleFile` (`process/modules.ts`) → `moduleImportClient.ts` → `serverImportClient.ts` → `authFetch` → `/api/import/module`; a CharX import given as a `File`/`Blob` goes `importCharacterProcess` (`characterCards.ts`) → `charxImportClient.ts` → `serverImportClient.ts` → `authFetch` → `/api/import/charx`.
- Callers:
  - `bootstrap.ts`: load, maintain, start saving, browser-local import.
  - `drive/backuplocal.ts` and `globalApi.loadInternalBackup`: backups (`flushResources`, the backup routes).
  - `characterCards.ts`: snapshots.
  - The contracts, through the mutation modules: `plugins/apiV3/v3.svelte.ts`, `process/mcp/*`, and the import functions (the browser Lua and trigger runtimes that also wrote through them were removed at the Phase 5 cutover).
  - `plugins/apiV3/permissionStore.ts`, `process/files/inlays.ts`: their own resources through `resourceClient.ts`; a live update reaches them through `setRemoteResourceOwner` (`refreshPluginPermissions` reads again in the grant queue and keeps a newer copy it holds; `noteRemoteInlay` drops the cached metadata; a metadata read or listing that began before an invalidation, or before this tab's own write or delete of that inlay, does not fill the cache, nor replace a newer cached revision, and an on-demand read reads again up to twice, then returns its answer uncached).
  - `network/eventFeed.ts`: live updates into `noteRemoteChanges` and `reconcileRemote`.

## Invariants

- The boot installs the records as the server sent them (`installBootRecords`); there is no client normalization or legacy-field cleanup (the removed `account`, `coldstorage`, and `enableRemoteSaving` fields are no record field, and a leftover `pluginCustomStorage._coldplugin` key is kept as data). Initialize nested parents before assigning children (`??=`).
- Every `Database` field belongs to exactly one resource (`shared/sections.ts`: a section, a collection, or a Phase 1 collection), is forwarded (`FORWARDED_ROOT_KEYS`: served from the selected preset or persona, or from this client's selection), or is dropped (`DROPPED_FIELDS`). The boot installation, the records, the settings views, the projections, and `applyToMirror` iterate those lists, so a new field needs only its place in `shared/sections.ts` (and its `SectionSpec` entry on the server). A new Phase 1-style collection also needs a server kind (`server/src/data/kinds.ts`) and the branches in `bootstrap.ts` and `resourceSync.svelte.ts`.
- A section or settings collection's projection must equal the server's normalized text for an unchanged record (`normalize(project(assemble(normalized))) === normalized`); otherwise every boot writes it. So the client applies no default to those fields, and boot code must not rewrite them.
- Chats are their own records: two tabs editing different chats, or different messages of one chat, save independently. A chat change never rewrites its character.
- Only `chatStore.svelte.ts` writes the chats; writing, defining, or deleting `chats`/`chatPage` on a character wrapper throws (the facade view is read-only). Code that holds a changed copy of a chat applies it with `applyChatResult` (or `chatEdits.ts`); code that changes a chat field calls `setChatMeta`, an entry of a map field `mergeChatMeta`, and some fields of a message `patchMessage` (`replaceMessage` sends a whole row, which on an older revision reverts the fields another writer changed).
- A message being generated is changed only by its generation. Other writers get an error from the module (`Chat.svelte` disables that message's edit, partial edit, delete, disable, and regenerate controls from `isMessageLocked` and checks every affected id again when the write is made (a delete-from-here that reaches a locked reply alerts), which also covers a finished reply whose final write is not yet acknowledged and a previous group speaker's reply; reroll and chat deletion check `isChatGenerating` and alert `chatGenerating`).
- Character defaults live in one pure helper, `normalizeCharacter` (`shared/characters.ts`): the server's `characters` normalizer applies it on every write and in its startup pass; the client applies it when a character enters (`prepareNewCharacter`, also the creation steps: `creation_date`, the lorebook conversion, a first chat, each chat's `fmIndex`/`localLore`, the `postHistoryInstructions` transfer, `ttsMode` `"none"`), to a whole replacement (`replaceCharacterFields`), and before a save: a character about to be written whose projection lacks a default gets it raw first (`canonicalCharacterText`, no mark), so the text sent and held is the server's normalized text. No default is applied at boot or on selection, and selecting a character stamps no `lastInteraction` (a send does).
- Every write of a character's own fields is saved, whichever character is selected (the character records). The list's membership changes only through `characterStore` (`addCharacter`, `replaceCharacterAt`, `removeCharacter`, `removeCharacters`): a `push`, `splice`, or index assignment through the character list's wrapper (`characterList()`) throws, and a character's `chaId` never changes.
- Mutation rule per collection: the external contracts (plugins, MCP, imports) write every record through a mutation module (`characterStore.svelte.ts`, `collectionStore.svelte.ts`, `pluginStorageStore.svelte.ts`, the chat module). The settings records transport their own writes (`records.svelte.ts`): a write through a view or a wrapper, from the UI or a `bind:` on a view, is saved without any watcher, and a bulk writer runs in one `batchRecordWrites` scope. The character records transport their own writes the same way.
- Server data never becomes an outgoing write: the saved text is recorded from the server's own response, and a mirror reload records the text of the hydrated mirror (its own key order), so a root another tab wrote with its keys in another order is not echoed back. A server copy goes into a settings record through `applyRaw`, which marks nothing; after `presets` or `personas` the selection is resolved again.
- Every mutation carries the loaded epoch; after a restore every write is refused until the page reloads. `pluginStorage` is serialized straight from the proxy (not through `$state.snapshot`, which drops an own `__proto__` key) because plugins choose its keys.
- Keep the logical asset key conventions (`assets/<name>`). They are on-disk names.
- A preset field must be added to `botPreset` and `PRESET_DEFAULTS` (`shared/presets.ts`, which `normalizePreset` and the partition in `shared/sections.ts` follow; a field without a default, or with a `null` one, also needs its kind in `kindsWithoutDefault`, or `shared/presets.ts` throws on load). The settings views then serve it under its flat root name (`readSettingsRoot`), and `activePreset` under its own name (except the list metadata in `PROMPT_PRESET_LOCAL_FIELDS`, which only the record holds); a field whose `null` is a value readers handle also goes in `PRESET_NULLABLE_FIELDS` (`normalizePreset` replaces any other `null` with the default).
- A section field must be added to `SECTION_FIELDS` and to that section's `SectionSpec` in `server/src/data/normalize/` (the type makes a missing entry an error), with its JSON kind and its fresh-boot default. Secret fields must also be scrubbed in `downloadPreset`.
- Every preset, persona, translator preset, HypaV3 preset, and toggle preset carries an `id`, assigned synchronously where the element is created (`normalizePreset`, `newPersonaId`, `createTranslatorPreset`, `createHypaV3Preset`, `createTogglePreset`); copies and imports get fresh ids, and the `.risup`, `.risutl`, and HypaV3 JSON exports carry none.
- Preset and profile objects carry no credentials: `openAIKey` is a global `llmSecrets` field, the reverse proxy's and a custom model's key is a named key a profile binds, and `proxyKey` is dropped; `normalizePreset`, `normalizeModelPreset`, and `normalizeModelProfile` keep only their record's fields, so the server drops any key from stored records. `downloadPreset` writes neither (a prompt preset file has no endpoint or credential). No credential reaches the tab: the `llmSecrets` reads are masked, its credential fields read `""` in the tab's record, and a credential is written only through the secret queue; a key-dependent call goes to the server (`/api/llm/request` or an auxiliary operation of `/proxy2`, `global-api.md` `auxFetch`).
- `exportAsDataset` does no redaction. The settings report (`buildSettingsReport` in `snapshots.svelte.ts`, downloaded or copied by `SettingsExportButtons.svelte`) does: it drops every `llmSecrets` field, the personal and bulky keys (`irisDialogue`, `googleSearchCredentials`, `pluginCustomStorage`, the characters, the personas, `customModels`, the named keys' `credentials`, `modelPresets`, `modelProfiles` (they hold URLs), `togglePresets` (text/textarea values are free user text), ...), and every key whose name contains `key`, `proxy`, or `hypa`.
- The server's `customModels` normalizer drops a legacy `customModels[].key` and `credentialId` and keeps the model entry: a custom model is a definition, and the profile that uses it binds the key. The `credentials` normalizer likewise drops a `key` (and keeps `clientEmail`/`projectId` only on a `vertex` entry); a named key's value exists only in `llmSecrets.credentials`.

## Recipes

- Add a persisted setting:
  1. Add the field to `Database` in `shared/database.ts`.
  2. Give it its place in `shared/sections.ts` (a section's `SECTION_FIELDS`, a collection, or a preset field in `PRESET_DEFAULTS`).
  3. A section field gets its kind and fresh-boot default in that section's `SectionSpec` (`server/src/data/normalize/`), and any migration there; a preset field gets its default in `PRESET_DEFAULTS` (the server `presets` normalizer and the settings views use it).
  4. Verify: a fresh server shows the default, the value survives a reload, and an idle reload writes nothing.
- Add a collection with its own resource: see the field-to-resource invariant above. Verify a save, a reload, a two-tab conflict, and a backup round trip.
- Move more browser-local user data to the server: add a step to `importBrowserLocalData` that writes, reads back, and only then deletes the local entry.
- Change the asset backend: `assetClient.ts` (and the auth in `serverAuth.ts`). Asset keys are logical, not file paths: the server maps `assets/<name>` to `save/assets/<encoded name>` and accepts no other namespace (see `self-host-server.md`).

## Known Hazards

- `togglePresets` saves as a whole collection record. Two tabs saving presets concurrently can drop one tab's new preset on a conflict reload while its chat link still lands, leaving the sidebar in the deleted state. Chat metadata merges preserve other toggle keys, but do not make the collection save and link atomic.

- A tab learns of a restore or import from the live-update socket's `epoch` frame (or the `hello` of its reconnect, or its next request: 412 or a changed epoch), and halts and reloads (`haltForRestore`). A tab whose server job the maintenance ended (its `maintenance` terminal, which comes before the replacement) also watches for it (`watchForRestore`: one small read a second, each bounded to 5 s, for two minutes), so the owner of a running send is told even when its socket is down.
- A quarantined resource remains only in the local mirror until its projection changes and saves successfully. Other edits do not retry it or acknowledge an unsaved character create. `flushResources` rejects immediately with its refusal reason; closing the tab does not warn solely for quarantined data. Preserve that data by export before reloading if needed.
- A refused create retained locally is quarantined for the session and excluded from collection-removal reconciliation; a server-side deletion of its parent character still follows character recovery.
- An unindexed permanent refusal switches the session to separate resource/chat/order requests; atomicity remains per request, and creating a character precedes creating its chats.
- One chat group larger than the server's 100 MiB body limit cannot be saved (the adapter quarantines the chat and alerts).
- The server's `/api/remove` takes several keys, each hex-encoded and joined with `$$` (no client calls it); it validates every segment before deleting. A filesystem error mid-batch (e.g. a missing file) returns 500 and keeps earlier deletions.
- `selectedChat()` and `findChat` return the live read-only chat; take `$state.snapshot` before handing it to code that mutates. A snapshot or spread of a character has no chats: build the legacy shape with `withChatsCopy` at a plugin boundary.
- Folder moves touch the character (`chatFolders`), the chat (`folderId`), and the chat order, each saved on its own; a conflict on one of them (a folder deleted in one tab while another moves a chat into it, or a folder write refused while the chat's `folderId` saved) can leave a chat whose `folderId` names no folder of its character. No repair clears a dangling id, on boot or later, so it outlives a reload (an explicit write still can: a move, a plugin's chat copy without it, or deleting a folder of that id, which clears it from the chats carrying it); the sidebar chat list (`SideChatList.svelte`) renders such a chat at the root as unfiled (`chatFolderOf`, `src/lib/SideBars/chatFolders.ts`) and keeps the id as stored: a drop at the root does not remove it, a move into a folder replaces it. The pinned rail and the modal chat list do not group chats by folder.
- A chat quarantined after a 400 stops saving for the rest of the session; `flushResources` then rejects after its retry cycles.
- A server job's message is locked on the server for every client (`reason: "generating"`), and every tab learns it from the change feed (Save step 9). A tab without the lock can still edit the generating reply before the job's first write's frame arrives, after a `hello` dropped its feed locks, or after an adopted whole read at a newer revision released them (another writer's change of the chat), until the job's next write announces the lock again (every `CHECKPOINT_INTERVAL_MS`, 3 s, while it streams; a job waiting on its provider or a callback may write nothing for longer). Such an edit is refused by the server and dropped (Save step 6), but the mirror shows the dropped edit until the chat's whole read, which waits for the chat's other refused work and this tab's own generation locks. An all-dropped group has no retry block, so a later edit of that message can go out at the next cycle, before the read. An edit sent before recovery completes can land over the finished reply.
- The browser's former LocalForage `mcp-tool-calls` store is no longer read: a remembered tool call lives only in its chat (`chat.toolCalls`), and one remembered by an older version or without a chat no longer resolves (alpha, no migration).
- A server job's membership changes (a record or chat created or deleted) are not hydrated on its socket; they reach every tab through the live updates.
- Live updates show another writer's change only when this tab has no unsent change of that record; two tabs editing one record still converge through the 409 path (the later saver's edit is discarded with the notice). An observing tab sees a server job's reply at its 3 s checkpoints (an eligible by-id feed patch applies directly; otherwise a chat read), then the final text. A tab whose socket is disconnected catches up at the reconnect's reconcile.
- The browser-local import has no cross-tab lock. `removeIfUnchanged` reads each entry and compares it with the imported value just before deleting it, so an entry another tab changed earlier is kept, but a change that lands between that comparison read and the deletion is lost.
- A page restored from the back-forward cache after `pagehide` may still wait for an unload request's answer; `flushResources` retries at most ten cycles and then rejects with "Could not save every change".
- The section normalizers apply fresh-boot defaults and carry no cross-section migration: a legacy root `formatversion` is dropped, and a field such as `providers.loreBookToken` takes its default (8000) instead of a value derived from older data (alpha: no migration).
- The client mutation modules check a value's kind and shape but do not normalize it, so a kind-valid but non-canonical value (from a plugin, an import, an MCP tool) stays in the tab's mirror as written after the server normalized its copy, until a reload or a later server copy (`plugins-mcp.md`).
- `incrementStatic` treats a missing or non-finite count as 0 and marks the `statics` record (a field patch when smaller); two tabs counting at once go through the ordinary conflict path (merged as a best-effort count, see Save step 5), not an atomic counter.
- `setCharacterOrder` refuses a folder without a `data` member list, while `checkCharOrder` reads a missing list as empty. `checkCharOrder` removes empty folders before it filters members, so a folder its filtering empties survives one call and goes on the next.
- `replaceCharacterAt` replaces a character and installs its chats but does not repair `characterOrder`; a new id is missing from the order until the next `checkCharOrder`.
- A same-id recreation reconciles only the chats this client knows: a chat another tab created under that character that this tab never saw survives on the server, a reused chat id's `replace` on a base another tab changed conflicts through the usual 409 path (the replacement chat's content is discarded with the notice), and an old chat quarantined after a 400 keeps its quarantine, so its delete is never sent and the reorder waits.
- A preset's or custom model's record and its `llmSecrets` credential are separate requests (the credential after the cycle's batch). A refused credential write leaves the entry without its key until it is entered again, and a deleted owner's entry stays until its cleanup succeeds; a retryable failure keeps the operation queued.
- The records are deep write-through wrappers without a resolve cache (a cache halved the cost, but its invalidation rule was never proven). The spike benchmark (`projectionSpike.test.ts`, dev mode, 2026-10-04) measured about 6× a direct write for a nested leaf write (13 µs against 2 µs), 4.3–4.5× for a 300-entry lorebook drag (28 ms against 6 ms), and 3.3–3.8× for a preset reorder, against an intended 2×. In the production build the cost shows in list re-renders reading every row through its wrapper (`measureRecords.mjs`, headless Chrome, medians of 10): the 50-preset reorder went from 15.3 ms to 22.2–24.4 ms and the 300-entry module lorebook drag from 92–93 ms to 104–107 ms when the records became the source of truth (commit `3ea20656` against `35678fd4`); at commit `2f658598` they measure 17.9–18.2 ms and 106–107 ms (against 17.5–17.8 ms and 103–105 ms at `6fa405d1`). Both handlers already change their list in one write (`moveRecordListItem`, `replaceRecordList`).
- The echo of this tab's own save is a live-update notice; one that arrives before the save's acknowledgement is newer than the held revision and schedules a cycle 50 ms later (`noteRemoteChanges`) instead of the 500 ms debounce. During continuous typing that cycle sends the keys typed since, so a field can save more often than once per debounce. Measured with 100 keystrokes 50 ms apart (about 5 s) into a settings field (`measureRecords.mjs`): 35–52 batches at commit `6fa405d1`, but 9 at `2f658598`, which is the debounce cadence. At `2f658598` the extra saves were not reproduced; the 50 ms echo cycle remains in the code. Coalescing or dropping echoes of a revision this client already holds would bound it.
- A character wrapper's read-only `chats` view builds a fresh array of the loaded chats on every read; read one chat through `findChat`, not by scanning `chats` in a loop (a test helper doing that over 1,000 chats timed out).
- A noticed loaded idle chat whose feed patch could not apply is read whole (`refreshIdleChats`) before the cycle's trim; once the read settles its notice the trim may evict it, so that read can be wasted.
- `installRead` treats an incomparable revision as older (and reads again) while `adoptChatRead` treats it as not older. Production tokens are always comparable within an epoch; only test fixtures with tokens like `r1` reach the difference.
- A stored chat row without `fmIndex` is not backfilled: a summary reads it as `-1`, a whole-chat read can omit it (readers default it). Alpha: no migration.
