# Self-Host Server (Hono on Node), Docker

## Scope

- Owns:
  - `server/src/**`: the Hono self-host server on Node (`@hono/node-server`). Handles static `dist`, auth, asset storage, the resource store and its routes, resource snapshots and backup archives, the reverse proxy, the hub proxy, and streaming proxy jobs over WebSocket.
  - Local TLS certificates.
  - Docker packaging.
  - The launcher scripts.
  - The client/server contract, seen from the server side.
- Paths: `server/{src/**,tsconfig.json,ssl/*}`, `Dockerfile`, `.dockerignore`, `server.sh`, `server.bat`. Domain-specific runtime semantics stay with the guides linked in `Tests`; request history and diagnostics have a dedicated [owner](diagnostics.md).
- Client counterparts, owned by other guides:
  - `src/ts/storage/serverAuth.ts` and `src/ts/storage/assetClient.ts` → `persistence.md`.
  - `globalApi.svelte.ts` `fetchNative` → `global-api.md`.
  - `characterCards.ts` `hubURL` → `characters-modules.md`.

## Files

Request history, diagnostic journals/reports, and support shares have one owner: [diagnostics](diagnostics.md).

The server is TypeScript run directly by Node's type stripping (`pnpm run server` = `node server/src/main.ts`, Node `>=24`). There is no build step. Layout: `main.ts`, `app.ts`, and `types.ts` (`AppEnv`) at the root; route modules in `routes/`; the resource data layer in `data/`; shared HTTP helpers in `http/`; the server-side processing modules in `prompt/`, `scripts/`, and `lua/`; tests and their support in `tests/`. The server may import the persisted types in the root `shared/` folder (`persistence.md`); `server/tsconfig.json` includes it, so `pnpm check` strict-checks it. Relative imports use explicit `.ts` extensions, and only erasable syntax is allowed (`server/tsconfig.json` sets `erasableSyntaxOnly`; `pnpm check` runs `tsc -p server/tsconfig.json`).

- `server/src/main.ts`: entry. Reads `PORT`, `RISU_HOST`, `RISU_SAVE_DIR`, and `RISU_AGENT_DEV_AUTH_BYPASS` through `listenConfig.ts`, plus `RISU_PASSWORD_SHA256` through `createServerContext` and `listenConfig.ts`'s `parsePasswordSeed`, `TRUST_PROXY`, `RISU_MAX_IMPORT_BYTES`, `RISU_MAX_UPSTREAM_DB_BYTES` and `RISU_UPSTREAM_IMPORT_HEAP_MB` (the upstream import's decoded-database cap, default 1 GiB, and its worker's heap limit, default twice that cap in MiB within 256 to 4096), `RISU_UPSTREAM_EXPORT_HEAP_MB` (the upstream export worker's heap limit, default 2048 MiB, independent of the import's cap; read when the export routes are registered), `RISU_REQUEST_HISTORY_MAX_BYTES`, `RISU_DIAGNOSTICS_DIR`, and `RISU_DIAGNOSTICS_MAX_BYTES`, loads the TLS certificate (`getHttpsOptions`), calls `serve()` with Node's `requestTimeout` raised to `REQUEST_TIMEOUT_MS` (4 hours for the whole request, over HTTP and HTTPS: the backup, module, and CharX imports upload a whole file in one request, which Node's 300 s default fails with 408 under about 1.9 MB/s for 580 MB; `headersTimeout` stays Node's default), attaches the WebSocket upgrade handler, and starts job GC, the snapshot timer, and the diagnostics state timer. A `process` `uncaughtExceptionMonitor` and the HTTP server's `error` listener record a `runtime` diagnostic event and write `state.json` before the process exits (a monitor keeps Node's crash behavior; with no `unhandledRejection` listener in the process an unhandled rejection reaches it with origin `unhandledRejection`; a failure caught by `startServer` before the context exists is not recorded). On SIGINT/SIGTERM it begins shutdown, drains HTTP for up to 8 s, force-closes remaining connections, then awaits `dispose()` and exits. `cwd` is the root: `cwd/dist`, `cwd/save` (unless `RISU_SAVE_DIR`), `cwd/server/ssl/certificate`.
- `server/src/listenConfig.ts` `readListenConfig(env, rootDir)`: `PORT` (default 6001); `RISU_HOST`, the address `serve()` listens on (unset: every interface); `RISU_SAVE_DIR`, the storage directory resolved against the root (default `rootDir/save`); `RISU_AGENT_DEV_AUTH_BYPASS` (`TRUE`/`1` or `FALSE`/`0`, else an error), which throws unless `RISU_HOST` is a loopback address (`isLoopbackHost`: numeric `127.0.0.0/8` or `::1`; a name such as `localhost` or a bracketed `[::1]` is refused, since Node hands either to the resolver, which could map it elsewhere), so the bypass never answers another machine. `pnpm dev:agent` sets all four ([build-test-platforms](build-test-platforms.md)). `parsePasswordSeed(raw)` trims `RISU_PASSWORD_SHA256` (unset or empty means no seed), requires 64 hexadecimal characters, and returns lowercase; an invalid value throws at context creation with the SHA-256 command to use.
- `server/src/app.ts` `createServerContext({ rootDir, savePath, authBypass, trustProxy, resourceKinds, snapshotIntervalMs, scriptWorkerOptions, maxImportBytes, generationRunner, ..., realmStagingTimer, generationEffectClock, generationAbortGraceMs, generationHypaV3SeparatorLimits, routeLimits, cbsTimeLimits })`: builds the Hono app and owns all state, including the generation lock, the resource store (built with the lock as its guard), the snapshot manager, and the generation jobs. `resourceKinds` replaces `DEFAULT_RESOURCE_KINDS`, `snapshotIntervalMs` the 10-minute interval, `scriptWorkerOptions` the script workers' time limits (`ScriptWorkerTimingOptions`: the boot cap, the synchronous-call wait, the watchdog and abort graces, and the defaults of a Lua run's, an engine preparation's and a regex script run's allowance, a regex's deadline and a job's Lua budget), and `generationRunner` the jobs' runner (tests use them; the default is `createGenerationRunner`, below). Test-only timer seams, production defaults unchanged: `realmStagingTimer` schedules the staged Realm imports' expiry (`createRealmStaging`), `generationEffectClock` is the default runner's trigger effect-loop clock (`GenerationRunnerDeps.effectClock`, default `performance.now`), `generationAbortGraceMs` an aborted job's grace (`createGenerationJobs({ abortGraceMs })`, default `JOB_ABORT_GRACE_MS`, 5 s), and `generationHypaV3SeparatorLimits` the default runner's HypaV3 separator limits (`GenerationRunnerDeps.hypaV3SeparatorLimits`, given to the memory host as `MemoryHost.separatorLimits`; default 5 s chunking, 1 s per split); `routeLimits` (`RouteLimits`) lowers route caps so a test reaches them in a few requests: `requestsPerMinute` for the three 2000-per-minute buckets (authenticated, storage, auth; the login limiter is unchanged), `assetBatchRecords` for a batch write (`registerStorageRoutes({ maxBatchRecords })`, `AssetRecordParser({ maxRecords })`), `archiveRecords` for the version-2 import (`registerBackupRoutes({ maxArchiveRecords })`, `indexArchive`'s `maxRecords`), and `charxEntryBytes` for the CharX import (`registerCharxImportRoutes({ maxEntryBytes })`: the decoded cap and the declared-size rules of `excludedBeforeReading`); `cbsTimeLimits` (`ServerCbsTimeLimits`: `templateMs`, `jobMs`) replaces the CBS wall times of every job, render, and translation (`serverCbsLimits`, through `GenerationRunnerDeps.cbsTimeLimits` and `createTranslationRunner`'s; default 5 s per template, 60 s per job); `createTestServer` passes them through, and `server/src/tests/unhurriedLimits.ts` holds ten-minute values for tests whose subject is not a limit. The context builds its own HypaV3 memory task service (`createMemoryTasks`, below) when the resource kinds include `characters` (a test registry without them has none: an empty `hello` list and 503 routes), on the request layer, the embeddings, the script workers, the token counter, `cbsTimeLimits`, and `generationHypaV3SeparatorLimits`, and gives it to the default runner, which hands chats off to it after a send ([chat pipeline](chat-pipeline.md)); its start and cancel routes are open. The `memoryTasks` option (`"disabled"` or a `MemoryTaskService`, tests) gives the runner a fake service or, with `"disabled"`, none (every HypaV3 step summarizes inside its job) in its place; either closes the routes (503 `notEnabled`), since nothing then hands a chat to the context's service. `memoryTaskOptions` (`{ now?, limits? }`, test seams) replaces its clock and `MemoryTaskLimits`. Its wiring: the event sockets' `hello` reads its `snapshot()`; its maintenance listener (`pause`, `resume` at the end) is registered after the translations' and before the jobs', so its tasks end `cancelled` (`maintenance`) before the jobs' listener waits for the jobs and the request layer pauses; a change feed listener registered after the sockets' calls `resetEpoch()` on an `epoch` event (the clients get the `epoch` frame before any status of the new registry); `onChatInvalidated` calls `invalidate(notice)`; every `onStatus` event is published on the change feed as a `memoryTask` event. It also owns the change feed (`data/changeFeed.ts`, given to the store) and the live-update sockets (`routes/events.ts`). Returns `{ app, snapshots, scriptWorkers, generationJobs, llmRequests, requestHistory, translationRunner, memoryTasks, push, eventSockets, diagnostics, attachWebSocket, startBackgroundTasks, beginShutdown, dispose }` (`memoryTasks`: the context's service, or null). `attachWebSocket(server)` installs the one `upgrade` listener per server: `generationJobs.handleUpgrade`, then `eventSockets.handleUpgrade`, else the socket is destroyed. `beginShutdown` stops admissions and timers, ends the memory tasks (`cancelled`, `shutdown`; first, before the jobs' aborts release their writer leases and the request layer's shutdown fails the tasks' requests), aborts every generation job, removes the upgrade listener, and closes the live-update sockets (1001) before the snapshot manager stops; `dispose` is async and idempotent (it waits for the jobs to end and for the memory tasks' and translations' unsettled work (bounded, `drain`), terminates the script workers, and waits for admitted resource handlers and backup operations before closing the store). `app.request()` works for in-process checks, but it has no Node socket, so the client IP is undefined there.
- `server/src/routes/auth.ts` `createAuthStore`: `save/server/password` plus `save/server/known_public_key_hashes.json`, durable directory creation and writes, missing/set/damaged password states, malformed key files renamed aside with a warning, and an optional `passwordSeed` that initializes only a missing password file; `verifyJwt`, `checkAuth`, `checkProxyAuth`, `isAuthorizedProxyToken`, and the `/api/test_auth|login|crypto|set_password` routes. `{ bypass: true }` (`RISU_AGENT_DEV_AUTH_BYPASS`) makes `verifyJwt` accept every token (so `checkAuth`, `checkProxyAuth`, and the socket checks pass) and `/api/test_auth` answer `success` before the password check, so the tab registers nothing and asks for no password.
- `server/src/routes/storage.ts`: the key-to-file mapping (`STORAGE_NAMESPACES` = `assets` only, `decodeKeyHeader`, `encodeFileName`/`decodeFileName`, `isAssetStorageKey`, `resolveStorageKey`), the in-process `readStorageFile`/`writeStorageFile` (a server job's asset reads and writes, under the routes' rules: no symlinks, regular files, staged writes flushed before rename and directory sync), `/api/read|write|list|remove`, and the batch routes `/api/assets/write|read` (`shared/assetBatch.ts`: the backup archive's record framing, each record named by its full logical key). `registerStorageRoutes` empties `save/.tmp/` at startup; writes and removals hold the maintenance gate. A batch write reads its body through `AssetRecordParser.events`, streams each record's bytes into a staged `save/.tmp/<uuid>.tmp` file as they arrive (memory holds a chunk, not a record), and holds the gate only to rename that record into place, never across the body read (maintenance waits for every admitted mutation); it always overwrites, as `/api/write` does. Each staged record is flushed before close; after the whole body parses successfully, each target directory is synced once outside the gate before success is answered. At the first failure it stops writing and removes the staged file, but still reads the body to its end before answering: `@hono/node-server` resets a connection whose body is left unread (after 500 ms or 64 MiB), which the client would see as a network failure and resend. Records renamed before the failure stay, without the final directory sync because the batch was not acknowledged. A batch read answers `storedFileRecord` per key through `iteratorStream`. Like `/api/write`, neither batch route is tracked by `snapshots.track`, so shutdown does not wait for one. Content-name writes record verification after the rename: `/api/write` hashes before admission, batch writes hash each data event, and `writeStorageFile` accepts a server-computed digest or hashes while streaming into staging. `/api/remove` forgets verification for each attempted removal; `/api/asset/*` consults the current handle stat and queues unknown content names for hashing.
- `server/src/data/changeFeed.ts` `createChangeFeed()`: `subscribe(listener)` and `publish(event)`, where an event is `{ type: "change", epoch, changes }` (a `ChangeSet` of `shared/resources.ts`: resource, chat, and chat-order refs with their new revisions, null for a deletion; data only as a record patch (`RecordFieldPatch` or `RecordItemPatch`) or a by-id chat patch (`ChatPatchBody`)), with an optional `streaming` (`ChatStreaming[]` of `shared/events.ts`: per chat, every message a generation job owns, as `StreamingMessage`; `[]` for none), `{ type: "memoryTask", epoch, characterId, chatId, status }` (a chat's memory task status change, `MemoryTaskEntry` of `shared/events.ts`, published by the app's `onStatus` listener in the epoch of its transition, not by the store), or `{ type: "epoch", epoch }`. Listeners only: no buffer, no replay; a publication inside a listener reaches the remaining listeners at once (before the outer event reaches them). A listener that throws is logged and never fails the write that published.
- `server/src/routes/events.ts` `createEventSockets({ feed, epoch, authorize, memoryTasks })`: the live-update socket `/api/events/ws` (`shared/events.ts`). `handleUpgrade` (false, the socket untouched, for another path) admits a JWT in the `risu-auth` query or header (`auth.isAuthorizedToken`, never the password); the socket gets `hello { epoch, memoryTasks }` (`memoryTasks`: every chat's memory task status, `MemoryTaskEntry[]` from the service's `snapshot()`, read in the same synchronous step as the epoch; a throwing read closes the socket with 1011 instead of sending a partial `hello`), then every published event as a `change` (its `streaming` included), `memoryTask`, or `epoch` frame (each type its own mapping), and a `ping` every 15 s. Frames reach every socket in publication order: a frame published while another is being sent waits until that one reached every socket. A socket more than 4 MiB behind, or whose `send` throws, is terminated (its client reconnects and reconciles); a throw never keeps the frame from the sockets after it. `close()` closes every socket with 1001 and refuses new ones (503). Sockets are not tracked by the snapshot manager and not gated by maintenance.
- `server/src/data/resourceStore.ts` `createResourceStore({ file, kinds, guard?, feed?, patchBaseMaxUnits?, inspectStoredText? })` (the last two are test seams: the patch-base cache's budget, default 64 Mi units, and a reader of a record's stored text for an in-memory store): typed resource documents in one `node:sqlite` database (`save/data/resources.sqlite`), with revision tokens, conditional writes, `epoch`/`assertEpoch`, `writeCount`, `readKinds(kinds, { chats, chatSummaries })` (with `chatSummaries`: every chat's `ChatSummary` projected from its metadata, no message rows read, and every order; exclusive with `chats`), `readRefs(refs, { chats, chatCollections, chatSummaryCollections })` (`chatSummaryCollections`: characters' orders and chat summaries; in the result only when asked), `readChatSource(characterId, id)` (one chat as `readRefs` reads it, with its `sourceGeneration`, in one synchronous call), `chatSourceGeneration(characterId, id)` and `onChatInvalidated(listener)` (the chat source generation, see Invariants; `ChatInvalidation`), `listRevisions()` (every record's, chat's, and chat order's revision, no data), `readKindRevisions(kinds)` (the revisions of every record of some kinds, no data parsed), `chatMeta(characterId, id)` (a chat's metadata and revision with an empty `message` list, no message rows read), `revisionOf(kind, id)` (one record's revision, no data read), `chatRevision(characterId, id)` (a chat's revision, no metadata or messages read), `applyBatch`/`applyChanges` (resource ops, chat groups, and reorders in one transaction; a resource op writes `data`, deletes, or applies a record `patch` at a string `baseRevision`: a field patch `{ set?, remove? }` of an object record (those top-level fields assigned or deleted) or an item patch `{ items?, changes?, order? }` of an array record whose items have unique non-empty string ids (`shared/recordPatch.ts` `checkItemPatch`/`applyItemPatch`: whole items put in place by id, field patches of base items, and with `order` exactly those ids in that order); the result is normalized and stored like any write, and its change-feed entry carries the changed fields or items; a kind with `project` or `prepareWrite` (`llmSecrets`) takes no patch, and a patch that does not fit the stored record is a 400 naming the op), `applyChanges` also accepts `inTransaction: { before(tx)?, after(applied, tx)? }`: synchronous checkpoint callbacks after BEGIN/before batch writes and after conflict-free application/before COMMIT, with a callback-bound `CheckpointTransaction` (`save`, `prune`, `setFloor`, `readPolicy`, `writePolicy`); a throw or thenable rolls everything back, public store writes from callbacks or their async continuations throw, escaped writers expire when their callback returns, and their writes count only at commit; `committed` retains its after-commit behavior. `transaction`, `backupTo` (online backup to a single-file copy), `checkpoints` (the chat checkpoint table methods of `checkpointStore.ts`: standalone writes run in their own transaction, count toward `writeCount`, and publish no feed event; reads take none; `readFloor` is public read-only access, while floor writes are exposed only as `inTransaction` callbacks' `tx.setFloor`), `readSnapshot` (validates a snapshot file with the store's kinds; the module-level `readSnapshotFile(file, kinds)` does the same without a store, for the upstream export worker) and `replaceAll` (installs it with a new epoch), the normalization pass (`normalizeStoredRecords`, run when the store opens and inside `replaceAll`), `ResourceConflictError`, `ResourceBatchConflictError`, `ResourceEpochError`, `ResourceValidationError`, `ResourceStoreClosedError`, and `isValidResourceId`.
- `server/src/data/chats.ts`: the pure chat normalizers: `normalizeChatMeta` (drops `message` and the streaming flags, sets `id`, defaults `name`/`note`/`localLore` and `fmIndex` (-1), type-checks them), `normalizeMessage` (`user`/`char` role, string `data`, valid `chatId`; a `translation` that is not a `MessageTranslation` is dropped, not refused), `normalizeMessageList` (a whole chat's messages: missing, invalid, or duplicate ids get UUIDs), `assertPatchableMetaKeys`, `CHAT_SCHEMA_VERSION`.
- `server/src/data/chatStore.ts`: the chat tables (`chats`, `messages`, `chatOrders`, and `chatGroups`, the remembered group ids: `CHAT_GROUP_TABLE_SQL`, `MAX_CHAT_GROUP_IDS`; `mayHaveForgotten` refuses possibly expired retries with `reason: "expired"`) inside the resource store: batch preparation before any transaction (`prepareChatGroups`, `prepareChatOrders`, `countChatOperations`: shapes, legal op combinations, normalization, errors prefixed `chats[i].ops[j]`), `createChatTables` (applies groups and reorders inside the store's transaction, reads, restore), the generation fence, restore-floor checks after remembered results and locks, and `readChatSnapshotRows` (snapshot validation). `prepareWholeChat` keeps whole-array JSON semantics (array/element `toJSON` and invalid sparse holes) while measuring depth per message, as append does (`serialize` with `arrayElementDepth`).
- `server/src/data/checkpointStore.ts` `createCheckpointTables(db, tokens)`: named per-chat checkpoints (a chat's message rows as stored plus the chat fields that carry story state) inside the resource store: the checkpoint tables (created when missing), and synchronous methods that join the caller's transaction and never open one: `save` (a missing chat is null; the 101st manual checkpoint is a `ResourceValidationError`; names truncated; never prunes), `prune` (keeps the newest of a kind), `list` (summaries newest first, no page read), `rename`/`delete` at the checkpoint's revision token (`ResourceConflictError` otherwise; a missing chat or checkpoint is null), `compose` (the replacement `Chat` for a load: captured fields from the checkpoint, the others and the `toggle_` entries of `GLGlobalVariables` from the chat as stored now), `readPolicy`/`writePolicy` (the auto-checkpoint policy row), `readFloor`/`setFloor` (the numeric restore barrier; the writer copies the current chat revision without lowering an existing floor), and `sweep` (drops pages no ref names). Messages are cut into pages after a message whose id's SHA-256 first byte is 0 mod 16, or at 64 messages or 1 MiB of row text; each captured field is one page; pages are content-addressed (SHA-256 of the text) and shared by every checkpoint. The field classification, wire types, and limits are in `shared/chatCheckpoints.ts` (`CHECKPOINT_CHAT_FIELDS`, typed over every `ChatMeta` key so a new chat field fails `pnpm check` until it is classified). The separate `chatRestoreFloors` table cascades with its chat; it is created before `createChatTables` prepares its floor lookup, is outside the optional four-table snapshot group, and is never restored. Snapshots and archives carry them: `readCheckpointSnapshotRows` (called by `readSnapshot`) validates the four tables as one optional group, and `replaceAll` restores them on the restored chats (Flows, "Snapshots and restore").
- `server/src/data/checkpointService.ts` `createCheckpointService({ store, busy, memoryTasks, afterLoad? })`: synchronous `list`, `readPolicy`, `writePolicy`, `save`, `rename`, `remove`, and `load`, each taking `{ body, epoch? }` (list and policy reads use query fields as `body`) and returning `{ status, body }`, independent of Hono. Captures and composition use the stored chat; unknown fields/invalid ids or types are 400, missing chat/checkpoint 404, revision conflicts 409 with `revision`, busy save/load 409 `{ reason: "generating" }`, and epoch mismatch 412. `readPolicy`/`writePolicy` expose only `{ autoEvery, autoKeep }` or null (off); writes accept those integers (1–100 and 1–20) or `off: true` alone and preserve an existing baseline, while a new policy starts at null. A missing chat is 404 even for an unchanged policy. `autoSave(characterId, chatId)` runs without a request or HTTP result, checks busy/policy/chat, and saves, advances the baseline, and prunes in one transaction (Flows, "Automatic checkpoint"); its errors propagate to the job hook. The caller checks maintenance immediately before an HTTP mutation. `afterLoad` is a test seam inside the transaction, after its writes; throwing proves rollback. The app supplies its own `MemoryTasks | null`, regardless of the runner's `options.memoryTasks` override; `busy` combines job slots and all message locks of the chat.
- `server/src/routes/chatCheckpoints.ts` `registerChatCheckpointRoutes`: authenticated, shared-limiter HTTP mapping for the checkpoint service (Routes below), ids in JSON or query fields, `x-resource-epoch` for mutations, maintenance checked after body parsing directly before the synchronous service call. POST and policy PUT bodies are capped at 16 KiB after auth (declared and actual bytes); the app-level middleware sets `no-store` on every answer, including auth, cap, limiter, maintenance, and shutdown errors. This module registers only the six endpoint templates, with no wildcard middleware route. The app tracks handlers through shutdown like resource routes.

It reads the legacy `\0RISUSAVE\0` with version `\x07` (raw MessagePack), `\x08` (gzip, what older upstream backups write) or `\x09` (stream gzip) with upstream's `Unpackr` options (`useRecords: false`; ext 0 is `undefined`) plus `int64AsType: "number"` (upstream's `\x08` reader would give a BigInt, which upstream's encoder never writes for a number). gzip is inflated by `node:zlib` with `maxOutputLength` at the cap, so a bad CRC or ISIZE, truncation, or an output past the cap is refused (upstream's `fflate.decompressSync` trusts the trailer and skips the CRC); the cap alone does not bound the MessagePack decode's allocations (msgpackr 2 refuses an array or map header longer than the bytes left, but nested headers add up), so untrusted input is decoded under a heap limit. Legacy saves answer `kv: {}`. It also reads the block save current upstream backups write (`encodeRisuSave`: `RISUSAVE\0` with no leading zero, then blocks of a type byte, a gzip flag byte (1: the block is its own gzip member, inflated as above), a name length byte, the name, a little-endian 32-bit length, and JSON text), in file order as upstream's `RisuSaveDecoder` does: the root's keys fill only unset or falsy fields (keys starting with `__` skipped), character blocks append to `characters`, the preset, module, plugin, loadout, and plugin storage blocks set their field (an empty one, upstream's encoding of an undefined field, leaves it unset), a root component sets its key, `kv:<namespace>` blocks go to `kv`, and the config block is ignored; `characters` defaults to `[]`, and a missing or empty `botPresets` resets `botPresetsId` to 0 (the converter supplies the default preset). The cap charges each block its framing plus the larger of its stored and decoded size, so an accepted block save fits the stage's encoded-record bound. It is stricter than upstream, which skips what it cannot read: a truncated block or a length past the end, a block over the cap, damaged JSON, a missing root, a block type upstream has no reader for, a remote block, and a root `__directory` naming a block the file lacks are refused (the last two mark a live save whose data is outside the file; no path is ever resolved). It throws `UpstreamFormatError` (with its `format`) for these, headerless data, an unknown version, a non-gzip payload, damaged data, a size over the cap, and a root that is not an object with a `characters` list. `encodeUpstreamDatabase(db)` writes `\x08` as upstream's `encodeRisuSaveLegacy(db, "compression")` does (`Packr({ useRecords: false })`, `fflate.compressSync`, the 11-byte header); `msgpackr` is pinned at 2.0.6 (upstream locks 1.10.1, whose Node encoder throws on Node 23 and later for every string of 64 or more characters; fixed in 1.11.1), which writes the same bytes as 1.10.1 for the values a `Database` holds.

- `writeAsJob` (`RunningJob.write(build)`): synchronous. Refuses an ended job, checks the maintenance gate, takes the lock of every `begin` op's message (a later `begin` of the job replaces the generation), and calls `store.applyChanges(changes, { epoch, jobToken, committed })`; a final generation write whose checkpoint is `applied` releases its message only if its generation still owns it (so `[final(g1), begin(g2)]` keeps g2 locked). That bookkeeping (watermarks, `metaWrite`, `generated`, `current`, the final release) runs in `committed`, after the commit and before the change is published, which then returns every chat of the write with its locks (`chatStreaming`: every job's owned messages of the chat, each with its owner's watermark `seq`); the published `change` carries them as `streaming`, so a `begin`'s frame shows the new lock and a final write's frame the release. A conflict naming only resource records calls `build` again (it re-reads) and applies once more; any other conflict, or a second one, throws `JobWriteConflictError`. After each chat write the scope adopts the stored metadata and revision (`refreshChatAfterWrite`, a metadata-only write) or reads the chat again, and the engine and run characters are re-read only when their revision changed (`refreshCharacter`; the run character the Lua getters read is the scope's copy, checked the same way). With `deps.lock`, a chat write that rewrites or removes a message any generation owns, this job's own included, is skipped with a warning, as the tab's `liveWrite` without a generation capability is refused. With `deps.frozen` (the script transform) the scope is a render's snapshot: no character or chat is read again from the store (`refreshAll` and `services.refresh` do nothing; the run character is the scope's; the inlay records and media files an image getter checks are still read live), a chat-variable write (Lua `setChatVar`, a CBS setter) changes the snapshot chat's `scriptstate` only, and any other chat write is a fatal failure.

- `server/src/scripts/workerPool.ts` `createScriptWorkerPool({ rootDir, size, maxSize, idleMs, bootMs, resourceLimits, egress, wallMs, syncHostTimeoutMs, sleepCaps, watchdogGraceMs, abortGraceMs, luaCpuMs, prepareCpuMs, regexScriptsCpuMs, regexDeadlineMs, luaBudgetMs })`: the `worker_threads` pool that runs Lua and user regexes (`runLua(task, { host, signal, budget })`, `regex(op)`, `runScripts(input, { host, signal })`, `createBudget`, `warm`, `stats`, `dispose`); task results never throw. `warm()` returns `Promise<void>` once `size` workers report ready, including workers already booting; it rejects on a warm worker's boot failure, with an internal catch for fire-and-forget callers. Disposal resolves pending readiness waits; `warm()` after disposal resolves without spawning. `runScripts` runs the regex script engine (`runRegexScripts`) on a worker as a Lua-kind task (`REGEX_SCRIPTS_MODE`) under 5 s of the worker's own time (`regexScriptsCpuMs`): `parse`, `repeatBack`, and `effect` are its synchronous host functions, answered on the main thread while the worker waits, so CBS stays with the job's evaluator and an effect lands where its script matched; a host throw only skips that script, so the caller latches a fatal failure and aborts the run's signal. A host argument or a result over 16 MiB as JSON fails the task, and no host call follows the failure. A worker holds one top-level task, counted as busy even while booting, and dispatches it only after `ready`. Regex deadlines are armed immediately before posting; Lua watchdog baselines start at dispatch, so boot time consumes neither task budget. Each spawn has a separate `bootMs` cap (30,000 ms by default), cleared on `ready`; a worker that never becomes ready fails held tasks with `Script worker did not start within <bootMs> ms`, without a task timeout flag, and is not replaced ahead of demand. A regex its run's host call spawns (`HostContext.regex`) goes to the same worker, and a host context stops working when its run ends. The watchdog charges the worker thread's busy time (`eventLoopUtilization`), less synchronous answers and spawned regexes, and terminates the worker past the CPU budget plus `watchdogGraceMs` (1 s); a Lua task has a 10-minute wall cap and a regex a 1,000 ms deadline (`regexDeadlineMs`, also a spawned regex's). An abort of a dispatched Lua task sets a shared flag the Lua hook reads, and terminates the worker if the run has not ended after `abortGraceMs` (500 ms); an abort while held settles immediately and releases the slot without killing the booting worker. Budgets (`createLuaBudget`; `createBudget()` makes one of `luaBudgetMs`, 30 s by default, which the job runners create per job and a render per request, shared across its targets) reserve each run's allowance at its start, when assigned to a slot, even while the worker is booting. A held task that aborts or whose worker dies releases its reservation without a CPU charge. Terminated or crashed workers fail their tasks and abort their host calls. `size` (2) workers stay once started, up to `maxSize` (6) while all are busy; the queue holds 1,000 tasks. Host answers must be primitives (structured data crosses as a JSON string, since a JS object would reach Lua as a live proxy), and no answer (`undefined` or `null`) reaches Lua as `nil`, never wasmoon's truthy `null` userdata; inputs, results, logs, and regex results are capped. ### Routes

Registration order in `createServerContext`:

1. `onError` (`HTTPException` responses pass through; maintenance and a closed resource store answer 503 with `Retry-After`; other errors are a 500 `Internal Server Error`). Shutdown admission middleware runs before body parsing, tracks resource handlers (`/api/resources`, `/api/llm-secrets`, `/api/chats/search`, `/api/memory/tasks`, and `/api/chat-checkpoints`), refuses new resource, message search, credential, backup, module import, CharX import, Realm import, token, and request history requests with 503, and adds `Connection: close` to every response during shutdown; every `/api/request-history` answer gets `Cache-Control: no-store` there, so a 429 or 413 carries it too.
2. `bodyLimit` (100 MiB, 413 `{error:"Request body too large"}`), skipped for `POST /api/backups/import`, `POST /api/backups/import-upstream/prepare`, `POST /api/import/module`, and `POST /api/import/charx`, which stream their bodies to disk under their own cap, and for `POST /api/import/realm` and its `/commit` and `/cancel`, which cap their `{ id }` or `{ token }` body at 4 KiB, and for `POST /api/chat-checkpoints/*` and `PUT /api/chat-checkpoints/policy`, which cap their bodies at 16 KiB after authentication, and for `POST /api/chats/search`, which caps its body at 4 KiB of received bytes, and for `POST /api/tokens/count` and `/api/tokens/encode`, which cap theirs at 2 MiB after authentication. A route that caps its own body with `bodyLimit` uses the shared helper in `server/src/routes/limitedBody.ts`: a body over the cap answers 413, and a request stream that fails while the limiter reads it answers 400, never the app's 500.
3. `GET /` and `GET /index.html` (one shared handler), then the same handler for the client's screen routes: a `GET *` handler serves it when `isClientRoutePath` (`shared/routes.ts`: first segment `chat`, `playground`, `realm`, `characters`, or `settings`) matches and passes every other path on ([URL routes](app-shell.md)).
4. `serveStatic` for every other GET/HEAD.
5. The routes below.

Routing is non-strict (a trailing slash matches).

"+ epoch" means the `x-resource-epoch` header must name the current database epoch (412 `{ error: "EpochMismatch", epoch }` otherwise). Mutations answer 503 with `Retry-After` while a restore or an import runs. During shutdown, new resource requests (including reads), backup requests, and module and CharX imports also answer 503 with `Retry-After`; a typed store-closed error maps to the same retryable response. Every `/api/resources` and `/api/llm-secrets` response is `Cache-Control: no-store`. Every read route (`/api/resources?kinds=`, `/api/resources/read`, `/api/resources/:kind`, `/api/resources/:kind/:id`) and the PUT response answer a kind with `project` in its projected form: `llmSecrets` is masked.

The resource, proxy, and job rows marked "2000/min" share one limiter; `test_auth` has its own. Login has its own. The storage rows marked "2000/min (storage)" have their own bucket with the same threshold, so an asset burst (a module import or export) cannot starve resource sync.

`/api/asset/*` answers with `Content-Security-Policy: sandbox; default-src 'none'; img-src 'self' data:; media-src 'self'; style-src 'unsafe-inline'`, `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: same-origin`, `Accept-Ranges: bytes`, and `Content-Disposition: inline`, including errors and 304s. Byte responses and 304s use the extension's MIME from `shared/assetMime.ts` (unknown types: `application/octet-stream`); `html`, `htm`, `xhtml`, `xml`, `js`, and `mjs` use `attachment` and `application/octet-stream`, while SVG stays inline under the CSP sandbox. Successful responses and 304s are `Cache-Control: private, no-cache` with a weak ETag unless the content name is verified against the stat of the handle supplying the bytes. Verified names use `Cache-Control: private, max-age=31536000, immutable` and the strong ETag `"sha256-<hex>"` on 200/206 responses. A verified name accepts either its strong tag or its current weak stat tag in `If-None-Match`; a 304 carries the tag that matched and the immutable Cache-Control, so revalidating an earlier weak-tagged copy upgrades its caching policy. Comparison is weak for both tag forms, lists, whitespace, and a lone `*`; a strong-tag match takes precedence when both tags match. The weak ETag uses size, nanosecond mtime, and inode; a matching `If-None-Match` takes precedence over Range. Errors remain `no-store`. A single satisfiable `bytes=` range gets 206 with `Content-Range` and its length; an unsatisfiable range gets 416 with `Content-Range: bytes */<size>`. HEAD ignores Range and returns the full length (or 304); empty files ignore Range and return an empty 200.

## Flows

Boot:

1. `pnpm run server` runs `node server/src/main.ts`.
2. `createServerContext` creates `save/` if missing. `createAuthStore` durably creates `save/server/`, loads the three-state `password` (missing, set, or empty/damaged), seeds it from a validated `RISU_PASSWORD_SHA256` only when missing, and loads `known_public_key_hashes.json` (malformed content is renamed aside with a warning and no keys are loaded). `registerStorageRoutes` recreates `save/.tmp/` empty.
3. `serve()` listens on HTTPS or HTTP. A listen error (e.g. `EADDRINUSE`) logs and exits 1.

Client detection:

1. `GET /`, `GET /index.html`, and the client route paths inject `__NODE__`, which makes `isNodeServer` true in the client. Without it the client shows only the `NodeServerRequired` notice, so no route may serve `index.html` raw.
2. The client always uses this server (`storage/assetClient.ts` for assets, `storage/serverAuth.ts` for auth).

Development (`pnpm dev`, or `pnpm dev:human` / `pnpm dev:agent`, which start both processes: [build-test-platforms](build-test-platforms.md)):

1. Run `pnpm run server` and `pnpm dev` side by side. The Vite dev server (port 5174) injects `__NODE__` into its own `index.html` (plugin `risu-node-flag`, serve only) and proxies `/api`, `/proxy`, `/proxy2`, and `/hub-proxy` (including the WS upgrade) to `RISU_DEV_SERVER` (default `http://localhost:6001`; set `https://...` when the server found a certificate).
2. The dev origin keeps its own IndexedDB `DPoPDB` key pair, so it logs in separately from the server origin.
3. The server sees every proxied request as coming from the Vite process, so all dev clients share one rate-limit bucket (including the 10-per-30 s login limiter). The dev proxy does not add `X-Forwarded-For`, so `TRUST_PROXY` alone does not separate them.
4. The client's auth (`serverAuth.ts`) needs `crypto.subtle`, so open the dev server via `localhost` (a plain-HTTP LAN address is not a secure context).

Auth:

1. The client's auth check (`serverAuth.ts`) creates an ES256 JWT (P-256, 5-minute expiry, public JWK). The key pair is kept in IndexedDB `DPoPDB`, entry `node`.
2. It calls `/api/test_auth`, then either `/api/set_password` followed by `/api/login` with the same digest (first run, so the first request is already authorized) or `/api/login`. One check runs at a time for the whole tab (one auth state).
3. Once logged in, the server knows the key hash, and later requests only send the JWT.

Resources and saving (client side: `persistence.md`):

1. The client reads every kind and every chat with one `GET /api/resources?kinds=...&chats=1` at boot and keeps the epoch.
2. Its save adapter sends one `/api/resources/batch` per save cycle: resource ops, chat groups (one per chat: its ops on the chat revision they were based on), and chat reorders. All of them are validated and normalized first, then every base revision is compared inside one transaction; any conflict rolls the whole batch back and the 409 lists all of them (resource conflicts, `kind: "chat"`, `kind: "chatOrder"`).
3. Chat groups: `create` (first op; the chat with its messages, inserted in the order at `index`), `delete` (alone), `replace`, `meta` (`set`/`unset` per field; `merge` adds entries to a map field of `CHAT_META_MERGE_KEYS` (`toolCalls`, `GLGlobalVariables`, `scriptstate`) as stored and `mergeUnset` removes entry ids from it first, so writers of different entries keep each other's), `append` (at the end, the start, or after a message id), `setMessage` (the whole row), `patchMessage` (`set`/`unset` of some fields onto the stored row; `chatId` and `__proto__` refused, `role`/`data` never unset, a `translation` field ignored, no generation, at least one field), `setText`, `remove`, `begin`, `setTranslation`. A group result carries the chat's new revision, the ids of messages it created, the outcome of each generation-carrying op (`applied`, `duplicate`, `ignored`), the outcome of each `setTranslation` (`translations`: `applied`, or `ignored` when the message's text no longer matches the translation's `sourceHash`; `null` always clears), and `stale: true` when it applied on an older revision. `setMessage` and `patchMessage` never change a stored `translation`: the stored one (or its absence) replaces the sent message's. `setTranslation` leaves the generation fence alone.
4. Deleting a character deletes its chats and chat order in the same transaction.
5. Inlays and plugin permission grants use the single-record routes.

Checkpoint load:

1. After authentication and bounded body parsing, check maintenance and epoch, then refuse if any job owns the chat slot or any of its messages. Compose the checkpoint against the current chat (captured story state plus current kept fields/toggles); refuse a missing checkpoint/chat or a `chatBaseRevision` different from the current token before writing anything.
2. Call the context's `memoryTasks.acquireSummaryWriter({ chaId: characterId, chatId }, "checkpoint-load")` without awaiting: the lease immediately ends a running memory task `cancelled`/`writerLease` and prevents another summary writer from starting.
3. In the same synchronous call, `applyChanges` applies one `replace` group with a fresh UUID. Its `inTransaction.before` saves a safety checkpoint named `Before loading <checkpoint name>` (truncated by the store). Its `after` copies the new chat revision into the floor, resets an existing policy's `lastAutoTurns` to the loaded checkpoint's `userTurns` (no policy is created), and prunes safety checkpoints beyond `SAFETY_KEEP` (3). Any conflict, callback throw, or returned thenable rolls back the chat, safety checkpoint, floor, baseline, and prune; write counts, source generation, and feed notices advance only on commit.
4. In `finally`, attach a continuation to release the promised lease whether committed or rolled back. A committed replace advances the chat source generation once and invalidates the memory task's old retained input and pending manual request. Answer `{ epoch, chatRevision, safety }`. A lost answer is not retried: the client must re-read the chat and report the outcome as unknown. Queued groups based below the floor conflict; remembered group ids still receive their recorded answers.

Automatic checkpoint:

1. After a send, continue, reroll, or group job ends with the final `done` terminal, `finalize` invokes `onChatJobDone` after releasing locks and the chat slot, sending hydration and the terminal, and resolving `finished`. The app calls `checkpoints.autoSave`; aborts, errors, commands, and previews do not invoke it. A throw only logs `checkpoint.auto` and cannot change the terminal or the job's end.
2. Return if the chat is busy (a job slot or any message lock), has no policy, or its stored data is missing. Read the stored chat and count messages whose `role === "user"`. If this count fell below `lastAutoTurns`, reset the baseline to this count and save nothing. Otherwise save when the baseline is null or at least `autoEvery` user turns have passed. A new policy therefore saves on the next qualifying done job; rerolls and continues normally add no user turn.
3. Save the checkpoint named `Auto` with kind `auto`, set the baseline to the saved `userTurns`, and prune autos beyond the newest `autoKeep` in one `applyChanges({}, { inTransaction: { before } })` transaction. A throw rolls all three back; checkpoint writes count toward `writeCount` at commit, and the empty batch publishes no feed event. No restore floor changes and no memory-writer lease is acquired.
4. Capture the reply and memory committed at that moment. The job's own memory and final reply writes have committed; no memory task or detached translation is awaited, so either may write later. A checkpoint load resets an existing policy's baseline to the loaded checkpoint's user turns, so counting resumes from that state.

Snapshots and restore:

1. `startBackgroundTasks` starts a timer (10 minutes). A tick takes a snapshot only when committed writes happened since the last one: `backupTo` writes `.<name>.tmp` and switches it to rollback-journal mode; the manager flushes the completed copy through a writable handle, renames it to `resources-<UTC yyyymmddThhmmssmmmZ>-<8 hex>.sqlite`, and syncs `save/backups/` before reporting success; the newest 20 are kept.
2. Restore (`/api/backups/:id/restore`) runs under maintenance: epoch check, `readSnapshot` (integrity check, layout version, real `resources`/`meta`/`chats`/`messages`/`chatOrders` tables with this store's columns and an epoch, then every row: registered kind at its schema version (rows of a retired kind are skipped), valid id, singleton rules, unique kind and id, JSON the kind's normalizer accepts; every chat, message, fence, and order row, with each chat's parent character and each order a permutation of its chats; positions compacted; the checkpoint tables as one optional group: all four absent restores none, some absent or any with other columns is refused, and every checkpoint, ref, page, and policy row is checked (a chat the snapshot holds, a valid id unique in its chat, a known kind, the name and policy limits, refs exactly the hashes its `pages` and `fields` name, each page's hash the SHA-256 of its text, message pages lists of messages the message normalizer accepts with ids unique across the checkpoint, field pages chat metadata the meta normalizer accepts, no `toggle_` entry in the `GLGlobalVariables` page); pages no ref names are dropped), a safety snapshot, a second epoch check, then `replaceAll` in one transaction with a new random epoch; it restores the checkpoints, their pages (text as stored), and the policies on the new chat `seq`s, so a checkpoint saved after the snapshot is gone and the safety snapshot still holds it. Every token issued before is stale afterwards.

Backup archives:

1. The container is concatenated records of `u32le nameLength`, the UTF-8 name, `u32le dataLength`, and the bytes. Version 2 starts with `manifest.json` (`{ version: 2, createdAt, partial, assets, missing }`), then `resources.sqlite` (a fresh copy), then each asset under its full key `assets/<name>`.
2. Export takes the database copy first (the staged copy then loses its `llmSecrets` row and is `VACUUM`ed, so the archive carries no LLM credential; snapshots on the server keep it), then selects assets: every file of `save/assets`, explicit `partial` keys, or, for `partial: true`, `shared/backups.ts` `selectPartialBackupAssets` over that same staged database's `characters`, `personas`, `ui`, `characterOrder`, and `presets` rows. The direct query parses only those rows, without `readSnapshot` or chat reads. Thus partial profile selection follows the archived resource state even when another writer changed an image after the client's inventory. Requested or selected keys that cannot resolve to storage or have no eligible file enter `missing`; the partial-key and archive-record caps still apply. The copy lives in `save/.tmp/export-<uuid>/` and is removed once, and the tracked lifetime released, when the stream ends or is cancelled, or when the request signal aborts: its listener returns the generator (as `http/fileImport.ts` does), whether it never started, waits at a `yield`, or is inside a step, so a client that leaves while the adapter has stopped pulling is cleaned up too. An asset listed in the manifest that can no longer be read fails the stream.
3. Import authenticates and checks the epoch before reading the body, spools it to `save/.tmp/import-<uuid>/` with a byte count, then validates the whole archive before writing anything: manifest first and unique, the declared assets exactly the asset records, exactly one `resources.sqlite` that `readSnapshot` accepts, only `assets/` keys. Refused: a Risu Account archive (`encryption.risudat`), an upstream RisuAI backup (`database.risudat`: upstream's own and this fork's older upstream-format backups; the message says to choose it again so it is imported as one, which only a client older than the upstream import still posts here), a truncated or malformed one. `coldstorage_*.json` records are ignored. Then, under maintenance: epoch check, safety snapshot, assets that do not exist yet are flushed and added by hard link (existing files are never overwritten), one assets directory sync when anything was added, then the adjacent synchronous epoch check and `replaceAll`. One import at a time.
4. Upstream RisuAI backups (`data/upstream/archive.ts` `planUpstreamArchive(handle, savePath)`) are classified from the index alone; the database is not read. Upstream writes basenames only (`.png` assets, then cold-storage payloads, then `encryption.risudat` if any, then `database.risudat`), and no rule depends on that order. Refused with `ArchiveRejectedError`, in this order: a malformed container; `encryption.risudat` (a Risu Account backup, decryptable only on risuai.xyz; the message says to export an unencrypted backup there); `manifest.json` or `resources.sqlite` (a version-2 archive: use the regular import); a duplicate name (a doubled `database.risudat` included); a name with `/` or `\`; no `database.risudat`. The rest is sorted: `database.risudat` is the database; `coldstorage_<uuid>.json` and the bare `<uuid>.json` of builds v2026.4.120 to v2026.6.215 (UUID-shaped, hex in either case, upstream's `getColdStorageBackupKey` pattern) are cold storage, grouped by the UUID as written with each key's records in archive order; every other name is an asset under `assets/<name>`, with its `resolveStorageKey` target, or `ignored` (`invalidAssetKey`) when the key has no storage location. `readColdRecord` parses one payload under a cap (64 MiB by default) as upstream does (`TextDecoder`, `JSON.parse`), classifies any JSON value as `data` (an array or an object with `character` or `message`) or `plugin`, and reports `tooLarge` or `invalidJson` instead of throwing; `readColdEntry` returns a key's last accepted data record as `value` and its last plugin record as `pluginValue` (each falling back to the other), as upstream's restore writes data records in archive order and restores plugin records afterwards.
5. The upstream import (`routes/backupsUpstream.ts`, two steps so the user reads the report before anything is replaced). The prepare, `POST /api/backups/import-upstream/prepare`, runs `serveFileImport` on the backup import's slot (one archive import at a time): auth, 413 for a declared length over `maxImportBytes`, 409 while another import runs, 503 during maintenance, then (`preflight`, before the body is read) 412 for another epoch and 409 `Another RisuAI backup import is waiting for its answer` while a prepared import waits. The body is spooled to `save/.tmp/upstream-<uuid>/archive.bin` and classified on the serving thread (`planUpstreamArchive`), so a refused archive, a Risu Account backup included, is a 400 before anything streams. The rest runs in one `worker_threads` worker per import under a heap limit (`importRunner.ts`; the event loop stays free): decode, cold-storage reads, conversion, the staged store and its `readSnapshot` check, and every asset extracted into the staging folder, so the commit only links. The 200 answer is NDJSON: `{ phase, done, total }` lines (only the latest is sent while the client reads), then `{ token, report, selection }` once the import is staged (added to `upstreamStaging` first, then the folder kept and the slot freed), or one `{ error }` line for a backup the worker refused or could not finish (the headers are sent by then, so this is no status code). The epoch and `writeCount()` are recorded when the prepare ends. A client that leaves, or shutdown, terminates the worker; the folder is removed after it has ended. The live store is never written.
6. The prepared import waits outside the slot for at most `UPSTREAM_STAGED_TTL_MS` (10 minutes); expiry, `POST .../cancel` (204 always), and shutdown remove its folder. The commit, `POST .../commit` with `{ token, acceptWrites? }`: 400 for an invalid body; 404 `Import expired`; 409 while another import runs, 503 during maintenance, and 412 for another epoch (the tab's or the prepare's) leave the import waiting. Then the changed-since-review check, before maintenance so a refusal ends no job: when `writeCount()` moved since the prepare and `acceptWrites` is not exactly that difference, `409 { error: "changedSinceReview", writes }` and the import keeps waiting. It is not repeated under the lock, where the jobs' abort checkpoints count as writes; what lands before the gate closes is in the safety snapshot. Then the import is taken, the slot held, and under `withMaintenance`: the epoch, `readSnapshot` of the staged store on the serving thread (writes are closed anyway; a failure is a 400, and the jobs the maintenance ended stay ended), then `restoreValidated` (safety snapshot, assets linked where no file exists, epoch, `replaceAll`). The answer is `{ epoch, assetsWritten, assetsSkipped, selection }` with the `lifecycle` event `import`; the folder is removed whatever happened.
7. The upstream export (`routes/backupsUpstreamExport.ts`, two steps so the tab shows the report before the download; it writes nothing live and takes no import slot). The prepare, `POST /api/backups/export-upstream/prepare`, checks the body (400), shutdown (503), and the exports waiting or being prepared (409 at `MAX_UPSTREAM_EXPORTS_STAGED`), then, tracked by `snapshots.track` up to the token's hand-over (so shutdown waits for a refusal's removal too): `snapshots.exclusive(() => store.backupTo(...))` into `save/.tmp/export-upstream-<uuid>/`, the asset inventory (`listAssetKeys`, after the copy), then the export worker (`data/upstream/exportRunner.ts`, heap capped by `RISU_UPSTREAM_EXPORT_HEAP_MB`): `readSnapshotFile` of the copy, `buildUpstreamDatabase` (`data/upstream/exportDatabase.ts`, with `now`), `encodeUpstreamDatabase`, the size check, and `database.risudat` written to the folder; the request's signal and the staging's shutdown signal terminate it (a client gone gets the version-2 export's 400 `Request aborted`, shutdown 503), and the folder is removed only after the worker has ended. The copy (it holds every credential) is removed after the worker, and a reference absent from the inventory is reported missing. Each referenced asset becomes a record named by its key without `assets/` when such a record can hold the name (`upstreamAssetRecordName`: no `/` or `\`, not a name upstream's restore reads as its database, account marker, or cold storage, not a version-2 record name, and unchanged by upstream's default `TextDecoder`: no leading byte order mark or lone surrogate; otherwise reported as `asset-names`) and its file is a regular file of at most 4 GiB (otherwise reported missing). 413 when the database or the record count does not fit the format, or the database outgrows the worker's heap (the message names `RISU_UPSTREAM_EXPORT_HEAP_MB`). The export is added to `upstreamExportStaging` and the answer is `{ token, report }`; a client gone meanwhile gets nothing staged. The download, `GET .../download?token=`, takes the export out (the token is used up; 404 `Export expired` for one that names none), then streams with the version-2 export's lifetime: one record per asset, then `database.risudat` last; the folder is removed when the stream ends, is cancelled, or the client leaves, and shutdown waits for it. Expiry (`UPSTREAM_EXPORT_STAGED_TTL_MS`), `POST .../cancel`, and shutdown remove a waiting export.

Module import (`POST /api/import/module`, `routes/importModule.ts`):

1. Authenticated before the body is read; no epoch (it writes only content-addressed files, and the client adds the module record). Refused before the body is read: a declared length over `maxImportBytes` (413 `File too large`), another module or CharX import (409 `Another import is running`: the two routes share one slot), maintenance (503 `Maintenance in progress`, `Retry-After: 5`), no body (400 `Module body required`). Then the lifetime is tracked (503 once shutdown stopped admissions) and the body spooled to `save/.tmp/module-<uuid>/module.risum` under `maxImportBytes` (413 past it).
2. The whole file is validated before anything is written, read from the file by offset (memory holds the main record only): the header; the main record (at most 64 MiB, rpack-decoded in place, decoded as UTF-8 the way the client's `Buffer.toString` does, invalid bytes replaced and a BOM kept, then JSON `{ type: "risuModule", module }` whose `assets`, if any, is a list of lists); then each record's mark and length, skipping its bytes, up to the end mark. Bytes after the end mark are ignored and fewer records than `module.assets` are accepted (client parity, STRUCTURE D5). More records than assets, an unknown mark, no end mark, a short file, or a bad header or main record is 400 `Invalid module file`; a record over 100 MiB is 413 `Asset too large`. A client gone by then is 400 `Request aborted`.
3. The 200 answer is `application/x-ndjson` and `no-store`. Per record, one buffer: read, rpack-decoded in place, SHA-256 hex, key `assets/<hex>.png` (the client's `saveAsset` key, never sniffed; a zero-length record included); an existing file is skipped, otherwise `writeStorageFile` under `gate.enter()` for that write only; `module.assets[i][1]` takes the key. `{ done, total }` (records) at most every 200 ms and for the last record, then the `lifecycle` event `moduleImport` and `{ module, assetsWritten, assetsSkipped }`.
4. Once the stream has started, every failure (a maintenance that began meanwhile, a read or write error) is one last `{ error }` line (`Maintenance in progress` or `Import failed`, never a path), and nothing more is written; files written before it stay as content-addressed orphans and the client adds no record. A client gone mid-stream stops the writes at the next record.
5. One memoized finalizer (file closed, staging folder removed, slot freed, lifetime released) runs when a step before the stream fails, before the last line (so an import started on reading it is admitted), when the stream is cancelled, or when the request signal aborts: its listener returns the generator, whether it never started, waits at a `yield`, or is inside a step. Steps 1 and 5 are `http/fileImport.ts` `serveFileImport`, shared with the CharX import.

CharX import (`POST /api/import/charx`, `routes/importCharx.ts`):

1. The module import's steps 1 and 5 (`serveFileImport`): authenticated before the body is read, no epoch (only content-addressed files are written; the client adds the character, or the module of `importModule`'s `.charx` branch). Refused before the body is read: 413 `File too large`, 409 `Another import is running` (a module or CharX import holds the shared slot), 503 `Maintenance in progress` with `Retry-After: 5`, 400 `CharX body required`. The body is spooled to `save/.tmp/charx-<uuid>/file.charx` under `maxImportBytes` (413 past it); a client gone by the end of validation is 400 `Request aborted`.
2. The zip's structure is validated from the file before anything is written, by its central directory (never by scanning for signatures: `CharXWriter`'s stored entries can hold them; `shared/charxImport.ts`): the end record, found from the file's end over at most a 64 KiB comment (a split archive refused), then the zip64 locator and end record when a field holds its zip64 marker (the record at the locator's offset, or just before the locator for a prefixed file; without a locator the 32-bit fields stand); the prefix before the zip (a `charxJpeg`'s JPEG) is the central directory's position less its size and offset (mod 2^32 without zip64: fflate's writer wraps offsets past 4 GiB); the central directory (at most 64 MiB and 200,000 records), walked by its size, not the end record's count (fflate wraps it), each record's sizes and offset taking their zip64 values when marked, and each record on disk 0 (a disk number start of `0xFFFF` is the zip64 marker: refused when the record's zip64 extra field names another disk, accepted as disk 0 when the field holds no disk number); then every local header, walked in file order from the first entry, matched to the unconsumed record of its offset (mod 2^32) and name bytes, with the same method, its bytes (the central directory's compressed size, or the local header's when it declares one without a data descriptor) and its data descriptor (12 or 16 bytes, 20 or 24 for a zip64 entry) before the central directory. An entry on another disk, an encrypted entry, a method other than stored or deflated on an entry its declared sizes do not exclude, a mismatch, a record past its bounds, and a file without a `card.json` entry are 400 `Invalid character file` (a plain JPEG, a NovelAI zip, a truncated file), with nothing written.
3. The 200 answer is `application/x-ndjson` and `no-store`. Entries in file order, by the shared entry rules: `card.json` is the card's text (UTF-8, as `TextDecoder` reads it), `module.risum` its bytes base64-encoded, any other `.json` (the exporter's `x_meta/*.json`) is not read, every other entry is an asset: read by its offset, decoded (stored as read; deflated through Node's async `zlib.inflateRaw` capped at 50 MiB), SHA-256 hex, key `assets/<hex>.png` (the client's `saveAsset` key, never sniffed); an existing file is skipped, otherwise `writeStorageFile` under `gate.enter()` for that write only; `assets[entryName]` takes the key. An entry whose local header declares an uncompressed size of at least 50 MiB without a data descriptor (the in-tab rule), whose central-directory uncompressed size is over 50 MiB, or whose compressed size is over 51 MiB is never read; one that decodes past 50 MiB is dropped: either is listed in `excluded` and written nowhere (an excluded `card.json` or `module.risum` leaves `card` or `moduleData` null). `{ done, total }` (the asset entries not excluded before reading, an exact total from the validation; one dropped while decoding counts as done) at most every 200 ms and for the last, then the `lifecycle` event `charxImport` and `{ card, moduleData, assets, excluded }`.
4. Once the stream has started, every failure is one last `{ error }` line: `Invalid character file` for a corrupt deflate stream, `Maintenance in progress` for a maintenance that began meanwhile, `Import failed` for a read or write error (logged; never a path); nothing more is written, and files written before it stay as content-addressed orphans. A client gone mid-stream stops at the next entry and before the next write.

Realm import (`routes/importRealm.ts`), in two steps so that the tab's questions about the card (its `lowLevelAccess`, an rcc card's password) come before anything is written. The prepare, `POST /api/import/realm`:

1. `serveFileImport` with the download as its `source`: authenticated first (no body-limit middleware reads the body before that); 409 `Another import is running` (the slot shared with the module and CharX imports) and 503 `Maintenance in progress` before anything else; then, holding the slot, 409 `Too many imports are waiting` while `MAX_REALM_STAGED` (4) staged imports wait (before the body is read or Realm contacted), and the route reads the body itself: JSON `{ id }`, at most 4 KiB (413 `Request body too large` past it), with a Realm id (`REALM_ID_PATTERN`; anything else is 400 `Invalid Realm id`).
2. The download: `GET <realm origin>/api/v1/download/dynamic/<id>?cors=true` with only `x-risu-api-version: 4` (never a URL or header from the request), aborted when the client disconnects. Redirects are followed by hand, at most 3, only to the Realm origin or an HTTPS host under `risuai.net`/`risuai.xyz` on the default port. The headers must arrive within 30 s (redirects included) and the body may not stall for 60 s; there is no total deadline. A Realm answer other than 200 is a 502 with Realm's text (its first 4 KiB, what arrived of them within 10 s, or `Realm answered <status>`); a refused redirect, a timeout, a stall, or a network failure is a 502 `Realm download failed` (logged).
3. The answer's `content-type` (parameters dropped, any case) selects the reader: `image/png` the PNG reader, `application/zip` or `application/charx` the CharX reader, anything else the legacy JSON pass-through. The body is spooled to `save/.tmp/realm-<uuid>/realm.file` under `maxImportBytes` (16 MiB for JSON), counting decoded bytes; an answer without a content encoding whose `content-length` is over the cap is a 413 `File too large` before its body is read.
4. Validation and the card's parts before anything is written: `planCharxFile` (the CharX import's step 2) and `readCharxCardParts` (the `card.json` text and the `module.risum` bytes by the CharX entry rules), or `planPngFile` (the signature, every chunk within the file, at most 1,000,000 chunks and 200,000 asset chunks, card and asset chunks at most `MAX_PNG_TEXT_CHUNK_BYTES`, and the card text, `ccv3` else `chara` by the tab's 5 MiB keep rule); a failure, or an empty or unreadable card, is 400 `Invalid character file`.
5. The answer, one NDJSON line: the file is staged (`RealmStaging.add`: the folder kept with the plan, without the card text) and the slot is free again before the line is sent: `{ kind: "charx", token, card, moduleData }` or `{ kind: "png", token, card }`; for JSON, `{ kind: "json", body }` with nothing staged (its lifecycle event `realmImport` is recorded here). A store closed by shutdown meanwhile is one `{ error: "The server is shutting down" }` line. A client that leaves after the file is staged leaves it to expire.

The staged import waits outside the slot, at most `REALM_STAGED_TTL_MS` (10 minutes) from the prepare's answer; expiry, cancel, and shutdown (`realmStaging.close()` in `beginShutdown` and `dispose`) remove its folder. Maintenance leaves it (a restore replaces the database, not `save/.tmp`, and its assets are content-addressed); what a crash leaves is emptied at the next start. The commit, `POST /api/import/realm/commit` with `{ token }` (`serveStagedImport`):

1. Authenticated, then the body (as the prepare's: 413 past 4 KiB, 400 `Invalid import token` without a UUID `token`); 404 `Import expired` for a token that names no waiting import (expired, cancelled, or committed); 409 `Another import is running` and 503 `Maintenance in progress` leave the staged import waiting.
2. Admitted (the slot taken, the lifetime tracked), the staged import is taken out of the store (its timer stopped) and its file opened; the finalizer removes its folder.
3. The NDJSON answer: for a CharX file, the CharX import's lines without the card and module entries and with `{ kind: "charx", assets, excluded }` as the result; for a PNG, `{ done, total }` lines as the `chara-ext-asset_*` chunks are stored (`assets/<sha256>.png`, as the CharX assets), then the trimmed image (the signature and every non-`tEXt` chunk through `IEND`, copied to a staged file while hashed and renamed into place) and `{ kind: "png", image, assets }`. The lifecycle event is `realmImport`. Failures after the stream started are the CharX import's step 4.

The cancel, `POST /api/import/realm/cancel` with `{ token }`: authenticated, the body read as the commit's, the staged import removed; 204 whether it still waited or not.

Shutdown:

1. `beginShutdown()` sets the shutdown flag, closes generation admission and aborts every job (their 5 s deadline starts here), ends every server translation, removes the upgrade listener, stops the snapshot timer and backup admissions, and disposes proxy jobs and limiters. Middleware refuses new resource, backup, module import, CharX import, and Realm import (prepare, commit, cancel) requests with 503 plus `Retry-After: 5`, and the staged Realm imports waiting for a commit are removed (`realmStaging.close()`; `dispose` awaits it after the admitted operations); a running upstream prepare is aborted at once (`upstreamStaging.close()`: its worker is terminated and its folder removed, so `snapshots.stop()` does not wait out the HTTP drain for a conversion) and the prepared upstream imports are removed; every response during shutdown carries `Connection: close`, including a request admitted before the signal. Resource handlers are tracked before body parsing or auth and retain access to the open store. Backup operations retain their existing admission boundary.
2. `main.ts` awaits `server.close()` for at most 8 seconds, then calls `closeAllConnections()` before `dispose()`. Disconnects abort unfinished body reads and export streams; `dispose()` waits for the generation jobs to end (already bounded by their deadline), disposes the script workers, and awaits admitted handlers and backup cleanup before closing the database. The deadline leaves cleanup time within Docker's default 10-second stop timeout.
3. In-process callers use `dispose()` alone: it runs the begin step and waits for the jobs and admitted operations before closing.

Restore and import (`withMaintenance`): the `onMaintenance` listeners run under the snapshot lock while writes are still open. The jobs' listener closes generation admission, aborts every job with `maintenance`, and waits for their end, so an abort checkpoint lands in the old database (and in the safety snapshot); the translation runner's listener ends every server translation (none writes after); then the gate closes and the replacement runs. Admission reopens when the maintenance ends. A leftover store access raises `ResourceStoreClosedError`, mapped by both resource routes and `onError` to 503 with `Retry-After`, including reads.

Proxying:

- The client sends `risu-url` and `risu-header` (encoded JSON) to same-origin `/proxy2`.
- The request body is forwarded as raw bytes. `HEAD` fetches upstream with GET and returns headers only.
- Upstream request headers (`buildUpstreamHeaders`, case-insensitive):
  - The decoded `risu-header` must be a JSON object. Anything else is a 500.
  - Stripped: `host`, `connection`, `keep-alive`, `proxy-connection`, `transfer-encoding`, `te`, `trailer`, `upgrade`, `content-length`, `risu-auth`, and every field named in `Connection`. A `Connection: authorization` therefore drops `Authorization`.
  - `x-forwarded-for` is added only when absent.
- `/hub-proxy` reaches only the hub (`https://sv.risuai.xyz`; the former `x-risu-node-path` target override is gone, and the header is still stripped). It forwards the incoming headers minus `host`, `connection`, `content-length`, `x-risu-node-path`, and `risu-auth`, and sets `origin`. It follows one redirect within the hub's origin; a redirect elsewhere (the hub's documentation links) is answered to the browser as it is.
- `/proxy` and `/proxy2` response headers drop CSP, `clear-site-data`, `cache-control`, `content-encoding`, `content-length`, and `transfer-encoding`.
- On `/proxy` and `/proxy2`, `risu-timeout-ms` covers the whole exchange (`/hub-proxy` has no timeout):
  - Before upstream headers it returns 504 `{error}`.
  - Mid-stream it ends the response cleanly.
- A client disconnect aborts the upstream fetch on `/proxy`, `/proxy2`, and `/hub-proxy`.
- Node local-network streaming uses the job and WebSocket protocol with events `job_accepted`, `upstream_headers`, `chunk` (base64), `error`, `done`, and `ping`. Heartbeat is 5–60 s. Jobs have a 30 s done-grace period.
- Stream-job targets must pass `sanitizeTargetUrl`/`isLocalNetworkHost` (`ipaddr.js` ranges):
  - allowed: `localhost` and `*.local`;
  - IPv4 in 10/8, 172.16/12, 192.168/16, 127/8, 0/8, or 169.254/16;
  - IPv6 in fc00::/7 or fe80::/10, `::1`, and IPv4-mapped forms of those IPv4 ranges (bracketed URL hosts are accepted).
  - Single-label hosts other than `localhost` are rejected, although the client's `localNetwork.ts` treats them as local. The client also rejects IPv4-mapped IPv6.
- Stream-job forwarded headers are lowercased, then `risu-auth`, `risu-timeout-ms`, `host`, `connection`, and `content-length` are dropped.
- DELETE, the deadline, GC cleanup, and `dispose()` abort the job's upstream request and response even after upstream headers arrived. Deadline cancellation can deliver an `error` event to connected clients (the former client helper showed every 504 as a timeout). DELETE, GC cleanup, and `dispose()` close the WebSockets without guaranteeing a final event.

### Changes from the former Express server

- `/proxy` and `/proxy2` POST forward raw bytes. Express re-serialized parsed JSON and turned urlencoded bodies into `"{}"`.
- `risu-auth` is never forwarded upstream by `/proxy`, `/proxy2`, or `/hub-proxy`, and header stripping is case-insensitive.
- `HEAD` on `/proxy` and `/proxy2` returns headers only and closes the upstream.
- The proxy timeout spans the streamed body; a mid-stream timeout ends the response cleanly.
- A client disconnect aborts `/proxy`, `/proxy2`, and `/hub-proxy` upstreams.
- Batch `/api/remove` works. A missing `file-path` is a 400; Express never answered it.
- JSON bodies: malformed, whitespace-only, or primitive JSON is a 400. `set_password` persists before updating memory. Zero-length `/api/write` bodies are written.
- Stream-job targets use `ipaddr.js` ranges, which adds bracketed and IPv4-mapped IPv6 literals. Stream-job DELETE, deadline, GC, and dispose stop active upstreams.
- Static files use `@hono/node-server` `serveStatic`:
  - supported: ranges and `Last-Modified`;
  - no ETag, conditional requests, or `Cache-Control`;
  - a directory path serves its `index.html`, where Express had `index: false`.
- `/api/read` has no ranges or ETag.
- No request decompression or charset-aware decoding; JSON text is read as UTF-8.
- `/api/crypto` and `already set` are `text/plain`, not `text/html`. The 404 and 500 bodies are plain text.
- Paths are case-sensitive, a trailing slash is tolerated, and there is no automatic `OPTIONS`.
- The display transform's Lua cost, measured at the closeout (`util/playwright/measureTransformLua.mjs`, three logged runs at commit `2f658598` plus the closeout's changes, medians of each: the server in process with the real store and workers, a 200-message chat with one module trigger `listenEdit("editDisplay", ...)`, every target uncached and checked): a warm 200-target render in the tab's four concurrent chunks takes 142–145 ms with the module (0.71–0.73 ms per target) and 68–70 ms without it (0.34–0.35 ms); a one-target request takes 2.8 ms with it and 1.7–1.8 ms without. Each Lua trigger invocation of each target runs on its own engine from the worker's prepared pool. The cold first render (the workers booting) took 288–306 ms. Far below the 50 ms per target that would call for engine reuse per batch.

## State

Disk, under `save/`:

- `server/password`: the client-side SHA-256 digest via `/api/crypto`. Only a missing file opens setup (`ENOENT`; other read errors throw). An empty or whitespace-only file logs a warning and keeps setup and password login closed until the operator fixes or deletes it; registered JWT keys still work, and `/api/test_auth` checks them rather than returning `unset`. `RISU_PASSWORD_SHA256` can seed a missing file durably at startup, never overwrites an existing file (even an empty one, with a warning that the seed was ignored), and changing the variable never rotates an existing password.
- `server/known_public_key_hashes.json`: an array of strings. A missing file means no known keys; malformed JSON or another shape (including an empty file) is renamed beside it to `known_public_key_hashes.json.corrupt-<Date.now()>`, with a warning naming that path. Startup continues with no known keys, so every tab logs in again with the password; other read errors throw. Deleting only `password` lets you set a new one but does not revoke registered clients; delete this file too for that.
- `server/web_push_vapid.json` (mode 600): the Web Push VAPID pair. Replacing it (or the `RISU_WEB_PUSH_VAPID_*` variables) leaves every browser subscribed with the old key: each subscribes again the next time it opens the app.
- `server/push_subscriptions.json` (mode 600): `{ version: 1, subscriptions: [{ endpoint, keys: { p256dh, auth }, expirationTime, failureCount, lastError?, updatedAt }] }`.
- `.tmp/`: staged writes and the per-operation export/import staging folders, emptied at startup.
- `data/resources.sqlite` (plus its `-wal` and `-shm` files): the resource store. Table `resources` (`seq` autoincrement, `kind`, `id`, `revision`, `schemaVersion`, `data` JSON text, unique `(kind, id)`), table `meta` holding the random `epoch`, table `chats` (`seq`, `characterId`, `id`, `revision`, `schemaVersion`, `meta` JSON), table `messages` (`chatSeq`, message `id`, integer `position`, `data` JSON, and the generation fence: `generationId`, `generationSeq`, `generationFinal`, `generationHistory` of up to 8 earlier ids), table `chatOrders` (`characterId`, `seq`, `revision`, `ids` JSON), and table `chatGroups` (`seq` autoincrement, `chatSeq` referencing `chats.seq` with `ON DELETE CASCADE`, `groupId`, `revision`, `result` JSON, unique `(chatSeq, groupId)`), which `createChatTables` creates when missing, so a version-3 file from before it gains it on open without a version change; it is not part of the snapshot layout check, a snapshot's copy of it is not restored, and a restore leaves it empty (deleting the chats cascades). The checkpoint tables are created the same way and are outside the required layout (a snapshot without them is valid), but a snapshot that has any of them is checked and restored with them (`readCheckpointSnapshotRows`): `chatCheckpoints` (`seq` autoincrement, `chatSeq` referencing `chats.seq` with `ON DELETE CASCADE`, `id`, `kind` (`manual`, `auto`, `safety`), `name`, `createdAt`, `revision`, `chatRevision`, `userTurns`, `messageCount`, `preview` JSON, `pages` JSON (the ordered message page hashes), `fields` JSON (captured field → page hash), unique `(chatSeq, id)`), `checkpointPages` (`hash` primary key, `text`), `checkpointPageRefs` (`checkpointSeq` referencing `chatCheckpoints.seq` with `ON DELETE CASCADE`, `hash`, indexed), and `chatCheckpointPolicy` (`chatSeq` primary key referencing `chats.seq` with `ON DELETE CASCADE`, `autoEvery`, `autoKeep`, `lastAutoTurns`); a page no ref names is swept at open and in every checkpoint delete and prune, and a restore keeps only the snapshot's referenced pages, so a deleted chat's pages wait for the next sweep; `PRAGMA user_version` is the store version (3: settings sections and collections, no `root` record; the tables are those of version 2). Opening the store and every `replaceAll` run the normalization pass in one transaction: each record whose normalized text or schema version differs from the stored one is rewritten with its revision counter advanced (same `seq` and epoch), and each missing `materialize` singleton is created; a stored record its normalizer rejects, or one of a newer schema version than its kind, stops the start. A version-1 file or version-2 file (settings in a `root` record) is refused at startup with a message naming it, and a snapshot or archive of another version is refused on restore; there is no migration (formats of metatron's implementation phases, `persistence.md` compatibility rule). The connection runs with `journal_mode=WAL`, `busy_timeout=5000`, and `foreign_keys=ON`. `data/` is not a storage namespace.
- `backups/`: resource snapshots (`resources-*.sqlite`, single files, newest 20), not a storage namespace. Assets are not in snapshots.
- User files: a logical key `assets/<name>` lives at `save/assets/<encodeFileName(name)>`, e.g. `assets/<sha>.png` or `assets/inlay_<sha256>.png`. The legacy `save/database` and `save/remotes` folders are left in place and no longer read.
  - `encodeFileName` keeps `a-z 0-9 . _ -` readable and writes every other UTF-8 byte (uppercase letters, `/`, `%`, spaces, non-ASCII) as `%XX`. It also escapes a trailing dot and the first character of a Windows device name (`con.png` → `%63on.png`). A name whose readable form exceeds 255 bytes is stored as `~<lowercase hex>`; longer than that is rejected.
  - Only one encoding per name is canonical, and canonical names never differ by case alone, so case-insensitive filesystems do not merge keys.
  - The old flat layout (hex file names and `__password` directly in `save/`) is not read and was not migrated.

Process memory: the module-level `assetVerification` singleton holds bounded verification results and its hash queue, keyed by absolute paths so separate save directories do not collide. The remaining state is inside the `createServerContext` closure:

- `password` and the known key hashes.
- The generation jobs (registry, chat slots, sockets) and the generation lock. A restart loses both: running jobs end with the process, and the message generation fence of their messages closes on the next ordinary write.
- Rate-limit counters.
- The resource store's epoch and committed-write counter, the snapshot lock, the maintenance gate, the backup import slot (the version-2 import and the upstream prepare and commit), the import slot the module, CharX, and Realm imports share, the staged Realm imports (`realmStaging`), and the prepared upstream imports (`upstreamStaging`).
- The change feed's listeners and the live-update sockets (nothing is buffered; a restart loses them, and every client reconciles at its reconnect).
- The chat source generations and the `onChatInvalidated` listeners (one entry per chat deleted or replaced whole since the store opened or the last restore; a restart starts them over).
- The memory task registry (`createMemoryTasks`): per chat the running task, the queued input, the latest retained input, a waiting manual start, and the last terminal status (10 minutes), plus the held summary writer leases. A restart loses them: no task resumes.

## Invariants

- Live updates: every committed change is published by the resource store itself, so every writer (the routes, the generation jobs' in-process writes, a restore) reaches the feed only through the store's write methods. `put`, `delete`, `applyChanges`, and `transaction` collect the refs they change, side effects included (creating a character creates its chat order; deleting one deletes its chats and order), drop them when the write throws (it rolled back), keep a record's final revision when it changed twice, and publish once after the commit and after `transactionState` is cleared; a write inside `transaction` publishes with it. `replaceAll` publishes `epoch` after the new epoch is installed. The feed carries refs and revisions, with optional record or by-id chat patches. A record patch op carries its record patch (`feedPatch`) with its base revision, one write earlier: for an object record every top-level field whose stored JSON value changed (`RecordFieldPatch`, `diffFields`; normalization included), for an item list the changed items (`RecordItemPatch`, `diffItems`: a new item or one whose `__proto__` changed whole, another changed item as its changed fields, the id order when it changed). None (a plain ref) for a kind with `project` or a hidden hydration kind (so a `llmSecrets` or `authRefreshes` change never carries data), a record written twice in the scope, a changed top-level `__proto__`, a list without unique item ids, or a patch over `MAX_FEED_PATCH_BYTES` (64 KiB). For a `shallowNormalize` kind (`characters`, `modules`, `pluginStorage`: the normalizer changes nothing it is given and keeps the fields or items it does not replace by reference) a patch op serializes only what changed (`writePatch`, `patchParts`): the stored text is cut into its top-level fields or items (`cutRecord`, only when the text is exactly its parts joined as `JSON.stringify` joins them), the patched parts and whatever the normalizer replaced are serialized and checked alone, in the record's order and with their own keys (`storedParts`), and the rest is reused as stored text; the result is the text a whole `serialize` would give. The last 4 cut records (64 Mi estimated UTF-16 units, charging `text.length * 4`: 2 for text/parts and 2 for the parsed value graph; a larger record is not kept) are cached and reused only while the stored text is exactly theirs, so a rolled-back write, a restore, or any other write falls back to a new cut (one parse and one serialization per field). The feed gets a copy of the patch, never the cached values. About 220 ms → 15 ms per patch of a 9.6 MB character, measured in Vitest. `pluginStorage` qualifies because `requireObject` returns its input by reference; `presets`, `personas`, and `modelPresets` do not qualify because their normalizers clone every field. Any other kind, or a record that cannot be cut, still parses, normalizes, and serializes the whole record. That slow path builds `feedPatch` through `recordPatchText.ts:diffRecordText`: cut the old row text and new serialized text into top-level parts, skip identical fields/items, and parse only differing field values and new/replaced items. Array ids reuse the values already parsed by the write, including unchanged/reordered items, avoiding any extra whole-item parse. This retains normalization side effects and the 64 KiB cap without serializing unchanged cloned fields again. The budget factor was measured on Node 24.21.0 with seven `--expose-gc` heap samples: a 10,017,827-unit character with 20,000 lore entries retained 30.997 MB cut in ASCII and 59.832 MB with two-byte text; parsed values alone were 10.960/19.760 MB. Four units per text unit includes graph headroom, an estimate rather than a hard heap bound for every JSON shape. Whole resource or chat writes still publish plain refs. The existing-record writers in MCP (`updateCharacter`: entries become `set`/`remove`, `undefined` removes; `updateModule`: one item `changes` entry), Lua (`patchCharacter`, `patchPersonaPrompt`), and the runner's memory-trim character update now issue patch ops. The module/persona writers fall back to the former whole list write when `itemIds` rejects the list, preserving duplicate-id behavior. `enabledModules` and `authRefreshes` server writes stay whole. Job owners still receive whole `resource` events from `emitRecords`/`recordEvent`. For a chat group containing only by-id ops, `chatStore.ts:applyGroup` builds `chatFeedPatch`: the actual stored revision before the group (not a stale requested base), full stored meta only if a meta op applied, ids actually removed, and each touched row read back once in final position order with its immediate predecessor, plus the final `COUNT`. A begin-only group carries the count alone. No patch for zero applied ops, an id removed then appended again, or JSON over the same 64 KiB cap (construction stops at the cap). `recordChat` drops the patch if the chat was already recorded in the publishing scope; patches stay out of `ChatGroupResult` HTTP responses. The event socket serializes each published frame once for all sockets. `applyChanges`' `committed` (a generation job's write) runs after the commit inside the publishing scope and returns per-chat generation locks the published change carries (`streaming`; the last list per chat in a scope wins); it runs without a feed too and must not write; if it throws, the committed change is still published, without lists, and `CommittedWriteError` is thrown. `publishStreaming(entries)` publishes lists without a write (a `change` with empty refs; inside a publishing write it goes with that write).
- Chat source generation: the store keeps, per chat, an in-memory value that changes once in the commit of every write that deletes the chat (a group `delete`), replaces it whole (a group `replace`, from any writer: a route, a job, Lua, or a checkpoint load writing through `applyChanges`), or deletes its character (the cascade), and in no other write (`meta`, `append`, `setText`, a remembered group's replay). Each SQL transaction collects the chats it invalidates and drops them at its rollback (a conflict a `transaction` body caught included); its COMMIT advances them, once per chat, in the same synchronous step, before any caller code runs after it (the `committed` hook of `applyChanges` already reads the new value, and its throw, `CommittedWriteError`, does not undo it). Values come from one counter and are never issued twice while the store is open; an entry stays after its chat is deleted, so a chat recreated under the same ids never reads an earlier value. `replaceAll` gives every chat a new value (the map is cleared, the default moves past every issued value) without notices: the `epoch` event is that signal. `onChatInvalidated` delivers a `ChatInvalidation` (`epoch`, `characterId`, `id`, `sourceGeneration`, captured at the commit) per invalidated chat and committed transaction, in commit order, once every running publishing scope has published its change (a feed listener's own write waits for the outer publication; a restore's `epoch` reaches every listener first). An enclosing write whose input evaluation throws after a nested write committed publishes no change (the feed refs are dropped as before), but the nested write's notices are still delivered. A listener's own write queues its notices behind the ones being delivered, a listener throw is logged, and a listener may already see a newer state, so consumers compare generations. `close` drops the values and the listeners.
- Storage routes never use a raw path. `decodeKeyHeader` requires even-length hex and valid UTF-8 (verified by an exact byte round trip), then `resolveStorageKey` requires a namespace from `STORAGE_NAMESPACES` (only `assets`) and encodes the whole rest of the key, `/` included, into one file name. Only these folders are reachable; `save/server/` and `save/.tmp/` are not. The batch routes take each key as a record name (strict UTF-8, checked by `AssetRecordParser`) or a JSON string and resolve it with the same `resolveStorageKey`.
- File publication: asset writes, resource snapshot copies, auth passwords and registered public-key hashes, push subscriptions and VAPID keys, and the diagnostics journal's whole-file writes (`state.json`, saved reports, support-share copies) flush staged file data before close and publication (rename, or a backup import's hard link), then sync the target directory before completion. Each published file costs one file fsync and one directory fsync; a successful asset batch pays one file fsync per record and one directory sync per request (per distinct target directory, currently `save/assets`), outside the maintenance gate, and a backup import pays one fsync per added asset plus one directory sync before its resource replacement. First-time target directory creation also syncs the parent of the first new directory and every new directory down to the target. Only `EINVAL`/`EPERM` from opening or syncing a directory are tolerated (some network and Windows mounts refuse a directory fsync); a file-data sync error and any other directory error fail the write. The journal counts a directory-sync failure after the rename but still reports that the file landed.
- Unsupported keys: malformed hex/UTF-8 is 400 `Invaild Path` on every `file-path` route and `/api/asset/*` (a batch write record name that is not UTF-8 is 400 `Invalid asset batch`). A well-formed key with no storage location (other namespace, empty or too-long name) reads as missing (empty 200 from `/api/read`, no disk access; a zero-length record in a batch read), because the client reads whatever paths an old database stored; `write` and `remove` reject it with 400, and a batch write with 400 `{ error: "Invaild Path", index }` naming the record. `/api/asset/*` answers 404 `no-store` for an absent path suffix, a key with no storage location, a missing file, a symlink, or a non-regular file.
- Content names are `assets/<64 lowercase hex>.<ext>` or `assets/inlay_<64 lowercase hex>.<ext>`, with a nonempty alphanumeric extension. Only a name whose current handle stat matches a server verification of its bytes against that SHA-256 is immutable. A mismatched write is accepted and remembered as unverified; it stays `private, no-cache` with the weak ETag and is not rehashed until its stat changes or its entry is forgotten or evicted. Unknown content names stay no-cache for the current response and enter the background queue; other names are never queued. Skipped existing import assets are verified only when the route requests them.
- `/api/list` returns only regular files whose names are canonical `encodeFileName` output, so every listed key reads back the same file. Other entries (subfolders, symlinks, noncanonical file names) are ignored.
- Keep the logical keys and the hex wire encoding; the client depends on both. The mapping to file names must stay reversible and injective.
- Keep these unchanged:
  - the `__NODE__` injection;
  - the `risu-*` header names (`x-risu-node-path` no longer redirects `/hub-proxy`; see Proxying);
  - status codes and JSON error bodies, including the `Invaild Path` typo (one deliberate change: a `/api/read` filesystem error other than a missing file, symlink, or non-regular file is now a 500 instead of an empty 200);
  - the 100 MiB body limit (the backup, module, CharX, and Realm imports and the self-capping routes listed under Routes are exempt; the token routes cap at 2 MiB after authentication, the Realm prepare, commit, and cancel at 4 KiB).
- Rate limits must keep matching the former express-rate-limit v8 setup:
  - thresholds as in the Routes table;
  - windows start at a key's first hit;
  - IPv4-mapped IPv6 keys collapse to IPv4, other IPv6 addresses to their /56;
  - draft-6 `RateLimit-*` headers, plus `Retry-After` on 429.
- `TRUST_PROXY` keeps Express `trust proxy` semantics via `compileTrust`:
  - a number is a hop count;
  - a string is a comma list for `proxy-addr` (`loopback`, CIDRs, ...);
  - an invalid value fails at startup.
- `JSON` routes (`readJsonBody`):
  - a non-JSON content type or a zero-length body is `{}`;
  - malformed JSON (including whitespace only) or a top-level primitive is 400 `{error:"Invalid JSON body"}`.
- The WebSocket upgrade handling is one `upgrade` listener (`attachWebSocket`) on the server returned by `serve()`, dispatching by path to the `ws` handlers (`generationJobs.handleUpgrade`, `eventSockets.handleUpgrade`); each matches its path synchronously and returns false without touching another path's socket. Do not add a second listener, pass `websocket` to `serve()`, or add `@hono/node-ws`.
- Generation lock: a change that rewrites or removes a message a generation job owns (`setMessage`, `patchMessage`, `setText`, `setTranslation`, a `remove` naming it, `begin` on it, `replace` or `delete` of its chat), or deletes a character holding one, is a 409 whose entry carries `reason: "generating"` (the single DELETE route: the body's `reason`), unless it is the owner's in-process write carrying its job token. A chat entry also names the messages the group's ops target that another job owns (`messageIds`, in op order; absent when there is none, as for a whole-chat `replace`/`delete` of a chat holding a lock): the refusal's evidence, not every lock of the chat. The check runs inside the transaction before the revision checks, so a stale change of a locked message also reads as `generating`. `meta`, `append`, and edits of other messages apply. Every client learns the locks from the change feed (`streaming` on a job write's `change`, and on the job's end), not only the owner's job socket. The token never leaves the process; a client-supplied generation id grants nothing. Every generation is a server job since the cutover; the message generation fence stays for the tab's own writes.
- Job writes name the job's admitted epoch and live token, checked in the same synchronous call as the write; an ended job's token is dead (`JobTokenError`). No transaction spans a provider call: each job write is its own `applyChanges`.
- Resource revisions: a token is `<epoch>:<seq>:<revision>`, opaque to clients. A write matches all three parts, so a token from another database epoch, or from a deleted and recreated record (new `seq`), never passes. `baseRevision: null` creates and conflicts if the record exists; a write to a missing record is a 409 with `revision: null`. A token string that does not parse, including an empty `?baseRevision=`, is a 409 with the current revision; a `baseRevision` of the wrong JSON type, or a DELETE without the query parameter, is a 400.
- Resource writes normalize inside the store: `put` runs the kind's `normalize` once and stores its JSON result. A normalizer sees the stored form of its input (`serialize` runs first), so a nested non-finite number or over-deep input is refused before a JSON copy inside the normalizer could hide it. Reads never normalize; a new default or migration reaches stored records only through the normalization pass at the next start, so every normalizer must be idempotent (its output normalizes to the same JSON) or the pass rewrites that record on every start. A removed kind goes into `RETIRED_KINDS` (`resourceStore.ts`; `customSidebarItems`): the pass deletes its stored records and `readSnapshot` skips its rows, so older databases and backups still open and restore. The store is built with the kind registry and every method refuses a kind object the registry does not hold, so no caller can swap in another normalizer. A value is stored as `JSON.stringify` produces it (`toJSON` applies, `undefined` fields drop, Dates become strings, `-0` becomes `0`), and `put` and later reads return that stored form. `put` refuses, with `ResourceValidationError` (400), data whose JSON form would turn a non-finite number into `null` (`1e400` parses to `Infinity`), data `JSON.stringify` cannot serialize (a bigint, a cycle, a throwing getter, runaway nesting), and a JSON form nested deeper than 256 levels. `transaction(fn)` is one synchronous `BEGIN IMMEDIATE`; a throw, or any conflict inside it even if `fn` caught it, rolls back every write. A body whose return type can be a promise does not type-check (`TransactionBody`, best-effort: a body returning `any` passes, and an overloaded function reference is judged by its last overload, so wrap it in a zero-argument arrow), and at runtime a returned promise or thenable rolls back and throws. An `AsyncLocalStorage` scope follows the work the body starts through awaits, promise continuations, and timers: once the body returns, a write from that work throws, so it cannot autocommit after a rollback. Callbacks the body registers on an event emitter do not carry the scope and are not covered. Never await inside a transaction.
- Resource ids: 1-512 UTF-16 code units of well-formed Unicode, no control character, not `.` or `..`; clients encode them once with `encodeURIComponent` (so `§playground` and `assets/x.png` are valid ids). A singleton kind accepts only `main` and cannot be deleted.
- Epoch fencing: every mutation (PUT, DELETE, batch, restore, import) names the epoch in `x-resource-epoch`, checked in the same synchronous block as the write (restore and import check again inside maintenance), so nothing based on data from before a restore lands, including a create with `baseRevision: null`. Reads return the epoch; tokens stay opaque.
- Batch operations are `{ kind, id, baseRevision, data }` or `{ kind, id, baseRevision, delete: true }` (a string base revision); duplicates of one kind and id, both or neither of `data`/`delete`, unknown kinds, and invalid ids are 400 with the operation index.
- Chat groups (`chats[i]`): one per chat; `baseRevision` is null exactly for a group that starts with `create`; `create` only first and `delete` only alone; a batch that deletes a character and names its chats is 400. Every validation error names the group and op (`chats[i].ops[j]: ...`), including data refused only once merged inside the transaction (a `meta` patch), so a client can quarantine that one chat. A chat create under a missing character is a 409 chat conflict with revision null. A group may carry `groupId` (a string of 1 to 128 characters; the tab sends one with every group) and `retry: true` (a resend after a lost answer; needs a `groupId`).
- Group ids: every group with a `groupId` that a chat answers (also one that changed nothing: all targets `missing`, an identical `append`, an ignored translation) is remembered with its answer in `chatGroups`, inside the batch's transaction (a rolled-back batch remembers nothing), the newest `MAX_CHAT_GROUP_IDS` (100) per chat incarnation. A group whose id the chat remembers is answered before the lock, revision, and anchor checks with that answer and changes nothing: the revision as of that group (older than the current one when others wrote since), its `stale`, `translations`, and `targets`, `messageIds` (stored only when the server gave a message a fresh id; otherwise rebuilt from the group's own messages), and every `checkpoints` entry `duplicate`; the change feed still gets the remembered ref (tabs at or past that revision ignore it; a tab holding an older revision schedules a read). A `retry` group whose id the chat does not remember while it holds 100 ids and the group's base is not newer than the oldest remembered group's revision (it may have landed and been dropped) is a 409 chat conflict with `reason: "expired"` instead of a second application. Unlike `reason: "generating"`, this refusal may name a group that already landed; the client takes the ordinary reload/discard recovery with the notice, without anchor repair or a new identity. Groups without an id (the server's own writers) are not remembered.
- Restore floor: every non-null-base chat group whose parsed revision is below its `chatRestoreFloors` revision conflicts with the current revision and no `reason`, as for another incarnation. Remembered results/expired retries are checked first, then message locks (`generating` still wins), then the floor with revision validation. A checkpoint load sets the floor to its replacement revision atomically; floors never decrease, cascade with the chat, and are discarded rather than restored by `replaceAll` (which changes epoch).
- Chat revisions: every applied op moves the chat's revision (a replayed or no-op op does not). By-id ops (`append`, `setMessage`, `patchMessage`, `setText`, `setTranslation`, single `remove`, `meta`) apply to an older revision of the same chat incarnation at or above its restore floor while their message exists (`setMessage` too: as a whole row it then replaces fields the sender has not seen, so it needs the current revision for the fields it does not own, which the store does not enforce; a change of some fields is a `patchMessage`, and a `meta` `merge`/`mergeUnset` changes single map entries); `replace`, `delete`, a multi-id `remove`, reorders, and a `begin` of an unknown generation need the current revision (a `begin` on a message appended in the same group does not). Replays are idempotent: an identical `append` of an existing id and a single `remove` of a missing message are no-ops; an `append` of an existing id with other content is a 409. A `setText`, `setMessage`, `patchMessage`, or `setTranslation` whose message is gone when it runs changes nothing and is reported per op (`ChatGroupResult.targets`: one `applied`/`missing` entry per such op in op order, present only when one is `missing`; its `checkpoints` entry, for a generation write, and its `translations` entry are `ignored`, so those arrays stay aligned), and the group's other ops commit; the translation runner answers such a write 404 ("The message no longer exists"). Still 409s: an `append` whose `after` anchor is gone (the tab re-anchors it, see `persistence.md`), a multi-id `remove` with a missing id, and a `begin` of a missing message (its writer, a generation job, takes the message's lock before the write and the refusal gives it back).
- Reorders (`chatOrders[i]`: `{ characterId, baseRevision, ids }`) compare the order revision from before the batch; `ids` must be a permutation of the character's chats (400 otherwise).
- Generation fence (per message): `begin` takes the message over for a generation id (the previous id goes to the history). A write carrying `{ id, seq, final? }` is `applied` when it is the current generation with a higher `seq` and not final yet, `duplicate` when its `seq` was already applied, and `ignored` otherwise (another generation, or after `final`). A `setMessage` or `setText` without a generation, and every `patchMessage` (it carries none), closes an open fence; a `setTranslation` leaves the fence as it is. `replace` keeps the fences of surviving messages closed.
- Maintenance (restore, import) closes resource and storage mutations with 503 and waits for storage writes already admitted (a batch write is admitted per record, for its rename only); a restore or export that arrives meanwhile waits for the lock instead.
- `llmSecrets` is write-only: no route answers a stored credential. The reads answer `maskLlmSecrets` (each credential leaf `{ set, hint }`, `hint` the last four characters of a value of at least 16; the maps keep their nesting), a resource write may carry no credential path (400) and keeps the stored ones, the credentials change only through `/api/llm-secrets/*`, an exported archive holds no `llmSecrets` row, and an auxiliary operation's success answer carrying one is refused. Importing an archive (which has no row) materializes an empty record: every key is gone.
- Backup import never overwrites an existing asset file; resources are replaced atomically, assets are only added.
- Docker persistence depends on `/app/save`. Removing the volume loses the password, registered keys, and all data.
- The `ui` normalizer does not coerce `chatLoadInitialPages`/`chatLoadAdditionalPages`: a numeric string such as `"12"` falls back to the default.
- The `presets` normalizer (`normalizePresets`) turns a non-list or empty list into one default preset, canonicalizes every element, and gives a duplicate id a fresh one, before any selection resolves against the list.

## Known Hazards

- The job channel keeps one queue per client across that client's jobs (`createChannelHub`), and a queued request has no deadline of its own: a `provider` callback (up to 30 minutes) or an unanswered question of one job delays every other job's hooks of that tab, bounded only by the waiting job's own life (the registry's periodic `JOB_MAX_DURATION_MS` check, which closes its channel) and the signal a request was given. Without an owner attached the queued requests expire one after another, each its full timeout from its dispatch, so one that would have ended `disconnected` (a tail callback or an image callback the runner skips) can instead end `aborted` with its job, which fails the job and holds the chat's slot meanwhile. A dispatch deadline is a channel allowance, not an extension of the job's life. A cancelled callback whose drain report is lost (a failed request, a reloaded page) keeps the lane for its full `CANCELLED_CALLBACK_DRAIN_MS`.
- Group ids belong to a chat incarnation (`chatGroups.chatSeq`): a lost `create` that landed, then deleted by another tab, is created again by its resend. Past the newest 100 groups of a chat, a resend sent with `retry` conflicts with `reason: "expired"` rather than applying twice, but one sent without it (none from the tab) would apply again.
- A server job's rotated MCP refresh token is fenced like its other writes: a job aborted or a client closed while a rotating refresh is out drops the new token, although the MCP server has already spent the old one, so the stored entry keeps a spent token and the next refresh falls back to a full login.
- Local models run in a child process, so loading and inference do not hold the main thread, a kill stops them, and a native crash ends that process only (the task fails; the next one forks again). It is not a memory boundary: the process has no limit of its own, and under memory pressure the system or the container may end the server instead. Nothing bounds what a model allocates: embeddings hold about 0.2 to 0.6 GB while loaded, the captioner and the summarizer about 0.7 to 1 GB each for a call, a generation model its `fp32` weights (about 1.3 GB for `opt-350m`). The task queue is bounded by task count and queued payload size (see `transformers.ts` under Files), but a running task's payload, its copy in the child, and the child's allocations are outside that bound; the model files under `save/models/transformers` are unbounded, downloaded from `huggingface.co` on first use (a host without that access cannot use a local model; a file fetched once is reused offline).
- The vector cache bounds its vector bytes, not its file, and its trim runs on the main thread (a large eviction holds it for that time). It is shared by every client and keyed as the client keys it: by model name, not by endpoint (`memory.md`).
- A cancelled rate-limited batch (`shared/taskRateLimiter.ts`: HypaV3's experimental summaries, `HypaProcessorV2`'s API embeddings) leaves its retry timer running until the rate window passes (up to a minute); it starts nothing, but it holds the event loop for that time. The limiter is the client's, moved unchanged.
- Memory on the server calls the embedding and summary providers from the server process: the custom embedding URL is fetched as the settings name it, with no local-target restriction (the hazard recorded for provider URLs).
- The redactor (`server/src/llm/redact.ts`) knows a credential as stored, JSON-escaped, and as `encodeURIComponent` writes it (uppercase escapes). A percent-encoding with lowercase escape digits, or any other reversible encoding, is not matched: in a request log, a job error, or the completions answer check of memory.
- `voyageApiKey` and `hypaCustomSettings.key` are in the client-readable `secrets` section: a job's settings projection (`scope.db`) holds them. They are used inside `embeddings.ts` only and redacted from its errors; no host function, CBS function, or notice returns a settings field by name.
- `put` validates a value's depth on its parsed JSON form, so an over-deep value is rejected only after it has been fully serialized and parsed. Over HTTP the body is already parsed and capped at 100 MiB; only in-process callers could pass costlier values (getters, `toJSON`).
- The resource store assumes one server process and a local filesystem for `save/data/` (SQLite WAL uses shared memory; network filesystems are unsupported). Snapshots cover only `save/data/`; deleting both `save/data/` and `save/backups/` loses every resource.
- Snapshots do not hold assets, and inlay blobs are never deleted (a retained snapshot may reference them), so `save/assets/` only grows. Restoring the oldest retained snapshot can evict that file through the safety snapshot's retention (it was read in full first, so the restore itself succeeds).
- Restore and the version-2 import validate and install the database synchronously on the serving thread; a very large database blocks other requests for that time. The upstream import blocks the serving thread only inside its commit's maintenance window (its main-thread `readSnapshot` and `replaceAll`, while writes are closed anyway) and for the prepare's archive classification (the index is read asynchronously; the classification is one synchronous pass over at most 200,000 names).
- The upstream export's worker holds every record, the projected `Database`, and the encoded bytes at once, and up to `MAX_UPSTREAM_EXPORTS_STAGED` prepares may run at the same time as an import's worker, each with its own heap allowance. The serving thread still copies the store (`backupTo`, under the snapshot lock) and lists `save/assets` before the worker starts.
- The upstream import's and export's worker heap limits (`RISU_UPSTREAM_IMPORT_HEAP_MB`, `RISU_UPSTREAM_EXPORT_HEAP_MB`) cap the JavaScript heap only, not Buffers or SQLite's memory, so each is a ceiling against a runaway decode or projection, not process isolation; a legitimate backup whose conversion, or a store whose export, needs more is refused with the limit's name in the message. An import prepare holds two copies of the assets on disk (the spooled archive and the extracted files) until it is committed, cancelled, or expires.
- An asset over 4 GiB cannot be stored in an archive record and is reported as missing by an export.
- A backup, module, or CharX upload that takes longer than `main.ts`'s `REQUEST_TIMEOUT_MS` (4 hours for the whole request, about 40 KB/s for 580 MB) fails with 408 before it is spooled.
- Storage writes stage into `save/.tmp/` and `rename` onto the target for atomic replacement. `save/.tmp/` must be on the same filesystem as the namespace folders (one Docker volume at `/app/save`). One server process per `save/` is assumed: startup deletes `save/.tmp/`, and concurrent writes to one key are last-writer-wins. A failed rename (e.g. a Windows file locked by another process) returns 500 and keeps the old file; the server does not retry. The client save adapter retries resource batches with backoff; the asset client (`src/ts/storage/assetClient.ts`) retries a network failure before an answer arrives and a 429 or 503 answer of every asset read and write, single or batched, up to 8 attempts per request with backoff (`Retry-After` when sent, capped at 60 s). A failure while the answer's body is read, and any other non-2xx answer such as the 500 of a failed rename, are not retried.
- Durability has gaps the publication rule does not close: on a mount that refuses a directory fsync (`EINVAL`/`EPERM`, tolerated) the rename or link itself is not guaranteed to survive a power loss; the diagnostics journal's daily event appends (`events/*.jsonl`) and its folder creation are not synced; and a content-name import that skips an existing file (`contentAsset.ts`) can reuse a batch record already renamed but not yet directory-synced by a batch still in flight. SQLite's own `synchronous` setting governs `resources.sqlite` itself.
- Auth files are still written directly with `writeFileSync` (not atomic).
- `/api/read` and `/api/assets/read` open with `O_NOFOLLOW | O_NONBLOCK` where the OS has them and take size and bytes from one handle. Namespace folders themselves are trusted: a symlinked `save/assets` is followed. A hostile local process modifying `save/` is out of scope.
- `/api/asset/*` serves one byte range only; multiple ranges, other units, malformed ranges, or any `If-Range` are ignored and get the full response. Verification is in memory and starts empty at restart: the first request for a previously stored content name is no-cache and queues a hash. Result eviction has the same effect; a full hash queue leaves the name unknown until a later request can enqueue it.
- Asset verification matches size, nanosecond mtime, inode, and device. An outside change is detected when that stat changes; a same-size in-place edit that keeps or restores mtime (including a coarse timestamp tick), or inode reuse with matching size and mtime, is not detected. The weak ETag has the same size/mtime/inode limitation.
- A write of different bytes under a name a browser already holds as immutable is accepted, including after removal and re-creation, but does not reach that browser until its cache drops the entry. Removing the server file cannot invalidate that cached copy.
- An immutable asset response can be served by the browser HTTP cache without reaching authentication for any same-origin request of that URL. The service worker must keep unsigned request destinations away from that cache; the asset route's security headers remain on cached responses.
- Static serving runs before `/api/asset/*`: a file under `dist/api/asset/` would answer before authentication and the asset headers. The build emits no `api/` folder. These headers apply to the asset route only; `/api/read` keeps its existing response contract.
- The chat fence orders one client's generation writes; it does not lock a message against another device (a manual write from anywhere closes the fence).
- A batch remove stops at the first filesystem error, such as a missing file. It returns 500, and files deleted before the error stay deleted.
- `/api/set_password` and `/api/crypto` remain unauthenticated, with rate limits (10 per 30 s shared with `/api/login`, and the auth bucket at 2000/min, respectively). Without a seed and with a missing password file, the first caller still sets the password. An empty password file keeps setup closed until the operator fixes or deletes it.
- `/proxy` and `/proxy2` forward to arbitrary targets. Only proxy jobs are restricted to local targets.
- `/hub-proxy` is unauthenticated and forwards the browser's headers (except `risu-auth`) to the hub, so any visitor can read the hub through this server.
- JWT validation checks no issuer, audience, `typ`, or `iat`, and a token without `exp` never expires.
- Server CBS evaluation runs on the main thread under cooperative limits (`shared/cbs/limits.ts`), not under a hard deadline or a heap bound: the limits are checked at every `{{` and `}}`, every 4,096 work units, and inside the counted registry loops, so one operation between two checks runs to its end (a host call, one function on an input the budget allowed), and a result is charged before it is built only for the amplifying operations (`replace`, `join`, `cbr`, `range`, `#each`, `call::`, `#pure_display`); `split` and `history` build theirs first (a `history` over a 100M-character chat peaks near 380 MB before it is refused). Scanning costs memory too: a 9M-character text peaks near 460 MB of RSS. A job whose templates each stay under the limits can still hold the thread for up to its 60 s allowance; prompt assembly does not yield between its evaluations (the native effect loop does, after 50 ms). Hard interruption would need a worker or process boundary.
- Other main-thread work on card or model text has no bound: token encoding after its load (`tokenizers/index.ts`), Jinja rendering (`shared/prompt/chatTemplate.ts`), lore matching outside its worker regexes, and the calculator called directly by `v2Calculate` (outside the CBS allowance; the effect converts each `$name` reference itself, once per reference).
- Chat metadata setters coalesce only within a synchronous stretch (`jobScope.ts` `chatMetadataFor`): a trigger yield, worker host-call boundary, awaited command, or job output/callback barrier flushes it. A loop crossing these boundaries still pays one metadata transaction, adoption, and owner chatPatch per batch; each costs the metadata size (`hypaV3Data` included). Frozen display scopes never join the coalescer. Keep a pending batch as its own write before a message group: a generating refusal of the latter must not discard an earlier setter. The final trigger-copy whole-map replay can still replace concurrent scriptstate keys, as the recorded tab behavior requires.
- `/api/llm/request` fetches every configured provider URL from the server: a provider on the browser's `localhost` is reached only when the server runs on the same machine (in Docker, `localhost` is the container; configure `host.docker.internal` or the host's address). Like `/proxy2`, it fetches whatever URL the stored settings name.
- A server send reads the job's chat again after its own writes and its callbacks (`refreshChat`), not only its own and acknowledged writes: an unrelated edit made to that chat while the job runs can reach a later stage of the prompt, as the browser's live `chatNow()` reads do.
- Server CBS also runs the send's prompt (every `risuChatParser` of assembly, `editprocess`, the regex scripts' `parse` answers) on the main thread, under the cooperative limits above; only the regexes themselves run in a worker.
- Unconfirmed: a reverse proxy in front of the server that decodes `%2F` in a path splits a resource id containing a slash (an inlay id can); keep encoded path segments unchanged end to end.
- The server has one password and a list of registered browser keys; a JWT names a registered key, not a user. There is no multi-user model.
- Opening the resource store runs the normalizers over every row of every kind and rewrites non-canonical records, so startup time grows with the data; a normalizer that refuses a record stops the startup with the kind and the record id.
- The first load of `@mlc-ai/web-tokenizers` uses Node's experimental `vm.constants.USE_MAIN_CONTEXT_DEFAULT_LOADER` and prints its `ExperimentalWarning` once per process.
- Tokenizers stay loaded until the server context disposes them, and the web-tokenizer loader is shared process-wide and serialized; disposing frees the encoders but does not promise to return the memory, and encoding runs synchronously on the owner thread.
- A Lua run stuck in native code is not reached by the abort hook: after the abort grace (`abortGraceMs`, 500 ms) the pool terminates the worker, and queued work waits for its replacement. Workers start lazily, so the first task and each worker a burst adds wait for readiness while held on their slots; deadlines and watchdog baselines begin at dispatch. Lua budget reservations begin at assignment and are released if the held task ends before dispatch. The separate `bootMs` cap (30,000 ms by default) fails held tasks as startup errors, and a worker that dies before `ready` is not replaced ahead of demand. `warm()` returns a promise for `size` ready workers, including ones already booting; awaiting it reports boot failures, while fire-and-forget use has an internal rejection handler. Disposal resolves readiness waits, and warming a disposed pool does nothing.
- `server/src/lua/runtime.ts` reaches into wasmoon 1.16's non-public engine extension table and C API (`module.addFunction`, `lua_sethook`); recheck them on every wasmoon upgrade.
