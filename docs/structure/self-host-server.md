# Self-Host Server (Hono on Node), Docker

## Scope

- Owns:
  - `server/src/**`: the Hono self-host server on Node (`@hono/node-server`). Handles static `dist`, auth, asset storage, the resource store and its routes, resource snapshots and backup archives, the reverse proxy, the hub proxy, and streaming proxy jobs over WebSocket.
  - Local TLS certificates.
  - Docker packaging.
  - The launcher scripts.
  - The client/server contract, seen from the server side.
- Paths: `server/{src/**,tsconfig.json,ssl/*}`, `Dockerfile`, `.dockerignore`, `server.sh`, `server.bat`.
- Client counterparts, owned by other guides:
  - `src/ts/storage/serverAuth.ts` and `src/ts/storage/assetClient.ts` → `persistence.md`.
  - `globalApi.svelte.ts` `fetchNative` → `global-api.md`.
  - `characterCards.ts` `hubURL` → `characters-modules.md`.

## Files

The server is TypeScript run directly by Node's type stripping (`pnpm runserver` = `node server/src/main.ts`, Node `>=24`). There is no build step. Layout: `main.ts`, `app.ts`, and `types.ts` (`AppEnv`) at the root; route modules in `routes/`; the resource data layer in `data/`; shared HTTP helpers in `http/`; the server-side processing modules in `prompt/`, `scripts/`, and `lua/`; tests and their support in `tests/`. The server may import the persisted types in the root `shared/` folder (`persistence.md`); `server/tsconfig.json` includes it, so `pnpm check` strict-checks it. Relative imports use explicit `.ts` extensions, and only erasable syntax is allowed (`server/tsconfig.json` sets `erasableSyntaxOnly`; `pnpm check` runs `tsc -p server/tsconfig.json`).

- `server/src/main.ts`: entry. Reads `PORT` (default 6001), `TRUST_PROXY`, `RISU_MAX_IMPORT_BYTES`, `RISU_REQUEST_HISTORY_MAX_BYTES`, `RISU_DIAGNOSTICS_DIR`, and `RISU_DIAGNOSTICS_MAX_BYTES`, loads the TLS certificate (`getHttpsOptions`), calls `serve()`, attaches the WebSocket upgrade handler, and starts job GC, the snapshot timer, and the diagnostics state timer. A `process` `uncaughtExceptionMonitor` and the HTTP server's `error` listener record a `runtime` diagnostic event and write `state.json` before the process exits (a monitor keeps Node's crash behavior; with no `unhandledRejection` listener in the process an unhandled rejection reaches it with origin `unhandledRejection`; a failure caught by `startServer` before the context exists is not recorded). On SIGINT/SIGTERM it begins shutdown, drains HTTP for up to 8 s, force-closes remaining connections, then awaits `dispose()` and exits. `cwd` is the root: `cwd/dist`, `cwd/save`, `cwd/server/ssl/certificate`.
- `server/src/app.ts` `createServerContext({ rootDir, trustProxy, resourceKinds, snapshotIntervalMs, maxImportBytes, generationRunner })`: builds the Hono app and owns all state, including the generation lock, the resource store (built with the lock as its guard), the snapshot manager, and the generation jobs. `resourceKinds` replaces `DEFAULT_RESOURCE_KINDS`, `snapshotIntervalMs` the 10-minute interval, and `generationRunner` the jobs' runner (tests use them; the default is `createGenerationRunner`, below). It also owns the change feed (`data/changeFeed.ts`, given to the store) and the live-update sockets (`routes/events.ts`). Returns `{ app, snapshots, scriptWorkers, generationJobs, llmRequests, requestHistory, translationRunner, push, eventSockets, diagnostics, attachWebSocket, startBackgroundTasks, beginShutdown, dispose }`. `attachWebSocket(server)` installs the one `upgrade` listener per server: `generationJobs.handleUpgrade`, then `eventSockets.handleUpgrade`, else the socket is destroyed. `beginShutdown` stops admissions and timers, aborts every generation job, removes the upgrade listener, and closes the live-update sockets (1001) before the snapshot manager stops; `dispose` is async and idempotent (it waits for the jobs to end, terminates the script workers, and waits for admitted resource handlers and backup operations before closing the store). `app.request()` works for in-process checks, but it has no Node socket, so the client IP is undefined there.
- `server/src/routes/auth.ts` `createAuthStore`: `save/server/password` plus `save/server/known_public_key_hashes.json`, `verifyJwt`, `checkAuth`, `checkProxyAuth`, `isAuthorizedProxyToken`, and the `/api/test_auth|login|crypto|set_password` routes.
- `server/src/routes/storage.ts`: the key-to-file mapping (`STORAGE_NAMESPACES` = `assets` only, `decodeKeyHeader`, `encodeFileName`/`decodeFileName`, `isAssetStorageKey`, `resolveStorageKey`), the in-process `readStorageFile`/`writeStorageFile` (a server job's asset reads and writes, under the routes' rules: no symlinks, regular files, staged writes), and `/api/read|write|list|remove`. `registerStorageRoutes` empties `save/.tmp/` at startup; writes and removals hold the maintenance gate.
- `server/src/data/changeFeed.ts` `createChangeFeed()`: `subscribe(listener)` and `publish(event)`, where an event is `{ type: "change", epoch, changes }` (a `ChangeSet` of `shared/resources.ts`: resource, chat, and chat-order refs with their new revisions, null for a deletion; no data except a record patch's `RecordFieldPatch` or `RecordItemPatch`) or `{ type: "epoch", epoch }`. Listeners only: no buffer, no replay. A listener that throws is logged and never fails the write that published.
- `server/src/routes/events.ts` `createEventSockets({ feed, epoch, authorize })`: the live-update socket `/api/events/ws` (`shared/events.ts`). `handleUpgrade` (false, the socket untouched, for another path) admits a JWT in the `risu-auth` query or header (`auth.isAuthorizedToken`, never the password); the socket gets `hello { epoch }`, then every published event as a `change` or `epoch` frame, and a `ping` every 15 s. A socket more than 4 MiB behind is terminated (its client reconnects and reconciles). `close()` closes every socket with 1001 and refuses new ones (503). Sockets are not tracked by the snapshot manager and not gated by maintenance.
- `server/src/data/resourceStore.ts` `createResourceStore({ file, kinds, guard?, feed? })`: typed resource documents in one `node:sqlite` database (`save/data/resources.sqlite`), with revision tokens, conditional writes, `epoch`/`assertEpoch`, `writeCount`, `readKinds(kinds, { chats, chatSummaries })` (with `chatSummaries`: every chat's `ChatSummary` projected from its metadata, no message rows read, and every order; exclusive with `chats`), `readRefs(refs, { chats, chatCollections, chatSummaryCollections })` (`chatSummaryCollections`: characters' orders and chat summaries; in the result only when asked), `listRevisions()` (every record's, chat's, and chat order's revision, no data), `readKindRevisions(kinds)` (the revisions of every record of some kinds, no data parsed), `chatMeta(characterId, id)` (a chat's metadata and revision with an empty `message` list, no message rows read), `revisionOf(kind, id)` (one record's revision, no data read), `applyBatch`/`applyChanges` (resource ops, chat groups, and reorders in one transaction; a resource op writes `data`, deletes, or applies a record `patch` at a string `baseRevision`: a field patch `{ set?, remove? }` of an object record (those top-level fields assigned or deleted) or an item patch `{ items?, changes?, order? }` of an array record whose items have unique non-empty string ids (`shared/recordPatch.ts` `checkItemPatch`/`applyItemPatch`: whole items put in place by id, field patches of base items, and with `order` exactly those ids in that order); the result is normalized and stored like any write, and its change-feed entry carries the changed fields or items; a kind with `project` or `prepareWrite` (`llmSecrets`) takes no patch, and a patch that does not fit the stored record is a 400 naming the op), `transaction`, `backupTo` (online backup to a single-file copy), `readSnapshot` (validates a snapshot file) and `replaceAll` (installs it with a new epoch), the normalization pass (`normalizeStoredRecords`, run when the store opens and inside `replaceAll`), `ResourceConflictError`, `ResourceBatchConflictError`, `ResourceEpochError`, `ResourceValidationError`, `ResourceStoreClosedError`, and `isValidResourceId`.
- `server/src/data/chats.ts`: the pure chat normalizers: `normalizeChatMeta` (drops `message` and the streaming flags, sets `id`, defaults `name`/`note`/`localLore` and `fmIndex` (-1), type-checks them), `normalizeMessage` (`user`/`char` role, string `data`, valid `chatId`; a `translation` that is not a `MessageTranslation` is dropped, not refused), `normalizeMessageList` (a whole chat's messages: missing, invalid, or duplicate ids get UUIDs), `assertPatchableMetaKeys`, `CHAT_SCHEMA_VERSION`.
- `server/src/data/chatStore.ts`: the chat tables (`chats`, `messages`, `chatOrders`) inside the resource store: batch preparation before any transaction (`prepareChatGroups`, `prepareChatOrders`, `countChatOperations`: shapes, legal op combinations, normalization, errors prefixed `chats[i].ops[j]`), `createChatTables` (applies groups and reorders inside the store's transaction, reads, restore), the generation fence, and `readChatSnapshotRows` (snapshot validation).
- `server/src/data/kinds.ts`: `ResourceKind<T>` (name, `schemaVersion`, `singleton`, `materialize`, pure and idempotent `normalize(input, { id })`, and for a write-only record `project` (what every read route answers) and `prepareWrite(incoming, stored)` (runs before a resource PUT or batch write; throws `ResourceValidationError` to refuse it)), `createKindRegistry` (reserves `batch` and `read`; a `materialize` kind must be a singleton), and `DEFAULT_RESOURCE_KINDS`. Phase 1 kinds (`root` was removed in Phase 3): `presets`, `modules`, `plugins`, `pluginStorage`, `pluginPermissions` (singletons, id `main`), `characters`, `inlays`, with minimum-shape normalizers that return the input unchanged, except `characters` (the shared character defaults, `normalize/characters.ts`) and `presets`, which gets `normalizePresets` (`shared/presets.ts`) and is materialized (one default preset); `modules` checks each module's shape (`normalize/modules.ts`, the rule the client's module mutations apply too: `normalizeModule` in `shared/modules.ts`; a non-string name or description or a non-list lorebook, regex, or trigger refuses the write). A `characters` record may not hold `chats` (chats are their own tables); `chat` and `chatOrder` are reserved kind names (conflict discriminators). Phase 3 kinds (singletons, `materialize`): the sections `providers`, `secrets`, `llmSecrets` (write-only: `project` is `maskLlmSecrets`, and `prepareWrite` refuses a write carrying a credential path (400 "credentials are written through /api/llm-secrets") and merges the stored credentials into the rest, `withStoredSecrets`; `shared/llmSecrets.ts`), `ui`, `memoryTranslateMedia` and the collections `loreBook`, `globalscript`, `hotkeys`, `characterOrder`, `authRefreshes`, `globalChatVariables`, `personas`, `translatorPresets`, `hypaV3Presets`, `customModels`, `credentials`, `enabledModules`, `statics`, `modelPresets`, `modelProfiles` (`shared/sections.ts`).
- `server/src/data/normalize/`: the Phase 3 normalizers, pure and returning new objects. `shared.ts` (`normalizeSection`: every field of `SECTION_FIELDS[section]` in order, its value when it has the field's JSON kind and its fresh-boot default otherwise, no other key; `requireObject`, `requireArrayOfObjects`), one file per section with its `SectionSpec` (each field's kind and fresh-boot default, kept in sync with the hand-maintained `src/ts/storage/tests/fixtures/phase3/boot-snapshot.json`) and the migrations it owns (formerly the client's `setDatabase`) (`secrets`: `hypaCustomSettings`; `llmSecrets`: `google`, the `credentials` map of `{ key }` by named key id (the former `modelPresets` and `customModels` maps dropped); `providers`: the former `modelCredentials` and the NanoGPT/Ollama model fields dropped (they are profile fields now); `memoryTranslateMedia`: the NAI v4 fields; `ui`: `customColorScheme`, the quote colors, the chat load pages), `personas.ts` (id backstop, a repeated id re-keyed), `presets.ts` (`normalizePresets`, `normalizeModelPresets` for the `modelPresets` collection, and `normalizeModelProfiles` for `modelProfiles`, never empty), and `collections.ts` (the rest: shape checks, `customModels` entries without `key` or `credentialId`, `credentials` (the named API keys: a record id, a string `name`, a known `CREDENTIAL_TYPES` type, unique ids, `key` dropped, `clientEmail`/`projectId` kept only on `vertex`), the `hotkeys` merge of `defaultHotkeys` by `action`, `statics` counters, and the `{ items, selectedId }` records of `translatorPresets` (each preset through `createTranslatorPreset`: its steps normalized, 1 to 5, the old `{ prompt, maxResponse }` shape turned into one step) and `hypaV3Presets`, whose `selectedId` falls back to the first item). Each accepts `undefined` (materialization) and returns the fresh-boot value; a record or element of the wrong container shape is rejected. `characters.ts`: a character record is an object whose `chaId` is its id and that holds no `chats`, with the shared deterministic defaults filled in (`normalizeCharacter`, `shared/characters.ts`, the same helper the client applies at creation and before a save); a group whose `characters` is not a list is refused.
- `server/src/data/snapshots.ts` `createSnapshotManager`: periodic snapshots under `save/backups/`, the lock every whole-database operation takes (`exclusive`), `withMaintenance` (closes the `MaintenanceGate`, waits for admitted storage mutations), `track` (admits a resource handler or backup operation; refused after `stop`), `list`, `resolve`, `snapshotNow`, `start`, `stop`. `MaintenanceError` answers 503.
- `server/src/data/archive.ts`: the backup archive container (`encodeRecordHeader`, `indexArchive` with record-count and name-byte caps, `readRecord`, `copyRecordToFile`).
- `server/src/routes/resources.ts` `registerResourceRoutes`: `/api/resources` (multi-kind read), `/api/resources/read`, `/api/resources/batch`, `/api/resources/revisions` (registered before `/api/resources/:kind`), `/api/resources/:kind[/:id]`.
- `server/src/routes/backups.ts` `registerBackupRoutes`: `/api/backups` (list), `/api/backups/:id/restore`, `/api/backups/export`, `/api/backups/import`.
- `server/src/routes/proxy.ts`: `/proxy`, `/proxy2`, `/hub-proxy/*`. `ownBody` re-streams an upstream body and keeps the timeout alive until the body ends. A `risu-aux-op` header names one row of `server/src/llm/auxOps.ts`: the media and memory calls (`openai-tts`, `openai-dalle`, `openai-whisper`, `openai-embeddings`, `openai-completions`, `google-imagen`) and the model discovery, account, and count calls (`google-models`, `anthropic-models`, `openai-models`, `openrouter-providers`, `openrouter-models`, `nanogpt-balance`, `nanogpt-subscription`, `nanogpt-subscription-models`, `nanogpt-model-providers`, `nanogpt-models`, `ollama-cloud-tags`, `google-count-tokens`). JWT only; the row's exact HTTPS origin, path, and method (`GET` or `POST`; a GET or HEAD sends no upstream body); only the row's listed query parameters (`detailed` for the two NanoGPT model lists; any other is a 400; `key`, `api_key`, and `token` are dropped first); the stored credential (`openAIKey`, `supaMemoryKey`, `claudeAPIKey`, `openrouterKey`, `nanogptKey`, `ollamaApiKey`, or `google.accessToken`) injected as a bearer token, an `x-api-key` header, or the `key` query, replacing any the request carried; no redirect followed (a 3xx is a 502); every response header value without the credential (as stored and as injected, trimmed); an error body redacted, or, for JSON whose decoded keys or values carry it, replaced by a generic error; a successful JSON answer whose text or decoded keys and values carry it refused (502), and one that is not JSON or fails mid-read a 502 (504 on timeout or abort). The browser callers go through `src/ts/network/auxFetch.ts` (`global-api.md`).
- `server/src/routes/llmSecrets.ts` `registerLlmSecretRoutes({ store, kinds, auth, limiter, maintenance })`: the only way a client writes an `llmSecrets` credential. `PUT /api/llm-secrets/<path>` `{ value, baseRevision }` sets one (an empty value clears a leaf or removes a map entry), `DELETE /api/llm-secrets/<path>?baseRevision=` clears it. The path is the `shared/llmSecrets.ts` grammar (`<flat field>`, `<nested field>/<leaf>`, `OaiCompAPIKeys/~<id>`, `credentials/~<id>/key` (a named API key); each segment `encodeURIComponent`ed with `.` escaped, an id segment prefixed with `~` so that no id forms a dot segment, decoded once from the raw pathname). Each checks the JWT, the maintenance gate, the epoch, and the record's revision and writes in one synchronous block, and answers `{ epoch, revision, data }` with the masked record (`Cache-Control: no-store`); errors map as the resource routes do (`storeErrorResponse`). A value over 64 KiB is a 400. No value is logged or echoed.
- `server/src/routes/llm.ts` `registerLlmRoutes` and `server/src/llm/requests.ts` `createLlmRequests({ store, kinds, tokens, vertexTokens, claudeObserver, parentCallback })`: `POST /api/llm/request` runs `requestChatDataMain` of the server request layer (`llm-requests.md`) for the ids the body names (with `args.chatRef`, the chat's binding is checked as a job's, `send` mode; inside a callback of that chat's job the ids are compared with the job's targets, a `presetChain` pick included; a request without a chat is not checked) and answers with one ordered SSE stream: `accepted { id }`; side events (`log`, `notice`, `inlay`, `toolRecord`, `callback`); then `result`, or `streaming` with `chunk` events (per key `set`, `append`, `remove` against the previous snapshot; `chunkText` for a string chunk) and one `end` or `error`. A callback (`mcpTool`, `cbs`) waits 60 s from its event for `POST /api/llm/request/:id/answer`; a late, repeated, or unknown answer is ignored; a failed answer rejects it. A request ends once: its work finished, the stream was cancelled or the HTTP request aborted, the job callback its `channelCall` names settled, maintenance began (live requests are aborted and new ones answer 503 until it ends), or shutdown (`beginShutdown`; `dispose` waits at most 5 s); ending aborts every upstream fetch and settles every pending callback. More than 64 MiB of unread events ends it too. It is not a job: no chat lock, no persistence. A body with `channelCall` runs only while that job callback is outstanding for the same client (`generationJobs.parentCallback`), and its `bodyIntercepter` calls go through the job's channel as a child callback; without one, interceptors are skipped.
- `server/src/jobs/generationLock.ts` `createGenerationLock()`: the in-memory owner of each message a generation job writes (`chaId/chatId/messageId` → job, generation, token) and the live job tokens. The resource store reads it as its `MessageGuard`; the jobs `acquire`, `release`, and `endJob`.
- `server/src/jobs/generationJobs.ts` `createGenerationJobs({ store, kinds, gate, snapshots, lock, authorize, runner })`: the job registry (`shared/jobs.ts`). `create` admits one running job per chat (503 while shutting down or during maintenance, 412 for another epoch, 404 for a missing chat, 409 `chatBusy { jobId }`, checked before 409 `stale`, then the chat's binding: 409 `chatBindingIncomplete` with its `problems` (an unset or deleted field, or a pending import review) or `chatBindingMismatch` when the context's ids are not the chat's complete binding, for every kind, the previews included; `docs/plan/chat-binding.md`). The injected `GenerationRunner` gets a `RunningJob`: `signal`, `emit` (the registry adds the epoch; `accepted` is preceded by the job chat's hydration and always carries a `seq`; `done`/`error` end the job), `emitRecords` (fresh `resource` events, the job chat as a `chatPatch`; never `llmSecrets` or `authRefreshes`), `write` (`writeAsJob`, below), `channel` (above), `ownerAttached`, and `onClientMessage` (the owner socket's JSON from its current socket only). `emitRecords` returns the receipts of what it sent. A `command` job carries its `command` (`RunningJob.command`, a copy; null for other kinds; `GenerationCreateBody` is a union by `kind`). The default runner (`commandRunner.ts`) runs `command` jobs and the sends and previews (`server/src/prompt/runner.ts`). `setCallbackPreset(id)` changes the preset later callbacks name in their targets (a `presetChain` pick). Every abort (DELETE, the 30-minute limit, shutdown, maintenance) fixes one 5 s deadline, after which the job is ended for it. Ending is single: the first abort decides the outcome (a runner's `done` after it ends as the abort's error), a terminal that cannot be serialized becomes an error, the token dies, the job's locks and chat slot go, the chat's hydration and one terminal event are sent (a failing socket never stops the rest), and `finished` always resolves; later `emit`, `emitRecords`, and `write` throw `GenerationJobEndedError`. A job chat's `resource` event lists in `streaming` the job's messages of that chat still locked, each with its generation and the newest chunk `seq` the stored text includes (the runner declares it with the write: `write(build, { covers })`; every applied generation write replaces the claim with its own, and one without `covers` claims 0); a streamed text with a higher `seq` is newer than the copy. Only the current reply's generation is streamed: an older or foreign chunk is dropped, and a reply whose final write applied is no longer the current one. Events reach only sockets of the job's `clientId`, one at a time: an attach closes the job's older sockets (code 4001), and a handshake whose `attach` stamp is older than the newest admitted one is refused (409), so handshakes finishing out of order cannot displace the newest; nothing is buffered except what an attach re-sends (the job chat (a `chatPatch` while the job runs, whole once it ended) and every record it sent, read fresh; the last `preset`; the current `accepted` with the newest chunk's text and `seq`, only while its generation still owns the message; the terminal event). The job chat itself goes as a `chatPatch` (`GenerationChatPatchEvent`): the diff (`diffChat`) from `sentChat`, the copy the job last handed a socket (first the chat read at admission, at the revision the owner named), to the chat now: the new or changed messages as stored, each with the id before it, plus the stored rows of every message the job began a generation on (`generated`), the removed ids, the meta when it changed, and the count. `sendChat` (before `accepted` and at the end), `emitRecords` for the job chat, and an attach while the job runs send it; it goes whole when no patch expresses the change (another incarnation, a surviving message moved, a repeated or missing id), at the callback barrier (`hydrateAll`), on an attach after the end, and on the owner's `{ type: "resync" }` (`ChatResyncRequest`) from the current socket, followed by the current `accepted` while its generation still owns the message (`currentReply`, as an attach sends it). A socket taking the event moves `sentChat`; an event no socket took does not. Patches never include another chat. An ended job stays readable for 60 s.
- `writeAsJob` (`RunningJob.write(build)`): synchronous. Refuses an ended job, checks the maintenance gate, takes the lock of every `begin` op's message (a later `begin` of the job replaces the generation), and calls `store.applyChanges(changes, { epoch, jobToken })`; a final generation write whose checkpoint is `applied` releases its message only if its generation still owns it (so `[final(g1), begin(g2)]` keeps g2 locked). A conflict naming only resource records calls `build` again (it re-reads) and applies once more; any other conflict, or a second one, throws `JobWriteConflictError`. A failed call restores every owner it replaced.
- `server/src/routes/generations.ts` `registerGenerationRoutes`: `POST /api/generations`, `GET`/`DELETE /api/generations/:id?clientId=` (see Routes). A malformed `hooks` list is a 400 (`parseGenerationHooks`; missing means none), as is a `command` job without `command` (`{ type: "button", data }`, data at most 64 KiB of UTF-8), a `command` on any other kind, or a malformed optional `context.selectedPersonaId` or `context.client` (`{ viewport, browserLanguage }`). `selectedPersonaId` stays in the contract for requests without a chat; a chat job does not read it.
- `server/src/routes/transform.ts` `registerTransformRoutes`: `POST /api/transform` and `POST /api/transform/continue` (see Routes), over `server/src/prompt/transform.ts`. Handwritten parsers (`parseTransformRequest`, `parseTransformContinue`): every id a resource id, 1 to 64 targets with unique correlation ids, a `message` target with its message id and no other kind with one, `chatIndex` -1 or more, `cbsConditions` only `firstmsg` and `chatRole`, a source or text of at most 512 KiB and 4 MiB together, the body at most 8 MiB (its own `bodyLimit`); `client` is parsed as a generation's (`parseClientEnv`, the emotions dropped). The epoch header is checked after the body (412 `EpochMismatch`). A render writes nothing and does not hold the maintenance gate.
- `server/src/push/pushService.ts` `createPushService({ savePath, env, transport })` and `server/src/routes/push.ts` `registerPushRoutes({ push, auth, limiter })` (`docs/plan/web-push.md`): Web Push for chat completions. The VAPID pair is `RISU_WEB_PUSH_VAPID_PUBLIC_KEY` plus `RISU_WEB_PUSH_VAPID_PRIVATE_KEY` (both, else push is off), else `save/server/web_push_vapid.json`, generated on the first start and never replaced (an unreadable or invalid file turns push off; a pair counts as valid only when both keys are unpadded base64url, the public key a P-256 point, and the private key derives it); the contact is `RISU_WEB_PUSH_CONTACT` (default `mailto:risuai@example.invalid`; one that is not a `mailto:` or `https:` URL turns push off). Subscriptions (per browser, so not resources: not synced, not in snapshots or backups) are `save/server/push_subscriptions.json`, written through a temporary file and a rename, at most 50 (the least recently registered dropped). A subscription is accepted only with an `https:` endpoint on the default port of an allowed push service (`fcm.googleapis.com`, `android.googleapis.com`, `updates.push.services.mozilla.com`, `web.push.apple.com`, `*.push.apple.com`, `*.notify.windows.com`, plus `RISU_WEB_PUSH_ALLOWED_HOSTS`, comma-separated, a leading `.` for subdomains), a 65-byte uncompressed P-256 `p256dh` on the curve, and a 16-byte `auth`; the stored file is checked the same way when read. The endpoint host must be a plain DNS name (letters, digits, hyphens, dots: any other character a WHATWG host keeps ends the host for `url.parse`), and the endpoint is stored and posted to as its canonical WHATWG `href` (`web-push` parses with the legacy `url.parse`, which reads an escaped host such as `127.0.0.1%2enotify.windows.com` differently), and the keys unpadded. `register` (the PUT route) and `remove` change the list only after the file was written: a failed write is reported (`unsaved`, a 500) and leaves the list as it was; delivery bookkeeping is best effort, and while the file may hold what memory does not (a bookkeeping write failed, or the file was not valid JSON) a removal writes even for an endpoint memory lacks. A file that cannot be read at all is never replaced: registrations and removals answer 500 (the read is retried first each time) until it can be read. `send(notification)` delivers one completion at a time (at most 4 waiting, later ones dropped) to every subscription in parallel (TTL 1 h, urgency `normal`, topic `chat-completion`, a 10 s socket timeout), removes a subscription the push service answers 404 or 410 for, records any other failure as `HTTP <status>` or `network` (never the endpoint), and never rejects; `close()` (at `beginShutdown`) drops later sends. The routes: `GET /api/push/key`, `PUT`/`DELETE /api/push/subscription` (paths in `shared/notifications.ts`), JWT before the body is read (the subscription routes skip the global 100 MiB limiter and cap their bodies at 16 KiB). `createServerContext({ pushTransport })` injects the transport in tests; the context exposes `push`.
- `server/src/routes/translate.ts` `registerTranslateRoutes` and `server/src/translation/runner.ts` `createTranslationRunner({ store, kinds, gate, lock, llm, tokens, rootDir })` (`docs/plan/translation.md` slice 1.3): `POST /api/translate/message` (the path and its body/answer types in `shared/translation/route.ts`; the tab's caller is `src/ts/translator/storedTranslation.svelte.ts`, slice 1.4) translates one stored message with the translator pipeline (`shared/translation/pipeline.ts`) and stores it with a `setTranslation` chat op, whose commit reaches the tabs as their `chats` event. The body is `{ characterId, chatId, messageId, presetId, modelPresetId, personaId, force? }` (the chat's display ids, `chatDisplayIds`), authenticated before it is read and capped at 16 KiB (its own `bodyLimit`); the epoch header is checked after it (412). ## Routes

Registration order in `createServerContext`:

1. `onError` (`HTTPException` responses pass through; maintenance and a closed resource store answer 503 with `Retry-After`; other errors are a 500 `Internal Server Error`). Shutdown admission middleware runs before body parsing, tracks resource handlers (`/api/resources` and `/api/llm-secrets`), refuses new resource, credential, backup, and request history requests with 503, and adds `Connection: close` to every response during shutdown; every `/api/request-history` answer gets `Cache-Control: no-store` there, so a 429 or 413 carries it too.
2. `bodyLimit` (100 MiB, 413 `{error:"Request body too large"}`), skipped only for `POST /api/backups/import`, which streams its body to disk under its own cap.
3. `GET /` and `GET /index.html` (one shared handler), then the same handler for the client's screen routes: a `GET *` handler serves it when `isClientRoutePath` (`shared/routes.ts`: first segment `chat`, `playground`, `realm`, `characters`, or `settings`) matches and passes every other path on (`docs/plan/url-routes.md`).
4. `serveStatic` for every other GET/HEAD.
5. The routes below.

Routing is non-strict (a trailing slash matches).

## Flows

Boot:

1. `pnpm runserver` runs `node server/src/main.ts`.
2. `createServerContext` creates `save/` if missing. `createAuthStore` creates `save/server/` and loads `password` and `known_public_key_hashes.json` from it. `registerStorageRoutes` recreates `save/.tmp/` empty.
3. `serve()` listens on HTTPS or HTTP. A listen error (e.g. `EADDRINUSE`) logs and exits 1.

Client detection:

1. `GET /`, `GET /index.html`, and the client route paths inject `__NODE__`, which makes `isNodeServer` true in the client. Without it the client shows only the `NodeServerRequired` notice, so no route may serve `index.html` raw.
2. The client always uses this server (`storage/assetClient.ts` for assets, `storage/serverAuth.ts` for auth).

Development (`pnpm dev`):

1. Run `pnpm runserver` and `pnpm dev` side by side. The Vite dev server (port 5174) injects `__NODE__` into its own `index.html` (plugin `risu-node-flag`, serve only) and proxies `/api`, `/proxy`, `/proxy2`, and `/hub-proxy` (including the WS upgrade) to `RISU_DEV_SERVER` (default `http://localhost:6001`; set `https://...` when the server found a certificate).
2. The dev origin keeps its own IndexedDB `DPoPDB` key pair, so it logs in separately from the server origin.
3. The server sees every proxied request as coming from the Vite process, so all dev clients share one rate-limit bucket (including the 10-per-30 s login limiter). The dev proxy does not add `X-Forwarded-For`, so `TRUST_PROXY` alone does not separate them.
4. The client's auth (`serverAuth.ts`) needs `crypto.subtle`, so open the dev server via `localhost` (a plain-HTTP LAN address is not a secure context).

Auth:

1. The client's auth check (`serverAuth.ts`) creates an ES256 JWT (P-256, 5-minute expiry, public JWK). The key pair is kept in IndexedDB `DPoPDB`, entry `node`.
2. It calls `/api/test_auth`, then either `/api/set_password` followed by `/api/login` with the same digest (first run, so the first request is already authorized) or `/api/login`. One check runs at a time for the whole tab (one auth state).
3. Once logged in, the server knows the key hash, and later requests only send the JWT.

Resources and saving (client side: `persistence.md`):

1. The client reads every kind and every chat with one `GET /api/resources?kinds=...&chats=1` at boot and keeps the epoch.
2. Its save adapter sends one `/api/resources/batch` per save cycle: resource ops, chat groups (one per chat: its ops on the chat revision they were based on), and chat reorders. All of them are validated and normalized first, then every base revision is compared inside one transaction; any conflict rolls the whole batch back and the 409 lists all of them (resource conflicts, `kind: "chat"`, `kind: "chatOrder"`).
3. Chat groups: `create` (first op; the chat with its messages, inserted in the order at `index`), `delete` (alone), `replace`, `meta` (`set`/`unset` per field), `append` (at the end, the start, or after a message id), `setMessage`, `setText`, `remove`, `begin`, `setTranslation`. A group result carries the chat's new revision, the ids of messages it created, the outcome of each generation-carrying op (`applied`, `duplicate`, `ignored`), the outcome of each `setTranslation` (`translations`: `applied`, or `ignored` when the message's text no longer matches the translation's `sourceHash`; `null` always clears), and `stale: true` when it applied on an older revision. `setMessage` never changes a stored `translation`: the stored one (or its absence) replaces the sent message's. `setTranslation` leaves the generation fence alone.
4. Deleting a character deletes its chats and chat order in the same transaction.
5. Inlays and plugin permission grants use the single-record routes.

Snapshots and restore:

1. `startBackgroundTasks` starts a timer (10 minutes). A tick takes a snapshot only when committed writes happened since the last one: `backupTo` writes `.<name>.tmp`, switches it to rollback-journal mode, and renames it to `resources-<UTC yyyymmddThhmmssmmmZ>-<8 hex>.sqlite`; the newest 20 are kept.
2. Restore (`/api/backups/:id/restore`) runs under maintenance: epoch check, `readSnapshot` (integrity check, layout version, real `resources`/`meta`/`chats`/`messages`/`chatOrders` tables with this store's columns and an epoch, then every row: registered kind at its schema version (rows of a retired kind are skipped), valid id, singleton rules, unique kind and id, JSON the kind's normalizer accepts; every chat, message, fence, and order row, with each chat's parent character and each order a permutation of its chats; positions compacted), a safety snapshot, a second epoch check, then `replaceAll` in one transaction with a new random epoch. Every token issued before is stale afterwards.

Backup archives:

1. The container is concatenated records of `u32le nameLength`, the UTF-8 name, `u32le dataLength`, and the bytes. Version 2 starts with `manifest.json` (`{ version: 2, createdAt, partial, assets, missing }`), then `resources.sqlite` (a fresh copy), then each asset under its full key `assets/<name>`.
2. Export takes the database copy first (the staged copy then loses its `llmSecrets` row and is `VACUUM`ed, so the archive carries no LLM credential; snapshots on the server keep it), then selects assets: every file of `save/assets`, explicit `partial` keys, or, for `partial: true`, `shared/backups.ts` `selectPartialBackupAssets` over that same staged database's `characters`, `personas`, `ui`, `characterOrder`, and `presets` rows. The direct query parses only those rows, without `readSnapshot` or chat reads. Thus partial profile selection follows the archived resource state even when another writer changed an image after the client's inventory. Requested or selected keys that cannot resolve to storage or have no eligible file enter `missing`; the partial-key and archive-record caps still apply. The copy lives in `save/.tmp/export-<uuid>/` and is removed once, when the stream ends, is cancelled, or the client left before it started. An asset listed in the manifest that can no longer be read fails the stream.
3. Import authenticates and checks the epoch before reading the body, spools it to `save/.tmp/import-<uuid>/` with a byte count, then validates the whole archive before writing anything: manifest first and unique, the declared assets exactly the asset records, exactly one `resources.sqlite` that `readSnapshot` accepts, only `assets/` keys. Refused: a Risu Account archive (`encryption.risudat`), an archive from before version 2 (`database.risudat`), a truncated or malformed one. `coldstorage_*.json` records are ignored. Then, under maintenance: epoch check, safety snapshot, assets that do not exist yet are added by hard link (existing files are never overwritten), and `replaceAll`. One import at a time.

Shutdown:

1. `beginShutdown()` sets the shutdown flag, closes generation admission and aborts every job (their 5 s deadline starts here), ends every server translation, removes the upgrade listener, stops the snapshot timer and backup admissions, and disposes proxy jobs and limiters. Middleware refuses new resource and backup requests with 503 plus `Retry-After: 5`; every response during shutdown carries `Connection: close`, including a request admitted before the signal. Resource handlers are tracked before body parsing or auth and retain access to the open store. Backup operations retain their existing admission boundary.
2. `main.ts` awaits `server.close()` for at most 8 seconds, then calls `closeAllConnections()` before `dispose()`. Disconnects abort unfinished body reads and export streams; `dispose()` waits for the generation jobs to end (already bounded by their deadline), disposes the script workers, and awaits admitted handlers and backup cleanup before closing the database. The deadline leaves cleanup time within Docker's default 10-second stop timeout.
3. In-process callers use `dispose()` alone: it runs the begin step and waits for the jobs and admitted operations before closing.

Restore and import (`withMaintenance`): the `onMaintenance` listeners run under the snapshot lock while writes are still open. The jobs' listener closes generation admission, aborts every job with `maintenance`, and waits for their end, so an abort checkpoint lands in the old database (and in the safety snapshot); the translation runner's listener ends every server translation (none writes after); then the gate closes and the replacement runs. Admission reopens when the maintenance ends. A leftover store access raises `ResourceStoreClosedError`, mapped by both resource routes and `onError` to 503 with `Retry-After`, including reads.

Proxying:

- The client sends `risu-url` and `risu-header` (encoded JSON) to same-origin `/proxy2`.
- The request body is forwarded as raw bytes. `HEAD` fetches upstream with GET and returns headers only.
- Upstream request headers (`buildUpstreamHeaders`, case-insensitive):
  - The decoded `risu-header` must be a JSON object. Anything else is a 500.
  - Stripped: `host`, `connection`, `keep-alive`, `proxy-connection`, `transfer-encoding`, `te`, `trailer`, `upgrade`, `content-length`, `risu-auth`, and every field named in `Connection`. A `Connection: authorization` therefore drops `Authorization`.
  - `x-forwarded-for` is added only when absent.
- `/hub-proxy` forwards the incoming headers minus `host`, `connection`, `content-length`, `x-risu-node-path`, and `risu-auth`, and sets `origin`.
- `/proxy` and `/proxy2` response headers drop CSP, `clear-site-data`, `cache-control`, `content-encoding`, `content-length`, and `transfer-encoding`.
- On `/proxy` and `/proxy2`, `risu-timeout-ms` covers the whole exchange (`/hub-proxy` has no timeout):
  - Before upstream headers it returns 504 `{error}`.
  - Mid-stream it ends the response cleanly.
- A client disconnect aborts the upstream fetch on `/proxy`, `/proxy2`, and `/hub-proxy`.
- Node local-network streaming uses the job and WebSocket protocol with events `job_accepted`, `upstream_headers`, `chunk` (base64), `error`, `done`, and `ping`. Heartbeat is 5–60 s. Jobs have a 30 s done-grace period.
- Stream-job targets must pass `sanitizeTargetUrl`/`isLocalNetworkHost` (`ipaddr.js` ranges):
  - allowed: `localhost` and `*.local`;
  - IPv4 in 10/8, 172.16/12, 192.168/16, 127/8, 0/8, or 169.254/16;
  - IPv6 in fc00::/7 or fe80::/10, `::1`, and IPv4-mapped forms of those IPv4 ranges (bracketed URL hosts are accepted).
  - Single-label hosts other than `localhost` are rejected, although the client's `localNetwork.ts` treats them as local. The client also rejects IPv4-mapped IPv6.
- Stream-job forwarded headers are lowercased, then `risu-auth`, `risu-timeout-ms`, `host`, `connection`, and `content-length` are dropped.
- DELETE, the deadline, GC cleanup, and `dispose()` abort the job's upstream request and response even after upstream headers arrived. Deadline cancellation can deliver an `error` event to connected clients (the former client helper showed every 504 as a timeout). DELETE, GC cleanup, and `dispose()` close the WebSockets without guaranteeing a final event.

### Changes from the former Express server

- `/proxy` and `/proxy2` POST forward raw bytes. Express re-serialized parsed JSON and turned urlencoded bodies into `"{}"`.
- `risu-auth` is never forwarded upstream by `/proxy`, `/proxy2`, or `/hub-proxy`, and header stripping is case-insensitive.
- `HEAD` on `/proxy` and `/proxy2` returns headers only and closes the upstream.
- The proxy timeout spans the streamed body; a mid-stream timeout ends the response cleanly.
- A client disconnect aborts `/proxy`, `/proxy2`, and `/hub-proxy` upstreams.
- Batch `/api/remove` works. A missing `file-path` is a 400; Express never answered it.
- JSON bodies: malformed, whitespace-only, or primitive JSON is a 400. `set_password` persists before updating memory. Zero-length `/api/write` bodies are written.
- Stream-job targets use `ipaddr.js` ranges, which adds bracketed and IPv4-mapped IPv6 literals. Stream-job DELETE, deadline, GC, and dispose stop active upstreams.
- Static files use `@hono/node-server` `serveStatic`:
  - supported: ranges and `Last-Modified`;
  - no ETag, conditional requests, or `Cache-Control`;
  - a directory path serves its `index.html`, where Express had `index: false`.
- `/api/read` has no ranges or ETag.
- No request decompression or charset-aware decoding; JSON text is read as UTF-8.
- `/api/crypto` and `already set` are `text/plain`, not `text/html`. The 404 and 500 bodies are plain text.
- Paths are case-sensitive, a trailing slash is tolerated, and there is no automatic `OPTIONS`.
- The display transform's Lua cost, measured at the closeout (`util/playwright/measureTransformLua.mjs`, three logged runs at commit `2f658598` plus the closeout's changes, medians of each: the server in process with the real store and workers, a 200-message chat with one module trigger `listenEdit("editDisplay", ...)`, every target uncached and checked): a warm 200-target render in the tab's four concurrent chunks takes 142–145 ms with the module (0.71–0.73 ms per target) and 68–70 ms without it (0.34–0.35 ms); a one-target request takes 2.8 ms with it and 1.7–1.8 ms without. Each Lua trigger invocation of each target runs on its own engine from the worker's prepared pool. The cold first render (the workers booting) took 288–306 ms. Far below the 50 ms per target that would call for engine reuse per batch.

## State

Disk, under `save/`:

- `server/password`: the client-side SHA-256 digest via `/api/crypto`.
- `server/known_public_key_hashes.json`. Deleting only `password` lets you set a new one but does not revoke registered clients; delete this file too for that.
- `server/web_push_vapid.json` (mode 600): the Web Push VAPID pair. Replacing it (or the `RISU_WEB_PUSH_VAPID_*` variables) leaves every browser subscribed with the old key: each subscribes again the next time it opens the app.
- `server/push_subscriptions.json` (mode 600): `{ version: 1, subscriptions: [{ endpoint, keys: { p256dh, auth }, expirationTime, failureCount, lastError?, updatedAt }] }`.
- `.tmp/`: staged writes and the per-operation export/import staging folders, emptied at startup.
- `data/resources.sqlite` (plus its `-wal` and `-shm` files): the resource store. Table `resources` (`seq` autoincrement, `kind`, `id`, `revision`, `schemaVersion`, `data` JSON text, unique `(kind, id)`), table `meta` holding the random `epoch`, table `chats` (`seq`, `characterId`, `id`, `revision`, `schemaVersion`, `meta` JSON), table `messages` (`chatSeq`, message `id`, integer `position`, `data` JSON, and the generation fence: `generationId`, `generationSeq`, `generationFinal`, `generationHistory` of up to 8 earlier ids), and table `chatOrders` (`characterId`, `seq`, `revision`, `ids` JSON); `PRAGMA user_version` is the store version (3: the Phase 3 sections and collections, no `root` record; the tables are those of version 2). Opening the store and every `replaceAll` run the normalization pass in one transaction: each record whose normalized text or schema version differs from the stored one is rewritten with its revision counter advanced (same `seq` and epoch), and each missing `materialize` singleton is created; a stored record its normalizer rejects, or one of a newer schema version than its kind, stops the start. A version-1 file or version-2 file (settings in a `root` record, before Phase 3) is refused at startup with a message naming it, and a snapshot or archive of another version is refused on restore; there is no migration. The connection runs with `journal_mode=WAL`, `busy_timeout=5000`, and `foreign_keys=ON`. `data/` is not a storage namespace.
- `backups/`: resource snapshots (`resources-*.sqlite`, single files, newest 20), not a storage namespace. Assets are not in snapshots.
- User files: a logical key `assets/<name>` lives at `save/assets/<encodeFileName(name)>`, e.g. `assets/<sha>.png` or `assets/inlay_<sha256>.png`. The `save/database` and `save/remotes` folders of versions before Phase 1 are left in place and no longer read.
  - `encodeFileName` keeps `a-z 0-9 . _ -` readable and writes every other UTF-8 byte (uppercase letters, `/`, `%`, spaces, non-ASCII) as `%XX`. It also escapes a trailing dot and the first character of a Windows device name (`con.png` → `%63on.png`). A name whose readable form exceeds 255 bytes is stored as `~<lowercase hex>`; longer than that is rejected.
  - Only one encoding per name is canonical, and canonical names never differ by case alone, so case-insensitive filesystems do not merge keys.
  - The old flat layout (hex file names and `__password` directly in `save/`) is not read and was not migrated.

Process memory, inside the `createServerContext` closure:

- `password` and the known key hashes.
- The generation jobs (registry, chat slots, sockets) and the generation lock. A restart loses both: running jobs end with the process, and the Phase 2 fence of their messages closes on the next ordinary write.
- Rate-limit counters.
- The resource store's epoch and committed-write counter, the snapshot lock, the maintenance gate, and the import-in-progress flag.
- The change feed's listeners and the live-update sockets (nothing is buffered; a restart loses them, and every client reconciles at its reconnect).

## Invariants

- Live updates: every committed change is published by the resource store itself, so every writer (the routes, the generation jobs' in-process writes, a restore) reaches the feed only through the store's write methods. `put`, `delete`, `applyChanges`, and `transaction` collect the refs they change, side effects included (creating a character creates its chat order; deleting one deletes its chats and order), drop them when the write throws (it rolled back), keep a record's final revision when it changed twice, and publish once after the commit and after `transactionState` is cleared; a write inside `transaction` publishes with it. `replaceAll` publishes `epoch` after the new epoch is installed. The feed carries refs and revisions, and data only as a patch op's record patch (`feedPatch`) with its base revision, one write earlier: for an object record every top-level field whose stored JSON value changed (`RecordFieldPatch`, `diffFields`; normalization included), for an item list the changed items (`RecordItemPatch`, `diffItems`: a new item or one whose `__proto__` changed whole, another changed item as its changed fields, the id order when it changed). None (a plain ref) for a kind with `project` or a hidden hydration kind (so a `llmSecrets` or `authRefreshes` change never carries data), a record written twice in the scope, a changed top-level `__proto__`, a list without unique item ids, or a patch over `MAX_FEED_PATCH_BYTES` (64 KiB). For a `shallowNormalize` kind (`characters`, `modules`: the normalizer changes nothing it is given and keeps the fields or items it does not replace by reference) a patch op serializes only what changed (`writePatch`, `patchParts`): the stored text is cut into its top-level fields or items (`cutRecord`, only when the text is exactly its parts joined as `JSON.stringify` joins them), the patched parts and whatever the normalizer replaced are serialized and checked alone, in the record's order and with their own keys (`storedParts`), and the rest is reused as stored text; the result is the text a whole `serialize` would give. The last 4 cut records (64 Mi UTF-16 units counting each text twice; the parsed values are not counted; a larger record is not kept) are cached and reused only while the stored text is exactly theirs, so a rolled-back write, a restore, or any other write falls back to a new cut (one parse and one serialization per field). The feed gets a copy of the patch, never the cached values. About 220 ms → 15 ms per patch of a 9.6 MB character, measured in Vitest. Any other kind, or a record that cannot be cut, still parses, normalizes, and serializes the whole record. Whole writes (a job's, an MCP tool's, an import) still publish plain refs.
- Storage routes never use a raw path. `decodeKeyHeader` requires even-length hex and valid UTF-8 (verified by an exact byte round trip), then `resolveStorageKey` requires a namespace from `STORAGE_NAMESPACES` (only `assets`) and encodes the whole rest of the key, `/` included, into one file name. Only these folders are reachable; `save/server/` and `save/.tmp/` are not.
- Unsupported keys: malformed hex/UTF-8 is 400 `Invaild Path` on every route. A well-formed key with no storage location (other namespace, empty or too-long name) reads as missing (empty 200, no disk access), because the client reads whatever paths an old database stored; `write` and `remove` reject it with 400.
- `/api/list` returns only regular files whose names are canonical `encodeFileName` output, so every listed key reads back the same file. Other entries (subfolders, symlinks, noncanonical file names) are ignored.
- Keep the logical keys and the hex wire encoding; the client depends on both. The mapping to file names must stay reversible and injective.
- Keep these unchanged:
  - the `__NODE__` injection;
  - the `risu-*` header names and `x-risu-node-path`;
  - status codes and JSON error bodies, including the `Invaild Path` typo (one deliberate change: a `/api/read` filesystem error other than a missing file, symlink, or non-regular file is now a 500 instead of an empty 200);
  - the 100 MiB body limit (the backup import is the one route exempt from it).
- Rate limits must keep matching the former express-rate-limit v8 setup:
  - thresholds as in the Routes table;
  - windows start at a key's first hit;
  - IPv4-mapped IPv6 keys collapse to IPv4, other IPv6 addresses to their /56;
  - draft-6 `RateLimit-*` headers, plus `Retry-After` on 429.
- `TRUST_PROXY` keeps Express `trust proxy` semantics via `compileTrust`:
  - a number is a hop count;
  - a string is a comma list for `proxy-addr` (`loopback`, CIDRs, ...);
  - an invalid value fails at startup.
- `JSON` routes (`readJsonBody`):
  - a non-JSON content type or a zero-length body is `{}`;
  - malformed JSON (including whitespace only) or a top-level primitive is 400 `{error:"Invalid JSON body"}`.
- The WebSocket upgrade handling is one `upgrade` listener (`attachWebSocket`) on the server returned by `serve()`, dispatching by path to the `ws` handlers (`generationJobs.handleUpgrade`, `eventSockets.handleUpgrade`); each matches its path synchronously and returns false without touching another path's socket. Do not add a second listener, pass `websocket` to `serve()`, or add `@hono/node-ws`.
- Generation lock: a change that rewrites or removes a message a generation job owns (`setMessage`, `setText`, `setTranslation`, a `remove` naming it, `begin` on it, `replace` or `delete` of its chat), or deletes a character holding one, is a 409 whose entry carries `reason: "generating"` (the single DELETE route: the body's `reason`), unless it is the owner's in-process write carrying its job token. The check runs inside the transaction before the revision checks, so a stale change of a locked message also reads as `generating`. `meta`, `append`, and edits of other messages apply. The token never leaves the process; a client-supplied generation id grants nothing. Every generation is a server job since the cutover; the Phase 2 fence stays for the tab's own writes.
- Job writes name the job's admitted epoch and live token, checked in the same synchronous call as the write; an ended job's token is dead (`JobTokenError`). No transaction spans a provider call: each job write is its own `applyChanges`.
- Resource revisions: a token is `<epoch>:<seq>:<revision>`, opaque to clients. A write matches all three parts, so a token from another database epoch, or from a deleted and recreated record (new `seq`), never passes. `baseRevision: null` creates and conflicts if the record exists; a write to a missing record is a 409 with `revision: null`. A token string that does not parse, including an empty `?baseRevision=`, is a 409 with the current revision; a `baseRevision` of the wrong JSON type, or a DELETE without the query parameter, is a 400.
- Resource writes normalize inside the store: `put` runs the kind's `normalize` once and stores its JSON result. A normalizer sees the stored form of its input (`serialize` runs first), so a nested non-finite number or over-deep input is refused before a JSON copy inside the normalizer could hide it. Reads never normalize; a new default or migration reaches stored records only through the normalization pass at the next start, so every normalizer must be idempotent (its output normalizes to the same JSON) or the pass rewrites that record on every start. A removed kind goes into `RETIRED_KINDS` (`resourceStore.ts`; `customSidebarItems`): the pass deletes its stored records and `readSnapshot` skips its rows, so older databases and backups still open and restore. The store is built with the kind registry and every method refuses a kind object the registry does not hold, so no caller can swap in another normalizer. A value is stored as `JSON.stringify` produces it (`toJSON` applies, `undefined` fields drop, Dates become strings, `-0` becomes `0`), and `put` and later reads return that stored form. `put` refuses, with `ResourceValidationError` (400), data whose JSON form would turn a non-finite number into `null` (`1e400` parses to `Infinity`), data `JSON.stringify` cannot serialize (a bigint, a cycle, a throwing getter, runaway nesting), and a JSON form nested deeper than 256 levels. `transaction(fn)` is one synchronous `BEGIN IMMEDIATE`; a throw, or any conflict inside it even if `fn` caught it, rolls back every write. A body whose return type can be a promise does not type-check (`TransactionBody`, best-effort: a body returning `any` passes, and an overloaded function reference is judged by its last overload, so wrap it in a zero-argument arrow), and at runtime a returned promise or thenable rolls back and throws. An `AsyncLocalStorage` scope follows the work the body starts through awaits, promise continuations, and timers: once the body returns, a write from that work throws, so it cannot autocommit after a rollback. Callbacks the body registers on an event emitter do not carry the scope and are not covered. Never await inside a transaction.
- Resource ids: 1-512 UTF-16 code units of well-formed Unicode, no control character, not `.` or `..`; clients encode them once with `encodeURIComponent` (so `§playground` and `assets/x.png` are valid ids). A singleton kind accepts only `main` and cannot be deleted.
- Epoch fencing: every mutation (PUT, DELETE, batch, restore, import) names the epoch in `x-resource-epoch`, checked in the same synchronous block as the write (restore and import check again inside maintenance), so nothing based on data from before a restore lands, including a create with `baseRevision: null`. Reads return the epoch; tokens stay opaque.
- Batch operations are `{ kind, id, baseRevision, data }` or `{ kind, id, baseRevision, delete: true }` (a string base revision); duplicates of one kind and id, both or neither of `data`/`delete`, unknown kinds, and invalid ids are 400 with the operation index.
- Chat groups (`chats[i]`): one per chat; `baseRevision` is null exactly for a group that starts with `create`; `create` only first and `delete` only alone; a batch that deletes a character and names its chats is 400. Every validation error names the group and op (`chats[i].ops[j]: ...`), including data refused only once merged inside the transaction (a `meta` patch), so a client can quarantine that one chat. A chat create under a missing character is a 409 chat conflict with revision null.
- Chat revisions: every applied op moves the chat's revision (a replayed or no-op op does not). By-id ops (`append`, `setMessage`, `setText`, `setTranslation`, single `remove`, `meta`) apply to an older revision of the same chat incarnation while their message exists; `replace`, `delete`, a multi-id `remove`, reorders, and a `begin` of an unknown generation need the current revision (a `begin` on a message appended in the same group does not). Replays are idempotent: an identical `append` of an existing id and a single `remove` of a missing message are no-ops; an `append` of an existing id with other content is a 409.
- Reorders (`chatOrders[i]`: `{ characterId, baseRevision, ids }`) compare the order revision from before the batch; `ids` must be a permutation of the character's chats (400 otherwise).
- Generation fence (per message): `begin` takes the message over for a generation id (the previous id goes to the history). A write carrying `{ id, seq, final? }` is `applied` when it is the current generation with a higher `seq` and not final yet, `duplicate` when its `seq` was already applied, and `ignored` otherwise (another generation, or after `final`). A `setMessage` or `setText` without a generation closes an open fence; a `setTranslation` leaves the fence as it is. `replace` keeps the fences of surviving messages closed.
- Maintenance (restore, import) closes resource and storage mutations with 503 and waits for storage writes already admitted; a restore or export that arrives meanwhile waits for the lock instead.
- `llmSecrets` is write-only: no route answers a stored credential. The reads answer `maskLlmSecrets` (each credential leaf `{ set, hint }`, `hint` the last four characters of a value of at least 16; the maps keep their nesting), a resource write may carry no credential path (400) and keeps the stored ones, the credentials change only through `/api/llm-secrets/*`, an exported archive holds no `llmSecrets` row, and an auxiliary operation's success answer carrying one is refused. Importing an archive (which has no row) materializes an empty record: every key is gone.
- Backup import never overwrites an existing asset file; resources are replaced atomically, assets are only added.
- Docker persistence depends on `/app/save`. Removing the volume loses the password, registered keys, and all data.
- The `ui` normalizer does not coerce `chatLoadInitialPages`/`chatLoadAdditionalPages`: a numeric string such as `"12"` falls back to the default.
- The `presets` normalizer (`normalizePresets`) turns a non-list or empty list into one default preset, canonicalizes every element, and gives a duplicate id a fresh one, before any selection resolves against the list.

## Recipes

- Add a storage operation:
  - Add a route in `routes/storage.ts` with `auth.checkAuth`, the shared limiter, `decodeKeyHeader`, and `resolveStorageKey`.
  - Add the matching client function in `src/ts/storage/assetClient.ts`.
- Add a storage namespace: add it to `STORAGE_NAMESPACES`; the client key prefix is the folder name.
- Change auth:
  - Client: `src/ts/storage/serverAuth.ts` (`createAuth`, `checkAuth`, `digestPassword`).
  - Server: `routes/auth.ts` (`verifyJwt`, the `/api/login` route).
  - Verify first run, restart, token expiry, and unknown keys.
- Change proxy policy: server `sanitizeTargetUrl`, client `localNetwork.ts` + `fetchNative`.
- Change generation jobs: `shared/jobs.ts` (the contract), `server/src/jobs/generationJobs.ts`, `server/src/routes/generations.ts`, the client transport `src/ts/network/generationJobs.ts`, and the client primitives (`applyServerGeneration`, `hydrateChat`, `applyHydration`, `persistence.md`).
- Add a resource kind: add a `ResourceKind` to `DEFAULT_RESOURCE_KINDS` with a pure, idempotent `normalize` (throw `ResourceValidationError` to reject), a `schemaVersion`, `singleton` if it has one record, and `materialize` if the store should create that record (then `normalize(undefined)` must return its default); the routes, snapshots, and archives pick it up. Add the kind name to `RESOURCE_KIND` in `shared/resources.ts` for the client.
- Change the archive format: `server/src/data/archive.ts`, `planImport` and the export in `routes/backups.ts`, `BackupArchiveManifest`, and the client reader in `src/ts/drive/backuplocal.ts`; bump the manifest version.
- Change packaging: `Dockerfile`, the README Docker steps, and `package.json` `runserver` together. Any new root folder the server imports at runtime (like `shared/`) needs a `COPY` in the `runtime` stage.

## Known Hazards

- A server job's rotated MCP refresh token is fenced like its other writes: a job aborted or a client closed while a rotating refresh is out drops the new token, although the MCP server has already spent the old one, so the stored entry keeps a spent token and the next refresh falls back to a full login.
- Local models run in a child process, so loading and inference do not hold the main thread, a kill stops them, and a native crash ends that process only (the task fails; the next one forks again). It is not a memory boundary: the process has no limit of its own, and under memory pressure the system or the container may end the server instead. Nothing bounds what a model allocates: embeddings hold about 0.2 to 0.6 GB while loaded, the captioner and the summarizer about 0.7 to 1 GB each for a call, a generation model its `fp32` weights (about 1.3 GB for `opt-350m`). The task queue is unbounded, and so are the model files under `save/models/transformers`, which are downloaded from `huggingface.co` on first use (a host without that access cannot use a local model; a file fetched once is reused offline).
- The vector cache bounds its vector bytes, not its file, and its trim runs on the main thread (a large eviction holds it for that time). It is shared by every client and keyed as the client keys it: by model name, not by endpoint (`memory.md`).
- A cancelled rate-limited batch (`shared/taskRateLimiter.ts`: HypaV3's experimental summaries, `HypaProcessorV2`'s API embeddings) leaves its retry timer running until the rate window passes (up to a minute); it starts nothing, but it holds the event loop for that time. The limiter is the client's, moved unchanged.
- Memory on the server calls the embedding and summary providers from the server process: the custom embedding URL is fetched as the settings name it, with no local-target restriction (the hazard recorded for provider URLs).
- The redactor (`server/src/llm/redact.ts`) knows a credential as stored, JSON-escaped, and as `encodeURIComponent` writes it (uppercase escapes). A percent-encoding with lowercase escape digits, or any other reversible encoding, is not matched: in a request log, a job error, or the completions answer check of memory.
- `voyageApiKey` and `hypaCustomSettings.key` are in the client-readable `secrets` section: a job's settings projection (`scope.db`) holds them. They are used inside `embeddings.ts` only and redacted from its errors; no host function, CBS function, or notice returns a settings field by name.
- `put` validates a value's depth on its parsed JSON form, so an over-deep value is rejected only after it has been fully serialized and parsed. Over HTTP the body is already parsed and capped at 100 MiB; only in-process callers could pass costlier values (getters, `toJSON`).
- The resource store assumes one server process and a local filesystem for `save/data/` (SQLite WAL uses shared memory; network filesystems are unsupported). Snapshots cover only `save/data/`; deleting both `save/data/` and `save/backups/` loses every resource.
- Snapshots do not hold assets, and inlay blobs are never deleted (a retained snapshot may reference them), so `save/assets/` only grows. Restoring the oldest retained snapshot can evict that file through the safety snapshot's retention (it was read in full first, so the restore itself succeeds).
- Restore and import validate and install the database synchronously on the serving thread; a very large database blocks other requests for that time.
- An asset over 4 GiB cannot be stored in an archive record and is reported as missing by an export.
- Storage writes stage into `save/.tmp/` and `rename` onto the target: atomic replacement, but no fsync, so no power-loss durability. `save/.tmp/` must be on the same filesystem as the namespace folders (one Docker volume at `/app/save`). One server process per `save/` is assumed: startup deletes `save/.tmp/`, and concurrent writes to one key are last-writer-wins. A failed rename (e.g. a Windows file locked by another process) returns 500 and keeps the old file; the server does not retry. The client save adapter retries resource batches with backoff; asset writes are not retried.
- Auth files are still written directly with `writeFileSync` (not atomic).
- `/api/read` opens with `O_NOFOLLOW | O_NONBLOCK` where the OS has them and takes size and bytes from one handle. Namespace folders themselves are trusted: a symlinked `save/assets` is followed. A hostile local process modifying `save/` is out of scope.
- The chat fence orders one client's generation writes; it does not lock a message against another device (a manual write from anywhere closes the fence).
- A batch remove stops at the first filesystem error, such as a missing file. It returns 500, and files deleted before the error stay deleted.
- `/api/set_password` and `/api/crypto` have no auth and no rate limit. The first caller can set the password, and an empty password leaves the server effectively unset.
- `/proxy`, `/proxy2`, and `/hub-proxy` (through `x-risu-node-path`, unauthenticated) forward to arbitrary targets. Only proxy jobs are restricted to local targets.
- JWT validation checks no issuer, audience, `typ`, or `iat`, and a token without `exp` never expires.
- Server CBS evaluation runs on the main thread under cooperative limits (`shared/cbs/limits.ts`), not under a hard deadline or a heap bound: the limits are checked at every `{{` and `}}`, every 4,096 work units, and inside the counted registry loops, so one operation between two checks runs to its end (a host call, one function on an input the budget allowed), and a result is charged before it is built only for the amplifying operations (`replace`, `join`, `cbr`, `range`, `#each`, `call::`, `#pure_display`); `split` and `history` build theirs first (a `history` over a 100M-character chat peaks near 380 MB before it is refused). Scanning costs memory too: a 9M-character text peaks near 460 MB of RSS. A job whose templates each stay under the limits can still hold the thread for up to its 60 s allowance; prompt assembly does not yield between its evaluations (the native effect loop does, after 50 ms). Hard interruption would need a worker or process boundary.
- Other main-thread work on card or model text has no bound: token encoding after its load (`tokenizers/index.ts`), Jinja rendering (`shared/prompt/chatTemplate.ts`), lore matching outside its worker regexes, and the calculator called directly by `v2Calculate` (outside the CBS allowance; the effect converts each `$name` reference itself, once per reference).
- A server trigger writes every chat-variable and author's-note change to the store as it happens (the tab writes its mirror), and each write sends the job's chat to the tab: a trigger loop that sets a variable on every iteration costs one SQLite transaction and one chat event per change (about 0.2 ms per write locally; 100,000 effects take about 11 s).
- `/api/llm/request` fetches every configured provider URL from the server: a provider on the browser's `localhost` is reached only when the server runs on the same machine (in Docker, `localhost` is the container; configure `host.docker.internal` or the host's address). Like `/proxy2`, it fetches whatever URL the stored settings name.
- A server send reads the job's chat again after its own writes and its callbacks (`refreshChat`), not only its own and acknowledged writes: an unrelated edit made to that chat while the job runs can reach a later stage of the prompt, as the browser's live `chatNow()` reads do.
- Server CBS also runs the send's prompt (every `risuChatParser` of assembly, `editprocess`, the regex scripts' `parse` answers) on the main thread, under the cooperative limits above; only the regexes themselves run in a worker.
- Unconfirmed: a reverse proxy in front of the server that decodes `%2F` in a path splits a resource id containing a slash (an inlay id can); keep encoded path segments unchanged end to end.
- The server has one password and a list of registered browser keys; a JWT names a registered key, not a user. There is no multi-user model.
- Opening the resource store runs the normalizers over every row of every kind and rewrites non-canonical records, so startup time grows with the data; a normalizer that refuses a record stops the startup with the kind and the record id.
- The first load of `@mlc-ai/web-tokenizers` uses Node's experimental `vm.constants.USE_MAIN_CONTEXT_DEFAULT_LOADER` and prints its `ExperimentalWarning` once per process.
- Tokenizers stay loaded until the server context disposes them, and the web-tokenizer loader is shared process-wide and serialized; disposing frees the encoders but does not promise to return the memory, and encoding runs synchronously on the owner thread.
- A Lua run stuck in native code is not reached by the abort hook: after `ABORT_GRACE_MS` the pool terminates the worker, and queued work waits for its replacement. Workers start lazily, so the first task and each worker a burst adds pay the worker's boot (about 100 ms, measured once by hand).
- `server/src/lua/runtime.ts` reaches into wasmoon 1.16's non-public engine extension table and C API (`module.addFunction`, `lua_sethook`); recheck them on every wasmoon upgrade.
- `POST /api/resources/read`'s non-array body error still reads "Body must be { refs?, chats?, chatCollections? } of arrays", without `chatSummaryCollections` (validated separately); tests pin the wording.
- The `characterOrder` folder and `customModels` normalizers do not deduplicate entries; only a `customModels` entry has its `id` checked (a string).
- An MCP OAuth login's code question is bound to the client's closing signal only (`server/src/mcp/client.ts`): a caller's abort rejects that caller but leaves the question open until the client closes, the job's channel ends, or the question times out.
