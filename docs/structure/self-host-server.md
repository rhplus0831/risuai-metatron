# Self-Host Server (Hono on Node), Docker

## Scope

- Owns:
  - `server/src/**`: the Hono self-host server on Node (`@hono/node-server`). Handles static `dist`, auth, asset storage, the resource store and its routes, resource snapshots and backup archives, the reverse proxy, the hub proxy, and streaming proxy jobs over WebSocket.
  - Local TLS certificates.
  - Docker packaging.
  - The launcher scripts.
  - The client/server contract, seen from the server side.
- Paths: `server/{src/**,tsconfig.json,ssl/*}`, `Dockerfile`, `.dockerignore`, `server.sh`, `server.bat`.
- Client counterparts, owned by other guides:
  - `src/ts/storage/nodeStorage.ts` → `persistence.md`.
  - `globalApi.svelte.ts` `fetchNative`/`fetchViaProxyJobWs` → `global-api.md`.
  - `characterCards.ts` `hubURL` → `characters-modules.md`.

## Files

The server is TypeScript run directly by Node's type stripping (`pnpm runserver` = `node server/src/main.ts`, Node `>=24`). There is no build step. Layout: `main.ts`, `app.ts`, and `types.ts` (`AppEnv`) at the root; route modules in `routes/`; the resource data layer in `data/`; shared HTTP helpers in `http/`; the server-side processing modules in `prompt/`, `scripts/`, and `lua/` (Phase 5); tests and their support in `tests/`. The server may import the persisted types in the root `shared/` folder (`persistence.md`); `server/tsconfig.json` includes it, so `pnpm check` strict-checks it. Relative imports use explicit `.ts` extensions, and only erasable syntax is allowed (`server/tsconfig.json` sets `erasableSyntaxOnly`; `pnpm check` runs `tsc -p server/tsconfig.json`).

- `server/src/main.ts`: entry. Reads `PORT` (default 6001), `TRUST_PROXY`, and `RISU_MAX_IMPORT_BYTES`, loads the TLS certificate (`getHttpsOptions`), calls `serve()`, attaches the WebSocket upgrade handler, and starts job GC and the snapshot timer. On SIGINT/SIGTERM it begins shutdown, drains HTTP for up to 8 s, force-closes remaining connections, then awaits `dispose()` and exits. `cwd` is the root: `cwd/dist`, `cwd/save`, `cwd/server/ssl/certificate`.
- `server/src/app.ts` `createServerContext({ rootDir, trustProxy, resourceKinds, snapshotIntervalMs, maxImportBytes, generationRunner })`: builds the Hono app and owns all state, including the generation lock, the resource store (built with the lock as its guard), the snapshot manager, and the generation jobs. `resourceKinds` replaces `DEFAULT_RESOURCE_KINDS`, `snapshotIntervalMs` the 10-minute interval, and `generationRunner` the jobs' runner (tests use them; the default is `createGenerationRunner`, below). Returns `{ app, snapshots, scriptWorkers, generationJobs, attachWebSocket, startBackgroundTasks, beginShutdown, dispose }`. `attachWebSocket(server)` installs the one `upgrade` listener per server: `proxyStreamJobs.handleUpgrade`, then `generationJobs.handleUpgrade`, else the socket is destroyed. `beginShutdown` stops admissions and timers, aborts every generation job, and removes the upgrade listener; `dispose` is async and idempotent (it waits for the jobs to end, terminates the script workers, and waits for admitted resource handlers and backup operations before closing the store). `app.request()` works for in-process checks, but it has no Node socket, so the client IP is undefined there.
- `server/src/routes/auth.ts` `createAuthStore`: `save/server/password` plus `save/server/known_public_key_hashes.json`, `verifyJwt`, `checkAuth`, `checkProxyAuth`, `isAuthorizedProxyToken`, and the `/api/test_auth|login|crypto|set_password` routes.
- `server/src/routes/storage.ts`: the key-to-file mapping (`STORAGE_NAMESPACES` = `assets` only, `decodeKeyHeader`, `encodeFileName`/`decodeFileName`, `isAssetStorageKey`, `resolveStorageKey`), the in-process `readStorageFile`/`writeStorageFile` (a server job's asset reads and writes, under the routes' rules: no symlinks, regular files, staged writes), and `/api/read|write|list|remove`. `registerStorageRoutes` empties `save/.tmp/` at startup; writes and removals hold the maintenance gate.
- `server/src/data/resourceStore.ts` `createResourceStore({ file, kinds })`: typed resource documents in one `node:sqlite` database (`save/data/resources.sqlite`), with revision tokens, conditional writes, `epoch`/`assertEpoch`, `writeCount`, `readKinds(kinds, { chats })`, `readRefs(refs, { chats, chatCollections })`, `applyBatch`/`applyChanges` (resource ops, chat groups, and reorders in one transaction), `transaction`, `backupTo` (online backup to a single-file copy), `readSnapshot` (validates a snapshot file) and `replaceAll` (installs it with a new epoch), the normalization pass (`normalizeStoredRecords`, run when the store opens and inside `replaceAll`), `ResourceConflictError`, `ResourceBatchConflictError`, `ResourceEpochError`, `ResourceValidationError`, `ResourceStoreClosedError`, and `isValidResourceId`.
- `server/src/data/chats.ts`: the pure chat normalizers: `normalizeChatMeta` (drops `message` and the streaming flags, sets `id`, defaults `name`/`note`/`localLore`, type-checks them and `fmIndex`), `normalizeMessage` (`user`/`char` role, string `data`, valid `chatId`), `normalizeMessageList` (a whole chat's messages: missing, invalid, or duplicate ids get UUIDs), `assertPatchableMetaKeys`, `CHAT_SCHEMA_VERSION`.
- `server/src/data/chatStore.ts`: the chat tables (`chats`, `messages`, `chatOrders`) inside the resource store: batch preparation before any transaction (`prepareChatGroups`, `prepareChatOrders`, `countChatOperations`: shapes, legal op combinations, normalization, errors prefixed `chats[i].ops[j]`), `createChatTables` (applies groups and reorders inside the store's transaction, reads, restore), the generation fence, and `readChatSnapshotRows` (snapshot validation).
- `server/src/data/kinds.ts`: `ResourceKind<T>` (name, `schemaVersion`, `singleton`, `materialize`, pure and idempotent `normalize(input, { id })`, and for a write-only record `project` (what every read route answers) and `prepareWrite(incoming, stored)` (runs before a resource PUT or batch write; throws `ResourceValidationError` to refuse it)), `createKindRegistry` (reserves `batch` and `read`; a `materialize` kind must be a singleton), and `DEFAULT_RESOURCE_KINDS`. Phase 1 kinds (`root` was removed in Phase 3): `presets`, `modules`, `plugins`, `pluginStorage`, `pluginPermissions` (singletons, id `main`), `characters`, `inlays`, with minimum-shape normalizers that return the input unchanged, except `presets`, which gets `normalizePresets` (`shared/presets.ts`) and is materialized (one default preset). A `characters` record may not hold `chats` (chats are their own tables); `chat` and `chatOrder` are reserved kind names (conflict discriminators). Phase 3 kinds (singletons, `materialize`): the sections `providers`, `secrets`, `llmSecrets` (write-only since Phase 5 slice 7b: `project` is `maskLlmSecrets`, and `prepareWrite` refuses a write carrying a credential path (400 "credentials are written through /api/llm-secrets") and merges the stored credentials into the rest, `withStoredSecrets`; `shared/llmSecrets.ts`), `ui`, `memoryTranslateMedia` and the collections `loreBook`, `globalscript`, `hotkeys`, `customSidebarItems`, `characterOrder`, `authRefreshes`, `globalChatVariables`, `personas`, `translatorPresets`, `hypaV3Presets`, `customModels`, `enabledModules`, `statics` (`shared/sections.ts`).
- `server/src/data/normalize/`: the Phase 3 normalizers, pure and returning new objects. `shared.ts` (`normalizeSection`: every field of `SECTION_FIELDS[section]` in order, its value when it has the field's JSON kind and its fresh-boot default otherwise, no other key; `requireObject`, `requireArrayOfObjects`), one file per section with its `SectionSpec` (each field's kind and the default from `src/ts/storage/tests/fixtures/phase3/boot-snapshot.json`) and the `setDatabase` migrations it owns (`providers`: the keep-on-switch containers; `secrets`: `hypaCustomSettings`; `llmSecrets`: `google`, the `presets` map of `{ proxyKey }` by preset id, the `customModels` map of `{ key }` by custom model id (slice 7b); `memoryTranslateMedia`: the NAI v4 fields; `ui`: `customColorScheme`, the quote colors, the chat load pages), `personas.ts` (id backstop, a repeated id re-keyed), `presets.ts` (`normalizePresets`), and `collections.ts` (the rest: shape checks, `customModels` entries without `key`, the `hotkeys` merge of `defaultHotkeys` by `action`, `statics` counters, and the `{ items, selectedId }` records of `translatorPresets` and `hypaV3Presets`, whose `selectedId` falls back to the first item). Each accepts `undefined` (materialization) and returns the fresh-boot value; a record or element of the wrong container shape is rejected.
- `server/src/data/snapshots.ts` `createSnapshotManager`: periodic snapshots under `save/backups/`, the lock every whole-database operation takes (`exclusive`), `withMaintenance` (closes the `MaintenanceGate`, waits for admitted storage mutations), `track` (admits a resource handler or backup operation; refused after `stop`), `list`, `resolve`, `snapshotNow`, `start`, `stop`. `MaintenanceError` answers 503.
- `server/src/data/archive.ts`: the backup archive container (`encodeRecordHeader`, `indexArchive` with record-count and name-byte caps, `readRecord`, `copyRecordToFile`).
- `server/src/routes/resources.ts` `registerResourceRoutes`: `/api/resources` (multi-kind read), `/api/resources/read`, `/api/resources/batch`, `/api/resources/:kind[/:id]`.
- `server/src/routes/backups.ts` `registerBackupRoutes`: `/api/backups` (list), `/api/backups/:id/restore`, `/api/backups/export`, `/api/backups/import`.
- `server/src/routes/proxy.ts`: `/proxy`, `/proxy2`, `/hub-proxy/*`. `ownBody` re-streams an upstream body and keeps the timeout alive until the body ends. A `risu-aux-op` header (Phase 5 slice 7a, owner answer 2) names one row of `server/src/llm/auxOps.ts`: the media and memory calls (`openai-tts`, `openai-dalle`, `openai-whisper`, `openai-embeddings`, `openai-completions`, `google-imagen`) and, since slice 7b, the model discovery, account, and count calls (`google-models`, `anthropic-models`, `openai-models`, `openrouter-providers`, `openrouter-models`, `nanogpt-balance`, `nanogpt-subscription`, `nanogpt-subscription-models`, `nanogpt-model-providers`, `nanogpt-models`, `ollama-cloud-tags`, `google-count-tokens`). JWT only; the row's exact HTTPS origin, path, and method (`GET` or `POST`; a GET or HEAD sends no upstream body); only the row's listed query parameters (`detailed` for the two NanoGPT model lists; any other is a 400; `key`, `api_key`, and `token` are dropped first); the stored credential (`openAIKey`, `supaMemoryKey`, `claudeAPIKey`, `openrouterKey`, `nanogptKey`, `ollamaApiKey`, or `google.accessToken`) injected as a bearer token, an `x-api-key` header, or the `key` query, replacing any the request carried; no redirect followed (a 3xx is a 502); every response header value without the credential (as stored and as injected, trimmed); an error body redacted, or, for JSON whose decoded keys or values carry it, replaced by a generic error; a successful JSON answer whose text or decoded keys and values carry it refused (502), and one that is not JSON or fails mid-read a 502 (504 on timeout or abort). The browser callers go through `src/ts/network/auxFetch.ts` (`global-api.md`).
- `server/src/routes/llmSecrets.ts` `registerLlmSecretRoutes({ store, kinds, auth, limiter, maintenance })` (Phase 5 slice 7b): the only way a client writes an `llmSecrets` credential. `PUT /api/llm-secrets/<path>` `{ value, baseRevision }` sets one (an empty value clears a leaf or removes a map entry), `DELETE /api/llm-secrets/<path>?baseRevision=` clears it, `POST /api/llm-secrets/presets/copy` `{ from, to, baseRevision }` gives preset `to` a copy of preset `from`'s `proxyKey` (or removes `to`'s). The path is the `shared/llmSecrets.ts` grammar (`<flat field>`, `<nested field>/<leaf>`, `OaiCompAPIKeys/~<id>`, `presets/~<id>/proxyKey`, `customModels/~<id>/key`; each segment `encodeURIComponent`ed with `.` escaped, an id segment prefixed with `~` so that no id forms a dot segment, decoded once from the raw pathname). Each checks the JWT, the maintenance gate, the epoch, and the record's revision and writes in one synchronous block, and answers `{ epoch, revision, data }` with the masked record (`Cache-Control: no-store`); errors map as the resource routes do (`storeErrorResponse`). A value over 64 KiB is a 400. No value is logged or echoed.
- `server/src/routes/llm.ts` `registerLlmRoutes` and `server/src/llm/requests.ts` `createLlmRequests({ store, kinds, tokens, vertexTokens, claudeObserver, parentCallback })` (Phase 5 slice 7a): `POST /api/llm/request` runs `requestChatDataMain` of the server request layer (`llm-requests.md`) for the ids the body names and answers with one ordered SSE stream: `accepted { id }`; side events (`log`, `notice`, `inlay`, `toolRecord`, `callback`); then `result`, or `streaming` with `chunk` events (per key `set`, `append`, `remove` against the previous snapshot; `chunkText` for a string chunk) and one `end` or `error`. A callback (`mcpTool`, `cbs`) waits 60 s from its event for `POST /api/llm/request/:id/answer`; a late, repeated, or unknown answer is ignored; a failed answer rejects it. A request ends once: its work finished, the stream was cancelled or the HTTP request aborted, the job callback its `channelCall` names settled, maintenance began (live requests are aborted and new ones answer 503 until it ends), or shutdown (`beginShutdown`; `dispose` waits at most 5 s); ending aborts every upstream fetch and settles every pending callback. More than 64 MiB of unread events ends it too. It is not a job: no chat lock, no persistence. A body with `channelCall` runs only while that job callback is outstanding for the same client (`generationJobs.parentCallback`), and its `bodyIntercepter` calls go through the job's channel as a child callback; without one, interceptors are skipped.
- `server/src/routes/proxyStreamJobs.ts` `createProxyStreamJobs`: the job map, `sanitizeTargetUrl`, `isLocalNetworkHost`, `requestLocalTargetStream` (Node `http`/`https`), the POST/DELETE routes, `handleUpgrade` (false, the socket untouched, for a path it does not own), and GC.
- `server/src/jobs/generationLock.ts` `createGenerationLock()` (Phase 5 slice 5): the in-memory owner of each message a generation job writes (`chaId/chatId/messageId` → job, generation, token) and the live job tokens. The resource store reads it as its `MessageGuard`; the jobs `acquire`, `release`, and `endJob`.
- `server/src/jobs/generationJobs.ts` `createGenerationJobs({ store, kinds, gate, snapshots, lock, authorize, runner })` (Phase 5 slice 5): the job registry (`shared/jobs.ts`). `create` admits one running job per chat (503 while shutting down or during maintenance, 412 for another epoch, 404 for a missing chat, 409 `chatBusy { jobId }`, checked before 409 `stale`). The injected `GenerationRunner` gets a `RunningJob`: `signal`, `emit` (the registry adds the epoch; `accepted` is preceded by the job chat's hydration and always carries a `seq`; `done`/`error` end the job), `emitRecords` (fresh `resource` events; never `llmSecrets` or `authRefreshes`), `write` (`writeAsJob`, below), `channel` (above), `ownerAttached`, and `onClientMessage` (the owner socket's JSON from its current socket only). `emitRecords` returns the receipts of what it sent. A `command` job carries its `command` (`RunningJob.command`, a copy; null for other kinds; `GenerationCreateBody` is a union by `kind`). The default runner (`commandRunner.ts`) runs `command` jobs and the sends and previews (`server/src/prompt/runner.ts`, slice 9). `setCallbackPreset(id)` (slice 9) changes the preset later callbacks name in their targets (a `presetChain` pick). Every abort (DELETE, the 30-minute limit, shutdown, maintenance) fixes one 5 s deadline, after which the job is ended for it. Ending is single: the first abort decides the outcome (a runner's `done` after it ends as the abort's error), a terminal that cannot be serialized becomes an error, the token dies, the job's locks and chat slot go, the chat's hydration and one terminal event are sent (a failing socket never stops the rest), and `finished` always resolves; later `emit`, `emitRecords`, and `write` throw `GenerationJobEndedError`. A job chat's `resource` event lists in `streaming` the job's messages of that chat still locked, each with its generation and the newest chunk `seq` the stored text includes (the runner declares it with the write: `write(build, { covers })`; every applied generation write replaces the claim with its own, and one without `covers` claims 0); a streamed text with a higher `seq` is newer than the copy. Only the current reply's generation is streamed: an older or foreign chunk is dropped, and a reply whose final write applied is no longer the current one. Events reach only sockets of the job's `clientId`, one at a time: an attach closes the job's older sockets (code 4001), and a handshake whose `attach` stamp is older than the newest admitted one is refused (409), so handshakes finishing out of order cannot displace the newest; nothing is buffered except what an attach re-sends (the job chat and every record it sent, read fresh; the last `preset`; the current `accepted` with the newest chunk's text and `seq`, only while its generation still owns the message; the terminal event). An ended job stays readable for 60 s.
- `writeAsJob` (`RunningJob.write(build)`): synchronous. Refuses an ended job, checks the maintenance gate, takes the lock of every `begin` op's message (a later `begin` of the job replaces the generation), and calls `store.applyChanges(changes, { epoch, jobToken })`; a final generation write whose checkpoint is `applied` releases its message only if its generation still owns it (so `[final(g1), begin(g2)]` keeps g2 locked). A conflict naming only resource records calls `build` again (it re-reads) and applies once more; any other conflict, or a second one, throws `JobWriteConflictError`. A failed call restores every owner it replaced.
- `server/src/routes/generations.ts` `registerGenerationRoutes`: `POST /api/generations`, `GET`/`DELETE /api/generations/:id?clientId=` (see Routes). A malformed `hooks` list is a 400 (`parseGenerationHooks`; missing means none), as is a `command` job without `command` (`{ type: "button", data }`, data at most 64 KiB of UTF-8), a `command` on any other kind, or a malformed optional `context.selectedPersonaId` or `context.client` (`{ viewport, browserLanguage }`).
- `server/src/jobs/channel.ts` `createChannelHub()` (Phase 5 slice 6): the job channel (`shared/jobs.ts`), one hub per server shared by every job; a job's runner uses `RunningJob.channel`. `notice` is sent at once; notices before the owner's socket first attaches (a job starts before its owner can attach) are kept, within 1 MiB of serialized UTF-8, and sent on that first attach in their order among the requests made meanwhile, or, for a job that ended before it, before its terminal (`takeEarly`). `ask` (questions, 120 s) and `callback` (plugin callbacks, 60 s; `provider` passes the job's timeout) are requests with one deadline from the moment they are queued (capped by a parent's; a reattach does not reset it). Per client one request is outstanding at a time and the rest wait in FIFO order, across that client's jobs; a callback naming the client's outstanding callback as `parentId` (an aux request's callback, slice 7a) runs at once, one level deep; another parent or a third level is `refused`. A notice and a question of one script reach the hub in the order the worker posted them, except that a question asked through an async host call and a notice of a sync call made before awaiting it travel on two ports, so the notice can arrive first. A callback whose hook the job's list lacks is `refused` without being sent (`generateImage` and `inlayImage` are client capabilities, always admitted). Before a callback the job chat and every record the job sent are hydrated (read and sent synchronously), and the callback carries their receipts (`revisions`). At the deadline the outcome is `timedOut` with an owner socket attached, else `disconnected`, and the owner gets `cancel`; an abort or the job's end settles every request `aborted` (and their children) at once. Answers are validated and taken only for the outstanding request of that id from the job's current socket; a reattach re-sends every outstanding request with `replay: true`. The channel reports outcomes only: the runner applies the hook policy, except that `isBarrierFailure` (an answer `failed` with `failure: "barrier"`) ends the job whatever the policy. Payloads are serialized before they take a slot.
- `server/src/jobs/jobScope.ts` `loadJobScope(store, kinds, context)` (Phase 5 slice 8a; it is slice 9's `PromptScope`): what a job reads, in consecutive synchronous reads. Frozen: `db`, the database projection CBS and lore read (the sections, collections, presets, modules, and characters in stored order, the job's preset fields forwarded under their root names, the selected persona's fields, the selection indexes, every credential `""` as in the client mirror), the preset, the effective and the selected persona, and `request` (`loadRequestDb`, the request layer's settings with credentials). Live: the job's chat (the only chat in the projection) and the characters, read again by `refreshChat`/`refreshCharacter` after the job's writes and callbacks (data and revision together). A missing character, chat, preset, or persona fails the job with 404. Main thread only.
- `server/src/jobs/cbsHost.ts` `createJobCbsHost(scope, options)`: the server `CbsHost` over a scope, answering as the client host does (`scriptstate` chat variables with the defaults fallback, written through the job; `GLGlobalVariables` overrides; the frozen effective persona for the job's chat; `jobModules`, the client's `getModules` resolution over stored modules; `pickHashRand` from `shared/hashRand.ts`; `isMobile` false; `appVer` from `version.json`; the viewport and language of `context.client`, else 0×0 and `en`). Every server CBS evaluation goes through it. It carries the evaluation limits (`serverCbsLimits(usage)`, slice 9b; `shared/cbs/limits.ts`): one top-level parse may spend 10,000,000 work units (a unit per character scanned or produced, plus the registry's charges for `range`, `dice`/`roll`/`rollp`, `cbr`, `replace`, `join`, `filter`, `bkspc`/`erase`) and 5 s, and the job's evaluations together 60 s (`JobRunState.cbsUsage`, shared by every run setup of the job). The default variables are parsed once per source text. `bindings.ts` wraps the run's evaluator: a reached limit (`CbsLimitError`) is latched as the job's fatal failure with the chat owner's name, so the job ends with it whatever evaluated the text (assembly, lore, a Lua `cbs` inside `pcall`, a trigger effect, a regex script's `parse` answer), and nothing is evaluated after a fatal failure. The native effect loop (`triggers.ts`) yields a turn once it has held the thread 50 ms.
- `server/src/jobs/commandRunner.ts` `createGenerationRunner(deps)`: the server's runner. A `command` job runs a Lua button (`runLuaButtonTrigger`) or a manual trigger (slice 8b), both refused in a group chat (400). A button: each `triggerlua` trigger of the character (with its `lowLevelAccess`) and of its modules (each with its module's), in the client's order, runs `onButtonClick` on a fresh engine under one aggregate budget, stopping when the chat is gone. A handler error is logged and the next trigger runs; a load failure, a spent budget, or a worker failure ends the job with a Lua error, as does a fatal host failure (`LuaJobFatalError`). A manual trigger: the trigger runtime (`server/src/prompt/triggers.ts`) runs the chat's character's triggers of that name on a copy of the chat as stored, with the command executor (`server/src/prompt/commands.ts`) for `v2Command`, then `applyTriggerChat` (`server/src/jobs/chatResult.ts`) applies the copy in one group on the stored revision: removals in one op, merged message fields, anchored inserts, chat fields set or unset, a reorder only as a `replace` while the revision is still the baseline's and no message of the chat is locked (`deps.lock`); a change to a message another job owns fails the group and ends the job (409). A trigger error ends the job with `Trigger: …` (500). `accepted` and `done` carry no message. Every other kind runs `runPromptJob` (below). The setup both share is `server/src/jobs/runSetup.ts` `createRunSetup(job, deps, state, scope, ids)` (slice 9): per run (one per group speaker), the bindings for the run's character on the job's chat, the native context, `runLua` (a load, handler, budget, or pool failure reported for the caller to decide; a fatal failure or an abort thrown), the trigger runtime with its command executor (`/trigger` included), `runOnCopy` (a trigger on a copy of the chat as stored, applied with `applyTriggerChat`, which writes a message the job generates as a checkpoint of its generation), and the native `request` trigger every request of the bindings runs (`bindings.setRequestTrigger`; the chat owner's, none for a group); `createJobRunState(job)` is what every run of one job shares (one aggregate Lua budget, the native effect count, the fatal abort).
- `server/src/prompt/runner.ts` `runPromptJob(job, deps)` (Phase 5 slice 9): `send`, `continue`, `reroll` (as `send`), `group`, `preview`, `previewPrompt`. `accepted` without a message; the input stage (a nonempty `input`, unless the chat already holds the user message `userMessageId`): for a character the `input` trigger on a copy, `editinput`, then the user message appended under that id, for a group the input as it came, then `accepted { userMessageId }`; `presetChain` (picked and read at the job's start with the admitted configuration, by name, with `deps.random`; applied after the input stage, its chat and character read again): the picked preset's scope with `setPreset`'s keep rules for the five root fields (none when the pick is the selected preset), later callbacks name it, and `preset { presetId }` tells the tab; the speakers (the character, or the group's members in `groupOrder`'s order, each with its own bindings and its `speakerName` on the job's frozen request projection, one budget, effect count, and script cache for all; a preview stops after the first); per speaker a continue's message locked first (`begin` on the current revision, `accepted` with its text), `assemblePrompt`, and `preview` (`done.result`: the messages) or `previewPrompt` (`done.result`: the provider body) or the request (`services.request`, mode `model`). A streaming reply is appended with `begin` in one write (a continue keeps its message and its text as stored after the hooks); every chunk's first value (`trimUntilPunctuation` with `removeIncompleteResponse`) after the prefix, trimmed, goes out as `chunk`, a raw `setText` checkpoint 3 s after the last one whenever text is not yet stored (a timer, so a stalled provider does not hold it back; `covers` the chunk it holds; the write counter is separate from the chunk counter), and the final write at the end, after an abort (inside the grace, written as the job without the Lua fence), or after a read failure. A non-streaming reply is appended, begun, and closed in one write (a continue's `setMessage` replaces its metadata); the other `multiline` texts and every streaming value are `done.alternatives`. A final write the store ignored (another write closed the generation) ends the job (409). A generation the send did not close (a continue that failed) is closed as stored. `throwError` writes the error into the chat with `inlayErrorResponse` (the generation's own message as a checkpoint), else ends the job with it. One `done` for the whole job, with the last reply's id; `stopped: true` when a speaker ended without counting as sent (a trigger's stop, an error written into the chat, nothing to continue), which the tab's `sendChat` returns as false. The stored reply is raw: the tail is slice 11's.
- `server/src/prompt/assemble.ts` `assemblePrompt(host, input)` (slice 9): `sendChatInner` from the prompt-info snapshot to `generationInfo`, for one speaker, statement by statement (both template passes, the legacy `formatingOrder`, `positionParser`, the provider merge rule, `systemizeChat`, cache points, `depth_prompt`, Lua `editRequest` twice with `promptTextInfoInsideChat`, the removable-only recheck), with `exampleMessage`, `parseToggleSyntax`, `getAuthorNoteDefaultText`, and `getGenerationModelString` ported beside it. Everything it reads of the job comes through `AssemblyHost`. Recorded differences: the memory algorithms do not run (the no-memory trim and its `lastMemory` write always apply), `additionalInformations` gives nothing, an image inlay for a model without image input gets no caption (slice 10 each).

## Routes

Registration order in `createServerContext`:

1. `onError` (`HTTPException` responses pass through; maintenance and a closed resource store answer 503 with `Retry-After`; other errors are a 500 `Internal Server Error`). Shutdown admission middleware runs before body parsing, tracks resource handlers (`/api/resources` and `/api/llm-secrets`), refuses new resource, credential, and backup requests with 503, and adds `Connection: close` to every response during shutdown.

## Flows

Boot:

1. `pnpm runserver` runs `node server/src/main.ts`.
2. `createServerContext` creates `save/` if missing. `createAuthStore` creates `save/server/` and loads `password` and `known_public_key_hashes.json` from it. `registerStorageRoutes` recreates `save/.tmp/` empty.
3. `serve()` listens on HTTPS or HTTP. A listen error (e.g. `EADDRINUSE`) logs and exits 1.

Client detection:

1. `GET /` and `GET /index.html` inject `__NODE__`, which makes `isNodeServer` true in the client. Without it the client shows only the `NodeServerRequired` notice, so no route may serve `index.html` raw.
2. `AutoStorage` always uses `NodeStorage`.

Development (`pnpm dev`):

1. Run `pnpm runserver` and `pnpm dev` side by side. The Vite dev server (port 5174) injects `__NODE__` into its own `index.html` (plugin `risu-node-flag`, serve only) and proxies `/api`, `/proxy`, `/proxy2`, `/hub-proxy`, and `/proxy-stream-jobs` (including the WS upgrade) to `RISU_DEV_SERVER` (default `http://localhost:6001`; set `https://...` when the server found a certificate).
2. The dev origin keeps its own IndexedDB `DPoPDB` key pair, so it logs in separately from the server origin.
3. The server sees every proxied request as coming from the Vite process, so all dev clients share one rate-limit bucket (including the 10-per-30 s login limiter). The dev proxy does not add `X-Forwarded-For`, so `TRUST_PROXY` alone does not separate them.
4. `NodeStorage` needs `crypto.subtle`, so open the dev server via `localhost` (a plain-HTTP LAN address is not a secure context).

Auth:

1. `NodeStorage.checkAuth` creates an ES256 JWT (P-256, 5-minute expiry, public JWK). The key pair is kept in IndexedDB `DPoPDB`, entry `node`.
2. It calls `/api/test_auth`, then either `/api/set_password` followed by `/api/login` with the same digest (first run, so the first request is already authorized) or `/api/login`. One check runs at a time per `NodeStorage` instance.
3. Once logged in, the server knows the key hash, and later requests only send the JWT.

Resources and saving (client side: `persistence.md`):

1. The client reads every kind and every chat with one `GET /api/resources?kinds=...&chats=1` at boot and keeps the epoch.
2. Its save adapter sends one `/api/resources/batch` per save cycle: resource ops, chat groups (one per chat: its ops on the chat revision they were based on), and chat reorders. All of them are validated and normalized first, then every base revision is compared inside one transaction; any conflict rolls the whole batch back and the 409 lists all of them (resource conflicts, `kind: "chat"`, `kind: "chatOrder"`).
3. Chat groups: `create` (first op; the chat with its messages, inserted in the order at `index`), `delete` (alone), `replace`, `meta` (`set`/`unset` per field), `append` (at the end, the start, or after a message id), `setMessage`, `setText`, `remove`, `begin`. A group result carries the chat's new revision, the ids of messages it created, the outcome of each generation-carrying op (`applied`, `duplicate`, `ignored`), and `stale: true` when it applied on an older revision.
4. Deleting a character deletes its chats and chat order in the same transaction.
5. Inlays and plugin permission grants use the single-record routes.

Snapshots and restore:

1. `startBackgroundTasks` starts a timer (10 minutes). A tick takes a snapshot only when committed writes happened since the last one: `backupTo` writes `.<name>.tmp`, switches it to rollback-journal mode, and renames it to `resources-<UTC yyyymmddThhmmssmmmZ>-<8 hex>.sqlite`; the newest 20 are kept.
2. Restore (`/api/backups/:id/restore`) runs under maintenance: epoch check, `readSnapshot` (integrity check, layout version, real `resources`/`meta`/`chats`/`messages`/`chatOrders` tables with this store's columns and an epoch, then every row: registered kind at its schema version, valid id, singleton rules, unique kind and id, JSON the kind's normalizer accepts; every chat, message, fence, and order row, with each chat's parent character and each order a permutation of its chats; positions compacted), a safety snapshot, a second epoch check, then `replaceAll` in one transaction with a new random epoch. Every token issued before is stale afterwards.

Backup archives:

1. The container is concatenated records of `u32le nameLength`, the UTF-8 name, `u32le dataLength`, and the bytes. Version 2 starts with `manifest.json` (`{ version: 2, createdAt, partial, assets, missing }`), then `resources.sqlite` (a fresh copy), then each asset under its full key `assets/<name>`.
2. Export takes the database copy first (the staged copy then loses its `llmSecrets` row and is `VACUUM`ed, so the archive carries no LLM credential; snapshots on the server keep it; Phase 5 slice 7b, owner answer 12 (a)), then lists the assets (every file of `save/assets`, or the `partial` keys), so every asset the copy references already exists. The copy lives in `save/.tmp/export-<uuid>/` and is removed once, when the stream ends, is cancelled, or the client left before it started. A listed asset that can no longer be read fails the stream.
3. Import authenticates and checks the epoch before reading the body, spools it to `save/.tmp/import-<uuid>/` with a byte count, then validates the whole archive before writing anything: manifest first and unique, the declared assets exactly the asset records, exactly one `resources.sqlite` that `readSnapshot` accepts, only `assets/` keys. Refused: a Risu Account archive (`encryption.risudat`), an archive from before version 2 (`database.risudat`), a truncated or malformed one. `coldstorage_*.json` records are ignored. Then, under maintenance: epoch check, safety snapshot, assets that do not exist yet are added by hard link (existing files are never overwritten), and `replaceAll`. One import at a time.

Shutdown:

1. `beginShutdown()` sets the shutdown flag, closes generation admission and aborts every job (their 5 s deadline starts here), removes the upgrade listener, stops the snapshot timer and backup admissions, and disposes proxy jobs and limiters. Middleware refuses new resource and backup requests with 503 plus `Retry-After: 5`; every response during shutdown carries `Connection: close`, including a request admitted before the signal. Resource handlers are tracked before body parsing or auth and retain access to the open store. Backup operations retain their existing admission boundary.
2. `main.ts` awaits `server.close()` for at most 8 seconds, then calls `closeAllConnections()` before `dispose()`. Disconnects abort unfinished body reads and export streams; `dispose()` waits for the generation jobs to end (already bounded by their deadline), disposes the script workers, and awaits admitted handlers and backup cleanup before closing the database. The deadline leaves cleanup time within Docker's default 10-second stop timeout.
3. In-process callers use `dispose()` alone: it runs the begin step and waits for the jobs and admitted operations before closing.

Restore and import (`withMaintenance`): the `onMaintenance` listeners run under the snapshot lock while writes are still open. The jobs' listener closes generation admission, aborts every job with `maintenance`, and waits for their end, so an abort checkpoint lands in the old database (and in the safety snapshot); then the gate closes and the replacement runs. Admission reopens when the maintenance ends. A leftover store access raises `ResourceStoreClosedError`, mapped by both resource routes and `onError` to 503 with `Retry-After`, including reads.

Proxying:

- The client sends `risu-url` and `risu-header` (encoded JSON) to same-origin `/proxy2`.
- The request body is forwarded as raw bytes. `HEAD` fetches upstream with GET and returns headers only.
- Upstream request headers (`buildUpstreamHeaders`, case-insensitive):
  - The decoded `risu-header` must be a JSON object. Anything else is a 500.
  - Stripped: `host`, `connection`, `keep-alive`, `proxy-connection`, `transfer-encoding`, `te`, `trailer`, `upgrade`, `content-length`, `risu-auth`, and every field named in `Connection`. A `Connection: authorization` therefore drops `Authorization`.
  - `x-forwarded-for` is added only when absent.
- `/hub-proxy` forwards the incoming headers minus `host`, `connection`, `content-length`, `x-risu-node-path`, and `risu-auth`, and sets `origin`.
- `/proxy` and `/proxy2` response headers drop CSP, `clear-site-data`, `cache-control`, `content-encoding`, `content-length`, and `transfer-encoding`.
- On `/proxy` and `/proxy2`, `risu-timeout-ms` covers the whole exchange (`/hub-proxy` has no timeout):
  - Before upstream headers it returns 504 `{error}`.
  - Mid-stream it ends the response cleanly.
- A client disconnect aborts the upstream fetch on `/proxy`, `/proxy2`, and `/hub-proxy`. Proxy stream jobs are different: a WebSocket client disconnecting does not abort the job; only DELETE, the deadline, GC, or `dispose()` does.
- Node local-network streaming uses the job and WebSocket protocol with events `job_accepted`, `upstream_headers`, `chunk` (base64), `error`, `done`, and `ping`. Heartbeat is 5–60 s. Jobs have a 30 s done-grace period.
- Stream-job targets must pass `sanitizeTargetUrl`/`isLocalNetworkHost` (`ipaddr.js` ranges):
  - allowed: `localhost` and `*.local`;
  - IPv4 in 10/8, 172.16/12, 192.168/16, 127/8, 0/8, or 169.254/16;
  - IPv6 in fc00::/7 or fe80::/10, `::1`, and IPv4-mapped forms of those IPv4 ranges (bracketed URL hosts are accepted).
  - Single-label hosts other than `localhost` are rejected, although the client's `localNetwork.ts` treats them as local. The client also rejects IPv4-mapped IPv6.
- Stream-job forwarded headers are lowercased, then `risu-auth`, `risu-timeout-ms`, `host`, `connection`, and `content-length` are dropped.
- DELETE, the deadline, GC cleanup, and `dispose()` abort the job's upstream request and response even after upstream headers arrived. Deadline cancellation can deliver an `error` event to connected clients (`proxyJobWs.ts` shows every 504 as a timeout). DELETE, GC cleanup, and `dispose()` close the WebSockets without guaranteeing a final event.

### Changes from the former Express server

- `/proxy` and `/proxy2` POST forward raw bytes. Express re-serialized parsed JSON and turned urlencoded bodies into `"{}"`.
- `risu-auth` is never forwarded upstream by `/proxy`, `/proxy2`, or `/hub-proxy`, and header stripping is case-insensitive.
- `HEAD` on `/proxy` and `/proxy2` returns headers only and closes the upstream.
- The proxy timeout spans the streamed body; a mid-stream timeout ends the response cleanly.
- A client disconnect aborts `/proxy`, `/proxy2`, and `/hub-proxy` upstreams.
- Batch `/api/remove` works. A missing `file-path` is a 400; Express never answered it.
- JSON bodies: malformed, whitespace-only, or primitive JSON is a 400. `set_password` persists before updating memory. Zero-length `/api/write` bodies are written.
- Stream-job targets use `ipaddr.js` ranges, which adds bracketed and IPv4-mapped IPv6 literals. Stream-job DELETE, deadline, GC, and dispose stop active upstreams.
- Static files use `@hono/node-server` `serveStatic`:
  - supported: ranges and `Last-Modified`;
  - no ETag, conditional requests, or `Cache-Control`;
  - a directory path serves its `index.html`, where Express had `index: false`.
- `/api/read` has no ranges or ETag.
- No request decompression or charset-aware decoding; JSON text is read as UTF-8.
- `/api/crypto` and `already set` are `text/plain`, not `text/html`. The 404 and 500 bodies are plain text.
- Paths are case-sensitive, a trailing slash is tolerated, and there is no automatic `OPTIONS`.

Disk, under `save/`:

- `server/password`: the client-side SHA-256 digest via `/api/crypto`.
- `server/known_public_key_hashes.json`. Deleting only `password` lets you set a new one but does not revoke registered clients; delete this file too for that.
- `.tmp/`: staged writes and the per-operation export/import staging folders, emptied at startup.
- `data/resources.sqlite` (plus its `-wal` and `-shm` files): the resource store. Table `resources` (`seq` autoincrement, `kind`, `id`, `revision`, `schemaVersion`, `data` JSON text, unique `(kind, id)`), table `meta` holding the random `epoch`, table `chats` (`seq`, `characterId`, `id`, `revision`, `schemaVersion`, `meta` JSON), table `messages` (`chatSeq`, message `id`, integer `position`, `data` JSON, and the generation fence: `generationId`, `generationSeq`, `generationFinal`, `generationHistory` of up to 8 earlier ids), and table `chatOrders` (`characterId`, `seq`, `revision`, `ids` JSON); `PRAGMA user_version` is the store version (3: the Phase 3 sections and collections, no `root` record; the tables are those of version 2). Opening the store and every `replaceAll` run the normalization pass in one transaction: each record whose normalized text or schema version differs from the stored one is rewritten with its revision counter advanced (same `seq` and epoch), and each missing `materialize` singleton is created; a stored record its normalizer rejects, or one of a newer schema version than its kind, stops the start. A version-1 file (Phase 1) or version-2 file (settings in a `root` record, before Phase 3) is refused at startup with a message naming it, and a snapshot or archive of another version is refused on restore; there is no migration. The connection runs with `journal_mode=WAL`, `busy_timeout=5000`, and `foreign_keys=ON`. `data/` is not a storage namespace.
- `backups/`: resource snapshots (`resources-*.sqlite`, single files, newest 20), not a storage namespace. Assets are not in snapshots.
- User files: a logical key `assets/<name>` lives at `save/assets/<encodeFileName(name)>`, e.g. `assets/<sha>.png` or `assets/inlay_<sha256>.png`. The `save/database` and `save/remotes` folders of versions before Phase 1 are left in place and no longer read.
  - `encodeFileName` keeps `a-z 0-9 . _ -` readable and writes every other UTF-8 byte (uppercase letters, `/`, `%`, spaces, non-ASCII) as `%XX`. It also escapes a trailing dot and the first character of a Windows device name (`con.png` → `%63on.png`). A name whose readable form exceeds 255 bytes is stored as `~<lowercase hex>`; longer than that is rejected.
  - Only one encoding per name is canonical, and canonical names never differ by case alone, so case-insensitive filesystems do not merge keys.
  - The old flat layout (hex file names and `__password` directly in `save/`) is not read and was not migrated.

Process memory, inside the `createServerContext` closure:

- `password` and the known key hashes.
- The proxy stream job map.
- The generation jobs (registry, chat slots, sockets) and the generation lock. A restart loses both: running jobs end with the process, and the Phase 2 fence of their messages closes on the next ordinary write.
- Rate-limit counters.
- The resource store's epoch and committed-write counter, the snapshot lock, the maintenance gate, and the import-in-progress flag.

## Invariants

- Phase 4 (external contracts) changed no route, kind, table, or normalizer: the client mutation modules write the same records through the same batch route.
- Storage routes never use a raw path. `decodeKeyHeader` requires even-length hex and valid UTF-8 (verified by an exact byte round trip), then `resolveStorageKey` requires a namespace from `STORAGE_NAMESPACES` (only `assets`) and encodes the whole rest of the key, `/` included, into one file name. Only these folders are reachable; `save/server/` and `save/.tmp/` are not.
- Unsupported keys: malformed hex/UTF-8 is 400 `Invaild Path` on every route. A well-formed key with no storage location (other namespace, empty or too-long name) reads as missing (empty 200, no disk access), because the client reads whatever paths an old database stored; `write` and `remove` reject it with 400.
- `/api/list` returns only regular files whose names are canonical `encodeFileName` output, so every listed key reads back the same file. Other entries (subfolders, symlinks, noncanonical file names) are ignored.
- Keep the logical keys and the hex wire encoding; the client depends on both. The mapping to file names must stay reversible and injective.
- Keep these unchanged:
  - the `__NODE__` injection;
  - the `risu-*` header names and `x-risu-node-path`;
  - status codes and JSON error bodies, including the `Invaild Path` typo (one deliberate change: a `/api/read` filesystem error other than a missing file, symlink, or non-regular file is now a 500 instead of an empty 200);
  - the 100 MiB body limit (the backup import is the one route exempt from it).
- Rate limits must keep matching the former express-rate-limit v8 setup:
  - thresholds as in the Routes table;
  - windows start at a key's first hit;
  - IPv4-mapped IPv6 keys collapse to IPv4, other IPv6 addresses to their /56;
  - draft-6 `RateLimit-*` headers, plus `Retry-After` on 429.
- `TRUST_PROXY` keeps Express `trust proxy` semantics via `compileTrust`:
  - a number is a hop count;
  - a string is a comma list for `proxy-addr` (`loopback`, CIDRs, ...);
  - an invalid value fails at startup.
- `JSON` routes (`readJsonBody`):
  - a non-JSON content type or a zero-length body is `{}`;
  - malformed JSON (including whitespace only) or a top-level primitive is 400 `{error:"Invalid JSON body"}`.
- Streaming job protocol: the event names, base64 chunks, authentication on the WebSocket upgrade, and timeouts must all match `src/ts/network/proxyJobWs.ts` and `fetchViaProxyJobWs`.
- The WebSocket upgrade handling is one `upgrade` listener (`attachWebSocket`) on the server returned by `serve()`, dispatching by path to the `ws` handlers (`proxyStreamJobs.handleUpgrade`, `generationJobs.handleUpgrade`); each matches its path synchronously and returns false without touching another path's socket. Do not add a second listener, pass `websocket` to `serve()`, or add `@hono/node-ws`.
- Generation lock (Phase 5, PLAN.md Decision 4): a change that rewrites or removes a message a generation job owns (`setMessage`, `setText`, a `remove` naming it, `begin` on it, `replace` or `delete` of its chat), or deletes a character holding one, is a 409 whose entry carries `reason: "generating"` (the single DELETE route: the body's `reason`), unless it is the owner's in-process write carrying its job token. The check runs inside the transaction before the revision checks, so a stale change of a locked message also reads as `generating`. `meta`, `append`, and edits of other messages apply. The token never leaves the process; a client-supplied generation id grants nothing. Client generations (the flag-off path) never enter the lock and keep the Phase 2 fence.
- Job writes name the job's admitted epoch and live token, checked in the same synchronous call as the write; an ended job's token is dead (`JobTokenError`). No transaction spans a provider call: each job write is its own `applyChanges`.
- Resource revisions: a token is `<epoch>:<seq>:<revision>`, opaque to clients. A write matches all three parts, so a token from another database epoch, or from a deleted and recreated record (new `seq`), never passes. `baseRevision: null` creates and conflicts if the record exists; a write to a missing record is a 409 with `revision: null`. A token string that does not parse, including an empty `?baseRevision=`, is a 409 with the current revision; a `baseRevision` of the wrong JSON type, or a DELETE without the query parameter, is a 400.
- Resource writes normalize inside the store: `put` runs the kind's `normalize` once and stores its JSON result. A normalizer sees the stored form of its input (`serialize` runs first), so a nested non-finite number or over-deep input is refused before a JSON copy inside the normalizer could hide it. Reads never normalize; a new default or migration reaches stored records only through the normalization pass at the next start, so every normalizer must be idempotent (its output normalizes to the same JSON) or the pass rewrites that record on every start. The store is built with the kind registry and every method refuses a kind object the registry does not hold, so no caller can swap in another normalizer. A value is stored as `JSON.stringify` produces it (`toJSON` applies, `undefined` fields drop, Dates become strings, `-0` becomes `0`), and `put` and later reads return that stored form. `put` refuses, with `ResourceValidationError` (400), data whose JSON form would turn a non-finite number into `null` (`1e400` parses to `Infinity`), data `JSON.stringify` cannot serialize (a bigint, a cycle, a throwing getter, runaway nesting), and a JSON form nested deeper than 256 levels. `transaction(fn)` is one synchronous `BEGIN IMMEDIATE`; a throw, or any conflict inside it even if `fn` caught it, rolls back every write. A body whose return type can be a promise does not type-check (`TransactionBody`, best-effort: a body returning `any` passes, and an overloaded function reference is judged by its last overload, so wrap it in a zero-argument arrow), and at runtime a returned promise or thenable rolls back and throws. An `AsyncLocalStorage` scope follows the work the body starts through awaits, promise continuations, and timers: once the body returns, a write from that work throws, so it cannot autocommit after a rollback. Callbacks the body registers on an event emitter do not carry the scope and are not covered. Never await inside a transaction.
- Resource ids: 1-512 UTF-16 code units of well-formed Unicode, no control character, not `.` or `..`; clients encode them once with `encodeURIComponent` (so `§playground` and `assets/x.png` are valid ids). A singleton kind accepts only `main` and cannot be deleted.
- Epoch fencing: every mutation (PUT, DELETE, batch, restore, import) names the epoch in `x-resource-epoch`, checked in the same synchronous block as the write (restore and import check again inside maintenance), so nothing based on data from before a restore lands, including a create with `baseRevision: null`. Reads return the epoch; tokens stay opaque.
- Batch operations are `{ kind, id, baseRevision, data }` or `{ kind, id, baseRevision, delete: true }` (a string base revision); duplicates of one kind and id, both or neither of `data`/`delete`, unknown kinds, and invalid ids are 400 with the operation index.
- Chat groups (`chats[i]`): one per chat; `baseRevision` is null exactly for a group that starts with `create`; `create` only first and `delete` only alone; a batch that deletes a character and names its chats is 400. Every validation error names the group and op (`chats[i].ops[j]: ...`), including data refused only once merged inside the transaction (a `meta` patch), so a client can quarantine that one chat. A chat create under a missing character is a 409 chat conflict with revision null.
- Chat revisions: every applied op moves the chat's revision (a replayed or no-op op does not). By-id ops (`append`, `setMessage`, `setText`, single `remove`, `meta`) apply to an older revision of the same chat incarnation while their message exists; `replace`, `delete`, a multi-id `remove`, reorders, and a `begin` of an unknown generation need the current revision (a `begin` on a message appended in the same group does not). Replays are idempotent: an identical `append` of an existing id and a single `remove` of a missing message are no-ops; an `append` of an existing id with other content is a 409.
- Reorders (`chatOrders[i]`: `{ characterId, baseRevision, ids }`) compare the order revision from before the batch; `ids` must be a permutation of the character's chats (400 otherwise).
- Generation fence (per message): `begin` takes the message over for a generation id (the previous id goes to the history). A write carrying `{ id, seq, final? }` is `applied` when it is the current generation with a higher `seq` and not final yet, `duplicate` when its `seq` was already applied, and `ignored` otherwise (another generation, or after `final`). A write without a generation closes an open fence. `replace` keeps the fences of surviving messages closed.
- Maintenance (restore, import) closes resource and storage mutations with 503 and waits for storage writes already admitted; a restore or export that arrives meanwhile waits for the lock instead.
- `llmSecrets` is write-only (Phase 5 slice 7b): no route answers a stored credential. The reads answer `maskLlmSecrets` (each credential leaf `{ set, hint }`, `hint` the last four characters of a value of at least 16; the maps keep their nesting), a resource write may carry no credential path (400) and keeps the stored ones, the credentials change only through `/api/llm-secrets/*`, an exported archive holds no `llmSecrets` row, and an auxiliary operation's success answer carrying one is refused. Importing an archive (which has no row) materializes an empty record: every key is gone.
- Backup import never overwrites an existing asset file; resources are replaced atomically, assets are only added.
- Docker persistence depends on `/app/save`. Removing the volume loses the password, registered keys, and all data.

## Known Hazards

- `put` validates a value's depth on its parsed JSON form, so an over-deep value is rejected only after it has been fully serialized and parsed. Over HTTP the body is already parsed and capped at 100 MiB; only in-process callers could pass costlier values (getters, `toJSON`).
- The resource store assumes one server process and a local filesystem for `save/data/` (SQLite WAL uses shared memory; network filesystems are unsupported). Snapshots cover only `save/data/`; deleting both `save/data/` and `save/backups/` loses every resource.
- Snapshots do not hold assets, and inlay blobs are never deleted (a retained snapshot may reference them), so `save/assets/` only grows. Restoring the oldest retained snapshot can evict that file through the safety snapshot's retention (it was read in full first, so the restore itself succeeds).
- Restore and import validate and install the database synchronously on the serving thread; a very large database blocks other requests for that time.
- An asset over 4 GiB cannot be stored in an archive record and is reported as missing by an export.
- Storage writes stage into `save/.tmp/` and `rename` onto the target: atomic replacement, but no fsync, so no power-loss durability. `save/.tmp/` must be on the same filesystem as the namespace folders (one Docker volume at `/app/save`). One server process per `save/` is assumed: startup deletes `save/.tmp/`, and concurrent writes to one key are last-writer-wins. A failed rename (e.g. a Windows file locked by another process) returns 500 and keeps the old file; the server does not retry. The client save adapter retries resource batches with backoff; asset writes are not retried.
- Auth files are still written directly with `writeFileSync` (not atomic).
- `/api/read` opens with `O_NOFOLLOW | O_NONBLOCK` where the OS has them and takes size and bytes from one handle. Namespace folders themselves are trusted: a symlinked `save/assets` is followed. A hostile local process modifying `save/` is out of scope.
- The chat fence orders one client's generation writes; it does not lock a message against another device (a manual write from anywhere closes the fence).
- A batch remove stops at the first filesystem error, such as a missing file. It returns 500, and files deleted before the error stay deleted.
- `/api/set_password` and `/api/crypto` have no auth and no rate limit. The first caller can set the password, and an empty password leaves the server effectively unset.
- `/proxy`, `/proxy2`, and `/hub-proxy` (through `x-risu-node-path`, unauthenticated) forward to arbitrary targets. Only proxy jobs are restricted to local targets.
- JWT validation checks no issuer, audience, `typ`, or `iat`, and a token without `exp` never expires.
- Server CBS evaluation runs on the main thread under cooperative limits (`shared/cbs/limits.ts`, slice 9b), not under a hard deadline or a heap bound: the limits are checked at every `{{` and `}}`, every 4,096 work units, and inside the counted registry loops, so one operation between two checks runs to its end (a host call, one function on an input the budget allowed), and a result is charged before it is built only for the amplifying operations (`replace`, `join`, `cbr`, `range`, `#each`, `call::`, `#pure_display`); `split` and `history` build theirs first (a `history` over a 100M-character chat peaks near 380 MB before it is refused). Scanning costs memory too: a 9M-character text peaks near 460 MB of RSS. A job whose templates each stay under the limits can still hold the thread for up to its 60 s allowance; prompt assembly does not yield between its evaluations (the native effect loop does, after 50 ms). Hard interruption would need a worker or process boundary.
- Other main-thread work on card or model text has no bound: the `<Thoughts>(.+)</Thoughts>` regex of assembly and the display trigger (`assemble.ts`, `triggers.ts`; quadratic on unmatched opening tags, about 2.5 s for 200 KB), token encoding after its load (`tokenizers/index.ts`), Jinja rendering (`shared/prompt/chatTemplate.ts`), lore matching outside its worker regexes, and the calculator called directly by `v2Calculate` (outside the CBS allowance; the effect converts each `$name` reference itself, once per reference).
- A server trigger writes every chat-variable and author's-note change to the store as it happens (the tab writes its mirror), and each write sends the job's chat to the tab: a trigger loop that sets a variable on every iteration costs one SQLite transaction and one chat event per change (about 0.2 ms per write locally; 100,000 effects take about 11 s).
- `/api/llm/request` fetches every configured provider URL from the server: a provider on the browser's `localhost` is reached only when the server runs on the same machine (in Docker, `localhost` is the container; configure `host.docker.internal` or the host's address). Like `/proxy2`, it fetches whatever URL the stored settings name.
- A server send reads the job's chat again after its own writes and its callbacks (`refreshChat`), not only its own and acknowledged writes: an unrelated edit made to that chat while the job runs can reach a later stage of the prompt, as the browser's live `chatNow()` reads do (slice 9 relaxation of the amendment's frozen working state; Stop C owner item).
- A tab that reloads during a `presetChain` send applies the `preset` event again when it attaches: a selection changed in between is switched back to the pick (slice 9).
- Server CBS also runs the send's prompt (every `risuChatParser` of assembly, `editprocess`, the regex scripts' `parse` answers) on the main thread, under the cooperative limits above; only the regexes themselves run in a worker.
