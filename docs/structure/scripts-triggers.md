# Regex Scripts, Triggers, Lua Scripting

## Scope

- Owns:
  - regex find/replace scripts (the shared engine and the editors),
  - triggers v2 and Lua (the data model and the editors; the runtime is the server's since the Phase 5 cutover),
  - the server's script entry points as the tab reaches them (Lua buttons, manual triggers, the script transform).
- Paths:
  - `shared/scripts/regex.ts`, `shared/triggers.ts`
  - `src/ts/process/regexFiles.ts`
  - `src/ts/process/serverCommands.ts`
  - `public/lua/json.lua` (read by the server's script workers)
  - `src/lib/SideBars/Scripts/*`
  - `src/lib/Setting/Pages/GlobalRegex.svelte`
  - `src/lib/Playground/{PlaygroundSyntax,PlaygroundParser}.svelte`
- Not here:
  - The runtime itself: `server/src/prompt/{scripts,triggers,commands}.ts`, `server/src/lua/*`, `server/src/scripts/*` → `self-host-server.md`.
  - `edittrans` regex application → `media-aux.md` (`translator.ts:applyEdittransRegex`, the one regex the tab still runs: plain `RegExp` replacement on translation text, no Lua or trigger).
  - Module-provided scripts are collected by `process/modules.ts` → `characters-modules.md`.

## Files

- `shared/scripts/regex.ts`: the regex engine (the server's workers run it).
  - `runRegexScripts(data, scripts, { mode, chatID, parse, repeatBackSource, applyEffect? })` returns `{ data, effects }`: flags, `<order n>` and the other `<...>` actions, the `@@` directives, and the script loop (a script that throws is skipped). It writes nothing itself: `@@emo` and `@@inject` go to `applyEffect` where their script matched, inside that script's `try` (so a later script's CBS reads the write, and a throwing sink skips the rest of that script only), and are also returned as the ordered `effects` (`{ kind: "emotion", name }`, `{ kind: "inject", text }`). `parse` is the run's CBS; `repeatBackSource` answers `@@repeat_back`'s previous message.
  - `RegexScriptMode` = `editinput|editoutput|editprocess|editdisplay`.
  - `regexScriptCacheKey` and `createScriptCache` (the final output, 1,000 entries).
- `regexFiles.ts`: `exportRegex`/`importRegex` (the regex file export and import of the editors).
- `shared/triggers.ts`: the trigger model (`triggerscript`, `triggerEffect` = `triggerCode | triggerEffectV2`, the `triggerV2*` effect types) and the allowlists `displayAllowList`/`requestAllowList` (with their side-effect-free subset; the server runtime and `TriggerV2List.svelte` both read them).
  - `triggerscript.conditions` is `unknown[]`, kept for shared-format compatibility with upstream readers. Newly created triggers write `[]`; imported arrays are preserved, and the runtime skips triggers with non-empty conditions.
- `serverCommands.ts`: the tab's side of a server command job (`runServerButton`, `runServerManualTrigger`) and of a send job (`runServerJob`), and the job follow (`followJobToEnd`, `resumeServerJobs`).
- `SideBars/Scripts/RegexData.svelte`, `RegexList.svelte`: the regex editor. Flags are native `g/i/m/u/s` plus `<move_top>`, `<move_bottom>`, `<repeat_back>`, `<cbs>`, `<no_end_nl>`, `<order n>`.
- `SideBars/Scripts/TriggerList.svelte`: picks the editor mode (v2 or Lua). Any other non-empty list (legacy v1 data, `triggercode`) shows `triggerLegacyUnsupported` and is replaced when switching mode.
- `TriggerV2List.svelte`: the v2 editor, about 4100 lines.
  - `effectCategories`, `checkSupported`, `makeDefaultEditType`.
  - Block edit helpers: `deleteEffect`, `copyEffect`, `getInsertIndent`, `getBlockRange`.
  - Save-time `v2EndIndent` generation.
- `GlobalRegex.svelte`: edits `db.globalscript`, which the runtime never reads.

## Flows

Where each hook runs (all on the server since the Phase 5 cutover; the browser runtimes `scripts.ts`, `triggers.ts`, and `scriptings.ts` were removed, and wasmoon is no longer in the client bundle):

| Hook                                                               | Where                                                      |
| ------------------------------------------------------------------ | ---------------------------------------------------------- |
| the `input` trigger, then `editinput`                              | the send job's input stage (`server/src/prompt/runner.ts`) |
| `start` trigger, `editprocess`, `editoutput`, `output` trigger     | the send job (`assemblePrompt`, the tail)                  |
| `editdisplay` (Lua `editDisplay`, the display trigger, CBS, regex) | `/api/transform` (`ParseMarkdown`, `transformClient.ts`)   |
| the `request` trigger                                              | every request of a server job (`runSetup.ts`)              |
| `manual` trigger                                                   | a `command` job (`runServerManualTrigger`)                 |
| Lua `onButtonClick`                                                | a `command` job (`runServerButton`)                        |

The tab's own LLM requests (translation, suggestions, the HypaV3 modal, plugins) run no `request` trigger.

v2 layout:

- A flat effect array. Index 0 of the trigger list is the `v2Header` sentinel.
- Blocks are expressed with `indent`, `v2Else`, and generated `v2EndIndent` entries. Loops jump using `endOfLoop`.

## State

- `customscript` = `{comment, in, out, type, flag?, ableFlag?}` (declared in `shared/database.ts`). `type` is a free string. The UI also offers `edittrans` and `disabled`.
- Sources:
  - DB: `presetRegex` (active) and `globalscript` (unused).
  - Character: `customscript`, `triggerscript`, `lowLevelAccess`.
  - Module: `regex`, `trigger`, `lowLevelAccess`.
- Runtime variables are strings. They persist as `chat.scriptstate['$'+key]`. Display-mode triggers use temp variables only.
- Lua buttons (Phase 5 slice 8a; `self-host-server.md`): a Lua button (`risu-btn`; an element with both attributes runs its manual trigger) runs on the server: `serverCommands.ts` `runServerButton` takes the target and settings ids before any await, flushes (a refused or discarding flush runs nothing), posts a `command` job, and follows it to its end (`followJobToEnd`: one follow per job, shared by the button, a busy job of this tab, and the boot resume `resumeServerJobs`; a socket that closes early attaches again, five times at most, a failed status read is retried, an ended job is attached again for its final records; the end is reported once; a lost job is released like an ended one, its channel requests cancelled). The job's chat and character changes arrive as the server's records; its alerts and questions through the job channel, shown one at a time (the browser runtime's `alertNormal` did not wait, and a following question replaced it at once). `server/src/lua/bindings.ts` serves the host functions there: the client's guards, exposures (synchronous or a promise), and results; chat functions on the job's chat by id through `job.write`, the chat read again after every write and callback; setters on the run's character, read live; `cbs`, persona, and lore over the job's frozen scope (`jobScope.ts`, `cbsHost.ts`); `LLM`/`axLLM`/`simpleLLM` through the server request layer (`runInJob` with the client's outer loop, `outer.ts`; no tools until slice 12; a plugin or a tab's dynamic model is refused, as it runs in the browser); `getTokens` with the server counter; `hash` SHA-256; `generateImage` a `generateImage` callback (the tab generates and writes the inlay; no run character: the failure string without a callback); `getCharacterImage`/`getPersonaImage` an inlay under the asset key (an existing image inlay whose media is stored at once, else an `inlayImage` callback: the tab's canvas draws it; the tab's inlay writer stops when the callback is cancelled); `similarity` searches with the server's embeddings (`memory.md`, "Server"; the values and the result cross as JSON through the prelude's wrapper, the script gets a table). A refused write of a message another generation owns is skipped, as the browser runtime did; any other conflict, a lost owner, a barrier failure, or an abort ends the job (`LuaJobFatalError`, latched outside Lua). Each run is a fresh engine: Lua globals do not survive between runs (Safety Contract).
- Manual triggers (Phase 5 slice 8b; `self-host-server.md`): a manual trigger (`risu-trigger` in `Chat.svelte`, with its `risu-id`; `/trigger name` typed in the chat input, `processMultiCommand` from `DefaultChatScreen.svelte`) runs on the server as a `command` job `{ type: "manual", name }` with `context.triggerId` (`serverCommands.ts` `runServerManualTrigger`, the button's preflight and follow; `CurrentTriggerIdStore` is set once the job exists and cleared 100 ms after, as in the tab). `server/src/prompt/triggers.ts` `createTriggerRuntime` is the port of the former browser `runTrigger` (removed at the cutover) with the same effect switch, allowlists (`shared/triggers.ts`), defaults, and early returns; `server/src/prompt/commands.ts` the port of `processMultiCommand` on the job's chat; `server/src/jobs/chatResult.ts` `applyTriggerChat` the port of `applyChatResult` as one atomic job write. Recorded differences from the browser runtime: the character is always a deep copy (display and request runs no longer edit the live lore in place); every effect checks the job's abort, and a job stops with an error past 100,000 effects (nested runs and `/trigger` included; a privileged recursion yields each level, so the limit ends it, not the stack); a question that is not answered ends the job with its error; `v2RunTrigger` passes the display mode, display data, and temporary variables to the nested run and takes its display data back; `v2Command` always targets the job's chat; `{{trigger_id}}` is the job's id throughout; `v2SetPersonaDesc` writes the job's effective persona while `v2GetPersonaDesc` reads the selected persona as frozen with the job; `v2CheckSimilarity` searches with the server's embeddings (a failed search is the run's error, as in the tab); `v2ConsoleLog` goes to the server log; `/multisend` queues its parts on a command job (slice 11b: `done.followUps`; the tab sends them after the job with `command.ts` `runMultisend`, started once per job in a tab, so the trigger's later effects come first) and does nothing in a send job, as in the tab while a send runs; `/speak` is a `tts` notice; `/?` an `alertMd` notice; the six native regex sites (`v2ExtractRegex`, `v2SplitString`, `v2QuickSearchChat`, `v2GetLorebookByName`, `v2RegexTest`, `v2ReplaceString`) run in the worker's regex tasks, each with the tab's error behavior (a regex the tab would throw on ends the job). A `triggerlua` effect runs on the trigger's working copy (`bindings.withWorking`): the chat functions read and edit the copy, `getChatVar`/`setChatVar` go through the trigger's variables, CBS, lore activation, and the character functions keep the job's chat and records; a Lua character setter also updates the copy of every running trigger of that character, so a native getter after it reads the new value (the Phase 4 residual). Inherited from the tab and kept: the final diff re-sets `scriptstate` and the note from the copy, so a command's `/setvar` during the run can be overwritten by the copy's older map; the variable writes during a run change the chat's revision, so a reorder by the trigger is then dropped.
- Scripts on a send (Phase 5 slice 9; `self-host-server.md`): `server/src/prompt/scripts.ts` `createScriptProcessor` is the port of the former browser `processScriptFull` for `editinput`, `editprocess`, and (slice 11a, once on the completed reply) `editoutput`, in the tab's order: the Lua edit hook (`editInput` or `editOutput` on the character's Lua triggers, or the modules' only for a group, without low-level access; none for `editprocess`; a load failure returns the content as it came in, a handler failure is logged, a spent budget or a worker failure ends the job), the plugin hook as a channel callback named the mode (a hook that failed ends the send; a mode with no hook registered when the job was created makes no callback and keeps the text; a hook set unloaded during the job, or any other refusal, ends the job), CBS, and the regex scripts (`presetRegex`, the character's, the modules') through the worker's `runScripts`. `@@emo` is an `emotion` notice; `@@inject` writes the message at `chatID` unless any generation owns it, this job's included. The result cache is the job's own, shared by its processors. The dynamic-asset step follows the regex scripts with the tab's conditions (slice 10), which exclude `editinput` and `editprocess`: it runs for `editoutput`; its best-match cache is the job's. The `output` trigger runs after `editoutput` on a copy of the chat, its changes applied under the reply's generation; its `sendAIprompt` is another round of the job. Lua `editRequest` (`editRequest`) runs the same hook on the assembled messages. The native `request` trigger runs before every attempt of every server request of a job (sends, Lua `LLM`, `v2RunLLM`), as the browser's `requestChatData` ran it: the chat owner's (none for a group), in display mode on the chat as it is, an invalid result keeping the messages, a fatal failure (the job's effect limit included) ending the request. A Lua or command write to a message the job generates is refused, as in the tab.
- The script transform (Phase 5 slice 13; `self-host-server.md`, `cbs-rendering.md`): the display (`ParseMarkdown`, the translator's `translateHTML`) and `editprocess` (the HypaV3 modal, the plugin `parseRisuChat`) stages run on the server (`src/ts/parser/transformClient.ts`); without a context (no chat, a chat not saved on the server yet) the stage is skipped. A render writes nothing there: a Lua `editDisplay` `setChatVar` changes the render's copy of the variables only (the browser runtime wrote the chat). `@@emo` effects come back with the result and are applied once per tab and result, never for a `simple` character argument and never from an answer older than a Re-render of its message. A message keeps its first render until a keyed input changes; the message menu's "Re-render" skips the server cache for it.

## Coupling

- The tab's script entry points (`serverCommands.ts`, `transformClient.ts`) depend on the job channel, the chat module, and the save adapter's flush.
- UI owners:
  - Character regex and triggers: `CharConfig.svelte`.
  - `presetRegex`: `BotSettings.svelte`.
  - Module regex and triggers: `ModuleMenu.svelte`.

## Invariants

- Never rename the serialized discriminators: `customscript.type`, `triggerscript.type`, effect `type`, v2 `indent`, the header at index 0.
- Regex order matters. `<order n>` applies only when `ableFlag` is true. Native flags are sanitized to `dgimsuvy`, deduplicated, and default to `u`.
- The cache stores final output, not compiled `RegExp` objects. An empty-string result is falsy and therefore never cache-hits.
- Display and request modes silently skip effects missing from `displayAllowList`/`requestAllowList`. The editor's `checkSupported` reads the same lists (`shared/triggers.ts`).
- Low-level effects are gated twice: filtered in the UI and checked at runtime via `trigger.lowLevelAccess`. Lua edit hooks always run with `lowLevelAccess:false`.
- A trigger effect or Lua function that changes a character writes one field of the run's character; never the selected index or the whole working copy.
- v2 block edits must preserve paired `v2EndIndent` entries and indentation.
- Lua `request` restrictions (`server/src/lua/egress.ts`): HTTPS only, URL at most 120 characters, the three banned Risu prefixes, no `localhost` and only public addresses, 30 requests per minute per server, a 10 s timeout and a 2 MB answer; it requires low-level access.

## Recipes

- Add a regex mode: extend `RegexScriptMode` (`shared/scripts/regex.ts`), wire its caller on the server, add the UI option in `RegexData.svelte`, and update `translator.ts:applyEdittransRegex` if the mode is translation-only.
- Add a regex flag: add it to the UI in `RegexData.svelte`, parse the `<...>` metadata in `parseScripts` and implement it in `executeScript` (both in `shared/scripts/regex.ts`, strict-checked by the server `tsc`), and add the translator equivalent if needed.
- Add a v2 effect:
  1. Add the type and union member in `shared/triggers.ts`.
  2. Update `effectCategories`, `checkSupported`, and `makeDefaultEditType` in `TriggerV2List.svelte`.
  3. Add the field editor branch.
  4. Add a case to the server runtime (`server/src/prompt/triggers.ts`).
  5. Update the allowlists (`shared/triggers.ts`) if the effect should run in display or request mode.
  6. Add the `triggerDesc` language key in `src/lang/en.ts`.
- Add a block-type v2 effect: also update `deleteEffect`, `copyEffect`, `getInsertIndent`, `getBlockRange`, and the save-time `v2EndIndent` generation.
- Add a Lua API: the server bindings (`server/src/lua/bindings.ts`, with the guard of its provenance), plus the prelude wrapper in `server/src/lua/runtime.ts` if it is async or JSON-based. Add a case to `server/src/tests/luaBindings.test.ts` (the name contract).

## Known Hazards

- `GlobalRegex.svelte` ignores the return value of `importRegex()`.
- `triggercode` effects have no runtime case. Only `triggerlua` executes.
- `GlobalRegex.svelte` edits `db.globalscript`, which no runtime reads.
- The deprecated `v2ModifyLorebook`, `v2SetLorebookActivation`, and their reads address lore entries as arrays (`entry[0]`, `entry[2]`), but entries are objects: the first never matches, the second adds a junk `"2"` key (pre-existing; a separate task).
- After a Lua setter writes the live character inside a trigger, the native getters (`v2GetCharacterDesc`, ...) still read the working copy taken at run start, so a native set fed from them can restore the old value (the server runtime updates the working copies of the running triggers: the Phase 4 residual is closed there).
