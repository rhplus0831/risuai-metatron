# UI Components and Theming

## Scope

- Owns:
  - the Svelte component tree below `App.svelte` (chat screen, message rendering components, sidebar),
  - the reusable GUI primitives,
  - popups and portals,
  - theme colors and CSS tokens,
  - GUI sizing, tooltip, and longpress actions,
  - chat branches.
- Paths:
  - `src/lib/ChatScreens/*`
  - `src/lib/SideBars/*`, except `Scripts/`, `LoreBook/`, `CharConfig.svelte`
  - `src/lib/Others/*`, except the files owned by other guides
  - `src/lib/UI/*`, except `Realm/`, the model pickers, `PromptDataItem.svelte`, `MainMenu.svelte`, `Title.svelte`
  - `src/lib/UI/GUI/*`, `src/lib/UI/NewGUI/*`
  - `src/lib/Mobile/*`
  - `src/lib/Playground/PlaygroundMenu.svelte`
  - `src/styles.css`
  - `src/ts/gui/*`, except `highlight.ts` and `codearea/`
- Not here:
  - Screen selection in `App.svelte` → `app-shell.md`.
  - Settings pages → `settings-i18n.md`.
  - Markdown/HTML rendering internals → `cbs-rendering.md`.
  - The send path → `chat-pipeline.md`.

## Files

Chat:

- `ChatScreen.svelte`: layout theme switch (`waifu`, classic). Mounts `BackgroundDom`, `TransitionImage`, `ResizeBox`, `ChatList`, and the module menu.
- `DefaultChatScreen.svelte`: input box, send/reroll (see `chat-pipeline.md`), and menus. The hamburger menu pins with `setChatMeta(ref, { pinned: true })` and unpins by unsetting `pinned`. Chooses home, playground, the closed chat (`ClosedChatScreen.svelte`, while `selection.chatOpen` is false), or chat.
  - The `metatron` theme adds `metatron-chat-theme` to the chat scroller; `src/styles.css` styles each message (`.risu-chat`) as a card under it. Any other non-`waifu` theme keeps the classic layout.
  - Owns the loaded row window and accepts guarded trims from `Chats`. Unfolding adds `messages.length - foldedIndex` to preserve the folded window's oldest row. Binds `Chats.revealing` to hide the separate greeting with `visibility: hidden` until the opening batch finishes revealing. Screenshot capture waits for all rows and their current markdown (`whenRendered`) with `loadPages = Infinity`, releases any reveal batch, suspends trimming/containment, and restores the previous window and scroll offset for the same chat in `finally`.
  - Jumps to a message: the bookmark list's by index (`ScrollToMessageStore` → `scrollToMessage`) and a message search hit's by id. The search jump (`src/ts/messageSearch.svelte.ts` `requestMessageJump`) is claimed once (`claimMessageJump`, before any await) when the selected chat is its ref, loaded and shown with the transcript bound; `scrollToMessageId` runs `runMessageJump` (`messageJump.ts`, pure, its state and DOM injected) and ends it with `completeMessageJump` or `cancelMessageJump`. After every await it checks the token, the selected and shown chat and the same transcript, and finds the message again by `Message.chatId` (never outside the ref). A target above a fold clears it, keeping the rows shown (`messageJumpWindow`: `loadPages + length - folded`, as the show-all button); the window grows to five rows past the target, waits for `Chats.whenRendered`, scrolls a row three before, waits (at most 4 s) for the scroller's images, then scrolls the row (looked up under the scroller by `data-chat-index` and checked by `data-chat-id`) twice and rings it (`ring-primary-500`, 2 s). A message gone from the chat alerts `messageSearch.messageGone`. Both jumps count in `scrollingToMessage`, so trimming stays suspended while either runs.
  - The chat scroller publishes `settings.ui.chatScreenWidth` (Display, default 900) as `--chat-screen-width`. The transcript (`Chats`), the first greeting (`.default-chat-screen > .risu-chat`), the composer, and the rows around them carry `chat-screen-content-width` (`src/styles.css`): one centered column of `min(--chat-screen-width, 100%)`. A new row in the chat scroller gets the class too.
- `Chats.svelte`: mounts `Chat` instances imperatively, keyed by the chat and the message id (`Message.chatId`).
  - `updateChatBody` diffs mount, update, and remove, keeping reverse-chronological DOM order (it moves only rows out of place). Its effect tracks message identities/order/ids/roles, streaming state, the loaded window, folded index, reload store and character/user props; it never tracks message text. The streaming-index scan is cached separately on message ids/order and the active stream/selection. Before creating rows, the diff identifies an opening window: nonempty, with no shown key already in `rows` (initial mount or chat switch).
  - An opening window mounts its newest rows first: accumulate estimated heights of `min(480, 48 + message.data.length * 0.2)` pixels until reaching the scroller's `clientHeight`, with at least 3 and at most 8 rows (or all rows in a smaller window); a zero-height scroller uses 8. This text/geometry read happens only inside the untracked opening diff. Older rows get containers in DOM order immediately, but their effects wait to mount `Chat` until armed. They have no content layout box or containment observation before mounting. A deferred row mounts with its latest input and character/user context, including any text, edit, name or image changes; removing it disposes its effect without mounting it.
  - Deferred rows arm when all first-stage render waits resolve/reject or their rows are removed, on any subsequent non-opening window diff, on scroller `wheel`/`touchmove`/`pointerdown` input, on capture (`loadPages === Infinity`), `suspendTrim`, `Chats.whenRendered` (before its DOM flush), a new opening window or destroy, or after 3000 ms from batch start. Arming only writes row state; the row effects perform mounting. First-stage waits follow replacement instances while pending and do not wait for images. Mounting has a separate lifetime from visibility: neither image completion nor the 1200 ms visibility deadline arms deferred rows. Capture and `suspendTrim` bypass staging. Appends, load-more, unfolds, remounts and mixed updates mount every row immediately.
  - An opening window also starts a reveal batch and resets the scroller's `scrollTop` to 0. Every mounted batch row keeps its layout box with `.chat-row-pending` (`visibility: hidden`); deferred containers are pending too, but cannot settle until mounting. Settled rows reveal in newest-to-oldest order, checked in an animation frame. Settling waits for the current instance's `whenRendered` and its descendant images' load/error; failed waits count as settled. A still-hidden row remount restarts its wait, and removal no longer blocks the queue. Once the oldest visible row's top reaches/passes the scroller's top, all remaining rows reveal together. One 1200 ms batch deadline releases visibility even with pending parses/images. A new batch, destroy, capture, `suspendTrim` or `Chats.whenRendered` also releases visibility and clears its timer/frame/image listeners. Capture and `suspendTrim` skip gating. Appends, load-more, unfolds, single remounts and mixed updates do not start batches or hide additional rows; already-visible rows are never hidden again by the active batch. `revealing` stays true until the visibility batch releases.
  - Each mounted row owns a disposable `$effect.root`: its effect tracks that message's text, disabled value (JSON comparison preserves legacy object values), role, reload entry, portrait/mount context and its position/streaming inputs. A streamed text write reaches only this effect, through `Chat.updateRow` in every mode (`off` too). A text edit or start/stop of streaming mounts that row again. Adding/removing another message sends only changed index fields through `updateRow`. Equal cloned messages keep their instances. Character identity, portrait, role, disabled and reload changes remount the row and reset its local state. Character/user names and image sources instead send only changed `name?: string` / `img?: string | Promise<string>` fields through `Chat.updateRow`, without resetting the `ChatBody` key or directly invalidating its parse (existing CBS dependencies remain reactive); image promises are reused until their source changes. The simple character and reroll callbacks are captured only at mount; callback identity changes do not remount rows.
  - One `IntersectionObserver`, rooted at the scroller with two viewport heights of margin, marks only distant rows `far`; first observation follows layout and records a measured content-box block size. A transcript `MutationObserver` remeasures only changed rows after async markdown/descendant updates; image loads and scroller resizes also refresh the sizes, so the first empty-body height cannot become a permanent offscreen placeholder. Near rows have no containment, preserving fixed partial-edit/card overlays and overflowing highlights. Open editors stay uncontained. Without the observer there is no containment. Screenshot mode (`loadPages === Infinity`) clears it.
  - On an append to the same chat at the bottom (`scrollTop > -4` in the reversed scroller), `trimWindow` asks `DefaultChatScreen` to lower `loadPages`: keep at least `CHAT_ROW_CAP` (150), or the rows intersecting/below the viewport plus one configured load page, whichever is larger. Only entirely older rows go. The tail detaches once, disposing its row effects/observations immediately; detached component instances finish teardown in 4 ms frame budgets (the synchronous 2,000-row teardown exceeded 100 ms). Folded windows, screenshots, scroll-to-message and an open original/translation/partial editor in any candidate row block trimming.
  - Auto-scroll's at-bottom read happens before DOM changes and only on a same-chat append of a character message with auto-scroll enabled; streamed chunks never read geometry here.
- `Chat.svelte`: one message. Branching clears `pinned` on the new chat; with `createFolderOnBranch`, a source chat that `chatFolderOf` lists under no folder (none, or a dangling `folderId`) and its branch go into a new "Branches of" folder. Controls, bookmarks (`toggleBookmark`), TTS button, `displaya`, partial edit, and `renderGuiHtmlPart` for custom GUI HTML. Message theme branches are `mobilechat`, `cardboard`, `customHTML`, and classic. Both original-message editors bind a separate `draft`, initialized on opening and cleared on save; a long-press cancel keeps the draft for reopening but never changes `message`, the display, partial-edit source, or storage. `isEditing` exposes open original/translation editors to the trim guard. `ChatBody` is keyed only by the reload pointer; `whenRendered` loops until the bound body stays the same across its render wait and DOM flush, including replacements from `ReloadGUIPointer`. Body-less rows settle immediately. Optional `pendingReveal` hides the greeting's whole row without changing its layout.
- `ChatBody.svelte`: `markParsing`, which handles translation and parsing, then `{@html}`. `whenRendered` waits for the current parse and its DOM update for ordered reveal and screenshot capture (forwarded by `Chat` and `Chats`), rechecking replacement parses after each flush. The rendered auto-translate path's initial empty result is not settled: the wait includes its delayed `translated` update and the resulting real parse. Raw streaming settles immediately and remains visible as raw text.
  - While a render is pending it shows `lastParsed`; only the newest render (`parseRun`, kept by its retries) writes it, so an older render that settles later does not show again (`ChatBody.svelte.test.ts`).
- `Suggestion.svelte`: reply suggestions through `requestChatData`.

Others:

- `BookmarkList.svelte`, `ChatList.svelte`, `GithubStars.svelte`, `Help.svelte`, `SavePopupIcon.svelte`.
- `MessageSearch.svelte`: the message search panel (mounted once by `App` after boot, rendered while `messageSearchPanel.open`). Opened by the sidebar chat list's toolbar (this character) and the character catalog's header (all characters); its scope switch reaches this chat, this character, and all characters. A query of 2 to 200 code points (NFC, trimmed) runs 300 ms after typing stops or on Enter (not while an IME composes); every edit, new search, continuation or close aborts the running request and ignores its answer (a generation counter). Pages come from `searchMessages` (`src/ts/messageSearch.svelte.ts`, `POST /api/chats/search` through `authFetch`); hits already shown (chat ref and message id) are dropped, a page with no new hit and a `next` asks again up to 5 times before "Load more", and a 409 (`reason: "epoch"`) restarts the search once. The snippet renders as text with the match in a `<mark>` (never `{@html}`). Finished results survive a close; reopening with another scope or query, or after a search the close or an edit interrupted, searches again. "Load more" is offered only while the field and scope still match the shown results. Opening a hit closes the panel, clears `gridOpenStore`, calls `openPinnedChat`, then `requestMessageJump` (an alert when the chat no longer exists). Escape closes it through a document capture listener, after an alert, the terminal notice, a picker list or the binding dialog, and before the global hotkey closes the grid under it.
- `PopupEditor.svelte`: Monaco popup.
- `HypaV3Progress.svelte`: the HypaV3 progress overlay, mounted by `App` for the selected chat (`currentChatRef()`). `jobChannel.ts` keeps `memoryProgressStore` (`stores.svelte.ts`): each job's open memory run from its `memoryProgress` notices, keyed by job (a newer `runId` replaces the job's entry; a closing notice removes only its own run; the job's end removes its entry), and the chat of every job that reported a run. `App` shows the newest run of a job in the selected chat (`memoryProgressFor`), so a chat switch hides and restores it without a new notice; otherwise the legacy `hypaV3ProgressStore` (the `progress` notice and the client copy of the algorithm), except a value a job's `progress` notice wrote once that job reported a memory run for another chat (`legacyProgressShown`). A legacy value written before the job's first `memoryProgress` notice still shows in any chat until that notice arrives. A run shows its phase, the reason line when it has one, `done/total` with a filled bar (an indeterminate bar without counts) or the selection's embedding queue text. An `initial` run has "Stop here and continue": `stopMemoryRun(jobId, runId)` with the job and run captured at the click posts `POST /api/generations/:id/memory-stop`, one request at a time; the entry's `stop` (`pending`, `requested`, or `unavailable` after a `jobEnded`/`noMemoryRun`/`otherMemoryRun` 409 or a 412) keeps the button disabled across a remount, and another failure re-enables it (a retry may post again) with an error alert while the run is still the job's entry, in whichever chat is selected. The `memoryGap` question (`jobChannel.ts` `ask`) is a two-button selection answering `MEMORY_GAP_CHOICES` by index; its text replaces `|` with `¦`, since the selection dialog splits on `||`.
- HypaV3 background memory tasks in the tab (`src/ts/process/memoryTasks.svelte.ts`): `eventFeed.ts` routes a `memoryTask` frame of the loaded epoch (`noteMemoryTaskFrame`), a `hello`'s `memoryTasks` snapshot (`noteMemoryTaskHello`, the whole status set), and the revision listing read after that `hello` (`noteMemoryTaskListing`, before `reconcileRemote`); another epoch (a `hello`, an `epoch` frame, a listing's or a route's 412) resets it (`resetMemoryTasks`). It keeps each chat's last status (`memoryTaskStatus`, `summarizingChats()` for the badges) and its hydration-pending fence, keyed by the `chatStatusKey` format: `live` while a task is queued or running; `starting` from before this tab's "Summarize now" flush through its request; `uncertain` after a transport failure or unrecognized answer, reported by `memoryTaskAwaitingSync` until a live or terminal frame, a `hello`, or a retry's live answer resolves it; `revision` after a terminal whose `terminalRevision` the mirror does not hold (the save loop is told to read the chat); and, on every `hello`, `listing` for every chat it tracked or the snapshot lists that is not live, which the listing turns into `revision` with the chat's listed revision. A `revision` fence holds until the chat is loaded with a held revision (`heldChatRevision`) at least that one, or is no longer a member; a read refused for pending local work does not advance it. A disconnect, a `hello`, and time keep fences. A terminal of another task while a task is live (a queued task cancelled while another runs) changes neither the status nor the fence. The module imports no alert or language module; its actions return outcomes. `startMemoryTask` fences the chat before saving the tab's pending changes (`flushResources`; any discarded change refuses, as a send does), then `POST`s `MEMORY_TASKS_PATH` with the epoch header; a valid `running`/`queued` answer installs a live fence only if its task is not already known terminal, clears the pending-manual flag when accepted as live, and supplies the status only when no frame or hello of the chat arrived meanwhile. A refusal, a `pendingManual` answer, or a save failure puts back the prior fence, including intervening feed updates; a transport failure or unrecognized answer leaves an `uncertain` fence, which later definite refusals or pending-manual answers preserve. A pending-manual answer superseded by a newer observation returns no notice. `cancelMemoryTask` `DELETE`s the chat's task. One request per chat at a time; answers after a reset change nothing. Until the server hands chats to its service both answer 503 `notEnabled`, shown as a notice.
- `HypaV3Modal.svelte`: `memoryWriteFence(ref)` refuses a write of the memory copy with `chatGenerating` while a send of this tab or a followed job runs in the chat, and with `memoryTasks.editFenced` while `memoryTaskFenced(ref)` holds; a refused edit is undone in the copy and never replayed. Lore writes are not fenced by tasks (tasks never enter `generatingChatKeys`). Under the header, for the selected chat: the status line (queued, running `k/n`, or the last end that matters: a failure, a skip, a warning on `done`, a stop other than a cancel, each with its reason text from `memoryTasks.reasons`), "waiting for the latest summaries" while only the mirror lags (checked every second, since a held revision catching up notifies nothing), the `pendingManual` notice, "Summarize now" (disabled while a task is live or a request is in flight), and "Cancel" (while a task is live or a manual start waits).

## Flows

- Desktop: `App` → `Sidebar` + `ChatScreen` → `DefaultChatScreen` → `Chats` → `Chat` → `ChatBody`.
- First greeting: rendered as a separate `Chat` with `idx: -1`. `fmIndex: -1` means `firstMessage`. `fmIndex >= 0` selects `alternateGreetings[fmIndex]`. The chat screen, the CBS registry, triggers (`v2GetFirstMessage`) and regex `repeatBack` read it through `shared/greetings.ts` (`greetingIndex`, `greetingText`, `nextGreetingIndex`, `previousGreetingIndex`): a missing, non-integer or out-of-range index reads as -1. Not converted yet: `server/src/prompt/assemble.ts` (prompt assembly) and `src/ts/characters.ts`, `src/ts/gui/branches.ts` and `src/lib/Others/HypaV3Modal/utils.ts` index `alternateGreetings` directly.
- Popups: `PopupButton` → `popupStore` → `App` renders `PopupList`, which closes on the next document click.
- Theme: at boot `bootstrap.ts` calls `updateColorScheme`, `updateTextThemeAndCSS`, `updateAnimationSpeed`, and `updateGuisize`. The display settings call the same functions. Plugins can call them via `apiV3`.

## State

- Components mutate the settings through the record views (`settings.ui.*`, `settingsViews.svelte.ts`) and the characters through the character module's records (`selectedCharacter()`, `characterList()`), and rely on the records' write-through saves: each write queues the record it changed (`persistence.md`).
- Invalidation signals:
  - `ReloadGUIPointer`: structural changes.
  - `ReloadChatPointer`: message re-render, by `reloadChatKey` (`m:` and the message id; the greeting `i:` and its index), so a row keeps its counter when messages before it are added or removed. Mounted row effects subscribe through the store; a changed entry remounts only its row.
  - Reassigning an array after an in-place mutation, e.g. `chat.bookmarks = [...]`.
- Theme DB fields: `theme`, `colorScheme`, `colorSchemeName`, `customColorScheme`, `textTheme`, `customCSS`, `textAreaSize`, `sideBarSize`, `textAreaTextSize`.

## Coupling

- The chat tree depends on `process/index.svelte.ts` (`sendChat`, `doingChat`), the parser, `scripts`, the translator, `globalApi` (`changeChatTo`, assets, folding), `characters.ts`, and `database.svelte.ts`.
- The sidebar depends on `characters.ts`, `dragTypes.ts`, SortableJS, and the GUI primitives.
- The GUI primitives are imported by the settings, playground, sidebar, and prompt editors.

## Invariants

- Use theme tokens (see STRUCTURE.md U1). To add a color: a root variable, an `@theme` token, a `ColorScheme` field, `updateColorScheme`, and presets.
- Message identity: `Chats` keys a row by the chat and `chatId` (a message without one by its index); see `updateChatBody` and the per-row effect above for remount conditions. `Chat.updateRow` changes only supplied position/streaming fields or display-only `name?: string` and `img?: string | Promise<string>` props; name/image updates never reset the `ChatBody` key. Never read every row's text in the structural effect; per-chunk transcript JavaScript work must not grow with mounted row count.
- Chat structure operations go through the chat module (`createChat`, `deleteChat`, `reorderChats`, `setChatMeta` for `folderId`; `persistence.md`) and select with `changeChatTo`/`selectChat`; `chatPage` is derived from the per-tab selected chat id and is never assigned. Components never `bind:` a chat field directly: bind a getter/setter pair that calls the module, or a synced editing copy. A locked message (`isMessageLocked`: generating, or its final write not yet acknowledged) has its edit, delete, and regenerate controls disabled; reroll and chat deletion alert `chatGenerating` while the chat holds a lock.
- HTML boundaries:
  - `ChatBody`, `BackgroundDom`, suggestions, and plugin panels use `{@html}` only on sanitized parser output.
  - `renderGuiHtmlPart` whitelists tags and allows only `https` links.
  - Custom CSS is injected via `CustomCSSStore` and must stay disabled in `SafeModeStore`.
- A list of inputs over a list that can change while one of them has focus keys its rows by entry and binds each input to the entry captured at mount (getter/setter functions that drop a write once the list no longer holds it), never `bind:value={list[i]}` in an unkeyed `#each`: Chrome fires `change` on a focused, edited control while removing it, and an index binding resolves `list[i]` at that moment. The lorebook and character asset editors follow this ([characters-modules](characters-modules.md) Invariants).
- Runes and legacy stores are mixed: `$state`/`$derived`/`$props`/`$bindable`/snippets alongside `writable` stores, `.subscribe`, `createEventDispatcher`, and `on:save`. Match the local component.
- Primitive prop convention: an `interface Props`, destructured with `$props()`, `$bindable()` for mutable values, callback props (`onclick`, `onchange`), and `children: Snippet`.

## Recipes

- Change message rendering: `DefaultChatScreen` props → `Chats.updateChatBody` (row key, mount key, and `Chat.updateRow` fields) → `Chat`/`ChatBody`. Verify streaming, reroll, the first greeting, and custom HTML manually.
- Add a sidebar chat operation: `SideChatList.svelte`, plus `Chat` in `shared/database.ts` if the shape changes. Write through the chat module, open a chat with `changeChatTo` (or only select it with `selectChat`), and bump `ReloadGUIPointer`. Cross-character pins use `openPinnedChat`, selecting the chat before the character.
- Add a form primitive: follow the prop convention in `src/lib/UI/GUI/` and add cases to `guiRendering.test.ts`.
- Add a popup or portal: a store in `stores.svelte.ts`, then the trigger and host (`PopupButton`/`PopupList` or `Portal`). Clean up mounts and listeners.

## Known Hazards

- `src/lib/ChatScreens/Message.svelte` is an unused TODO rewrite; `src/lib/UI/GUI/SyntaxHighlightedTextarea.svelte` is empty. Confirm intent before extending either.

- A far row's fixed-position or overflowing custom content is contained while it is far. Near rows are deliberately uncontained; do not apply `content-visibility` to every row or to the transcript ancestor.
- Older rows do not rerender merely because the chat length changes. Length-dependent CBS updates when that row next renders (edit, reload, remount, etc.); restoring the old last-five key would add unnecessary renders on every append.

- `LazyPortal` and the generic `tooltip` action have no active callers found.
