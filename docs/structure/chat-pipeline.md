# Chat Pipeline: Send → Prompt → Request → Reply

## Scope

- Owns:
  - the tab's side of a send: the input box to the server job (`sendChat` is the job client) and the reply as the job's events and records bring it,
  - the prompt editor's helpers (`prompt.ts`, the templates, `templateCheck`), the lorebook codecs and the DevTool lore preview,
  - group membership (`group.ts`),
  - reroll,
  - slash commands,
  - inlays.
- Paths:
  - `src/ts/process/index.svelte.ts`, `src/ts/process/serverGeneration.ts`
  - `src/ts/process/{prompt,stringlize,group,prereroll,command,infunctions,inlayScreen}.ts`
  - `src/ts/process/lorebook.svelte.ts`, `shared/lore/activation.ts`
  - `src/ts/process/templates/*`, `shared/prompt/{chatTemplate,templateCheck}.ts`
  - `src/ts/process/files/{inlays,multisend}.ts`
  - `src/ts/process/dynamicutils/pdf.ts`
  - The send handlers in `src/lib/ChatScreens/DefaultChatScreen.svelte`
- Not here:
  - Prompt assembly, token trimming, the request, streaming, and the post-processing tail run in the server job → `self-host-server.md` (`runPromptJob`, `assemblePrompt`).
  - Memory algorithms → `memory.md`.
  - `requestChatData` internals → `llm-requests.md`.
  - Token counting (`shared/tokenizerChoice.ts`, `shared/prompt/chatTokens.ts`) → `llm-requests.md`.
  - Regex and trigger internals → `scripts-triggers.md`.
  - Rendering → `cbs-rendering.md`.
  - TTS and image generation → `media-aux.md`.

## Files

- `index.svelte.ts`: the send's job client (the browser assembly path was removed).
  - Exports `sendChat(chatProcessIndex, arg)` (`arg`: `serverGeneration.ts` `ServerSendArg` plus `onServerRefused`; `chatProcessIndex` is kept for the plugin API's signature and not read), `doingChat` and `sendingChatRef` (the tab's busy flag and actual send target: owned by `sendChat`; the target resets before the flag clears), `previewFormated`/`previewBody` (a preview's result), and the `OpenAIChat`/`MultiModal` types (declared in `shared/openai.ts`).
- `serverGeneration.ts` `sendChatOnServer(arg)`: the send as a server job (below).
- `src/ts/process/chatStatus.svelte.ts`: per-tab, in-memory generating, recovery, and unseen reply sources, with `chatStatusKey`, the terminal hooks, and the visibility watcher.
- `prompt.ts`: `tokenizePreset` and legacy-preset conversion; re-exports the prompt types declared in `shared/prompt.ts`.
  - Types: `PromptItem` (discriminated union), `PromptSettings`, `PromptRole`.
  - `tokenizePreset`.
  - Legacy import: `detectPromptJSONType`, `stChatConvert`, `promptConvertion`.
- `shared/lore/activation.ts` `activateLore(input, host)`: lore activation, shared with the server. It merges three sources: character `globalLore`, chat `localLore`, and the module lore the caller resolved; matches keys, regex keys (`/pattern/flags`: the last `/` ends the pattern, empty flags allowed), and decorators over the scanned messages; recurses; applies the token budget and `@@inject_lore`; and returns `{ actives, matchLog }`. `LoreHost` supplies the clone, the speaker names, the chat variables (the keep and don't-activate-after-match flags), CBS, the token count, and the regex test (on the server, the script worker's).
- `lorebook.svelte.ts`: the client wrapper of lore activation and the lorebook codecs.
  - `loadLoreBookV3Prompt(chatRef?)` runs `activateLore` for the chat with `getModuleLorebooks(ref)`, `loreBookDepth`, `loreBookToken`, and `getUserName(ref)` (the bound persona's name), and the client host.
  - Also `addLorebook`, `addLorebookFolder`, `importLoreBook`, `exportLoreBook`, `convertExternalLorebook`.
- `shared/prompt/chatTemplate.ts`: `renderChatTemplate(messages, { type, jinjaTemplate, characterName, userName })` (Hugging Face Jinja), `chatTemplates` (built-in Llama/Gemma/Mistral/...), `templateEffect`. `templates/chatTemplate.ts` re-exports `chatTemplates` and `templateEffect` (not `renderChatTemplate`), and its `applyChatTemplate(messages, { type?, custom? })` supplies the selected model preset's `instructChatTemplate`/`JinjaTemplate`, the selected character, and the user's name.
- `templates/templates.ts`: re-exports `prebuiltPresets` and `prebuiltNAIpresets` from `shared/presetTemplates.ts` (templates carry no id; a use goes through `normalizePreset`).
- `shared/prompt/templateCheck.ts` `templateCheck({ promptTemplate })`: prompt-template warnings (`templates/templateCheck.ts` re-exports it).
- `stringlize.ts`: serializers for non-chat-completion backends and stop strings.
  - `stringlizeChat`, `stringlizeAINChat`, `unstringlizeChat`, `getStopStrings`.
  - `stringlizeChatOba` is unreferenced. `multiChatReplacer` is empty.
- `group.ts`: `groupOrder` (name mentions, then shuffle and talkativeness), `addGroupChar`, `rmCharFromGroup`.
- `prereroll.ts`: `Prereroll`, `PreUnreroll`, `addRerolls`. In-memory swipe history keyed by `generationId`, with the chat and message the reply was generated in. A swipe first stores the reply's current text into the candidate on display (an edit is what swiping back brings), and works only while the selected chat is that chat (a copied chat keeps the reply's ids and generation but not its candidates); an empty candidate (an emptied reply or an empty alternative) is shown like any other, since the screen applies every candidate that is not null.
- `rerollHistory.ts` `createRerollHistory`: the screen's per-chat bundle history (`record`, `begin`, `canForward`, `forward`, `back`, `clear`), up to 16 chats by last use; owned copies with an anchor message id and a cursor, swapped through `editChatSync` only while the anchor and current tail ids still match. The bundle at the cursor is refreshed from the chat's current tail when `begin` keeps the slot and before `move` swaps it away, so an edit of a recorded reply is kept.
- `sendDraft.ts` `createSendDrafts`: the screen's per-chat send drafts (`idFor`, `settle`, `takeUnplaced`); failed sends keep their text and `userMessageId` until restored, and keep the id after restoration for a safe retry.
- `command.ts` `processMultiCommand(line, ref?)`: the chat input's slash commands (`/send`, `/sendas`, `/cut`, `/del`, `/multisend`, `/trigger`, variables, TTS, `?` help). `/trigger` runs on the server (`runServerManualTrigger`, `scripts-triggers.md`); a trigger's `v2Command` runs the server's command executor.
  - Pipes are `|`.
  - Unknown commands return `false` and fall through as ordinary text.
- `infunctions.ts` `calcString`: calculator for the CBS calc function.
- `inlayScreen.ts`:
  - `runInlayScreen`: turns image/emotion commands in the output into `{{inlay::id}}` via `generateAIImage(..., 'inlay')` and `writeInlayImage`.
  - `updateInlayScreen`.
- `files/inlays.ts`: inlays on the server. Metadata is the `inlays` resource (id = inlay id, `InlayResource` in `shared/resources.ts`); media bytes are assets named by content hash (`assets/inlay_<sha256>.<ext>`), so the same bytes are stored once; a signature keeps its JSON in the metadata `text`.
  - `writeInlayImage`: normalizes to PNG and caps the size at 1024² pixels.
  - `postInlayAsset`, `setInlayAsset` (Blob or data URI), `saveInlayedSignature`, `getInlayAsset` (base64 data URI), `getInlayAssetBlob` (Blob), `listInlayAssets` (metadata only, read fresh; replaces the cached view), `removeInlayAsset` (metadata only; the blob stays because retained snapshots may reference it), `getInlayMetadata`, `verifyInlay` and `repairInlayMedia` (the browser-local import), `invalidateInlayCaches`.
  - Caches: metadata seeded at boot (`seedInlays`) plus a GET on a miss, a negative cache for unknown ids that expires after 30 s, a 64 MiB blob cache (content-addressed, so never stale), and in-flight de-duplication. Metadata is only as fresh as this tab's own writes plus `invalidateInlayCaches`, which `bootstrap.ts` runs whenever the save adapter brought another tab's records into the mirror (`onRemoteRecordApplied`). Every public write to one id (preparation, upload, and metadata) runs after the previous one; a conflict with another tab re-reads once and writes over it (last writer wins, as before).
  - `supportsInlayImage`.
- `files/multisend.ts` `postChatFile`: file attachments (PO, TXT, XML retrieval, media → inlays). The PDF branch is unreachable from the picker.
- `dynamicutils/pdf.ts`: `convertPdfToImages`, `extractPdfText`. Not used by `sendChat`.

## Flows

Send, in `DefaultChatScreen.svelte`:

1. `send`/`sendContinue` → `sendMain`:
   1. If `$doingChat`, alert `chatGenerating` for the selected chat's local send, else `chatGeneratingElsewhere`, and stop; switching characters mid-send is allowed. A followed job of the selected chat (`ownedJobIds`, from `followedJobsOf`) alerts `chatGenerating` and stops before the text, translation draft, attachments, or reroll history are consumed.
   2. `processMultiCommand`.
   3. An incomplete binding (`chatBinding(ref)`, [chat bindings](persistence.md)) opens the chat's binding dialog (`chatBindingDialog`) and stops before anything is consumed (also for Continue): the text, the translation draft, and the attachments stay. The send button reads "Set up this chat" meanwhile (it keeps `button-icon-send`, so the send hotkey opens the setup too).
   4. Append queued `{{inlayed::id}}` tags.
   5. A nonempty input becomes the job's input with a new `userMessageId` (the job runs the input trigger, `editinput`, and appends the user message); an empty input appends "_says nothing_" when `useSayNothing` is on and the last message is not the user's (a continue from an empty input does it too).
   6. `sendChatMain`.
2. `sendChatMain` creates an `AbortController` and calls `sendChat(-1, {target, signal, continue, input, userMessageId})`, where `target` is the chat `sendMain` captured before any await (commands and multisend capture theirs the same way). Stop shows for the local send whose captured target is the selected chat, input translation, or any followed job of the selected chat; `abortChat` aborts the local controller only when its target is selected, and every followed job of the selected chat (`abortGenerationJob`). The controller and its target are cleared when its send ends, only if it is still that send's controller. This also makes a selected chat's Lua button or manual trigger command job stoppable, and a plugin's `sendChat`, autopilot, `/multisend`, or DevTool preview once its job exists and is followed; Stop cannot abort those callers during job creation. Auto mode checks `ownedJobIds` before each `sendChatMain`, alerts `chatGenerating`, and ends its loop when that chat has a followed job or `sendChatMain` reports that no send ran (a busy tab alerts as in step 1). After the send resolves or throws, `sendDrafts.settle` drops a draft whose user message landed or whose job ended `done` (`ok`). Otherwise the text returns to the composer when that chat is still selected and the composer is empty; an unplaced draft returns when the user switches back to the chat with an empty composer (`takeUnplaced`). The text keeps its `userMessageId` even after a refusal or error: an absent message may be a hydration gap, and retrying the same text under the same id makes the job skip an input it already appended. Only `sendMain` clears the composer; reroll and auto-mode sends leave a draft being typed alone. The reroll bundle starts after the captured anchor (the user message id for a typed send), resolved by id after the await.
3. `reroll`/`unReroll` alert as in step 1 while `$doingChat` is set, and refuse with the `chatGenerating` alert while the chat holds a lock (the reply stays locked until the job's last write lands; the buttons are disabled meanwhile). They try `Prereroll`/`PreUnreroll` (`setMessageText`) first, then the screen's history keyed by both character and chat id (`rerollHistory`). A stored bundle replaces the tail through `editChatSync` only if its anchor still exists (null means the start) and every current tail id matches the bundle at the cursor in order; a mismatch clears that chat's history and writes nothing. The outgoing tail, as the chat holds it then, is stored as the bundle at the cursor before the swap, and `begin` stores the removed replies there when it keeps the slot; a candidate swap stores the reply's current text into the candidate it leaves. Without a forward bundle, `reroll` captures every removed reply in order with `begin`, removes those replies (`editChatSync`), and calls `sendChatMain` with the captured chat. When the send did not run (a flush refused because the chat or another one waits for another tab's generation, `GenerationBlockedError`, which `runServerJob` alerts as `chatGenerating`; any other refusal before the save), the removed replies are put back (`restoreUnsentRemoval`, under the owner token taken before the removal) when the last matching pending `remove` is the queue's final op and the anchor is still last with none of the removed replies back. The restoration is provisional: a removal requeued after a lost response may have committed, so the idle read can remove the restored replies again. A removal no longer pending, including a single removal of a locked reply that the save adapter dropped (the chat is then read back), is left as it is. `sendChatMain` records the new bundle under that chat and anchor; a new user send clears that chat's history.

`sendChat` in `index.svelte.ts` (the only path since the cutover): the `doingChat` guard and the deleted-target check (a refusal leaves the flag alone), then sets the flag and captures the actual target in `sendingChatRef`, resets the target and clears the flag in `finally` when the send ends, through `serverGeneration.ts` `sendChatOnServer`, which writes `statics.messages` (`incrementStatic`; the target's `lastInteraction` is the server job's to stamp, `self-host-server.md`), and calls `serverCommands.ts` `runServerJob` (the send guard first: a chat whose binding is not complete (an unset or deleted field, or an import's pending review) shows its problems (`chatBindingRefusalText`) and runs nothing, for every job of a chat (send, continue, reroll, group, preview, command); the job's ids are the chat's bound ids (`chatContextIds`), or a held job's own (`options.identity`) for a rerun; the client environment taken before the first await; `flushResources()` with a refusal on a rejection or a discarded change (a `GenerationBlockedError`, the chat or character waiting for another tab's job, alerts `chatGenerating` unless the adapter's conflict recovery has just shown it), the job posted as `preview`, `previewPrompt`, `group` for a group chat, `continue`, or `send` with `input`, `userMessageId`, and an explicit `continueMessageId`, an abort of `arg.signal` sent as `DELETE` also while the job is created, and the job followed to its end through `followJobToEnd`). That one lifecycle per job registers it in `followedJobs` as soon as its chat is known (the caller's `ref` or the boot discovery, before the chat load), and removes it in `finally` at the lifecycle's end (terminal, lost, or load failure). Each update replaces the Map; entries are keyed by job id because the server frees the chat slot before sending the terminal, so an older follow's cleanup or a late boot discovery cannot hide a newer job of that chat. `runServerJob` takes a plugin call's prompt and model presets and effective persona from `arg.pluginContext`; a busy job of this tab is followed (and aborted with the signal) but does not count as this send; a create request without an answer is `unknown` (the job may exist). `sendChat` returns false for a refused, followed, or unknown send and for a `done` with `stopped`; `onServerRefused(ambiguous)` reports a refusal, and the screen settles its draft after the send. A preview's `done.result` becomes `previewFormated` or `previewBody`; a reply's `done.alternatives` go to `addRerolls` under its generation (none for a continue). A server refusal of the binding (409 `chatBindingIncomplete` with its problems, or `chatBindingMismatch` when the server holds a newer binding, which reads the chat again) shows the same message. The runner's own refusal and loss alerts are `language.serverJob` entries (`discarded`, keyed by the request's `label`: `send`, `button`, or `trigger`; `saveFailed` and `chatLoadFailed` with the error's text in their `{0}`; `chatNotSaved`; and `lost`, from `reportEnd`), never hard-coded text (`STRUCTURE.md` U2). The job's `preset` event (a `presetChain` pick) changes nothing in the tab: the pick is the job's own, neither the tab's selection nor the chat's binding (`generationJobs.ts` `applyGenerationEvent`).

The job (`self-host-server.md` `runPromptJob`, `assemblePrompt`) runs the input stage, `presetChain` (it picks a prompt preset only; the job keeps its model preset), the group order (one reply per active member), lore, memory, the prompt assembly and trimming, the request, and the tail on the server: `editoutput` once on the completed reply (not per chunk), the output trigger, inlays, the `chatOutput` listeners (a callback to the tab; each listener gets a fresh copy of the character and chat), TTS and notification as notices, auto-continue and a trigger's resend as rounds of the same job (at most 8 extra), `igp` on the last reply only, the emotion modes on the server with an `emotion` notice (the tab sends the emotions it showed last with the job), and the image view as an `imggen` callback. Before `done`, a send that was not aborted hands its replies (every reply of its speakers and rounds still in the chat) and then its user message to the translation runner (`handOffTranslations`, [translation](media-aux.md)), which translates them detached from the job when the chat auto-translates; the job sends a `translating` notice for the ids handed over, and the tab follows them (`followStoredTranslations`). A plugin provider model answers through a `provider` callback to the tab; remembered tool calls are read from and written to `chat.toolCalls`; a `/multisend` of a server command job is sent by the tab after the job (`done.followUps`, `runMultisend`). The tab reconstructs the job's `chunk` deltas (`base`, a sequence; `keep`, a UTF-16 prefix length; `text`, the new tail) from its raw stream buffer (`applyServerGenerationChunk`), then shows them through `applyServerGeneration` while the message is locked. A missing base asks for `resyncReply`, answered only with the current full-text `accepted`; it never requests a chat or marks it stale (`persistence.md`). Stored copies arrive through `chatPatch` or `resource` events.

Background memory contracts (HypaV3; the runner and the tab do not use them yet): `shared/jobs.ts` declares the `memoryGap` question (`{ gapTokens, plannedCalls, lastTaskError? }`, answered with a `MemoryGapChoice`, `MEMORY_GAP_CHOICES`: `generate` or `continue`), the `memoryProgress` notice (per job run `runId` and chat: `open`, `phase` `blocking`/`initial`/`selection`, `reason` `pluginModel`/`requestTrigger`/`gap`/null, `done`/`total` or an embedding queue's `text`; the legacy `progress` notice is unchanged), and the detached task service's `MemoryTaskService`, `MemoryTaskInput` (data only: the processed history with one `MemoryEntrySource` per entry, the counts, a credential-free `MemoryTokenPolicy`, the admission and effective preset ids, the epoch, the admitted revision, and the chat's source generation), and `MemoryTaskStatus`. The job's side: `server/src/llm/request.ts` `resolveJobRequestModel(db, mode)` resolves the model a job's own request would dispatch to (`requestChatDataMain` and `runInJob`'s lookup share `resolveRequestModel` and `requestModelLookup`, so a `memory` slot that runs in the tab is `LLMFormat.Plugin`, a server `LLMFormat.WebLLM` is not); `server/src/prompt/triggers.ts` `hasRequestTriggers(owner, moduleTriggers(scope))` is whether the owner's `request` trigger would run any effect (the same trigger selection and request allowlist as `runTrigger`; false for a group); `LuaBindings.askOptional` asks a question whose `timedOut` and `disconnected` are outcomes rather than the job's end (Lua and `memoryTrim` keep the latching `ask`); `RunningJob.registerMemoryControl(runId)` and `POST /api/generations/:id/memory-stop` (`requestMemoryStop`, owner only) carry the "stop here and continue" of an initial summarization run.

A failed job's `error` terminal says where it failed ([diagnostics](diagnostics.md)): `stage` (`setup`, `input`, `assembly`, `request`, `script`, `persist`, `tail`), `requestId` (the LLM request that failed, the request history's id), and `providerCode`, each optional and only on a runner's failure (an abort, a timeout, shutdown, or maintenance has none). The tab shows it with `alertJobError` (`src/ts/alert.ts`, from `serverCommands.ts` `reportEnd`): the error alert with "Copy debug info" (`src/ts/diagnostics/jobDebugInfo.ts`: a content-free block of the version, the time the tab received the end, the job, request, stage, status, reason, and provider code, each checked; never the message) and "Open in request history" (`alertRequestLogs({ jobId })`: the viewer filtered to the job; the popup keeps the filter across its tabs).

After `reportEnd`, `serverCommands.ts` `followJobToEnd` calls `chatStatus.svelte.ts` `noteJobLost` for a lost follow whose chat was discovered (including a failed chat load), or `noteJobDone` for a terminal event; a `gone` discovery adds no status. The existing lock release (`endServerJob`) marks a still-locked chat stale and wakes the idle refresh, so opening a lost chat needs no extra reload from the visibility watcher.

Not in `sendChat`:

- Input auto-translation happens in `DefaultChatScreen.updateInputTransateMessage`.
- Display translation happens in `ChatBody.svelte`.
- Suggestions come from `Suggestion.svelte`, which calls `requestChatData` directly. A send's actual target (`sendingChatRef`) cancels and clears only that chat's suggestions; other chats keep theirs visible. Completion requests suggestions if that chat is selected, else queues its chat key for a request when selected and loaded (only if suggestions are empty). Other selection changes request nothing; a new send or deletion drops the queued key.
- `writeInlayImage` rejects when the image has no pixels or fails to load; its per-id queue moves on to the next write, so a caller handles the rejection.
- A continue on a group runs the group speaker loop like a send (`continueSend` false): the continue target is not passed to each speaker.
- The chat screen renders a window over the selected chat's loaded messages (`chatLoadInitialPages`, `chatLoadAdditionalPages`); paging never fetches, and selecting a chat that is not loaded shows the loading state (or the error with a retry) until it is.

## State

- `src/ts/process/chatStatus.svelte.ts` holds three per-tab sources keyed by `${chaId}\u0000${chatId}`: reactive `generatingChatKeys()` unions `followedJobs` values with `chatStore.svelte.ts` `lockedChatKeys()`, `recoveryChatKeys` maps a lost chat to its job id, and `unseenChatKeys` holds up to 256 chats whose `done` carried a reply `messageId` while that chat was not visible (oldest dropped). `watchChatVisibility`, started once from `bootstrap.ts`, tracks visibility and both mark stores, clearing recovery and unseen for the open chat (screen 0, or 2 for `§playground`) even when a lost follow adds a mark without a visibility change; new follows clear that chat's recovery, and followed-job changes prune recovery for deleted chats. The writable inputs use lazy `fromStore` views for reactive reads without permanent mirror subscriptions; `resetChatStatusForTests` clears the marks and those views.
- `OpenAIChat` has `role`, `content`, `memo`, `removable`, `attr`, `multimodals`, `thoughts`, and `cachePoint`.
  - `memo` values `supaMemory`/`hypaMemory` mark memory cards.
- `PromptItem` types: `plain|jailbreak|cot`, `chatML`, typed `persona|description|lorebook|postEverything|memory`, `authornote`, `chat` (with a range), and `cache`.
- Reactive singletons: the records (through `settingsViews.svelte.ts` and `characterStore.svelte.ts`), `selection`, `doingChat` and `sendingChatRef` (the tab-wide send busy flag and actual send target, owned by `sendChat`; screen controls and suggestions follow the selected chat's own work), `followedJobs` (`serverCommands.ts`: the jobs this tab follows, job id → `${chaId}\u0000${chatId}`; `followedJobsOf` selects a chat's job ids), `CharEmotion`.
- The tab never mutates the chat in place: the chats are held by `src/ts/storage/chatStore.svelte.ts` (the screen reads `selectedChat()` and the lists `chatList()`), and every write goes through it (see `persistence.md`), addressed by chat and message id. Autosave does not see chats.
- Chats load on demand. The chat screen renders nothing chat-dependent while the selected chat loads (`selectedChatLoad()`: a loading state, or the error with a retry). A server job's target chat is pinned and loaded before the job is created (`runServerJob`; `followJobToEnd` for a resumed or followed job, through every reconnect and the terminal's hydration; a command job's `/multisend` follow-ups), and a send's chat stays pinned until `sendChatOnServer` has read the reply's alternatives; a target that cannot be loaded runs nothing. A typed command line (`processMultiCommand`), an auxiliary LLM request (`requestServer`: its chat and its parse chat, until its event stream ends), `editChat`, and a group output listener's speaker (`chatOutput`: its chats, before each listener) pin and load what they read. The synchronous chat readers (`chatVar`, `getModules(ref)`, the CBS host, `transformClient`'s context, the MCP tool records) read loaded chats only; their chat is the selected one, a pinned job or request target, or a plugin context that awaited its load, and an unloaded chat reads as gone, never as another chat. The bound persona (`checkPersonaBinded`, `capturePluginContext`) is read from the chat's list entry, so it holds while the chat is not loaded.
- Streaming display: a server job's message is locked while it streams (`isMessageLocked`); `Chat.svelte` disables its controls and renders it without the server transform until the lock ends. The display optimization (`streamingDisplayOptimizationMode`) follows the stream: `applyServerGeneration` sets `streamingState` on the generation's first stream update with the configured mode, and its lock's release clears it (`persistence.md`). `Chats.svelte` keeps the streaming row mounted in every mode while it streams (rows are keyed by message id; `Chat.updateRow` passes the text in) and mounts it again when it ends, `off` parses it like any message, and `strong` renders that text raw, without markdown (`util/playwright/checkStreamingModes.mjs`). Whatever the mode, the chat module writes the streamed text into the mirror at most once per frame (`persistence.md`), so a streaming row parses once per frame, not once per chunk.

## Coupling

- `sendChat` imports `serverGeneration.ts` (and through it `serverCommands.ts`, the job channel) and the chat module.
- Callers: `DefaultChatScreen.svelte`, `command.ts` (`/send`, `/multisend`), `files/multisend.ts`, `hotkey.ts`, `DevTool.svelte` (preview, autopilot), `plugins/apiV3` (`sendChat` permission).

## Invariants

- `chatId` is the address of every message write. Never address a message by index after an await; resolve the id again.
- A send captures its target chat before any await and passes it to the job; the job's prompt and model presets and persona are the chat's binding, fixed at its creation (a plugin's `sendChat` inside a hook passes `pluginContext`, so the job acts on the hook's chat and preset). Nothing falls back to the tab's selection: a chat whose binding is incomplete is not sent, and the server refuses it independently ([chat bindings](persistence.md)).
- Every context builder takes its ids from the captured chat, never from the views: a job or chat request from `chatBinding(ref)` (`runPinnedServerJob`, `requestChatDataServer`), a render or plugin context from `chatDisplayIds(ref)` (`captureTransform`, `capturePluginContext`). The tab's chat LLM requests have the same guard (`requestChatData` before its hooks and tools, again at `requestChatDataMain`; a request inside a job callback is compared with the job's targets). A request without a chat is not a send: it carries no `chatRef`, is never refused by a binding, and runs on the settings views, read once before any await.
- The reply being generated is locked by its server job: the tab's writes to it are refused by the server and skipped by the chat module.
- Script modes (run by the server since the cutover):

  | Mode          | Stage                       |
  | ------------- | --------------------------- |
  | `editinput`   | user input                  |
  | `editprocess` | prompt history and greeting |
  | `editoutput`  | model output                |
  | `editdisplay` | render                      |

  Lua edit triggers skip `editprocess`. The `request` trigger runs on the server job's requests only; the tab's own requests (translation, suggestions, the HypaV3 modal, plugins) go out without it.

- A new `PromptItem` type needs handling in both template switches of the server's `assemblePrompt`, plus `tokenizePreset`, `templateCheck`, import conversion, `PromptDataItem.svelte`, and `normalizePromptTemplate` (`shared/presets.ts`).
- Lore matching (`shared/lore/activation.ts`):
  - Only the last `scanDepth` messages are scanned.
  - Keys starting with `/` are regex.
  - Supports selective secondary keys, negative keys, and all-key mode.
  - Recursion is controlled by `recursiveScanning` and `@@recursive`/`@@unrecursive`/`@@no_recursive_search`, with no explicit depth counter.
  - Decorators are parsed with `CCardLib.decorator.parse`.
- Inlays are not stored in chat text. Removing an inlay (`removeInlayAsset`, the Inlay Explorer) breaks the `{{inlay::id}}` tags that name it; deleting messages never removes inlays.
- Images become `MultiModal` input only when the model has `LLMFlags.hasImageInput`. Otherwise the job captions them (`captionImage`, `memory.md`).
- Built-in Jinja templates enforce role rules: Gemma has no system role, and Mistral requires alternating roles.
- A suggestion result is applied only while its request token and the captured character and chat ids still match (`Suggestion.svelte`), never by the old chat index.

## Known Hazards

- Stop stays visible between a followed job's `done` and its socket close, when aborting the ended job does nothing. A boot resume that discovers its chat but cannot load it shows Stop during the load retries, until the follow ends as lost.
- The background memory contracts are unwired: no job asks `memoryGap`, sends `memoryProgress`, registers a memory run (so `memory-stop` always answers 409 `noMemoryRun` for a running job), or calls `resolveJobRequestModel`, `hasRequestTriggers`, or `askOptional`; the tab handles neither the question nor the notice.
- `disable_ui_prompt` lore decorators are collected into `disabledUIPrompts`, but that array is never consumed.
- `prereroll.ts` history is in memory only; the per-chat history and drafts live in `DefaultChatScreen`'s module instances and a remount loses them. Send recovery restores no translation draft, and does not restore a draft whose job ended `done` (`ok`) after a script removed its user message.
- A plugin's whole-chat setter (`setChatToIndex`, and a character setter's `chats` through `reconcileCharacterChats`) diffs the plugin's copy against the chat at call time: `captureChatBaseline` runs right before `applyChatResult`, not when the plugin read the chat. Wherever the copy differs from the chat then, the copy wins, so a change another writer made after the plugin's read is overwritten: a changed message field or chat field is set back to the copy's value, a message added meanwhile is removed. When that diff would change or remove a message being generated (`assertUnlocked`), the whole chat update is skipped with a console warning instead; a reorder of unchanged messages while the chat is generating drops only the order change (with a warning), the rest applies. `editChat`/`editChatSync` (`src/ts/storage/chatEdits.ts`) capture the baseline before their edit works on its copy, so they keep another writer's change to a field the edit left alone; where both changed the same field, the edit's value wins.
- `DevTool.svelte`'s autopilot sends each line as a job in the chat selected when it started; a group's speakers are chosen by the server (the browser path used the loop index).
- Group prompt assembly names a speaker it cannot resolve (`host.findCharacter`) `Unknown Character` in the group wrapper.
- Group lore activation takes the group as the character: its own `globalLore`, the chat's, and the modules'; the members' `globalLore` is not included, even with the group's `useCharacterLore`.
- Lore keys keep the inherited grammar: every key is split on commas before the `/pattern/flags` parse, so `/a{1,2}/` becomes two malformed keys; the last slash closes a pattern, and a bare or unclosed slash, an invalid flag, or a malformed later entry ends that key search instead of being skipped.
- `activateLore`'s `keepActivateAfterMatch` and `dontActivateAfterMatch` are function-wide, not per entry: once a decorator raises one, every later activated entry also gets the matching `__internal_ka_`/`__internal_da_` chat variable write.
- `exportLoreBook("local")` dereferences `selectedChat()` without waiting, so while the selected chat loads it alerts a `TypeError` instead of refusing; `exportLoreBook("sglobal")` takes the same path with no chat and also alerts an error instead of exporting.
