# What to Bring into metatron from PocketRisu / RisuBard (2026-10-20)

Research scope:

- PocketRisu v1.15.0 (`/home/codex/PocketRisu`, `f71e1ccc`): A fork that reduces RisuAI to a single Node self-hosted deployment. Forked on 2026-03-17, with approximately 1,110 fork-specific commits.
- RisuBard 0.9.72 (`/home/codex/RisuBard`, `6cf7d89`): A PocketRisu fork that adds Markdown wiki long-term memory, save slots, and file-native storage. Its root is a snapshot dated 2026-08-17.
- metatron inventory as of `44e18f2ae`.

The three reports (written by Opus sub-agents) are in the same folder:

- `pocketrisu-survey.md`: Approximately 60 features PocketRisu added or changed relative to upstream, 19 design concepts, 29 key bug fixes, and a route map.
- `risubard-survey.md`: Features RisuBard added on top of PocketRisu, 24 concepts, plugin APIs, and discrepancies between documentation and code.
- `metatron-inventory-vs-pocketrisu-risubard.md`: What metatron already has, partially has, or lacks.

This document compares the three reports and selects what to bring over. Status labels:
**Present** = already in metatron, **Partial** = something similar exists but differs in scope, **Absent** = not present.

## 0. Architectural Premises

- In metatron, the server owns records (SQLite `resources.sqlite` + content-addressed asset files), and prompt assembly, memory, Lua, triggers, and translation all run inside server jobs. Both forks retain the opposite architecture: **the browser holds the entire `Database`, and the server provides storage** (PocketRisu uses JSON-Patch + hashes; RisuBard adds a file-native source of truth on top).
- The forks' storage, synchronization, session locks, and client-side model adapter layers are therefore **not candidates to bring over**. The candidates are (a) user-visible features, (b) policies and patterns, and (c) bug fixes in shared code.
- metatron already has the forks' advertised features: "generation continuing on the server," "request logs," "server-side plugin storage," "per-chat persona and preset bindings," "toggle presets," and "snapshots and backups" (`metatron-inventory-vs-pocketrisu-risubard.md` §1–4).

## 2. Ideas and Policies to Adopt

Worth incorporating into metatron's design even without porting the features themselves. Items related to metatron's known leftovers come first.

### 2.1 Directly Related to metatron's Leftovers

- **Direct `<img src="/api/asset/<hash>">` URLs + `Cache-Control: immutable` + cookie authentication** (PocketRisu §2.1 inlay, concepts 9 and 12). Although metatron's assets are already content-addressed (`save/assets/<sha256>.<ext>`), `getFileSrc` creates blob URLs and retains them in tab memory (memory notes: "wrapper node retention," "blob URL lifetime/MIME," heap-memory plan). Serving them directly with immutable headers would let the browser cache hold them and eliminate blob lifetime issues. Since DPoP JWTs cannot be attached to `<img>`, this requires a design like PocketRisu's that accepts **HttpOnly session cookies** only for asset GETs. This needs a separate plan because it involves security design. Currently, all Cache-Control headers in `server/src/routes/*.ts` are `no-store`.
- **Server thumbnails** (wasm-vips, 320 px WebP, filenames containing the original mtime+size) (PocketRisu §2.1). Related to heap issues in asset and emotion-image lists (B1/B2, "image growth").
- **Performance tests that count I/O operations rather than time** (RisuBard §2.4.5, concept 20). Assert "an unchanged sync performs 0 body reads and 0 index writes." A concrete replacement for elapsed-time assertions in the 2026-10-19 timing-dependent test inventory (178 tests to rewrite).
- **Request purpose classification + per-source token attribution manifest + evidence reports without bodies** (RisuBard §2.2.7, concept 4). metatron's request history stores exact request bodies but does not show "what was included, omitted, or truncated" (`metatron-inventory-vs-pocketrisu-risubard.md` §3). Since assembly runs on the server, having `assemblePrompt` emit a list of `{kind, name, tokens}` is natural. The same point can also verify "whether injection actually happened" in the final prompt **after** Lua and regex edits.
- **A cache-friendly placement option that inserts memory blocks immediately before the latest user message** (RisuBard §2.2.6). metatron already sends Anthropic `cache_control` (`server/src/llm/anthropic.ts:20`), so a single HypaV3 block-position toggle could improve cache hit rates.
- **A marker on truncated canon: "omitted content is not evidence of absence"** (RisuBard concept 2). metatron already asks before no-memory trimming (aad461e63). Adding a one-line marker when trimming is nearly free.
- **"N turns ago" markers and a list of recent developments** (RisuBard §2.1.4). Adding turn distances to HypaV3 summaries could reduce confusion about sequence in long chats. Stable message IDs make this possible.
- **Retract derived memory before deleting its evidence; abort deletion if retraction fails** (RisuBard §2.3.5, concept 8). The same class of problem as HypaV3 summaries referring to deleted messages (memory notes: HypaV3 bulk cancel/selection bug).
- **Rerolls do not become memory (commit boundary)** (RisuBard concept 7). This is not an immediate issue because HypaV3 summarizes outside the recent window, but the rule that summarization should trigger after "the next successful generation" is worth documenting.

### 2.2 Storage and Deletion Policies

- **Fail-closed deletion, a grace period, opt-in automatic deletion, and a recheck immediately before deletion** (PocketRisu concept 8). Prerequisites for §1.2 #6 above.
- **Disk space preflight checks** (PocketRisu concept 11): 2× for backup import, estimated size +5% for server backups, and 2.2× for VACUUM. Check whether metatron's backup import (`server/src/routes/backups.ts:292`) checks available disk space.
- **Keep one previous version per record** (RisuBard `.bak`, §2.4.2). metatron has revision numbers but no history. A single `previous_json` column in SQLite could support "undo the character description I just overwrote." Adopt only the part that does not require file-native storage.
- **"Download unsaved edits as JSON" when reloading after a conflict** (PocketRisu `resolveSessionHandoff`, RisuBard `sessionHandoff.ts:17`). metatron has decided against a single-writer lock, so the lock should not be brought over, but adding this escape hatch to 409/412 reload notifications is independent of that.
- **Defer DB entries until imports have been decoded** (PocketRisu 4594674b). metatron's archive import already follows the same policy by replacing data only after full validation.

### 2.3 Adapters and Plugins

- **The "byte-identical when disabled" rule** and **pure adapters that do not read the DB** (PocketRisu concept 15). Worth using as criteria for server LLM adapter tests.
- **Plugin `getDatabase().pluginCustomStorage` defaults to empty + `setDatabase` merges keys** (PocketRisu §2.6). A Module Manager round trip actually wiped 255 keys down to 0. Check how metatron's v3 sandbox exposes `pluginStorage` records.
- **Key permission grants by `[name, desc]`, persist grants, and support per-plugin resets** (PocketRisu 23b3784d, acb8689b). Keying only by name is a security defect that can turn approval of one permission into approval of all permissions. Check metatron's `src/ts/plugins/apiV3/v3.svelte.ts`.
- **Verified plugin updates** (`no-store` fetch, report success only when the script has actually changed and been saved, retry through the server) (RisuBard §4.4).
- **Virtual projections for legacy memory plugins** (RisuBard concept 14): expose new memory only as a copy in existing fields such as `hypaV3Data.summaries`, and strip it on save. A compatibility protocol for a future metatron memory engine change.

### 2.4 Self-Hosted Operations

- **Cloudflare Quick Tunnel + QR** (PocketRisu `startTunnelProcess`, `server.cjs:8916`). metatron requires a secure context, and tunnels provide HTTPS, making this **a particularly good fit**. Add checksum verification for `cloudflared` downloads when bringing this over; PocketRisu lacks it. Tailscale provides the same effect with `tailscale serve`.
- **Portable-build self-updates** (PocketRisu §2.10): replace only app-managed files listed in the installation manifest, move conflicting user files to `backups/update-conflict-<ver>/`, and use an in-progress marker to determine whether rollback is needed. metatron uses git/Docker deployment, so this only matters if portable distribution is introduced. Also note the lack of archive signature verification.
- **ToS consent gate before using RisuAI servers** (PocketRisu concept 14; store consent by revision date and use a sentinel so "Yes" in another dialog does not count as consent). Whether to apply this to metatron's Realm browsing/downloads is a policy decision.
- **Termux support** (wasm-vips, `SQLITE_TMPDIR`, native notifications). Since metatron uses Node 24 + `node:sqlite`, first check whether it can run on Termux at all.

## 3. Major Features (Requiring Separate Plans)

Ordered by fit with metatron, rather than size.

1. **Named chat checkpoints (save/load)** — RisuBard §2.3.1. Each slot snapshots the chat (msgpack), variables/scriptstate, chat lorebook, and memory state together. Pages are deduplicated through content-addressed storage. Loading preserves personas, presets, and toggles. Autosave happens only after **both** generation and memory writes finish. metatron only has global snapshots (every 10 minutes, 20 retained), with no per-chat scope, names, or previews. A good fit because the server can bundle the chat row and `hypaV3Data` together. Medium scope.
2. **Grimoire (retrieval-based lorebook)** — RisuBard §2.8.3–2.8.4. Metadata lives in a **side table** keyed by `sourceLegacyId + sourceHash`, without modifying entries. Filters are read only from the latest user message. Logs explain exclusions. AI drafts go through review before application, and application is refused if the hash has changed. RisuBard implements it entirely on the client (4.5k TS), but metatron activates lore on the server, so the logic would live in `shared/` and run on the server. metatron already has server embeddings and a vector cache, making semantic search easy to combine with it. High value for Korean users with large lorebooks. Large scope.
3. **First Message Studio** — RisuBard §2.10. A no-code interactive first-message builder. On save, it **compiles to CBS + triggers + defaultVariables and works in stock RisuAI**. No storage coupling; the most portable feature. Medium scope (1.05k TS + 1.36k Svelte). Reusing the `character.firstMessageStudio` field and `extensions.risuai.firstMessageStudio` export convention preserves card compatibility.
4. **Attach to an in-progress stream from another device** — PocketRisu §2.3 (replay from byte 0, then skip bytes already received). metatron only supports reconnection in the same tab; other tabs/devices see the lock and final result (`metatron-inventory-vs-pocketrisu-risubard.md` §1). The job channel already sends delta chunks through the feed, so only "journal replay on attach" needs to be added. Medium scope.
5. **Message-level delta synchronization / server pagination for long chats** — PocketRisu §2.1 (opening a 2,000-message chat: 14 s→0.9 s). metatron fetches the entire chat on open. Fingerprint-based prefix validation + full retransmission on `409 CHAT_DELTA_BASE_MISMATCH`. A natural next step after the heap-memory plan and chat-open-reveal work. Medium to large scope.
6. **Character manager (search, sort, filter, hide, bulk disable/trash)** — PocketRisu §2.8, RisuBard Vault §2.5.1. Since metatron only fetches summaries at boot, "disable characters to lighten boot" is a weaker motivation, but hiding, bulk operations, and a trash tab improve UX. Include the rule that "disabled characters appear deleted to plugins." Medium scope.
7. **Prompt V2 workbench + block injector (overlays)** — RisuBard §2.9.1–2.9.2. Edit conditions through forms, but **compile them to stock CBS `#when`**. Overlay blocks from other presets before/after/in place of existing blocks without modifying the active preset. Complements metatron's toggle presets. Medium to large scope.
8. **AI persona builder / lore builder / character assistant (including playtesting)** — RisuBard §2.6.3, §2.8.5, §2.7. Best implemented as an extension of metatron's Iris assistant (`src/ts/iris.ts`). Independent ideas include the character assistant's six-round `<read ref>`/`<search>` loop, `<edit><find><replace>` cards, and playtests that run through the actual pipeline in "play test N" chats. The two builders are small to medium; the assistant is large.
9. **BardWiki (Markdown long-term memory + fixed-budget compiler)** — RisuBard §2.1–2.2, 11.7k server + 5.8k client. Porting it wholesale is not recommended. The author explicitly states that no A/B comparison against the full transcript has been performed, cumulative input tokens are almost the same as the full transcript (1.02×, due to wiki-writing costs), and the 80/96% recall figures are targets. What to adopt is the policies in §2.1 (commit boundaries, evidence retraction, budget manifests, "N turns ago" markers, cache-friendly placement) and **original-message retrieval** (events carry `sourceMessageIds` so the original wording can be retrieved as evidence). Start by retaining source message IDs in HypaV3 summaries.
10. **Gemini/Vertex context caching** — PocketRisu §2.3. Server-side, so the implementation location in metatron is clear. Provider-specific. Low priority.
11. **BardPainter** (selected text→NovelAI illustration, character/outfit IDs, scene-plan JSON) — RisuBard §2.12, 8.7k. NovelAI-only, large scope. Only if requested.

## 4. What Not to Bring Over (Architectural Conflicts)

- **File-native storage** (sha256 sidecars, journals, `.bak`, external-edit review, data-root locks) — Incompatible with the SQLite record store. The author's `fs.watch` monitoring in 0.9.41 stalled Linux/Docker/Termux servers, prompting a retreat to polling in 0.9.66; the V2 folder layout was also rolled back in 0.9.28. Adopt only the policies (§2.2).
- **Single-writer session locks** — metatron chose concurrent writers + revision conflicts + feeds.
- **JSON-Patch + configuration hashes + the `dbCache` save protocol, lazy asset manifests, and archive rows** — metatron's record/revision model already solves the same problems differently.
- **Client-side ModelPreset adapters, key pools, and registries** — metatron already separates these through server LLM adapters, model profiles, and write-only secrets. "Remote catalog refresh" was addressed in 4c (dynamic models).
- **Plain HTTP support** (server-signed HS256 JWTs, `uuid.v4()` replacement) — metatron requires a secure context by user decision (dev:agent defaults to loopback).
- **Removing group chats and removing Loadout/Easy Panel** — metatron retains group chats.
- **PocketRisu's update-check worker** (sends the installation UUID, OS, and language to a third-party worker on every boot, no UI opt-out, `/api/public-stats` ignores opt-outs) — Should not be brought over.
- **Promises in RisuBard's docs that the code does not fulfill**: request logs store bodies (2 MB cap), character deletion is hard deletion, automatic wiki saves are always `reviewed`, and wiki writes do not use fsync. For reference only.

## 6. Recommended Order

1. Compare the bugs in §5 (read-only, half a day).
2. §1.1 #1 scriptstate checkpoints, #2 lore key matching, #5 structured-output fallback — small changes directly tied to correctness.
3. §2.1 request manifests (per-source token attribution) and cache-friendly placement — fit directly into server assembly.
4. §1.2 #6 storage dashboard + orphan cleanup, #7 folders, #9 settings search.
5. From §3: checkpoints (1), First Message Studio (3), and attaching to streams from another device (4) — a separate plan for each.
6. §2.1 direct asset URLs + immutable caching — design alongside the heap-memory plan.
